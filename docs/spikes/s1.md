# S1 — Pi SDK in a forked worker (navigate_tree, custom panel, IPC)

- Date / Node / Pi SDK: 2026-10-10 / v24.14.1 / 1.1.0 (`@earendil-works/pi-ai`, `pi-coding-agent`, `pi-tui`)
- Time-box: 2 days · spent: ~1 h

## Question and done-when
Can pi-host host the SDK in a forked child and support navigate_tree and ctx.ui.custom() over IPC? Done when a scripted session prompts, branches, renders a custom panel.

## Measurements
Source: `spikes/s1/results.json`, from `cd spikes/s1 && node driver.ts > results.json`. The driver forks `host.ts` (Node IPC, `detached: true`) with a fresh temp dir as cwd, `agentDir`, `PI_CODING_AGENT_DIR` and `HOME`, plus `PI_OFFLINE=1` and `PI_TELEMETRY=0`. The model is the S2 scripted provider. Ranges are min / median / max over that run plus 4 more identical runs (5 runs, 8 hosts each).

- Prompts settled over IPC: yes. The main host ran 4 model prompts plus `/panel`; each of the 5 other prompted hosts ran 1. Every model prompt ended with `agent_settled`. The 2 never-prompted hosts got no prompt.
- Fork-to-ready (fork() call to the `ready` record): 646 ms on the main host. Over all 40 hosts: 637 / 656 / 683 ms.
  - Node start plus module loading (SDK imports, TS type stripping) takes most of it: the host module starts running at `importedAtMs` 600 / 620 / 645 ms after process start.
  - `boot()` itself (ModelRuntime, services, session, `bindExtensions`) takes `readyMs` 30 / 31 / 35 ms.
  - With the three built-ins (`createCodemodeExtension`, `createToolSearchExtension`, `createMcpExtension`): 637 / 650 / 683 ms, `readyMs` 33 / 33 / 35 ms (n=5).
- Shutdown (the `shutdown` record to the child's `exit`: `session.dispose()` then `process.exit(0)`): 12 ms. Range 11 / 12 / 12 ms.
- navigate_tree, then a prompt, created a sibling branch (`branched`): true in 5/5 runs.
  - `session.navigateTree(<"reply one" assistant entry id>, { summarize: false })` returned `{ cancelled: false }`.
  - The next prompt ("three") became the second child of that entry, next to "two". Same session file, no fork.
  - navigate_tree emits no session event: the only record between the request and its response is the response (`navigateRecords: ["response:q4"]`).
- Custom panel (`/panel`, an inline extension command calling `ctx.ui.custom<string>()`):
  - First render lines: `["> alpha", "  beta"]` (width 92).
  - `custom_input` `"\u001b[B"` moved the cursor: re-render with `> beta`.
  - `custom_input` `"\r"` called `done("beta")`. The host sent `custom_close`, the command resumed, and `ctx.ui.notify("panel:beta")` came out as `extension_ui_request { method: "notify", message: "panel:beta" }`.
  - The command received `beta` (notice `panel:beta`) in 5/5 runs.
  - Record order: `custom_render, custom_render, custom_close, extension_ui_request, response:panel`.
  - The prompt's response (`{ disposition: "handled" }`) arrives only after the command has finished, i.e. after the panel closed.
- RSS: 156 MB after ready (152 / 156 / 156). 157 MB after the scripted runs (152 / 156 / 157). That second figure is taken after 3 prompts and a navigate, before the panel and the probe prompt, as the brief's driver does.
  - Over all 40 hosts at ready: 152 / 155 / 156 MB. With the built-ins: 153 / 155 / 156 MB.
- Inline extension `path` reported by Pi for `pap-policy`: `<inline:pap-policy>`, i.e. `<inline:${name}>`.
  - The SDK's built-in factories carry no name. They come out as `<inline:1>`, `<inline:2>`, `<inline:3>`: their 1-based position in `extensionFactories`.
- Extension order (paths):
  - policy-first: `<inline:pap-policy>, <inline:s1-mutator>, <inline:s1-panel>`
  - policy-last: `<inline:s1-mutator>, <inline:pap-policy>, <inline:s1-panel>`
  - override-last: `<inline:s1-mutator>, <inline:s1-panel>, <inline:pap-policy>`. The factories were in policy-first order; `extensionsOverride: moveInlinePolicyLast` moved the policy to the end.
  - policy-first + built-ins: `<inline:1>, <inline:2>, <inline:3>, <inline:pap-policy>, <inline:s1-mutator>, <inline:s1-panel>`
- Command seen by `pap-policy` in each order:
  - policy-first: `echo probe` (not mutated). The mutator ran after it. Same with the built-ins.
  - policy-last: `echo probe # mutated-by-s1` (mutated).
  - override-last: `echo probe # mutated-by-s1` (mutated).
  - So `tool_call` handlers run in extension order. An in-place change to `event.input` is visible to every handler that runs later.
- When Pi first writes the session JSONL (R10). The host stats `session.sessionFile` synchronously in its `subscribe` listener on every event and logs each size change.
  - At `ready` the reported `sessionFile` path does not exist yet. A session that is created and never prompted leaves no file, even after `dispose()` and exit (`existsAtReady: false`, `existsAfterShutdown: false`).
  - First prompt: the file is still absent when subscribers get the user message's `message_end`. It exists (7151 bytes) at the next event, the assistant's `message_start`, before any provider output. Its entries at that point: `session, model_change, thinking_level_change, message:system, message:user`.
  - So the file is created when the first user message is persisted, not at session creation and not after the first assistant reply. That matches the SDK doc comment on `SessionManager._hasConversation`: setup entries stay in memory until a user or assistant message exists.
  - Each later entry (assistant, toolResult) also lands on disk after subscribers have seen its `message_end`, and is visible by the next event.
- Reopening a never-prompted session (R10, needed by Task 22). A second worker gets the first worker's `ready.sessionFile`:
  - `SessionManager.open(missingPath)`, the M1 worker's call: no error, ready, the prompt works, and the file is written at the same path. But Pi gives it a new session id: `ready.sessionId` and the JSONL header id both differ from the first worker's (`sameSessionId: false`). The file name still carries the old id: `2026-10-10T14-02-54-886Z_<old id>.jsonl` holds header `id: <new id>`.
  - `SessionManager.create(cwd, dirname(missingPath), { id: oldId })`: same session id and header id, but a new path, because the file name's timestamp prefix changes (`…14-02-56-247Z_<id>.jsonl` became `…14-02-56-918Z_<id>.jsonl`).
- Pi's own `--mode rpc` (fallback reference): its command list (`docs/rpc-commands.md`) has `get_tree` but no tree navigation command. `docs/rpc-extension-ui.md` says `custom()` returns `undefined` in RPC mode.
- Orphans and safety: no host process was left after any run (`ps`). When the driver was killed with SIGKILL mid-run, the idle host exited by itself within 3 s once its IPC channel closed; the driver's temp dirs then stayed behind and were removed by hand. Nothing was written to the real `~/.pi/agent` or `~/.pap`: the only change under `~/.pi/agent` was `mem0/health.json`, written by a long-running `pi` process (pid in the file).

## Result against done-when
A forked Node child hosts the Pi SDK 1.1.0 in-process and is driven entirely over Node IPC. Scripted prompts run and settle. `get_tree` plus `navigate_tree` (`AgentSession.navigateTree`) move the leaf, and the next prompt creates a sibling branch in the same session file. An extension's `ctx.ui.custom()` panel renders over IPC as whole line arrays (`custom_render`), takes keyboard input (`custom_input`), closes (`custom_close`), and returns its value to the extension. All three parts of the done-when hold in 5/5 runs, at about 650 ms fork-to-ready (about 620 ms of it module loading) and about 155 MB RSS per worker.

## Consequences for the plan
- Task 19 `POLICY_EXTENSION_PATH` = `<inline:pap-policy>`. Match on equality: the SDK built-ins appear as `<inline:1>`… with no name.
- Task 19 ADR 0002 (evaluate the policy last, on the final input): confirmed. Handlers run in extension order, and only a handler that runs after a mutator sees the mutated input. Listing the policy factory last works, and so does `extensionsOverride` moving `<inline:pap-policy>` last.
- Task 4 uses this host for RAM measurement: ok. The `ready` record carries `rssMb`, `readyMs` and `importedAtMs`; `get_tree` carries `rssMb`.
- Task 22 (R10): a created-but-never-prompted session has a `file_path` that does not exist.
  - Transcript and snapshot reads must treat a missing file as an empty transcript.
  - Reopening it with `SessionManager.open(path)` succeeds but returns a new `sessionId`, so the plan's `ensureLive` check `ready.sessionId !== row.id → worker_failed` fails on exactly this case.
  - Recreating it with `SessionManager.create(cwd, dirname(path), { id })` keeps the id but changes `file_path` (UNIQUE column).
  - Task 22 must pick one: accept the new id and path when the stored file is absent, or create with the stored id and update `file_path`.
- Task 20/21 IPC facts:
  - A prompt that runs an extension command answers only when the command has finished. The daemon must never wait for that response before it forwards `custom_input` or dialog responses, or it deadlocks.
  - navigate_tree emits no event: re-read the tree and state after its response.
  - A subscriber sees `message_end` before Pi has written that entry, so the daemon must not read the JSONL on `message_end` and expect the entry to be there.
  - The brief's host sent one stray `custom_render` after `custom_close` (handleInput calls `done()`, then the host re-rendered). Fixed by clearing the component in `done()`; M1's panel bridge needs the same guard.
  - The SDK's `KeybindingsManager` subclass (app keybindings) is exported as a type only. The host passes pi-tui's `KeybindingsManager(TUI_KEYBINDINGS)`, as pi-web does. Panels therefore see TUI bindings only.
- Task 20 inherits one type error from `spikes/s2/scripted.ts`. Under `tsc --strict`, `fauxToolCall(name, args)` wants a `JsonObject`, and `Record<string, unknown>` does not fit. It does not matter at runtime.

Decision: GO
