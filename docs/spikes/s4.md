# S4 — idle RAM of one pi-host worker

- Date / machine / Node / Pi SDK: 2026-10-10 / Linux 7.0.0-38-generic x86_64, AMD Ryzen 7 5800X3D (8 cores, 6 visible to the VM), 19 995 MB total RAM, no swap / v24.14.1 / 1.1.0 (`@earendil-works/pi-ai`, `pi-coding-agent`, `pi-tui`) · time-box 4 h · spent ~1.25 h

## Question and done-when
Idle RAM of one `pi-host` worker. Done when measured on Linux x64; this sets the default worker cap. No fallback: the values below are results that Task 13 and Task 23 apply.

## Measurements (MB, 10 samples each)
Source: `spikes/s4/results.json` (raw per-sample values included), from `node spikes/s4/measure.ts > spikes/s4/results.json`. The driver forks `spikes/s1/host.ts` (the S1 worker, scripted S2 provider) with a fresh temp dir as cwd, `agentDir`, `PI_CODING_AGENT_DIR` and `HOME`, plus `PI_OFFLINE=1` and `PI_TELEMETRY=0`. Per sample: fork, `ready`, 3 s idle, read memory, one scripted prompt to `agent_settled`, 3 s, read memory, shutdown. One discarded warm-up sample runs first.

| Variant | idle RSS median / p95 | after one prompt RSS median / p95 | after prompt PSS median / p95 |
|---|---|---|---|
| baseline (no built-ins) | 155 / 157 | 156 / 157 | 103 / 104 |
| with codemode + tool_search + mcp | 156 / 157 | 156 / 157 | 103 / 104 |

- Median is `sorted[floor(n × 0.5)]` of 10 samples (the upper median); p95 is `sorted[9]`, the maximum. Ranges (min / max): RSS 153-157 (baseline idle), 154-157 (built-ins idle), 154-157 after prompt; PSS 100-104 (baseline idle), 101-104 after prompt.
- Idle PSS: 102 / 104 (baseline), 102 / 104 (built-ins). Peak RSS (`VmHWM`) after the prompt equals the RSS reading: 156 / 157. Nothing spiked between the two reads.
- Where the RSS goes (after prompt, both variants): `RssAnon` 98 / 99, `RssFile` 58 / 58, private (`Private_Clean + Private_Dirty`) 98 / 99. The 58 MB of file-backed pages are the Node binary, shared libraries and mapped modules.
- Fork-to-ready (warm cache): 652 / 664 ms baseline, 661 / 673 ms with built-ins (median / p95). Same as S1 (about 650 ms).
- The worker has no child process of its own (`/proc/<pid>/task/<pid>/children` empty in every sample).
- The prompt in this table is text-only (the `reply one` step of `spikes/s1/fixtures/scenario.json`). The "with codemode + tool_search + mcp" row measures the three built-in extensions registered and unused: `codemode` and `tool_search` are registered inactive and neither ran, and no MCP server was configured, so none connected. Codemode execution is measured separately below.
- Four idle workers at once (built-ins variant, same 3 s settle): sum RSS 625 MB, sum PSS 407 MB, sum private 393 MB, PSS per worker 101-102 MB. RSS ×4 would overstate the real cost by about 1.5×.

## Codemode active and called (follow-up, 10 samples each)
Source: `spikes/s4/results-codemode.json`, from `node spikes/s4/measure.ts codemode > spikes/s4/results-codemode.json`. Same driver and worker, built-ins on, plus a `settings.json` in the temp `agentDir` with `defaultTools: ["+codemode", "+tool_search"]` (both are registered inactive; this activates them). One discarded warm-up first. Two scripted scenarios (`spikes/s4/fixtures/`):
- small (`codemode-small.json`): one `codemode` call (`searchTools()`, a nested `tools.read()`), then one `tool_search` call.
- heavy (`codemode-heavy.json`): one `codemode` script that allocates 1 MiB typed arrays until the sandbox runs out of memory.

| Scenario | idle RSS (active, not yet called) | peak RSS (`VmHWM`) | peak PSS (polled every 20 ms) | RSS / PSS 3 s after the prompt |
|---|---|---|---|---|
| small call | 156 / 157 | 190 / 191 | 134 / 135 | 178 / 186 and 125 / 132 |
| heavy call (sandbox at its cap) | 156 / 156 | 439 / 445 | 376 / 387 | 179 / 186 and 126 / 132 |

(median / p95, MB.)
- Both tools ran in every sample: `codemode` ended `Script completed` with no error in 20/20, the small script's nested `read` succeeded (`{"found":4,"tools":4,...}`), and `tool_search` answered `No matching tools found.` (no deferred tools exist without MCP servers). The heavy script returned `{"chunksMiB":255,"error":"InternalError: out of memory"}` in 10/10: it hit the sandbox cap, the QuickJS VM's 256 MB limit per script (`docs/codemode.md`, Limits). The sandbox is created per call (a worker thread plus wasm).
- Activating codemode and tool_search costs nothing at idle (156 / 157, as in the main table). A light call peaks about 34 MB above idle and leaves RSS 22-29 MB above idle 3 s later.
- A script that fills its sandbox peaks at 439 / 445 MB RSS, about 283-289 MB above idle. That is 1.9× `WORKER_BUDGET_MB` and about 210 MB over it at p95. After the call the worker is back to 179 / 186.
- Consequence: `WORKER_BUDGET_MB` = 236 (unchanged) covers an idle worker plus a light tool call (45 MB headroom over the small call's p95 peak). It is not a ceiling: one codemode execution can exceed it by far. The 256 MB sandbox cap bounds a single script; each call gets its own sandbox, so parallel codemode calls in one session could add up (not measured). Whether to enforce a hard per-worker memory limit or to budget the worst case is left to Task 13 and Task 23.

## RSS is not PSS, and the timings are warm-cache
- RSS counts every resident page a process maps, including the file-backed pages (Node binary, libraries) that all workers, and every other Node process on the host, share. Per-worker RSS therefore overestimates what one more worker costs. PSS (`/proc/<pid>/smaps_rollup`) splits shared pages among their sharers; here it is available and reads about 103 MB against 156 MB RSS. The marginal cost of an extra worker is its private memory, about 98 MB.
- This host runs other Node processes (pi, pi-web, this tool), so the file-backed pages are shared with far more than the workers: PSS stays about 101-102 MB per worker with 1 or with 4 workers. On a host with no other Node process, PSS per worker would be about `RssAnon + RssFile / N` = 98 + 58 / N MB (about 112 MB at N = 4, about 102 MB at N = 16). That is arithmetic on the numbers above, not a measurement.
- The derived values below use RSS on purpose: it is the conservative number, and Pi sessions grow beyond this idle floor.
- Timings and memory are warm-cache: a discarded warm-up worker ran first, the S1 and S2 runs had already loaded the module files into the page cache, and the temp dirs are on a normal filesystem. A cold first start after boot is slower.

## Derived values (results, applied by later tasks)
- `WORKER_BUDGET_MB` = ceil(built-ins after-prompt RSS p95 × 1.5) = ceil(157 × 1.5) = **236** → Task 13 `kernel/config.ts`
- default worker cap = clamp(floor(totalMemMb × 0.5 / `WORKER_BUDGET_MB`), 2, 16) → on this machine floor(19 995 × 0.5 / 236) = 42, clamped to **16**. Other sizes: 2 GB → 4, 4 GB → 8, 8 GB and up → 16 (17 before the clamp).
- `idleWorkerRssMb` budget = ceil(baseline idle RSS p95 × 1.2) = ceil(157 × 1.2) = **189** → Task 23 `budgets.json`

## Limits of this measurement
- The main table never ran codemode: `WORKER_BUDGET_MB` is derived from a text-only prompt with the built-ins registered but inactive. Codemode execute, its QuickJS sandbox (a worker thread and wasm, created per call, capped at 256 MB) and `tool_search` use are covered only by the follow-up above: one light call and one worst-case allocation. Not measured: parallel codemode calls, `models.*` calls from a script, `tool_search` over a real deferred set (it ranked over none), and any connected MCP server.
- The worker runs from `.ts` sources under Node's built-in type stripping, which loads the stripper into every worker. A trivial script took 58.4 MB RSS as `t.ts` and 41.9 MB as `t.js` (ad hoc check, 1.5 s after start, not committed), so about 16 MB of every figure here would go away with compiled JS. The figures are conservative for a compiled production worker.
- One short scripted prompt on the S2 faux provider. A real provider SDK client, a long transcript, tool output and connected MCP servers add memory that this run does not see; the 1.5× factor is the headroom for that, and it has not been checked against a long real session. Revisit `WORKER_BUDGET_MB` when M2 has a real provider.
- Memory was read 3 s after `ready` and 3 s after `agent_settled`; there was no soak run.
- n = 10 per variant on one machine, one run of the whole driver. The same figures came out within ±1 MB in two earlier full runs and in a re-run after the `codemode` mode was added (baseline idle RSS 155 / 156, built-ins after-prompt RSS 156 / 157). `results.json` is the committed run; its derived values stand.

## Cleanup and safety (R41)
- The driver tracks every forked child in a Set and every temp dir in another. `main()` runs in `try/finally`; on `finally`, `exit`, SIGINT and SIGTERM it sends SIGTERM, then SIGKILL after 2 s (the `exit` hook can only SIGKILL and remove the temp dirs). A per-worker shutdown waits 5 s, then terminates; every wait for a record has a 20 s timeout and also fails on early exit or `boot_error`. A failed warm-up sample is logged to stderr and discarded. Children are forked with `stdio: ["ignore", 2, 2, "ipc"]`, so worker output goes to stderr and stdout carries only the JSON.
- Edit to the S1 host: `spikes/s1/host.ts` gets `process.on("disconnect", () => process.exit(0))` (one line, not a copy). S1's own driver is unaffected.
- Failure injection, run on the final driver (SIGINT and SIGKILL of the driver were repeated in `codemode` mode after the follow-up was added: exit 130, no worker, no temp dir; worker gone through `disconnect` after SIGKILL): SIGINT on the driver with its worker SIGSTOPped: exit 130 after 2.0 s (SIGTERM stays pending on a stopped process, SIGKILL after 2 s ended it), no worker left. SIGTERM on the driver: exit 143, no worker, no temp dir. SIGKILL on the driver: the worker was gone within 0.2 s through `disconnect`; only the temp dir stayed (removed by hand).
- Nothing was written to the real `~/.pi/agent` or `~/.pap`: workers use temp `PI_CODING_AGENT_DIR` and `HOME`.
