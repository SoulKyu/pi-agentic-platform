# S5 — diff renderer: `@pierre/diffs` vs CodeMirror merge

- Date / Node / tooling: 2026-10-10 / v24.14.1 / Vite 8.3.4, React 19.3.0, `@pierre/diffs` 1.5.2, `@codemirror/merge` 6.12.2 (`state` 6.7.6, `view` 6.43.14), headless Chromium 153.0.8010.12 driven by `playwright-core` 1.64.0 · time-box 1 day · spent ~0.5 h (machine clock)

## Question and done-when
Diff renderer for the lane review screen (DESIGN §9.2 DiffView: unified, line numbers, line comments in the `you` colour, file checklist with Seen state). Done when a lane review prototype with line comments exists for each candidate. Fallback: the other candidate. Paths below are under `spikes/s5/`.

Fixture: pi-web `lib/worktree.ts` at `b3e1eed` (before, 250 lines) against HEAD (after, 320 lines): +82 −12 lines, several hunks and unchanged blocks. The brief's `lib/auth-throttle.ts` has a single commit (102 lines), so it has no pair to diff.

## Findings

### Prototype behaviour (Chromium, `browser-results.json`)
- Both candidates: 3 prompts, 3 list entries (`<ol data-testid="comments">`), 3 inline comments in the `you` tokens (`--you-tint` / `--you-line` / `--you-text`), 0 page errors. Pierre's comment sits directly under the clicked line, deleted line included. CodeMirror's sits under the line for added and unchanged lines, and under the whole deleted chunk for a deleted line.
- Pierre shows old-side numbers on deleted lines (52, 54) and new-side numbers elsewhere, collapses unchanged runs by default with expand buttons ("34 unmodified lines"), draws a file header with `-12 +82` counts, and highlights intra-line changes.
- CodeMirror shows no number for a deleted line (the deleted chunk is a block widget outside the line-number gutter), so a reviewer cannot read the old line a comment refers to without extra work.
- Pierre renders inside `<diffs-container>` (open shadow root, `adoptedStyleSheets`). Slotted annotation content stays in the light DOM, so our own CSS styles it with tokens.

### Large diff (same fixture repeated; `lines` = after-side lines, ≈ 2.2 k and ≈ 10.2 k; single run each, headless Chromium without GPU, relative numbers only)
| | CodeMirror | Pierre, main thread | Pierre + worker pool (2) |
|---|---|---|---|
| 2.2 k lines: first line / long tasks total (max) | 188 ms / 61 ms (61) | 1561 ms / 1383 ms (1305) | 341 ms / 318 ms (85) |
| 10.2 k lines: first line / long tasks total (max) | 369 ms / 170 ms (170) | 5508 ms / 5371 ms (4475) | 1209 ms / 1013 ms (553) |

### Pierre integration traps (apply them in M9 if it is chosen)
- Default selection makes the gutter `+` stick: after the first click the line is selected and the button stays on it, so the next comment opens for the same line. `controlledSelection: true` with `selectedLines={null}` fixes it (observed: without it, three clicks all reported `after 39`).
- A custom CSS-variable theme must also be given to the worker pool through `highlighterOptions.theme`, or the workers return default-theme colours (observed: keyword `rgb(255,103,141)`, surface `rgb(10,10,10)`).
- The `+` appears on hover. Touch behaviour (no hover on iOS) was not tested; `onLineNumberClick` exists as an alternative trigger.
- Not required, tried and dropped: memoising `options`, deferring `window.prompt`. Neither changed the result.

### CodeMirror integration traps (apply them in M9 if it is chosen)
- Handlers registered through `EditorView.domEventHandlers` never fire for events inside widgets (deleted chunks), so the deleted-line click is a plain `mousedown` listener on `view.dom`, relying on the class names `.cm-deletedChunk` / `.cm-deletedLine` and `view.posAtDOM` + `getChunks` + `getOriginalDoc` to find the old line number.
- Comments on deleted lines are anchored with a block widget at the chunk's `fromB`: under the chunk, not under the line. Per-line placement or old line numbers would need a custom deleted-chunk renderer, which `unifiedMergeView` does not offer.
- The bare prototype has no syntax highlighting (merge has no language of its own); the 46 KB difference above buys it.

### Bundle hygiene
- Without `"sideEffects": false` in `spikes/s5/package.json`, module-level code such as `new CommentMarker()` kept CodeMirror inside the Pierre build and inflated both numbers (Pierre initial read 287 KB instead of 214 KB). The numbers above come from builds that contain one candidate each; the `baseline` mode builds with neither.
- Pierre's 319 JS files are the grammar and theme chunks Shiki loads on demand; only the entry and the grammars of the files shown are fetched. Spec C already plans Shiki on demand for markdown, and the M8 editor already ships CodeMirror 6, so the marginal cost of either candidate in the real app is below the numbers above (not measured).

### Safari 16.4 static scan (`floor-scan.ts` → `floor-results.json`, runtime CSSOM scan in `browser-results.json`)
- JS: nothing newer than 16.4 in either bundle except Pierre's Shiki regex engine mentioning the `v` flag (Safari 17.0), behind a `new RegExp("[[]]", "v")` feature test that selects the ES2018 target when it throws, and CodeMirror's `requestIdleCallback`, feature-detected.
- CSS, Pierre only: native nesting, `light-dark()`, `scrollbar-gutter`; `color-mix()` (16.2), `@layer` (15.4), `subgrid` (16.0) and constructable stylesheets (16.4) are fine. The Safari versions are from caniuse knowledge, not re-verified here. On a browser without nesting, nested rules are dropped; without `light-dark()`, the declarations using it are invalid at computed-value time. What that does to the layout on 16.4 needs a real device or BrowserStack run. Lowering the shipped CSS at build time with lightningcss was not tried (the CSS is a string inside the package's JS).

## Environment and what was not run
- WebKit: `playwright-core install webkit` downloads a build, but `install-deps --dry-run webkit` lists 308 missing system packages on this Ubuntu 26.04 host and `ldd` of the build lacks about 50 libraries; installing them needs sudo. Not attempted further. Even Playwright's WebKit is far newer than Safari 16.4, so the floor needs a real Safari 16.4 / iOS 16.4 run either way.
- Chromium: the host's Playwright Chromium (revision 1243, headless shell) lacked 12 shared libraries and has no fonts. Run without sudo: `apt-get download` + `dpkg -x` of `libatk1.0-0t64 libatk-bridge2.0-0t64 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libasound2t64 libatspi2.0-0t64 libxrender1 libxi6 libxres1 fonts-dejavu-core` into a temp dir, `S5_LIBS` = its `usr/lib/x86_64-linux-gnu` (as `LD_LIBRARY_PATH`), `FONTCONFIG_FILE` = a minimal fonts.conf with the extracted font dir. The temp dir was removed afterwards.
- The page was driven against the production builds served by a tiny static server (the exact bundles measured). `vite --mode pierre` dev server was smoke-tested (index, `main.tsx`, `pierre-review.tsx` answer 200) but not driven in a browser.

## Deviations from the brief
- Fixture pair changed (above). `main.tsx` calls the prototype `worktree.ts`.
- Contract: `onComment(line, side)` and a `comments` prop on both candidates, and `mountCodeMirrorReview` returns `{ setComments, destroy }`. With the brief's `onComment(line)` a deleted-line comment cannot be expressed (`side` was hard-coded to `after`) and no comment would be shown inside the diff.
- Extra dependencies and files: `@codemirror/lang-javascript`, `@codemirror/language`, `@lezer/highlight` (syntax variant), `playwright-core`, `@types/node`; `tsconfig.json`, `src/tokens.css` (DESIGN §3 night and day tokens), `src/big-fixture.ts`, `browser-check.ts`, `floor-scan.ts`; modes `baseline`, `codemirror-syntax`, `pierre-worker`; `collapseUnchanged` on the merge view.
- `measure.ts` runs `corepack pnpm exec vite build` (pnpm only through corepack) and reports initial and total gzip with one decimal.
- `.gitignore` already contained `spikes/**/dist-*/` (R1, R19): nothing appended, no build output is tracked.

## Choice and decision
Choice for roadmap M9: CodeMirror merge (`unifiedMergeView` with the custom gutter, deleted-line listener and block-widget comments from `src/codemirror-review.ts`) because it meets every requirement of the done-when with plain permissive licensing and no modern-CSS dependency, while `@pierre/diffs` ships CSS that needs Safari 17.2 / 17.5 against a 16.4 floor that spec C §7.3 pins by a test, and nothing here proves it degrades gracefully. CodeMirror is also the single editor engine already planned for M8, and it handles a 10 k-line diff without a worker. The price: about 130 lines of glue, no old line number on deleted lines, and a deleted-line comment shown under its chunk.

What flips it to `@pierre/diffs`: a run on real Safari 16.4 / iOS 16.4 (or BrowserStack) where the review screen is usable, or a build-time lowering of its CSS that makes it so. It would then buy native per-line comments on both sides, old line numbers, hunk expansion and a worker pool (use `controlledSelection`, `highlighterOptions.theme` and the worker pool for diffs above ~2 k lines).

Decision: FALLBACK (CodeMirror merge)
