## Why
- The runtime masks paths under `/proc` (OCI masked/readonly paths). Measured in the default container (`extra-results.txt` §B, "/proc mounts"): `/proc/kcore`, `keys`, `timer_list`, `interrupts`, `latency_stats` are overmounted with `/dev/null`, `/proc/acpi` and `/proc/scsi` with empty tmpfs, and `/proc/bus`, `fs`, `irq`, `sys`, `sysrq-trigger` are read-only binds. With `systempaths=unconfined` only the plain `/proc` mount is left.
- `--unshare-pid --proc /proc` makes bwrap mount a fresh procfs for the new pid namespace; that mount returns EPERM while the current `/proc` carries overmounts (the kernel refuses a procfs mount that would reveal what is masked). This is the standard explanation of this error and is consistent with the measurements: the failure goes away exactly when the `/proc` masks go (`systempaths=unconfined`, `unmask=/proc/*`), and not with seccomp, AppArmor or capability changes.
- The user-namespace part is not the problem here: bwrap's own `unshare(CLONE_NEWUSER)` and mounts work in the default container (`minimal` and `unshare-net` pass), and `--unshare-pid` without `--proc` works (`ok pid=2`, `extra-results.txt` §B). The containers-common seccomp profile allows `clone`, `clone3`, `unshare`, `mount`, `umount2`, `pivot_root` with no condition (unrecorded: hand check of `/usr/share/containers/seccomp.json`).
- `kernel.apparmor_restrict_unprivileged_userns = 1` did not interfere under rootless podman. Inside the container the host's `bwrap` AppArmor profile attaches by path to `/usr/bin/bwrap` (label `bwrap//&unpriv_bwrap (enforce)`), but a copy at `/home/pap/bwrap-copy` (label `crun (unconfined)`) behaves the same (fails with (A) by default, passes with `systempaths=unconfined`), `extra-results.txt` §B. The sysctl is not a factor in this runtime; it may be one under rootful Docker (see Limits).
- `--cap-add SYS_ADMIN` is worse than nothing under podman: it puts the cap in the non-root user's permitted/effective/ambient sets (`CapEff 0x200000`, `extra-results.txt` §B), and non-setuid bwrap refuses to start with unexpected capabilities (B).

## Cost of `--security-opt systempaths=unconfined`
What the flag removes: it drops every default mask of the runtime for the whole container. `man podman-run` (`--security-opt unmask=`, text read by hand, unrecorded) lists them: masked `/proc/acpi`, `kcore`, `keys`, `latency_stats`, `sched_debug`, `scsi`, `timer_list`, `timer_stats`, `/sys/firmware`, `/sys/fs/selinux`, `/sys/devices/virtual/powercap`, and read-only `/proc/asound`, `bus`, `fs`, `irq`, `sys`, `sysrq-trigger`, `/sys/fs/cgroup`. So the flag also unmasks `/sys/firmware`, `/sys/fs/selinux`, `/sys/devices/virtual/powercap` and lifts the read-only mount on `/sys/fs/cgroup` (writable for container root, measured below), not only the `/proc` masks.

Measured for the image user `pap` (uid 10001, `CapEff 0`) outside bwrap, default vs flag (`extra-results.txt` §B; writes were tested with `access(2)`, nothing was written):
- `/proc/kcore` and `/proc/timer_list`: default = `/dev/null` overmount (reads return nothing); flag = mode 0400 owned by the unmapped host root, read denied.
- Readable with real content under the flag (default = empty `/dev/null`): `/proc/interrupts` (mode 0444, 26 lines: host IRQ counters), `/proc/keys` (0444, 1 line), `/proc/latency_stats` (1 line); directories `/proc/acpi` [wakeup], `/proc/scsi` [device_info scsi sg], `/sys/firmware` [acpi dmi efi memmap] become listable (default = empty tmpfs). The files below those directories were not read: untested.
- Nothing becomes writable for `pap`: `/proc/sysrq-trigger`, `/proc/sys/*`, `/proc/bus|fs|irq`, `/sys/fs/cgroup` are write-denied by `access(2)` in both modes.
- `/proc/sched_debug`, `/proc/timer_stats`, `/sys/fs/selinux`, `/sys/devices/virtual/powercap` do not exist on this kernel and host, so those masks could not be tested.
- Container root (`--user 0`, not the image user; `extra-results.txt` §C): same picture, `/proc/sys` and `sysrq-trigger` stay write-denied (files owned by the unmapped host root, no capability in the initial user namespace), but `/sys/fs/cgroup` turns from write-denied to write-OK: root can manage the cgroup subtree delegated to the container.

Reading: on this rootless host, with a non-root user without capabilities, the flag exposes read-only host information and no write access; the rest follows from file permissions, not from the runtime masks. That reasoning does not transfer. In a rootful Docker daemon container root is host root unless user-namespace remapping is on, and the masks are what keeps it from `/proc/kcore`, `/proc/sysrq-trigger`, `/proc/sys`, `/sys/firmware`. Adopting the flag there needs a security re-assessment, not only a bwrap re-run. The same holds for running this image as root, or with extra capabilities, even on podman.

## Result (provisional: podman rootless on this host; Docker at M9)
- Minimal option set that runs the pi-web profile: **`--security-opt systempaths=unconfined`**, nothing else (default seccomp, no AppArmor change, no capability, not privileged). It also works with `--cap-drop ALL --security-opt no-new-privileges`.
- Documentation line for `compose.yaml` and the image README: "Agents with `sandbox: bubblewrap` need `--security-opt systempaths=unconfined` (compose: `security_opt: [systempaths=unconfined]`). Without it the container's masked `/proc` makes bwrap fail with `Can't mount proc on /newroot/proc: Operation not permitted`, and those agents refuse to start. The flag unmasks `/proc` and `/sys` paths for the whole container: run as a non-root user, add `--cap-drop ALL --security-opt no-new-privileges`, never `--privileged` or `--cap-add SYS_ADMIN`."
- Fail-closed rule (C §9.2): an agent requiring the sandbox refuses to start when the probe fails; `pap doctor` reports it.
  - The probe must be the real profile, spawned: `bwrap <sandboxArgs(home, {network:false})> -- true`, non-zero exit means refuse. `bwrap --version`, a PATH scan (`pi-web/lib/agents/sandbox.ts` `bwrapAvailable` only scans PATH, "never spawns it") and the `minimal`/`unshare-net` profiles all pass in a default container where the real profile fails.
  - `pap doctor` prints the bwrap stderr and the hint: pass `--security-opt systempaths=unconfined`.
  - Do not copy pi-web's `threadSandboxWrapper`, which warns and runs bash unsandboxed when bwrap is missing.
  - Agents with `sandbox: none` are not affected.
- Alternative not recommended: dropping `--proc /proc` from the profile works under default flags but leaves the container's `/proc` visible to the sandbox, losing the "fresh /proc, no /proc/<daemon pid>/environ" property that `sandbox.ts` documents. Only the controller can accept that.

## Limits (not measured)
- **Docker was not measured** (R49).
  - Hypothesis, unmeasured: default Docker applies the same OCI masked and read-only `/proc` paths and should fail the same way with (A); `--security-opt systempaths=unconfined` is also Docker's flag for it.
  - Its default seccomp profile may differ: containers-common allows `clone`/`unshare`/`mount` unconditionally; Docker's default profile is understood to gate them on `CAP_SYS_ADMIN` (hypothesis, from memory of the moby profile; if true, Docker also needs a seccomp change).
  - Rootful Docker on Ubuntu 24.04+ runs the container under `docker-default` AppArmor, where `kernel.apparmor_restrict_unprivileged_userns = 1` may add a userns denial. Non-root `--cap-add` behaviour may differ from podman's.
  - M9 must re-run `RUNTIME=docker sh spikes/s8/matrix.sh` and `extra.sh` on an Ubuntu 24.04+ host and re-assess the security cost (previous section) before the Docker documentation line is final.
- Only bwrap 0.8.0 (Debian 12) was measured, one kernel (7.0.0-38), one host. No SELinux host, no cgroup v1, no rootful podman.

Decision: FALLBACK — sandboxed bash does not work under default podman rootless; it works with `--security-opt systempaths=unconfined` only. The fail-closed rule applies (agents requiring the sandbox refuse to start without it). Docker re-measure and security re-assessment at M9.
