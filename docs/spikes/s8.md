## Why
- The runtime masks paths under `/proc` (OCI masked/readonly paths). In the container: `/proc/kcore`, `keys`, `timer_list`, `interrupts`, `latency_stats` are overmounted with `/dev/null`, `/proc/acpi` and `/proc/scsi` with empty tmpfs, and `/proc/bus`, `fs`, `irq`, `sys`, `sysrq-trigger` are read-only binds (`/proc/self/mountinfo`).
- `--unshare-pid --proc /proc` makes bwrap mount a fresh procfs for the new pid namespace; that mount returns EPERM while the current `/proc` carries overmounts (the kernel refuses a procfs mount that would reveal what is masked). This is the standard explanation of this error; it is consistent with what was measured: the failure goes away exactly when the `/proc` masks go (`systempaths=unconfined`, `unmask=/proc/*`), and not with seccomp, AppArmor or capability changes.
- The user-namespace part is not the problem here: bwrap's own `unshare(CLONE_NEWUSER)` and mounts work in the default container (`minimal` and `unshare-net` pass), and `--unshare-pid` without `--proc` also works (`ok pid=2`). The containers-common seccomp profile allows `clone`, `clone3`, `unshare`, `mount`, `umount2`, `pivot_root` unconditionally (checked in the JSON).
- `kernel.apparmor_restrict_unprivileged_userns = 1` did not interfere under rootless podman. Inside the container the host's `bwrap` AppArmor profile attaches by path to `/usr/bin/bwrap` (label `bwrap//&unpriv_bwrap (enforce)`), but a copy of bwrap at `/home/pap/bwrap-copy` (label `crun (unconfined)`) works the same (fails with (A) by default, passes with `systempaths=unconfined`). The sysctl is therefore not a factor in this runtime; it may be one under rootful Docker (see Limits).
- `minimal` PASS means nothing: without `--unshare-pid`, `--proc /proc` ends in the container's own procfs (same superblock `0:62` in and out, same pid namespace number inside and outside), so the sandbox shares the container's pid namespace. It passes where the real profile fails.
- `--cap-add SYS_ADMIN` is worse than nothing under podman: it puts the cap in the non-root user's permitted/effective/ambient sets (`CapEff 0x200000`), and non-setuid bwrap refuses to start with unexpected capabilities (B).

## Isolation check under the minimal flag
`podman run --rm --security-opt systempaths=unconfined` with the pi-web profile, run as `pap`:
- pid namespace is new (inside `pid:[4026532272]`, outside `pid:[4026532267]`); `/proc` lists only the sandbox's own processes (1–6); the container's tini and probe are not visible.
- only `lo` in `/proc/net/dev`; `/usr/x` and `/etc/x` are "Read-only file system"; `/tmp` is empty (marker created outside is invisible); `/home/pap` shows only `agent-home` (the outside marker is hidden); `agent-home` writable; sandbox child `CapEff 0`; `echo 1 > /proc/sys/kernel/domainname` is "Permission denied".

## Result
- Minimal option set that runs the pi-web profile: **`--security-opt systempaths=unconfined`**, nothing else (default seccomp, no AppArmor change, no capability, not privileged). It also works with `--cap-drop ALL --security-opt no-new-privileges`.
- Documentation line for `compose.yaml` and the image README: "Agents with `sandbox: bubblewrap` need `--security-opt systempaths=unconfined` (compose: `security_opt: [systempaths=unconfined]`). Without it the container's masked `/proc` makes bwrap fail with `Can't mount proc on /newroot/proc: Operation not permitted`, and those agents refuse to start. Do not use `--privileged` or `--cap-add SYS_ADMIN`." Suggested hardening that was measured compatible: `--cap-drop ALL --security-opt no-new-privileges`, non-root user.
- Cost of the flag: the runtime stops masking `/proc` for the whole container (kcore, keys, timer_list, … visible; `/proc/sys`, `sysrq-trigger` no longer mounted read-only). In the measured rootless setup the user is `pap` with no capabilities, so the files stay protected by permissions; this reasoning does not transfer to a rootful Docker daemon without a re-measure.
- Fail-closed rule (C §9.2): an agent requiring the sandbox refuses to start when the probe fails; `pap doctor` reports it.
  - The probe must be the real profile, spawned: `bwrap <sandboxArgs(home, {network:false})> -- true`, non-zero exit means refuse. `bwrap --version`, a PATH scan (`pi-web/lib/agents/sandbox.ts` `bwrapAvailable` only scans PATH, "never spawns it") and the `minimal` profile all pass in a default container where the real profile fails.
  - `pap doctor` prints the bwrap stderr and the hint: pass `--security-opt systempaths=unconfined`.
  - Do not copy pi-web's `threadSandboxWrapper`, which warns and runs bash unsandboxed when bwrap is missing.
  - Agents with `sandbox: none` are not affected.
- Alternative not recommended: dropping `--proc /proc` from the profile works under default flags but leaves the container's `/proc` visible to the sandbox, losing the "fresh /proc, no /proc/<daemon pid>/environ" property that `sandbox.ts` documents. Only the controller can accept that.

## Limits (not measured)
- **Docker was not measured** (R49). Its default seccomp profile may differ: containers-common allows `clone`/`unshare`/`mount` unconditionally; Docker's default profile is understood to gate them on `CAP_SYS_ADMIN` (hypothesis, from memory of the moby profile; if true, Docker also needs a seccomp change). Rootful Docker on Ubuntu 24.04+ runs the container under `docker-default` AppArmor, where `kernel.apparmor_restrict_unprivileged_userns = 1` may add a userns denial. Non-root `--cap-add` behaviour also differs from podman's. M9 must re-run `RUNTIME=docker sh spikes/s8/matrix.sh` on an Ubuntu 24.04+ host before the Docker documentation line is final.
- Only bwrap 0.8.0 (Debian 12) was measured, one kernel (7.0.0-38), one host. No SELinux host, no cgroup v1, no rootful podman.

Decision: FALLBACK — sandboxed bash does not work under default podman rootless; it works with `--security-opt systempaths=unconfined` only. The fail-closed rule applies (agents requiring the sandbox refuse to start without it). Docker re-measure at M9.
