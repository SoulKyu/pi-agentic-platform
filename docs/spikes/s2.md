# S2 — scripted custom provider

- Date / Node / Pi SDK: 2026-10-10 / v24.14.1 / 1.1.0 (`@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent`)
- Time-box: 1 day · spent: ~0.5 h

## Question and done-when
Does a scripted custom provider drive full runs (text, tool calls, quota error)? Done when the integration test runs offline and deterministically.

## Measurements
| Scenario | native route deterministic | extension route deterministic | median ms |
|---|---|---|---|
| text | true | true | 1 (native) / 1 (extension) |
| tool | true | true | 5 (native) / 4 (extension) |
| quota | true | true | 5 (native) / 4 (extension) |

Source: `spikes/s2/results.json`, from `cd spikes/s2 && PI_OFFLINE=1 PI_TELEMETRY=0 node run.ts > results.json`. 20 runs per cell, each in a fresh temp dir used as cwd, `agentDir`, `PI_CODING_AGENT_DIR` and `HOME`. `distinctHashes` is 1 in all six cells. The native and extension routes produce the same event sequence and the same normalized transcript for each fixture.

- Network attempts during 120 runs: 0. A second full run under `bwrap --dev-bind / / --unshare-net` (no network at all) gave the same `results.json`, byte for byte apart from `medianMs`. That also checks determinism across processes.
- `fauxAssistantMessage` option names that worked: `stopReason`, `errorMessage` (as planned). The `.d.ts` also accepts `responseId`, `timestamp` and `deferred`. `fauxToolCall(name, args, { id })` keeps the id: the tool result has `toolCallId: "call-1"`.
- Two `fauxProvider` options are needed for determinism (the plan's code lacked them):
  - `api`: the default is `faux:<epoch ms>:<random>`, and it ends up in every assistant message's `api` field.
  - `tokenSize: { min, max }` with `min === max`: the default chunk size is random, so the number of `text_delta` / `toolcall_delta` events changes from run to run.
  - Fix used: `fauxProvider({ api: "scripted", models: [{ id }], tokenSize: { min: 4, max: 4 } })`. Before the fix, all six cells had 20 distinct hashes.
- The transcript's system message includes the cwd (`<cwd>…</cwd>` section). With a temp cwd per run, the runner replaces the root path with `<cwd>` before hashing.
- Unicode text (emoji, CJK, U+2028) round-tripped unchanged in the transcript: yes. The assistant text equals the fixture string exactly, U+2028 included.
- Event sequences (the same for both routes):
  - text: `agent_start, turn_start, message_start/end` (role `system`), `message_start/end` (role `user`), `message_start, message_update:text_start, 4× text_delta, text_end, message_end, turn_end, agent_end, agent_settled`.
  - tool: assistant `toolcall_start, 2× toolcall_delta, toolcall_end, message_end`, then `tool_execution_start, 2× tool_execution_update, tool_execution_end` (bash `result.content[0].text = "s2-tool-ok\n"`, `isError: false`), then a `toolResult` message, `turn_end`, a second turn with the scripted text, `agent_end, agent_settled`. The transcript is `user → assistant(toolCall bash) → toolResult("s2-tool-ok\n") → assistant("The command printed s2-tool-ok.")`.
- How a quota error surfaces (events, retries, final stopReason/errorMessage), with `retry: { enabled: true, maxRetries: 2, baseDelayMs: 1 }`:
  - Pi treats the `429 … usage limit reached` message as retryable.
  - Each attempt ends with `agent_end { willRetry: true }`, then `auto_retry_start { attempt, maxAttempts: 2, delayMs, errorMessage }` (delayMs 1 then 2, exponential from `baseDelayMs`), then `entry_appended` of a `context_edit` entry (`replacement: null`) that removes the failed assistant message from context.
  - After the last attempt: `agent_end { willRetry: false }`, `auto_retry_end { success: false, attempt: 2, finalError }`, `agent_settled { aborted: false }`.
  - `session.prompt()` resolves and does not throw. `session.messages` ends with one assistant message `{ content: [], stopReason: "error", errorMessage: "429 Too Many Requests: usage limit reached; resets at 2026-10-11T00:00:00Z" }`; the failed attempts are not kept.
  - Pi does not parse the "resets at" hint: the delay follows `baseDelayMs`.
  - The provider is called `1 + maxRetries` times, which is the 3 steps in `quota.json`.
- Retry settings needed to keep a quota test fast and deterministic: `retry.enabled=false` (checked ad hoc: one provider call, no `auto_retry_*` events, 7 ms, same final `stopReason`/`errorMessage`), or retry enabled with a tiny `baseDelayMs` and exactly `1 + maxRetries` error steps.
  - With the default retry settings (checked ad hoc), Pi retried 3 times with delays of about 2 s, 4 s and 8 s: the run took 14 046 ms. The 4th call found the queue empty, so the final `errorMessage` was `No more faux responses queued`, not the scripted one.
- Control (ad hoc): the extension route without the extension makes `session.prompt()` throw `Error: No API key found for faux. …`. So the provider registered by `pi.registerProvider(provider)` is the one that serves the run. An unregistered provider shows up as a thrown error, not as an event.
- Safety: no write to the real `~/.pi/agent`. The only file there newer than the run start was `mem0/health.json`, written by the running pi-web `next-server` (its pid is in the file). Every per-run temp dir was removed.

## Result against done-when
The scripted provider drives full Pi runs through both registration routes: `ModelRuntime.registerNativeProvider()`, and `pi.registerProvider(provider)` from an inline extension. All three scenarios worked: plain text with Unicode, a real `bash` tool call whose output comes back to the model, and a quota error that goes through Pi's auto-retry and ends in a recorded error. Runs make zero network attempts and also pass inside an empty network namespace. They are deterministic: one hash over 20 runs in each of the six cells, and identical output across processes. This holds once the provider pins `api` and `tokenSize` and the transcript is normalized for the per-run temp cwd. The done-when is met.

## Consequences for the plan
- Task 20 `scripted-provider.ts`: changes.
  - Call `fauxProvider({ api: "scripted", models: [{ id: script.modelId }], tokenSize: { min: 4, max: 4 } })`, otherwise `api` and the delta count change per run.
  - The script format and the option names (`stopReason`, `errorMessage`) need no change.
  - Task 2 copies `spikes/s2/scripted.ts`, so it inherits the fix.
- Task 23 / Task 27 provider scripts: no format change. Two points:
  - Tests must not compare the system message raw: it embeds the cwd (and the Pi docs path).
  - A script with an error step runs under the worker's `SettingsManager.create(cwd, agentDir)`, so Pi's default retry applies (3 retries, about 14 s). It needs either `"retry": { "enabled": false }` in the temp agentDir's `settings.json` or `1 + maxRetries` error steps.
  - Assert on text and tool results, not on `tool_execution_update` counts: those follow bash output chunking. The count was stable here (2), but it is not part of the script.

Decision: GO
