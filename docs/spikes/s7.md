# S7 — project trust file ownership

- Date / Node / Pi SDK: 2026-10-10 / v24.14.1 / 1.1.0 (`@earendil-works/pi-coding-agent`) · time-box 2 h · spent ~0.5 h

## Question and done-when
Is `~/.pi/agent/trust.json` Pi's own file (read in place), or must pap keep a `project_trust` table? Done when Pi's docs/code and pi-web's `lib/project-trust.ts` answer it. Paths below: `SDK/` = `node_modules/@earendil-works/pi-coding-agent/`, `PI_WEB/` = `/home/ubuntu/Workspace/soulkyu/pi-web/` (read only). The SDK in `PI_WEB` and in `spikes/s7` are both 1.1.0 and `dist/core/trust-manager.js` is byte-identical in the two.

## Findings
- File written by `ProjectTrustStore.set()`: `<agentDir>/trust.json`, path built in `SDK/dist/core/trust-manager.js:174` (`join(resolvePath(agentDir), "trust.json")`). `agentDir` is whatever the caller passes (the CLI passes `getAgentDir()` = `PI_CODING_AGENT_DIR` or `~/.pi/agent`, `SDK/dist/config.js:491-497`, `SDK/dist/main.js:576`). The file is the only regular file written (a transient `trust.json.lock` directory exists during each call).
- Format (probe, `spikes/s7/results.json`): one flat JSON object, key = canonical absolute folder path (symlinks resolved, `trust-manager.js:19`), value = `true` | `false`; `null` is accepted on read and means "no decision" (`set(path, null)` deletes the key). Keys sorted, 2-space indent, trailing newline (`trust-manager.js:96-104`):
  ```json
  {
    "<abs-path-of-project>": true,
    "<abs-path-of-other-folder>": false
  }
  ```
  The real `~/.pi/agent/trust.json` on this machine has exactly this shape (read for structure only, never written, not copied). Mode is `664` (umask, no explicit mode: `writeFileSync` at `trust-manager.js:104`), not `0600`.
- The `pi` CLI and the SDK share this store, same class: yes.
  - Docs: `SDK/docs/security.md:67-73` ("Saved decisions use canonical directory paths and live in `~/.pi/agent/trust.json`"; `/trust` saves for future Pi processes), `docs/slash-commands.md:48`.
  - Code: the CLI builds `new ProjectTrustStore(agentDir)` (`SDK/dist/main.js:576`, read at `:597`, `package-manager-cli.js:668-670`), saves through `resolveProjectTrusted` (`SDK/dist/core/project-trust.js:32,54`), the interactive implicit save (`SDK/dist/modes/interactive/interactive-mode.js:4405-4411`) and `/trust` (`:4422-4430`). The SDK exports the same class (`SDK/dist/index.js:31`).
  - Measured (`spikes/s7/cli-check.ts` → `cli-results.json`, real `pi --print` in temp dirs, offline, no key, stops at "No API key found"): a project extension's factory ran when `trust.json` (written by `ProjectTrustStore`) said `true`, did not run for `false` or for no entry; `--approve` ran it, `--no-approve` blocked it even with `true`; settings `defaultProjectTrust: "always"` ran it; the CLI never rewrote `trust.json` in print mode.
- What makes a folder require trust (`hasTrustRequiringProjectResources`, `trust-manager.js:151-169`, list at `:8-17`; measured over 14 layouts): `.pi/settings.json`, `.pi/mcp.json`, `.pi/extensions`, `.pi/skills`, `.pi/prompts`, `.pi/themes`, `.pi/SYSTEM.md`, `.pi/APPEND_SYSTEM.md`, and `.agents/skills` in the folder or any ancestor. Not: an empty folder, `AGENTS.md` only, a bare `.pi`, `~/.agents/skills` with the home folder as cwd (it reads `process.env.HOME`, so a worker env without the right `HOME` changes the answer). Existence is tested with `existsSync`, so a dangling symlink does not count (pi-web's stricter `hasTrustRelevantEntries`, `PI_WEB/lib/project-trust.ts:211`, exists for that).
- Decision lookup (`findNearestTrustEntry`, `trust-manager.js:21-34`; measured): the nearest ancestor entry wins. Trusting a parent makes every child trusted (`getEntry(child).path` is the parent); an explicit `false` on the child beats a trusted parent; `set(child, null)` returns to inheritance; entries are keyed by real path (a symlinked cwd lands under its target).
- pi-web pattern: `resolveProjectTrust: async () => new ProjectTrustStore(agentDir).get(cwd) === true` confirmed (`PI_WEB/lib/project-trust.ts:149-156`, resolver at `:155`), only installed when the folder has trust-requiring resources. Used by `PI_WEB/lib/rpc-manager.ts:2546-2553,2625`, `lib/subagent-runtime.ts:315`, `lib/skills-service.ts:9`, `app/api/models/route.ts:29`. Writes: `trustProject()` (`:121-125`) and `trustFreshFolderAndWrite()` (`:391`), reads: `getProjectTrustStatus()` (`:47`), `mayReadProjectConfigNow()` (`:97`, a store that throws counts as untrusted, one warning per distinct error). Its header comment says Pi Web and the `pi` CLI "share the same trust store" (`:144`).
- The SDK hook is `ResourceLoaderReloadOptions.resolveProjectTrust` (`SDK/dist/core/resource-loader.d.ts:25-27`), passed as `createAgentSessionServices({ resourceLoaderReloadOptions })` (`SDK/dist/core/agent-session-services.js:69`). It is not described in `SDK/docs/sdk.md`; the `.d.ts` is the contract. `reload()` calls the resolver, then `setProjectTrusted(result)` (`resource-loader.js:358-361`); a throwing resolver rejects the reload (no try/catch).

## Failure modes measured (`results.json`, `failures`)
| Case | `ProjectTrustStore.get()` |
|---|---|
| unparsable JSON | throws `Failed to read trust store <path>: …` |
| top-level array, or a value that is not true/false/null | throws `Invalid trust store <path>: …` |
| lock directory `trust.json.lock` already present | throws `Lock file is already being held` after ~180 ms (10 × 20 ms synchronous busy-wait, `trust-manager.js:109-127`, blocks the thread) |
| `agentDir` read-only | throws `EACCES … mkdir '<agentDir>/trust.json.lock'` |
| `agentDir` missing | returns `null` and creates the directory |
| normal read | returns the decision; `trust.json` and its mtime untouched, no leftover lock |

So `get()` never writes the decision file, yet it needs a writable agent dir (it takes a directory lock) and may throw. Writes are not atomic (`writeFileSync` truncates in place, `:104`); only calls through the class take the lock, so nobody should parse `trust.json` directly.

## Fail-open default of the SDK (`results.json`, `gate` and `late`)
- `SettingsManager.create(cwd, agentDir)` defaults to `projectTrusted: true` (`SDK/dist/core/settings-manager.js:238`). With no `resolveProjectTrust`, a project `.pi/extensions/*.js` is loaded and its factory runs (`no-gate-sdk-default`: `isProjectTrusted: true`, 1 factory run).
- With the resolver: no decision → not loaded (0 runs); `true` → loaded; `false` → not loaded. `SettingsManager.create(…, { projectTrusted: false })` without a resolver → not loaded.
- In-session reload does not re-ask: `AgentSession.reload()` calls `resourceLoader.reload()` with no options (`SDK/dist/core/agent-session.js:2948`), so the sticky `projectTrusted` decides. A folder that had no trust-requiring resources at open (resolver not installed, as in pi-web and in the Task 20 draft) loaded a `.pi/extensions` file that appeared afterwards (`late.resolver-only-when-resources-exist`: loaded, 1 factory run). With `projectTrusted: false` plus a resolver installed always: not loaded, 0 runs (`late.projectTrusted-false-and-resolver-always`). pi-web has the same gap at `PI_WEB/lib/rpc-manager.ts:2553`; it compensates for MCP by re-reading trust on every use (`mayReadProjectConfigNow`).
- The decision takes effect at the next open only; the CLI says "Restart pi for this to take effect" after `/trust` (`interactive-mode.js:4432`).

## Consequences for the plan
- No pap `project_trust` table, no `projectTrusted` boolean in `init` (the "Spike fallback / S7" lines in the plan are void). pap reads and writes Pi's file through `ProjectTrustStore`; decisions made in the `pi` CLI or pi-web apply as soon as pap uses the same `agentDir`. Trust is per agent dir: a pap that runs workers with its own `PI_CODING_AGENT_DIR` starts with no decisions, and one that shares `~/.pi/agent` shares them with the CLI and pi-web. Which one is a deployment choice for the controller (R27: T22's worker env sets `PI_CODING_AGENT_DIR`).
- Task 20 `open-session.ts` uses `ProjectTrustStore` read-only and must fail closed. Changes to the draft (plan l.7335-7347):
  - build `SettingsManager.create(cwd, agentDir, { projectTrusted: false })` and install `resolveProjectTrust` always, not only when `hasTrustRequiringProjectResources(cwd)` is true at open (otherwise a folder that gains `.pi/extensions` later, by `git pull` or the model's write tool, loads it at the next reload);
  - the resolver is `() => { try { return store.get(cwd) === true } catch { /* log once */ return false } }`: a corrupt or locked file means untrusted, never a rejected `createAgentSessionServices`;
  - `get()` needs a writable agent dir and can busy-wait ~200 ms: resolve trust in the worker (as drafted), with the agent dir writable for that process, and never on the daemon's request path;
  - keep `HOME` correct in the worker env (it feeds `hasTrustRequiringProjectResources`);
  - pap does not read `defaultProjectTrust` or the `project_trust` extension event: the CLI honours `defaultProjectTrust: "always"` (`cli-results.json`), pap stays untrusted unless `trust.json` says `true`. Document that difference.
- Trusting a project from the pap UI comes in roadmap M7: the daemon calls `store.set(cwd, true)` (never the sandboxed worker), applies pi-web's breadth refusals (home, filesystem root, a folder holding known folders or undecided projects: `PI_WEB/lib/project-trust.ts:316`) because a parent decision is inherited by every child, and restarts the cwd's workers because the decision applies at next open.

Decision: GO — `trust.json` is Pi's own file (shared by the `pi` CLI, the SDK and pi-web); pap reads and writes it in place through `ProjectTrustStore` and keeps no `project_trust` table.
