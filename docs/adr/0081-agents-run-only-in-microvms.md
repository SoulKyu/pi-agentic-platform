# ADR 0081: agents run only in microVMs

Status: accepted, sub-project 3 · Date: 2026-10-22 · Spec: `docs/specs/2026-10-22-agents-vm-only-design.md` · Supersedes ADR 0048 (the host sandbox) for agents and ends ADR 0078's opt-in (`PAP_AGENTS_RUNTIME`) · Extends ADR 0079 to the vault's values · Notes on ADR 0049. Decision 122. Topic note: `docs/agents/agents-vm.md`.

## Context

Sub-projects 1 and 2 (ADRs 0078 and 0079) made the microVM an opt-in runtime beside the host sandbox of ADR 0048 (bubblewrap on the host, a unix-socket egress proxy, a root-owned `python3`). Two runtimes meant two sets of rules, two proxies and tests that skipped without bwrap. The VM path also trusted what the VM said about itself in places: a worker reported its own taint, and a compromised VM could simply not report. On 2026-10-22 a role over the old 8000-character cap made every VM worker exit with an empty output and "The session process failed", because the code inside the VMs was older than the daemon and nothing said so. The owner wants this sub-project simple and fast: delete more than it adds.

## Decision

- **The VM is the default and the only agent runtime.** `PAP_AGENTS_RUNTIME` is no longer read; when it is set the daemon logs one warning ("PAP_AGENTS_RUNTIME is gone: agents always run in microVMs") and boots. The host sandbox code for agents is deleted: the bwrap argument list and spec, the probe and `PAP_BWRAP`, the host egress listener and its `python3` forwarder, the host-mode launch gate and precheck paths, and the tests that only proved them.
- **No KVM, no agents** (owner: "sans kvm, pas d'agent"). A host without `/dev/kvm`, pap-vmd, `pap0` or the gateway and proxy ports composes the agents module on loopback with an unusable status and stops no VM. Creating or starting an agent is refused with the typed error `sandbox_unavailable`; the Agents screen shows an EmptyState. Everything else (sessions, lanes, terminals, triggers that target no agent) works as before. There is no host fallback and no migration: agents made in host mode are deleted and created again (`pap doctor` lists them).
- **Prechecks are not for agents.** The owner does not use them, so they are not brought into the VM. A precheck stored on a trigger that targets an agent is refused at fire time with `precheck_agent`, never ignored (ignoring it would wake the agent at every tick).
- **The daemon decides from what it sees itself.** The VM proxy marks every session of a launch tainted when a tunnel or request reaches a host that does not keep content clean (a trusted source over `CONNECT` 443 does; a refused request marks nothing). The mark belongs to the launch, covers the live sessions and the ones that start later in it, is recorded in the policy module with no epoch (a worker's clear cannot race it) and is sticky. The worker's own reports can add taint (a networked shell's first result taints its session) and never clear it. Platform ops (`whenTainted`), delegation isolation and trusted autonomy read that record.
- **The vault comes into the VM** (owner, 2026-10-22). The vault's values the agent may use, its one-use values and `secret.request` work from a VM session: values travel in the worker's init record and live updates, reach the VM shell's environment, and are redacted by the worker from the first byte. This extends ADR 0079 (an agent's own credentials may live in its VM) to the vault; provider keys and the Claude token stay with the relay and never enter the VM.
- **Code skew is named.** The daemon takes the digest of the agent bundle built with it once per process and compares it with the installed one (`/opt/pap-vm/agent-bundle`, the Kata base image's tag) before a VM start. When they differ no VM starts and the thread says: "The code inside this agent's VM is older than pap. Run `sudo pap vm setup`, then open the thread again. Nothing was lost." A change that leaves the bundle alone asks for no root step. A silent `worker_exited` keeps the worker's last words (the daemon waits a short grace on the kernel `Clock` for the guest's `exited` frame).
- **Prompt chips** read the owner's imported `prompts/*.md` files (the host copy); files the agent writes in its VM are not listed, because the daemon never reads a VM disk.
- **Doctor**: the `vm.*` checks run whatever the environment says, plus `vm.bundle`, `vm.hostMade` and `vm.runtimeVar`; `bwrap` and the `python3` agent checks are gone.

## Consequences

- **VM only.** One runtime, one proxy, one set of rules. bubblewrap, `PAP_BWRAP` and a root-owned `python3` are no longer host requirements for agents (bwrap still runs inside the VM image, and the pi-host VM shell test needs a working `/usr/bin/bwrap` in CI).
- **A host without KVM has no agents.** That includes the container image and a CI runner: the int tests run on the process backend (`PAP_TEST_AGENT_RUNTIME=process`) and the Kata suite runs locally only. A test daemon never dials the real pap-vmd (`PAP_TEST_VMD_SOCKET`, required for a daemon with the scripted provider).
- **Prechecks do not exist for agents.** A stored one blocks the trigger until the owner clears the field.
- **ADR 0049's limits move into the VM.** A command the agent runs can print a vault value, the redactor misses values under 8 characters and encoded ones, and a process in the VM can read the shell's environment. A vault value an agent holds is readable by whatever runs in its VM, like the files of ADR 0079.
- **What the approval engine is inside a VM.** The approval mode, blocked commands and tool rules run in the worker, so in a compromised VM they are the agent's own choice. At the exits the daemon enforces the host list (proxy), the models and budget (relay) and the platform ops' callers and taint rule (gateway).
- **Known limit: no confinement of MCP stdio servers and extension subprocesses inside the VM** (owner's call). Once the exits trust nothing the VM says, what those children could read inside the VM (the gateway token file, the Pi profile, which holds no provider key) gives them nothing the agent does not already have, and pap does not control how a third-party extension starts its children; confining them would mean nesting bwrap around the whole worker. The VM is the boundary.
- Other limits kept: the existence oracle by a race on `grep`, `find` and `ls` roots (it reveals that a path exists, never its content); a VM already running old code keeps running after `sudo pap vm setup` until it restarts; a new launch starts clean, which is no weaker than the host mode it replaces.
- Cost if wrong: a machine whose owner needs agents but has no KVM loses them outright. The alternative (keep the host runtime) kept two sets of rules and the `python3` and AppArmor prerequisites the owner wanted gone.
