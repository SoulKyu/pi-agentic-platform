# ADR 0084: GitHub through a pap GitHub App

Status: accepted · Date: 2026-10-24 · Spec: `docs/specs/2026-10-24-boxes-b2-design.md` (lot B2), `docs/specs/2026-10-23-boxes-design.md` (programme). Decisions: 126, 127 (`docs/research/decisions-log.md`). Rulings: R1 to R7 of the lot ledger. Replaces ADR 0036 for box projects. Builds on 0081 and 0083.

## Context

ADR 0036 reaches forges through their own CLIs on the host: `gh` runs as the daemon's user with the owner's login, and git pushes with the owner's SSH agent. That fits host projects. A box project (ADR 0083) has no host checkout, and the host must not run `gh` or git on a box's content. pap held no forge credential at all, and a box's shell gets a closed environment and no ssh agent.

## Decision

- **A GitHub App that pap creates.** Settings › GitHub posts a manifest to GitHub from a page the daemon serves itself (its own CSP allows `form-action` to github.com; the SPA's CSP is unchanged). The App is public (`APP_PUBLIC` in `modules/github/manifest.ts`, owner 2026-10-24), webhooks are off, and its repository permissions are `contents`, `pull_requests` and `administration` write, plus `issues`, `checks`, `actions` and `metadata` read. Public lets each member install the same App on their own GitHub account (M14), each with their own consent; GitHub lists the App's name and client id, never its key.
- **Callbacks are matched by `state`, not by the cookie.** The session cookie is `SameSite=Strict` and does not come back on a redirect from github.com. The creation redirect and the install and authorization callback carry a random, single-use `state` (32 hex, ten minutes, bound to the user who started the flow, with a purpose). A reused, expired, foreign or missing `state` is refused and changes nothing. The callback origin is the one the owner's browser used, checked against the allowed origins.
- **What pap stores.** The App's id, slug, client id and secret and private key in `$PAP_HOME/secrets/github-app.json` (0600, no links followed, at most 16 KiB). The owner's user token and refresh token in the vault's user scope under `GITHUB_USER_TOKEN`, `GITHUB_REFRESH_TOKEN` and `GITHUB_TOKEN_META`. The values reach no log, audit row or response; the owner-secrets collector learns them.
- **Three kinds of token, each as narrow as its use.**
  - The owner's **user token** (8 hours, refreshed single-flight, the new pair written to the vault before use) does what only a user can: list repositories, fork, add and remove SSH signing keys.
  - A **box token** is an installation token for the project's repository only, `{contents: write, pull_requests: write}`, never `administration`. The host mints one at each box start and renews it every 45 minutes. The guest keeps it in `/run/pap-github/token` (tmpfs, 0600), read by a git credential helper and a `gh` wrapper; the project shell sees that file read-only.
  - **List tokens** are read-only installation tokens for the GitHub tab, cached 60 s.
- **The box token is revoked on unlink and delete** (`DELETE /installation/token`; a failure is logged with a fixed word and ignored). Delivery steps use `BoxOps.poll`, so a renewal never keeps a box awake.
- **The token is readable inside the box.** Every process of the box, the model included, can read it. Its reach is one repository for one hour and the proxy keeps the box to the project's hosts. A session therefore can push, and a session driven by an API token can too, though the push and PR methods themselves refuse a token.
- **Identity lives in the box's home; the key does not (R5, R8).** `home/.gitconfig` holds `user.name` (the login), the noreply email `<id>+<login>@users.noreply.github.com`, SSH signing (`gpg.format ssh`, `user.signingkey` = the public key `home/.ssh/pap_signing.pub`, `gpg.ssh.program` = `pap-ssh-sign`, `commit.gpgsign true`) and the credential helper. The signing private key is in `/boxes/<id>/.pap/signing/` (0600, guest root), outside every session bind. Guest root starts an `ssh-agent` (socket `/run/pap-github/agent.sock`, in the folder a shell sees read-only: a connect works on a read-only bind) and loads the key at delivery and at box boot; `pap-ssh-sign` points `ssh-keygen` at that socket. The key never leaves the box. Known limit: while the box runs and the project is linked, a session can ask the agent to sign, so it can make commits GitHub shows as Verified for the owner on this box; it cannot copy the key. Unlinking or deleting stops the agent and removes the key folder. Daemon-initiated commits run with no global config and pass the same settings on their command line, read from `.pap/github.gitconfig`, which no session writes.
  The guest writes `home/.gitconfig` and `home/.ssh/pap_signing.pub` through a temporary file and a rename, never through a link a session planted. The host adds the public key to the owner's account as `pap <project name> <first 8 of the id>` and removes it when the project is deleted or unlinked.
- **The daemon opens the pull request (R9).** For the project's own repository `projects.prCreate` pushes the current branch (`git.push`), then calls `POST /repos/{repo}/pulls` with a one-use installation token for that repository with `{pull_requests: write}` only (revoked right after), `head` = the pushed branch, `base` = the given or the repository's default branch. No `gh` runs as guest root on a repository a session can write; the guest op `gh.prCreate` does not exist. The `gh` wrapper in the box serves the sessions' own `gh`. A 422 (already open, bad head) is `conflict`; GitHub's words are never shown.
- **Callback origins (I4).** The sign-in carries the caller's origin (a checked allowed origin) in its state and uses it for the `redirect_uri` of both the authorize URL and the code exchange. An origin GitHub accepted is remembered, so the mismatch notice clears once the owner has added that callback URL next to the old one.
- **A fork's pull request opens GitHub's compare page.** The box token reaches the fork only, and the App is not installed on the upstream, so pap never calls the upstream's API.
- **The terminal moves into the box.** A terminal at or under a box project's root runs in the guest (node-pty, a `terminal` hello role, protocol 3). Host projects keep the host terminal and `gh` until lot B4.

## Consequences

- `AGENT_VM_PROTOCOL` is 3: run `sudo pap vm setup` after the update (new hello role, new ops, a rebuilt base image with node-pty, `openssh-client` and `gh`).
- `settings:admin` is never granted to an API token (R3): it now guards the App's creation and deletion.
- `PAP_TEST_GITHUB_ORIGIN` points a test daemon at a fake GitHub on loopback; it is for tests only and needs `PAP_TEST_PROVIDER_SCRIPT`. No test contacts a public host.
- The log of a failed check follows one redirect, only to `*.actions.githubusercontent.com` or `*.blob.core.windows.net`, without an Authorization header; the page shows the last 64 KiB and the download is capped at 32 MiB.
- Text from GitHub (titles, bodies, logs, notes) is shown as text, fenced as external content, and taints any session it is sent to.
- A GitHub App has one owner today: a second pap user cannot authorize it (M14).
- Cost if wrong: a public App would let members install it, at the price of a public App listing; the switch is one constant.
