# ADR 0053: subagents as durable child sessions

Status: accepted (M11b, Task 35)
Date: 2026-10-17
Spec: A D11; C §2.6, §5.3. Rulings: M11R134 to M11R141, M11R153 to M11R156, M11R172, M11R173, W5-R62, W5-R63, W5-R65, W5-R66. Owner answers m12, m13. Builds on ADR 0047 (session types and platform calls).

## Context

A model that can hand a task to another session gets a cleaner context and parallel work. Pi's own example extension does that with a helper process; pap needs the child to be a thing the owner can see, stop, approve for and pay for, and the child must never hold more than the session that made it. Third parties also ship extensions that offer a tool with the same purpose.

## Decision

- **pap's own `subagent` tool** (op `subagent.run`, registered by the inline `pap-platform` extension; callers `plain`, `lane`, `agent-thread`; arguments `task` up to 8 000 characters and an optional `profile` name). A third-party extension's subagent tool stays an unknown external tool: it asks, or is blocked, like any other (ADR 0020, ADR 0047). A tool of the same name from another source does not become pap's: pap's tools load first, and a collision is reported once per session as `extension_error` (W5-R12).
- **A child is an ordinary session** (`sessions.parent_session_id`; for an agent thread's child also `agent_id` and role `child`), in the parent's folder. It has its own worker, transcript, runs and cost, so it survives the call, can be opened, and can be continued by the owner. Its answer goes back to the parent's tool result and is never stored in `subagent_runs` (migration `202610151155_subagents.sql`: one row per call with parent, child, profile, title, state `starting | running | done | failed | cancelled | interrupted`, reason, times).
- **On by default, 2 at once, depth 1** (owner m12). `agents.subagents {enabled: true, maxConcurrent: 2}` (1 to 4) is read at every call and every worker start. Off: the dispatcher answers `unavailable` and the tool is gone from the next worker start. `child`, `task` and `agent-task` have no platform op, and a parent that is itself a child, a task or an agent's isolated session is refused (`bad_request`), so there is no third level.
- **Refusals**, in order: switch off, the call already cancelled, `maxConcurrent` running children for this parent (`limit_reached`), 30 children an hour per owner (`rate_limited`; a start that failed also counts), a parent that is archived or not the owner's (`not_found`), capacity (`unavailable`: one worker stays free for the owner and the memory floor holds), the agent over its own daily budget (`budget`). The call holds for the child's run, at most the op's 240 minutes, and returns `{childId, answer, clipped, tainted}`: the child's last assistant text up to 50 KiB, `clipped` past it.
- **Profiles are Pi's agent files, read-only** (owner m13). `<Pi agent dir>/agents/*.md` and, only while Pi trusts the parent's project, `<project>/.pi/agents/*.md` (never for an agent's session: its home is agent-written and not a project, W5-R27, W5-R29, whatever Pi's trust store says of an ancestor); the helper reads them with Pi loaded offline (a read never installs), at most 64 files per folder and 32 KiB each, a file marked `longTerm` (pi-web's) skipped, a project file replacing a user file of the same name. The trust check is made twice (the daemon passes the folder only when trusted; the helper checks Pi's trust store again). `subagents.profiles {sessionId}` lists names, descriptions and source; the call reads one file whole (tools, model, prompt of at most 32 KiB; two files with one name in a folder are `conflict`). Without a `profile` the child takes the parent's own preset and no extra prompt. The owner edits the files in Pi's folder; pap never writes them.
- **A child never has more than its parent.**
  - Tools: the profile's list narrowed to the parent worker's live active tools, fail closed (no loadout known keeps nothing; a cut loadout keeps only its known prefix); an empty result is `bad_request`.
  - Mode: the parent's, with `full-access` turned into `auto-accept-edits` (nobody watches a child directly).
  - Taint: the parent's at the start and sticky afterwards, as any session's (ADR 0020). A clean parent gives a clean child; a child that reads external content comes back with `tainted: true`, and its answer is fenced (a success that does not say `tainted: false` is fenced too). A tainted parent's task text reaches the child fenced as `subagent-task`.
  - A child of an agent thread keeps its agent's rules and its budget: profile `agent-thread`, the agent's hosts, blocked commands, sandbox and home (the launch gate runs for it). It has no platform op, no vault (never in its environment, never pushed by `sendToAgent`), no host grants, no autonomy, memory closed (ADR 0052). It is held to the agent's mode (capped as above) and to the agent's tool preset at every start: a reopen narrows its stored preset, never widens it. Its file tools are held to the same allow-list as the thread's: its home, the agent's own runs folder (read as external content), the files attached to the thread, the system folders the sandbox exposes, and Pi's skills folder read-only (W5-R63, W5-R65, W5-R66).
  - A child of a plain or lane session is an interactive session with the owner's rules, attended: its questions go to the parent's screen.
- **The prompt file** (W5-R62). A profile's prompt is appended to the child's system prompt at every start, and a child must survive a daemon restart, so the prompt lives in `$PAP_HOME/subagents/<child id>.prompt` (0600 in a 0700 folder), written before the session row and read at each launch. It is removed when the launch fails or the child session is deleted, kept when it is archived (an archive is reversible), and the boot removes files that no session row has. A missing file at a reopen logs `child_prompt_missing` and the child still starts with its limits, which come from the database; only the profile's words are lost.
- **Stop propagation** (`subagents/stop.ts`). Each running child is held by a guard; a stop happens once per child, aborts its worker (its open dialogs close with the run), clears the origin its first run waited for, ends the row `cancelled` with a reason, and the parent's held call answers `cancelled`. Five triggers:
  1. the parent tool's signal aborts: the owner's Stop (`stopped`) or the op's deadline (`timeout`);
  2. the parent's run ends for any reason while the child runs (`parent_run_ended`);
  3. the parent is archived (`parent_archived`) or deleted (`parent_deleted`);
  4. the agent is quarantined (`quarantined`; step `subagents` of `agents.quarantine`, after `tasks`);
  5. the daemon stops: the boot marks every `starting` or `running` row `interrupted`, so none counts against its parent for ever.

  A child whose run ends `limited` (usage limit) is not auto-resumed: `runs/resume.ts` plans none for a `child` session and skips one planned earlier (reason `child`), so no child outlives its parent's call. The owner's own "Resume now" on the child's tab stays.

  The owner can also stop one child (`subagents.cancel {runId}`, `sessions:operate`, owner only, reason `stopped`). The creation window is covered where it can be: the parent must be open at admission and again right after the guard exists (a parent archived while the child was made stops it), a signal already aborted stops the child at once, and the prompt is sent only while the guard has not stopped. A worker whose child ended is released at once (five tries, two seconds apart); the child stays a session.
- **Approvals in the parent.** The parent's stream carries `subagents` events and its snapshot `children` (the newest eight, each with its open dialogs, 256 KiB in all, approvals first, `hiddenDialogs` counting the rest; a child line that does not fit the snapshot is left out and counted in `hiddenChildren`). The owner answers on the parent's screen with `sessions.respondDialog` on the child's own session id, so permissions, a token's limits (deny or once only) and receipts are the child's. A child that waits makes its parent `needsInput` and an agent thread's rail `needs input`.
- **Roll-up.** A child's runs have `origin: "subagent"` and `runs.parent_session_id`; when the parent's run belongs to a task, they carry its task id too. They carry the agent's id for an agent's child. So: an agent's daily budget counts the children of its thread, and M10's budgets count a child of a task's run through the task id; `sessionCost(parent)` and the billing of the parent add its children's runs, open ones included (M9's compare column); and the task's `maxRunUsd` compares everything the task's runs, children included, spent since the task started, so a child alone reaching the cap fails the parent task (`run_budget`). The agent's own budget is also checked when a child is asked for (`budget`). The cost on a chip refreshes at the child's status changes and ending, not at every reply.
- **Screens.** The subagent bar above the composer (title, profile, state, cost, Open, Stop; folds into "N subagents" past three), each child's dialogs labelled "from subagent <title>", children filed under their parent in the ⌘B tree (plain and lane sessions only: an agent thread's children are not in the shell list), and Settings › Agents › Subagents (switch, 1 to 4, the profiles read-only). Titles and descriptions are the model's or a file's words: shown as text, hidden characters removed, clipped.

## Consequences

- A child is a second Pi worker for as long as it runs: capacity and the memory floor apply, and the last worker stays free for the owner.
- A fan-out is paid for in the places the owner already watches (budgets, the task cap, the compare column), not in a new counter.
- A profile cannot widen anything: it can only narrow what the parent has.

## Residuals

- No parent delete path exists yet for ordinary sessions: `parent_deleted` is reached only through `deleteTaskSession`, and a deleted child's prompt file goes with it.
- A stop that arrives while a child is still being made, before its guard exists, is not seen except through the checks above (quarantine is also covered by the launch gate's `agent_paused`).
- `ChildView.costUsd` lags between status changes.
- A project's agent files of a folder other than the newest session's are not listed in Settings, though a call from a session in that folder reads them.
- The profile prompt of a child made before a restart comes from its file; if the file is gone the child runs without the profile's words.
