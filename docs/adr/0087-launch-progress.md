# ADR 0087: launch progress

Status: accepted · Date: 2026-10-25 · Spec: `docs/specs/2026-10-25-launch-progress-design.md`, plan `docs/plans/2026-10-25-launch-progress.md`. Decision: 134 (`docs/research/decisions-log.md`). Rulings: R6 to R12 of the launch-progress ledger. Amends DESIGN.md §7.2 (motion) and builds on 0083 and 0086.

## Context

Starting a box (checks, project image, disk, VM, guest, session) can take from a second to half an hour, and the app showed one spinner and no cause. A task for a box that was building its image burned its 90 s deadline and five retries. A fifth Pi configuration read failed `capacity` while four were running. This ADR records how pap now says what it waits for.

## Decision

- **D1. The `launches` stream.** A kernel port (`kernel/launches.ts`) with an in-memory registry in `agent-vm/launches.ts`: one live launch per box, joined by a second opener, ended by the last handle. The stream carries `snapshot` (the live launches of the caller's boxes, so a reconnect restores them), `launch` (at most one per second per launch, plus every step state change at once), `end` (`{ id, done: true, ok, code? }`) and `helpers` (`{ active, max, waiting }`, at most one per second, only on change, no ids). A member receives only their own boxes' launches. A launch leaves no panel behind when it ends; a failed one leaves the caller's `InlineError`.
- **D2. Steps.** `checks`, `image`, `disk`, `vm`, `guest`, and `worker` only when a session or task waits. A step only moves forward (R7): a joined opener cannot move a finished step back or write a second sample. The box reads `starting` from the first step of any launch, a session's included. A watchdog ends a launch that outlives the sum of the step limits with `timeout` (R6), and `close()` ends live launches at shutdown.
- **D3. "Usual".** `launch_steps` (migration `agent-vm/202610251200_launch_steps.sql`) keeps the last 20 durations per box and step. The median is shown with at least 3 samples; a skipped image is not a sample. A step is slower than usual past twice the median, said in neutral text.
- **D4. pap-vmd: `image.progress`.** A new pap-vmd op answers `{ building, lines, last }` for a tag (and `tail` when asked), from the last 200 lines (512 characters each) pap-vmd keeps in memory while the build runs (`--progress=plain`). The daemon polls it every 2 s during an image step, with a 5 s deadline; any `VmdError` means no sign of life, never a failure. Every line passes the redactor before it is sent. This is new pap-vmd protocol: **run `sudo pap vm setup` after the update.** An old pap-vmd answers `bad_request`, which shows no line.
- **D5. The stuck ask.** The image step is observed for every build it runs (base, profile, agent), so its lines arrive. For an image whose last line (or whose start, when none came) is older than 120 s the panel says "No news from {step} for {ago}. pap gives up at {limit}."; at 75 % of a step's limit it says "{step} has been running for {elapsed}. pap gives up at {limit}." (R14). No ask shows while the launch waits in the build queue. Each offers what can help. It is pink because the person must answer, and it is a polite `role="status"` block, not an alert: it waits for them and is not the result of their last action. pap never relaunches by itself: the person decides, and a step that reaches its limit fails with its own error.
- **D6. DESIGN.md §7.2 exception.** The live counter on the active step repaints once a second, with tabular numerals. It is the second exception to "nothing repaints continuously", next to the indeterminate bar. Under reduced motion the ring is static, but the number keeps counting: it is information, not motion.
- **D7. Waiting is a reason, not a spinner.** A session or a task that waits says why (`session_slots`, `box_memory`, `image_build`, `pi_reads`, `budget`, `paused`, `relay`, `thread_busy`) with the numbers, the action that frees it and the next try. A queued task on a box that builds its image defers 10 s with `image_build`, with no session, no attempt and no retry. Waiting is neutral, never red or pink. The reason follows the cause (R16): a task held by the boxes' memory cap (`capacity` from `runtime-start.ts`, which carries the MB used and the cap) waits for `box_memory`; `session_slots` is for worker slots only (with their counts when the refusal carries them); a busy agent thread is `thread_busy`. A start that fails on the memory cap for an interactive launch still ends `capacity`: pap waits on `box_memory` only where it retries, the trigger task. `pi_reads` is said by the Pi helper queue, not by a launch's package pick (a pick may wait up to 30 s with no step running).
- **D8. The Pi read queue.** Pi helper reads queue FIFO, 16 waiting at most; the 17th, or a call that waited 30 s, is `pi_busy` (not `capacity`). The call's own deadline starts when it leaves the queue. Calls with `onPrompt` (sign-in flows) never queue and are refused `pi_busy` when the pool is full. `helpers` events feed the LoadingLine cause ("Pi is reading N things at once").
- **R8 (Show the log).** The ask offers Show the log only during the image step, the only step with a source of lines. There is no guest boot log yet: `launches.log` answers the build tail while an image builds and an empty list otherwise, and the panel says "Nothing to show yet."
- **R10 and R11 (Stop).** `launches.stop {id}` exists (`sessions:operate` for a project box, `agents:operate` for an agent box, owner-checked, `not_found` otherwise). It ends the launch with code `stopped`, then stops the box's VM through the runtime directly (not through the box's start queue, which waits for the start). The daemon decides (R13): the launch record carries `stoppable`, true only when the running step is `vm` or `guest`, or `worker` with this launch's `vm` step done (not skipped), and the box has no other live VM entry (an agent's isolated task VM, another VM). The web shows Stop if and only if `stoppable`; `launches.stop` answers `not_found` otherwise, so Stop never kills sessions that ran on the box before nor an agent's other VM. `checks` and `disk` give up by themselves; `image` keeps Show the log alone (R8). `stopped` is no error: every awaiting call rejects `stopped` (the worker step included: the exit a Stop causes is not the start's outcome), a pending guest wait is aborted, the web shows nothing, and a task whose start was stopped is cancelled (reason `stopped`), not retried. Cost if wrong: a stuck image build cannot be stopped from the panel, and neither can a stuck worker on a box that was already running (Restart can).
- **R12 (activity indicator).** The indicator in the shell counts and lists what has a global feed: live launches (a Rebuild's build launch included, R15) and lane setups (`creating`). It leaves out waiting tasks, whose tasks stream is per screen, and clones, which only have per-project views. Their cards show `waiting` where they live. Cost if wrong: a task waiting for a slot with no launch is not in "N in progress".
- **R15 (Rebuild).** Rebuild opens a build launch (`for: "rebuild"`, the `image` step only, title "Building the image"). A build launch never changes the box phase: the box does not read `starting` for it. A task on the box waits for it through the existing `image_build` precheck. The build is observed like any image step, and "Show the log" reads it by the project's id.
- **Buttons.** `Button` takes a `stage`: the spinner and the running step's words from the first moment, announced by a polite status region. LoadingLine shows nothing under 100 ms, then a spinner and label, the elapsed time from 3 s and a cause from 10 s.

## Refusals kept

No automatic relaunch and no automatic retry of a stopped or stuck start. No guest boot log (not built). No per-session counts in `helpers` events, so a member learns nothing about the owner's use.

## Consequences

- Each launch emits at most about one event a second per launch; the daemon holds no launch after it ends.
- The step panel, the log dialog and the activity list are lazy chunks; the initial bundle stays under the 300 KB ceiling.
- pap-vmd lags `pap update` until `sudo pap vm setup` (existing rule); with an old pap-vmd an image step shows no build line.
- A fifth concurrent Pi read now waits instead of failing, up to 30 s.
