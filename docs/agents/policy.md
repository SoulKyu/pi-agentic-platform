# Policy pipeline

Code: worker side `packages/pi-host/src/policy/` (`extension.ts` thin factory, `pipeline.ts`, stages, `trail.ts`, `audit-sink.ts`), `redact-stdio.ts`, `redacting-ipc.ts`; daemon side `modules/policy/` (rules, settings, `session_policy`), `modules/sessions/policy-link.ts`, `modules/audit/`, `cli/`. Contracts: `packages/contracts/src/{policy,policy-methods,pi-host,audit}.ts`. ADRs 0002, 0020, 0021, 0022, 0024, 0028, 0047, 0048. Rulings: `docs/research/m5-rulings.md`, `docs/research/m7-rulings.md`, `docs/research/m11-rulings.md`. Agent profiles: the section below and `agents.md`. Auth, tokens and devices: `auth.md`.

## The pipeline

- `pap-policy` is the last `tool_call` handler (ADR 0002). One evaluation runs the stages in order; the first `block` ends it. Any error, an unknown outcome or an unreadable input blocks (fail closed). Rules arrive in `init` and `policy_update` as `PolicyRules` v2 (`.strict()`: a key the worker does not know makes the rules invalid, and invalid rules block every call and stop the worker so the next prompt starts with fresh ones).
- Stages: 00 exposure (the tool set, recorded in the `session` row), 01 command denylist, 02 egress, 03 approval, 04 run guard, 05 containment (recorded only: `sandbox: bwrap (network off|on)` for an agent session with a sandbox, else `no sandbox profile for interactive sessions`; the sandbox itself is bwrap, ADR 0048), 06 redaction, 07 fencing and taint. Stage 03 can ask; 01 and 02 block, they never ask (except lever B below).
- Decision-time re-checks (MQ6): the rules version is compared before a call is let through (at most 3 evaluations, then "policy changed during evaluation"); a call a person answered is not asked again, but stages 01, 02 and the read-only rule run again on the current rules and taint, and a block wins. A mode change with open cards applies to the answer.
- A nested call (`parentToolCallId`, codemode) is judged and audited like any call; the guard counts top-level calls only.

## The matrix (stage 03, `decide.ts`)

| Mode | read | edit | exec / network / external-write | unknown |
| --- | --- | --- | --- | --- |
| read-only | allow | block | block | block |
| supervised | allow | ask | ask | ask |
| auto-accept-edits (default) | allow | allow | ask | ask |
| full-access | allow | allow | allow | allow |

- Overrides, in order: read-only blocks everything but a plain read; a write that needs review (outside the folder, a protected path, a folder too broad) and a protected read (pap's `state.db`, `secrets/`, `backups/`, `pap.lock`, Pi's `auth.json`, other sessions' transcripts) ask in every mode but read-only; a tainted session asks Deny / Allow once for every exfiltration-capable or external call, past any grant. Grants (once, session, always) only skip questions the table itself asks; `unknown` offers no always.
- Tool presets (M7 Task 15, ADR 0028): stage 02 blocks a coding tool the session's preset leaves out, by name (`PolicyRules.presetTools`, from the worker's own preset), whatever reached the call (codemode, `tool_search`); under the `read-only` preset (`readOnlyPreset`) the MCP read-only rule applies in every approval mode, and any call whose category is not `read` (an `unknown` extension tool, an extension under a built-in name) is asked in every mode, `full-access` included, with no grant to skip it (MC36, `stage-approval.ts`).
- Read-only commands (M7R11-R16, `stage-approval.ts`): in supervised and auto-accept-edits, Pi's own `bash` whose every simple command `coverCommand` covers is judged as a `read` (audit category stays `exec`, stage 03 `allow` "read-only command"), also in a tainted session. Stages 01, 02 and 04 run unchanged around it; read-only mode still blocks the shell. Off when `PolicyRules.readOnlyCommands` is false (owner's switch; `RESTRICTIVE_SETTINGS` turns it off). The shell facts come from `shell-facts.ts` at each evaluation: a Pi shell prefix or shell path, `BASH_ENV`/`ENV`, `CDPATH`, a relative or session-folder `PATH` entry, `GIT_*` repository variables and `RIPGREP_CONFIG_PATH` (rg only) make the affected commands ask. A `PolicyConfig` without `shell` covers nothing (`UNKNOWN_SHELL`). MC17: in a tainted session git segments are never covered (other covered commands still run); in any session a git segment is covered only when the guard finds an existing valid repository with a clean config at evaluation time ("no repository found" asks). Parallel writes (MC18): Pi judges every call of a message before any of them runs, so the guard reads the files as they were before the message. A folder that gains a bare layout (HEAD, objects, refs, config written as plain files) in the same message as a `git` call there would be read by git with the planted config. Closed: the worker pins `safe.bareRepository=explicit` for every git the agent runs (`git-env.ts`, appended to `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` at worker boot; an unreadable `GIT_CONFIG_COUNT` stops the worker), so git never discovers a bare repository unless given `--git-dir`; a write into a `.git` folder is a protected path and asks. Remaining, untainted session: the guard still judges a missing or empty target by the repository around it (git ignores the bare layout, so that is the repository git uses), and a config of a normal repository changed by something that is not a pap write after the check is not seen. The approval card does not say why coverage failed (`ApprovalAsk` has no reason slot for it).
- Full access covers pap's built-in checks only. A shell command in full access is limited by the blocked-command list alone: it can read or delete `$PAP_HOME` and `auth.json`. Settings and the full-access confirmation say so (owner Q1).
- Tool classification (`tool-kind.ts`): by the tool's registered source (`ToolInfo.sourceInfo.path`), never by name. Built-ins by `builtin:<name>`; MCP (`builtin:mcp`): `readOnlyHint === true` is a `read`, else `external-write`; every MCP tool is external and URL-bearing whatever its `openWorldHint` (stricter than MQ2: a local stdio server is fenced and taints too); `read_mcp_resource`, `list_mcp_resources` and `list_mcp_resource_templates` are external, URL-bearing reads (with a host list set, a custom scheme such as `fixture://` blocks); `codemode` (`builtin:codemode`) and `tool_search` (`builtin:tool-search`) are non-external reads, their nested calls judged on their own; extension tools are unknown and external unless `openWorldHint: false`. The production worker loads them since M7 (`packages/pi-host/src/builtins.ts`, listed by `open-session.ts` before the test-only extras): each is registered as `{ name: "mcp" | "codemode" | "tool-search", factory, builtin: true, replaceable: true }` with exactly those names (a bare factory gets `<inline:N>`, so its tools would classify as unknown and external), and codemode is created with `models: false`, so scripts have no `models.classify` or `generateImages` that would send script data to providers outside judged calls. Nothing is force-activated: Pi's own exposure model decides which of these tools are active. MCP `openUrl` never opens a browser on the server. In rpc mode Pi's own `/mcp` notice already shows the sign-in URL as text, whatever its scheme, before calling `openUrl`; pap adds only a fixed instruction (`signInNotifier` in `builtins.ts`): open the link above in your browser and paste the address you are sent to into the prompt, or, for a scheme other than http(s), that it is not a web address and must not be opened. pap's notice never repeats the URL. A result whose classification throws counts as external and its parent codemode call is fenced too (M7R33). In a tainted session every codemode result is fenced (`ToolKind.codemode`, by registered source): a script's `load()` returns what an earlier `store()` kept, and no nested external call marks that parent. Residual: a `store()` value is written to the session file, so it outlives a taint Clear (and resume or fork) and a later `load()` returns it unfenced in a session that is no longer tainted, like a file the agent wrote. `tool_search` results and codemode `searchTools` / `describeTool` output quote MCP tool descriptions unfenced and do not taint; the same text already reaches the model in tool declarations.
- Run guard (stage 04, `run-guard.ts`): 5 identical calls in a row (identity = the exact canonical input), 150 calls, 60 turns per run; counters reset at `agent_start`; blocked calls count. A trip asks Deny / Allow once; Allow once restarts the tripped streak; deny blocks; with no UI it blocks. Limit: Pi runs the calls of one assistant message in parallel and its `tool_call` hook ordering is not documented, so a burst in one message can pass a limit by a few calls.

## Agent profiles (M11a)

Rules for agent sessions are composed by `modules/sessions/agent-rules.ts` into the same `PolicyRules`: `profile` `agent-thread` (the agent's trusted thread) or `isolated-task` (a trigger, a tainted delegation), `agentHome`, `agentScratch`, `sandbox {required, network}`, `autonomy`, `trustedSources`, `hostGrants`. A profile literal the build does not know blocks every call (fail closed). A profile that does not parse composes read-only rules and logs `agent_profile_unreadable`.

- **Own folders are named by the rules.** `ownFolder` (`target-path.ts`) accepts the home or scratch folder the rules name only when it has no `.` or `..` segment, its real path has the shape `agents/<id>` or `agents/.runs/<id>/<task uuid>` under the real pap home, and the spelling ends the same way. A link at any level is not an own folder. A thread's edits in its home run in `auto-accept-edits` (they are not "outside the folder"); an isolated task writes its scratch folder only and its home is read-only (`MEMORY.md` is a protected path to it).
- **Stage 02 sandbox rule** (`sandbox-rule.ts`): with `sandbox.required`, any command-bearing tool that is not pap's `bash` (`<inline:pap-sandbox>`) is blocked, Pi's `bash` and `powershell` included. Stage 02 skips its URL walk for pap's networked sandboxed shell only (the proxy enforces hosts, ADR 0047); the denylist, the preset pin and the message mix still run.
- **The sandboxed shell in stage 03** (`agentCategory`, M11R30): without network it is an `edit` of its own folder and not external (unasked in auto-accept-edits, asked in supervised, blocked in read-only; it never taints); with network it is `exec` and external, so the taint question and the mode's exec question apply, and its result taints per the egress report (`egress-taint.ts`; stage 07 reasons `egress: trusted sources only`, `egress: no network used`, `egress: no report`, `egress: report cut`, `egress: untrusted host reached`). A shell whose own folder the rules do not name as a real agent folder is blocked.
- **Order in an agent thread:** sandbox own-folder block, read-only command cover, platform plan, the block on a read outside the thread's own folders, review or protected read, the matrix with the judged taint, the read-only preset's hold (MC36), then allow, block or ask. An isolated task has its own table (`decideIsolated`): reads inside the home or scratch folder only (a missing path counts as outside), writes in the scratch folder, the shell only in the sandbox and only with a host list when networked (it then asks through the Inbox), unknown tools and non-builtin read tools (`codemode`, `tool_search`) blocked, `full-access` blocked, questions always Deny / Allow once with no grant.
- **Message mix (W5-R11):** a Pi path tool and an allowed sandboxed-shell call in one assistant message: the second one judged is refused, in either order. Depends on Pi running one message's `tool_call` hooks one after another (`agent-sessions.int.test.ts` pins it).
- **Scratch folders and other homes are external content.** Any session but the task itself (an agent thread reads its own runs folder the same way, W5-R65, but is blocked from other agents' homes and runs folders, W5-R63) that reads `agents/.runs/...` or inside another agent's home gets fenced text (`agent-run`, `agent-home`) and is tainted, even after the read is allowed (W5-R45, W5-R46). An isolated task reading its own scratch folder is not fenced (W5-R9). A plain session asks for any agent home, `.trash` and `.runs`, and for a search rooted at `agents/`.
- **Platform tools** are classified by source and name (`<inline:pap-platform>`); an unknown name from that source is `unknown`. `platformPlan` allows untainted or `run` ops in every mode; a tainted `ask` op asks Deny / Allow once with no grant (the delegation card says the other agent runs it as an isolated task); `network_request` asks Deny / "Allow this host" (a host already granted needs no card; blocked before any card with the sandbox or network off). With `rules.autonomy` on an agent thread, a tainted `ask` op is allowed with the reason `trusted autonomy`.
- **Trusted autonomy for the shell** (`autonomous()` in `agent-stage.ts`, W5-R34, W5-R53): agent thread, `autonomy.hosts` not empty (the agent's own list), pap's sandboxed shell with network. One flag, `judgedTainted = tainted && !autonomous`, is computed once and used by the matrix, prefix and session rules, the read-only command cover and the scopes the card offers; the card therefore offers what will apply. The mode still asks what it asks in a clean thread. The result still taints from the report.
- **Vault values** (8 characters or more) are redacted as `[SECRET:NAME]` in tool results and never restored into a write; a name removed from the vault stays redacted until the worker exits; a one-use value stays redacted after use.
- **Pi's own configuration of an agent session:** context-file discovery is off (`AGENTS.md`, `CLAUDE.md` of the home or its parents never join the prompt, W5-R24), project trust is never given and refused inside `$PAP_HOME/agents` (W5-R27, W5-R29).

## Command denylist (stage 01)

- Applies to every command-bearing tool (built-in `bash`; any tool with a string `command`) except `powershell`, which gets the owner's patterns only. The built-in preset ("catastrophic commands", on by default) is word-level: recursive `rm` on `/`, `/*`, `~`, `~user`, `$HOME`, the home directory written as a literal path (`os.homedir()` and `$HOME`, taken once at load) and each of its ancestors (`/home`, `/home/*`); recursive `chmod`/`chown`/`chgrp` on `/`; `mkfs*`, `mke2fs`, `mkswap`; `dd of=/dev/<disk>` (`/dev/root` included); `shred`/`wipefs`/`blkdiscard` on `/dev`; a redirection to a disk; a fork bomb (checked first, on the raw text). Owner patterns are globs (`*`, `?`), anchored on a whole segment, matched by a step-budgeted matcher (never a regex from user input). Neither a mode nor a grant lets a denied command run.
- The reader (`shell-words.ts`, `shell-argv.ts`, `shell-heredoc.ts`) resolves quotes, splits on `; & | ( )` and newlines, reads `$(...)`, backquotes, `bash -c`, `eval` and here-document bodies again, strips wrappers (`sudo`, `env`, `nohup`, `xargs`...), emits redirections as words of their own. Limits: 64 KiB, 1 000 segments, 3 levels, a glob budget per call. Owner patterns fold Unicode blanks and lone surrogates, so a pattern may block a command bash would not run (conservative).
- Lever B (owner): when the reader gives up ("too complex", "too long") or an owner pattern runs out of budget, an interactive session with a UI asks Deny / Allow once (card title: "pap could not check this command...") and no grant can skip it. Built-in hits, owner-pattern hits and the fork bomb still block; a catastrophic shape found by a bounded rough scan of the raw text blocks too, and the same rough scan backs a reading the reader marked unsure (a quote inside a double-quoted `${...}`, which bash and the reader pair differently), with no new question. Unattended and read-only sessions block. With an egress host list set, an unreadable command blocks at stage 02 and lever B does nothing. Lever D: `daily-use.corpus.ts` keeps about 50 ordinary commands that must pass without a question in the default mode.
- Documented passes (each has a test row labelled so; the reader is best-effort, M5R18): a variable, substitution or ANSI-C word as the command (`c=rm; $c -rf /`, `$(echo rm) -rf /`, `$'rm'`); aliases and functions defined earlier (including one named `cat` or `tee`), scripts written then run, interpreters (`python3 -c`), output piped to a shell (`printf 'rm -rf /' | sh`), a here-string to a shell, a group, loop or function piped to a shell on a later line, a here-document reaching a shell through `$(...)`; `rm -rf /..`, `/[a-z]*`, brace expansion, `cd / && rm -rf *`, `find / -delete`, `find -exec rm`, `xargs rm`; `env -S`, `taskset <mask>`, `chmod --re=...`, `watch 'cmd'`, `flock -c`, `runuser -u x --`; `sg <group> '<cmd>'` without `-c`; on an unsure line (a quote inside a double-quoted `${...}`), quoted text that merely names a catastrophic command can be blocked by the rough scan (a false positive); wrappers the reader does not strip (`pkexec`, `chrt -f 99`, `systemd-run --user`) and any similar launcher; a target built by expansion (`rm -rf "$DIR"/*` with `DIR` unset); fork bombs without the pipe (`f(){ f & f; }`) or built from several functions; `tee /dev/sda` and `cp img /dev/sda`; a NUL, zero-width joiner or NBSP spliced into the command word. Here-document bodies for `cat`/`tee` with nothing piped on are data (pass); any other receiver (`python3 - <<EOF`, `psql`, `kubectl apply -f -`) is read as commands, so a long inline script may be "too complex" or match a pattern (a false positive). `rm -f a.txt $(ls -R /)` blocks when the reader gives up. An owner pattern can be skipped by spending the call's glob budget in an earlier segment (the stage asks, it does not match later segments); the fork-bomb check runs outside the step budget but inside the 4 MiB cap of the rough scan (linear, about 0.6 s at 2 MiB; function names are any word without blanks or shell metacharacters: `.`, `a.b`, `a-b`).

## Egress (stage 02)

- Unattended runs (M10R27, R28, R152; `policy/tool-allowlist.ts`): stage 02 first checks `rules.toolAllowlist` by exact name, then, while `rules.unattended`, blocks a tool of category `unknown` even when listed; both before the preset check. The worker pins the list of `InitRecord.tools.allowlist` (`pinAllowlist`: a `policy_update` can narrow it, never lift it) and makes the allowlisted registered tools the active set. While `unattended`, lever B asks nothing (`markAskable`): a command the reader cannot check blocks.
- Task sessions (M10, ADR 0041): `session_policy` gains `tool_allowlist` and `unattended` (a CHECK refuses `unattended = 1` without a list). `setTaskPolicy` writes mode, list, taint and the flag in one statement; `endTaskPolicy` clears the flag; `clearTaskPolicy` lifts the list (refused while unattended). `setSessionMode` answers `session_busy` for `full-access` or `null` on an unattended session, and `taskRules` clamps a stored `full-access` to `supervised` while unattended. The audit actor of a runner timeout denial is `system` (`AUTOMATION_CREDENTIAL`), not the owner. A fork copies the list, never the flag.
- Off by default (`allowHosts: null`). A list, even empty, restricts: a URL whose host is not on it blocks in every mode (a block, not a question). Patterns: `example.com` itself, `*.example.com` its subdomains, not the apex. Ports and paths are not judged.
- URLs come from every string of a non-built-in tool's input (depth 10, 10 000 strings), from the words of shell commands and from built-in network tools. A space-free string starting with `scheme://` is one URL judged whole, and the URLs inside it (redirect, archive and reader-proxy forms) are judged too, so both hosts must be listed. Refused: credentials, a scheme other than http(s)/ws(s), IP literals, backslashes, control characters. Clients with no judgeable host (`curl wget nc ncat socat ssh sftp ftp telnet dig nslookup host`, `git clone|fetch|pull|push|ls-remote`, `scp`/`rsync` with `host:path`) block with "host not checkable"; curl reroute flags (`--proxy`, `--resolve`...), `/dev/tcp`, git `-c *proxy=`, `-c alias.*`, `-c url.*` and `--config-env` (and, after `clone`, `-c` / `--config` / `--config=`) make the segment uncheckable.
- Residuals (also in Settings › Approvals): any allowed URL in a segment unlocks bare hosts next to it (`curl https://example.com evil.test`); host-only fields (`{host: "evil.test"}`); scheme-relative `//evil.test`; free text such as `see https:evil.test`; clients the list does not name, scripts that reach the network themselves, DNS by any program; proxies from the environment or files (`HTTPS_PROXY`, `export`, `~/.curlrc`, `curl -K`, `wget -e`, `.wgetrc`); a `/dev/tcp` path built by expansion; git aliases, proxies and URL rewrites from config files (`include.path`, `GIT_CONFIG_*`, a saved alias), `http.noProxy`, submodules, `remote update`, `archive --remote`, `lfs`; curl short-option clusters other than `-<letters>x`. False positives: `curl -oxfile`, underscore hosts under `*.`, arguments that look like `/dev/tcp`.

## Redaction (stage 06)

- Secrets (`secrets.ts`): (a) worker environment variables whose name holds a credential word (`TOKEN SECRET PASSWORD PASS APIKEY AUTH COOKIE BEARER JWT`..., plus `PGPASSWORD MYSQL_PWD SSHPASS`); their values must be 8 to 4 096 characters, not a path (leading `/`), not only digits, not `true`/`false`, not weak (lower-case letters only and under 12, one repeated character, or a placeholder such as `password`, `changeme`, `postgres`). These limits apply to environment variables only. (b) String values of Pi's `auth.json` in the fields of `AUTH_FIELDS` only (`key`, `apiKey`, `access`, `refresh`, `token`...), at least 8 characters, no other filter; a `key` that is a command (`!...`) or holds a `$VAR` reference is skipped (Pi resolves it), and the file is read up to 1 MiB (a larger one is not read, one stderr line). The set is rebuilt when `auth.json` changes and holds at most 256 secrets, keeping the longest values; vault values (M11) are pinned and never dropped for length. Matching is exact and linear (first 8 characters indexed).
- Where it applies: the `tool_result` hook (text parts, strings of `structuredContent` and `details`), the audit arguments, every record the worker sends (one wrapper of `ipc.send`, `redacting-ipc.ts`: a record that cannot be checked is dropped, a response fails), the worker's stdout and stderr (`redact-stdio.ts`). Reasons are redacted before they are clipped. Live output edges (`edges.ts`): a head or tail of 4+ characters of a known secret becomes `[SECRET:NAME]`, only when Pi marks the output cut or the string was clipped by the worker, never in identifier fields; a spent edge budget fails the record. A throwing redaction withholds the result.
- MCP exit tests (spec C §8.1) run through a real daemon worker against a local stdio fixture, no network: `apps/daemon/src/security/mcp-taint.int.test.ts` (direct exposure: fence, taint, ask, stage 02) and `codemode-nested.int.test.ts` (codemode exposure: nested call audited under its parent, results fenced). The pi-host `host.taint.mcp*.int.test.ts` files keep the in-worker unit-level cases.
- Marker restoration (owner MQ4): `[SECRET:NAME]` is restored in the input of Pi's built-in `write` and `edit` only, after the question is answered, with environment-sourced secrets only (never `auth.json` values: stricter than MQ4; an agent cannot write a provider key into a file). Never into bash, MCP or extension inputs. A secret with `"` or `\` written into a JSON file is restored unescaped.
- Limits: object keys are not redacted; a value split across text parts, or across `content` and `structuredContent`, is not matched; base64, URL-encoding, reversal, images and a value written to a file then read by another process are not caught; secret pieces split across streamed `message_update` deltas (`text_delta`, `thinking_delta`, `toolcall_delta`) are held back in the worker, per content block and prefix-aware: only the text before the longest possible start of a secret is released, and the rest is flushed at `*_end`, `message_end`, an error or an abort (W5-R60); the daemon coalescer stays value-free (W5-R54); Pi's own session file keeps model-typed assistant text and tool-call arguments raw (the M5 limit); Pi's own unsandboxed bash full-output file (`/tmp/pi-bash-*.log`) still gets M5 env secrets raw (a `read` of it is redacted); direct `fs.writeSync(fd)` and Node's fatal printer bypass the stdio wrapper, and a secret split across two stdout/stderr writes is not found (worker stderr lines built with `logLineOf` are exact-only); free-text string ends that start with a secret's prefix are not masked, only clipped strings are tail-masked, and a clip at a length not in the gate list escapes (`ui-lines` 512 cut then SGR or surrogate strip, session title 80 plus an ellipsis, compaction summary 65 536).

## Taint and fencing (stage 07, ADR 0020)

- External results reach the model inside `<untrusted source="..." id="<12 hex>">...</untrusted id="<same id>">`; `UNTRUSTED_RULE` is appended to the system prompt. Images and `structuredContent` are not wrapped. `bash` output and files are not external (spec C §5 known limit).
- The worker keeps `{tainted, epoch}` and sends `taint` records; the daemon stores them in `session_policy` (`policy-link.ts`, `markTainted(owner, session, observedEpoch)` raises only when `taint_epoch <= observedEpoch`). Path 2 (a `result` audit entry with `external: true`) raises with no epoch check and is load-bearing: never add one. `policy.clearTaint` bumps the epoch. The migration that creates `session_policy` taints every session that exists when it runs (nothing before M5 fenced external content; the cost is one Clear per old session the owner continues).
- Local tools (decision 117, A2): the owner can vouch for an extension tool by name and registered source (`PolicySettings.localTools`, at most 64, no duplicate pair, Settings › Approvals › Local tools). The list reaches every session's `PolicyRules.localTools` like the host list (running sessions on a settings change); `agent-rules.ts` leaves it alone, so agent threads and children carry the owner's list. An isolated task carries it too but gains nothing: `insideReach` is false for any non-built-in read, so the task still blocks the tool. `classifyTool` applies a rule only on the last fallback, to an extension tool whose source is not reserved (`isMarkableSource`: not `builtin:*`, not `<inline:*>`), when the name and `ToolInfo.sourceInfo.path` both match exactly: the tool is then a non-external read. A rule naming a built-in, MCP, platform, sandbox, codemode or tool-search tool, or a name those sources left unknown (`mcp` gateway tools included), has no effect. What Add allows: the tool's results are never fenced and never taint, and its own calls run without asking (« sans demander »), in every mode including Read only (« Lecture seule »), even after the session read external content. The owner vouches that the tool reads nothing from outside the machine, sends nothing outside (« n'envoie rien à l'extérieur ») and does not modify their files; the Settings help text and the card's confirmation say the same, in both languages. A trigger's `toolAllowlist` still applies by name (a local tool is allowed unattended only when the run's list names it). Trade-off: a local tool's output and its calls are trusted as local, so a listed tool that fetches or sends data lets it through; the source pin stops another extension from posing as the tool, not the tool from changing. The Settings help text says the same.
- What tainted the session (decision 117, A3, APR-8): stage 07 records a cause each time an external result raises the taint (`policy/taint-cause.ts`, kept by `createTaint`). One entry per (tool, source) with the newest time and a count (a chatty tool uses one slot), the newest 8 entries since the last clear, newest last, and a count of dropped older entries (`TaintCauses`: `{list, older}`, `ApprovalRequestRecord` and `Dialog`). `source` is `ToolFacts.path`, the exact registration path; `markable` is true only for the tool's own external classification of the unknown fallback from a source `isMarkableSource` allows (never a built-in, MCP, platform, sandbox, codemode or tool-search tool, never a result external only through its parent). A sticky bit per taint epoch (a cause that is not markable, a raise that named none, or any dropped entry) makes every entry `markable: false`, so the card never offers to lift a taint it did not fully name. A worker that was not clean when it learned of the taint (init, a daemon update) names no cause. The ask carries `taintCauses` only when the call is judged tainted. The card says `This session read external content: web_search (14:02), plan (14:05) and 2 others` (the two newest, dropped entries counted among the others); when every cause is `markable` and none was dropped it offers Mark as local tool: a confirmation naming each tool and its exact source, then `policy.getSettings` -> `policy.setSettings` (with the revision read; one retry after `conflict`) -> `policy.clearTaint` for this session. The pending question is not answered by it.
- Outside taint (decision 75 Q5): tool results appended to a session's Pi file by something other than pap (the Pi CLI, pi-web) taint it through the sessions scanner and before a cold worker starts, with no epoch. What it does not cover is listed under "Not covered" in `docs/agents/sessions.md` (scan port).
- Residuals: a daemon crash between a worker's taint send and its dispatch; a clone taken while the live leaf is null, or after a failed `markTainted` and before the next `agent_end`; insert and inherit are not one transaction; a late result entry after a clear taints again (the owner clears twice).

## Read-only commands: the table, the git check and what remains (M7 Tasks 1a-1c, 28, ADR 0024)

Table of `read-only-commands.ts` (an option that writes, runs a program or reads a list of files makes the line ask, in every getopt spelling; a command not listed is not read-only):

| Group | Commands | Operands and refused options |
| --- | --- | --- |
| Content readers | `cat head tail nl stat md5sum sha1sum sha256sum sha512sum b2sum cksum strings od cmp tac rev cut paste comm join fold jq` | judged as the built-in `read` |
| Text only | `tr basename dirname echo printf true false pwd whoami id uname nproc uptime free df ps which` | operands are text, not paths |
| `date` | `date` | `-s -f -r`, `--set --file --reference` refused (the letters `d`, `I` take the rest of the cluster) |
| Counters and sorters | `wc` `file` `sort` `uniq` `diff` | `wc` and `du` refuse `--files0-from`; `file` refuses `-C -f -m` and their long forms; `sort` refuses `-o --output --compress-program --files0-from`; `uniq` takes one operand; `diff` operands are judged as a search root |
| Paths and listing | `realpath readlink ls tree du find` | `ls -R` walks like `find`; `tree` refuses `-o -R --fromfile`; `find` refuses `-exec -execdir -ok -okdir -delete -fprint -fprint0 -fprintf -fls -files0-from` |
| Readers added by decision 117 | `sed fd fdfind eza` | `sed` only as a line printer: options exactly `-n --quiet --silent` (one is required), script exactly `Np`, `N,Mp`, `N,$p` or `$p` (a `$` makes the engine ask: it reads it as an expansion), files judged as `read`; `fd` first operand is the pattern, the rest judged like `find`, refuses `-x -X -l --exec --exec-batch --list-details --base-directory --search-path --ignore-file` (`-L` allowed, as for `find`); `eza` like `ls`, with `-R --recursive -T --tree` judged like `find` |
| Search | `grep egrep fgrep rg` | the session folder is judged too; `rg` refuses `--pre` and `--hostname-bin`, and asks when `RIPGREP_CONFIG_PATH` is set (MC16) |
| `git` | `status ls-files ls-tree rev-parse rev-list describe shortlog merge-base name-rev count-objects check-ignore show-ref diff log show blame grep cat-file`, `branch` (listing options only), `remote -v`, `stash list`, `worktree list` | `diff log show stash` refuse `--output --ext-diff --textconv` (`blame`, `cat-file`, `grep` their own); only `--no-pager -P --no-optional-locks` and `-C <dir>` before the subcommand; the folder git walks is judged like `find`'s root |

The git check (owner m3, `git-config-guard.ts`; the code is stricter than the plan's M7R147-M7R149 wording and the code wins):

- Which repository: the nearest folder upwards with a `.git` (folder, or a `gitdir:` file) or that is itself a bare repository (`git-discovery.ts`). Anything git might accept but the reader does not fully accept (a HEAD that is not `ref: refs/...` or 40 hex digits, no searchable `objects/` or `refs/`, a dangling `.git`) is "git config unreadable" and the command asks. Folders above that repository are never read (MC4 c). No repository at all asks (MC17).
- What is read: `config` and `config.worktree` of the git directory and of its `commondir`, with every `include` and `includeIf` target whatever the condition (at most 10 deep, 32 files per command line, 64 KiB each, strict UTF-8). A missing include, `~user/` or `%(prefix)/` include, an unreadable or unparsable file asks. `extensions.objectFormat` other than `sha1` asks.
- Which keys ask (`git-config.ts:163`, by section and key, whatever the subsection): `core.{fsmonitor,pager,editor,sshcommand,askpass,hookspath,gitproxy,alternaterefscommand}`, `diff.{external,command}`, any `*.textconv`, `filter.*.{clean,smudge,process}`, `gpg.program`, `credential.helper`, `sequence.editor`, `pager.<command>` with a value that is not a boolean, `extensions.partialclone`, `remote.*.{promisor,uploadpack,receivepack}`, `protocol.*.allow`, `uploadpack.packobjectshook`, `log.showsignature`. Relaxed (MC4): `core.fsmonitor` set to a boolean, and the exact git-lfs `clean`/`smudge`/`process` entries.
- Also ask: a `post-index-change` hook in the git or common directory (other hooks do not run on read commands, MC8); a `.gitmodules` in the work tree, a `modules/` folder, a `sharedindex.*` file, or any gitlink (mode 160000) in the index. The index reader (`git-index.ts`) walks versions 2, 3 and 4 exactly as git does, up to 64 MiB and 1 000 000 entries, accepts only the extensions `TREE`, `REUC` and `FSMN` (`UNTR` also asks: MC11 lists it as allowed, the code refuses it because git 2.53's reader writes past its array on a crafted one), and a seeded differential test against real git (`git-index.fuzz.ts`) pins it.
- The owner's `~/.gitconfig`, `/etc/gitconfig` and `GIT_CONFIG_*` are not read. `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY` and `GIT_INDEX_FILE` in the shell ask (`ShellFacts.gitEnv`, `shell-facts.ts`).
- Friction (expected): a repository with a program key in its local config asks for every git read command: `git lfs install --local` with a non-standard entry, a local `core.fsmonitor` command, a submodule, a partial clone. An exact or prefix always-rule covers that repository without the check (M5 semantics).
- Residuals: a process that is not a pap write rewrites `.git/config` between the check and git's read; an alias or function from an earlier approved command does not persist (Pi starts a fresh `bash -c` per call); `/proc/<pid>/environ`, `ps e` and other files outside M5's protected list are readable, like the built-in `read`. The Review pane is a separate runner: it empties a repository's filter drivers, needs git 2.31 or the pane refuses a repository that defines non-lfs drivers (`files.md`, MC13).
- The switch (Settings › Approvals, `readOnlyCommands`, default on) lists the covered command names from `READ_ONLY_COMMAND_NAMES` (`contracts/src/policy.ts:185`; a drift test in pi-host keeps it equal to the table). A settings Save used to reset a stored `false` to `true`: the form now carries the field (`policy-settings.vm.ts:55`, `:80`).

## Pattern always-rules (M7 Tasks 2a, 2b, ADR 0024)

- Three kinds in `approval_rules` (`kind`, `pattern`): `exact` (the M5 call key), `prefix` (bash only; `pattern` is the JSON words, 1..4 of `CommandWord`) and `tool` (`{"source":"builtin"|"mcp"}`, never bash). For the new kinds `grant_key` is the sha256 of `[tool, kind, pattern]`, computed by the daemon (`policy/pattern-rules.ts`). One list, one revoke path, one cap of 1 000 per owner and project counting every kind; a full project refuses the new rule with the M5 notice and the call still runs.
- A word of a read-only command with an unquoted wildcard (`*`, `?`, `[`) that could expand to an option asks ("glob operand"): the shell expands it before the command runs and a file named like an option (`--expression=...`, `--exec=...`, `-x`, `-delete`) would become one. It stays covered when its literal prefix is not empty and does not start with `-` (`src/*.go`, `a*`, `./*`), or for `--name=value` with the wildcard after the `=`. Quote it or start it with a path like `./`; there is no `--` exception. A quoted or escaped wildcard is literal (`Segment.wildcards`: word index to the index of its first unquoted wildcard).
- `cd <folder> && <one simple command>` (decision 117): the card offers the second command's prefix when the folder is a plain word that resolves, links followed, inside the session folder (`proposePrefix` with the session folder; `cd` with no operand, `-`, an option, `~`, an outside folder, `;`, `||`, `|`, a third segment or CDPATH offers only the exact command). A prefix rule covers the same shape and never a `cd` that leaves the session folder (`command-cover.ts`); a tainted session still counts no rule.
- The worker offers the scopes on its question (`alwaysScopes`: a `prefix`, or `tool` with `toolSource`). The daemon keeps the offer beside the dialog; the client's answer only names a scope (`exact`, `prefix`, `tool`). A scope that was not offered, or sent with an answer other than `always`, is `bad_request` before anything is taken. The stored prefix or source always comes from the stored offer, never from the frame.
- `prefixesFor` / `toolsFor` fill `alwaysPrefixes` / `alwaysTools` of the worker's rules. A row whose `pattern` no longer parses is skipped with one `policy_rule_unreadable` warning per read (never sent); the rules list still shows it, without words, so it can be revoked.
- Lists show a prefix rule as `pnpm test …` and a tool rule as "any input"; the card offers the choice after "Always" ("This exact command" is the default).

## Audit (ADR 0022)

- Rows: `call` (stages 01-04, 06 if markers were restored), `result` (a shell call's always, with its exit code and duration and no args; any other tool's only when 06 or 07 acted), `session` (00, 05; tools as `{count, truncated, names}`). Append-only by SQL triggers; a worker's entry is parsed, scrubbed of known token formats, budgeted (600 rows per session per minute, plus 120 platform calls per session per minute, a marker row at the gap), at most 100 invalid rows per session. Details: `daemon.md`.
- Card timing and results (decision 117, A4): the audit records when an approval card was shown, which answers it offered and when it was answered (`asked_at`, `answers`, `answered_at` on the call row), and a shell call's exit code and every result row's duration (`exit_code`, `duration_ms`; never output); `pap trace summary` turns them into the approvals block (`daemon.md`). A shell call's result always leaves a row. A tool that is not a shell has no exit code and a row only when a stage acted.
- Size: about 0.5 KB per call row, so 1 000 tool calls a day is about 180 MB a year; a shell call adds a result row (no args, smaller, about 0.3 KB). Retention is 12 months; `pap audit prune [--month YYYY-MM] [--dry-run]` removes a whole month older than that, with the daemon stopped (`systemctl --user stop pap-preview` first); the boot line `audit_prunable` says when months are prunable. A row can be purged only by editing the file. There is no per-session volume cap beyond the rate: a hostile session can grow the table by about 10 MB a minute until stopped (a compromised worker can already write files under the same account).

## Files, git and terminal (M8)

- The pipeline above judges the **agent's** tool calls. The owner's own actions in the explorer, the editor and the terminal are not tool calls and are not judged by it. The path boundary (`files.md`) applies M5's **lists** to them, with owner-side outcomes: refuse, confirm ("Save anyway?"), or confirm plus step-up.
- The lists are copied into `packages/contracts/src/protected-paths.ts` (`PROTECTED_SEGMENTS`, `PROTECTED_BASENAMES`, `HOOK_CONFIG_NAME`, `PAP_SENSITIVE_NAMES`) because the daemon may not import pi-host. `packages/pi-host/src/policy/protected-lists.test.ts` checks, in one direction, that everything in the contracts lists is protected by `checkEditTarget` / `checkReadTarget`; a name added to pi-host only is not caught. M8 edits nothing under `policy/`; a change to M5's lists means a change to both.
- Tokens never confirm a protected save and never write a protected name, under `<agentDir>` or a `.pi/` folder (`forbidden`, or `not_found` where the boundary hides the path); they never hold `terminal:*`. See `auth.md`.

- **Attachments (MC38 I3, closed at the M7 rebase).** `read-target.ts` asks for `$PAP_HOME/attachments/pending/**` always, for `attachments/<sid>/**` unless `sid` is the session's own (`PipelineDeps.sessionId()`, pap's session id from the init record (`papSessionId`, never Pi's own id); absent means every `sid` asks) and for a `grep` / `find` rooted at `attachments/` itself; `ls attachments` shows session ids only and passes. Links are judged as resolved, so a link from the session's own folder to another's asks. Built-in reads and read-only shell commands (`cover`) share the check; read-only mode blocks like for any protected read.

## Lanes (M9, ADR 0033)

- **The R97 narrowing** (`packages/pi-host/src/policy/target-path.ts`, `ownFolder`): when a session's folder is inside `<papHome>/worktrees/<laneId>` (named like a lane; any spelling of pap's home), that lane is the session's own folder and not a protected root, so an edit inside it is auto-accepted in the accept-edits mode instead of asking. Other lanes, `worktrees/` itself and the rest of `$PAP_HOME` stay protected, and protected names (`.git`, hooks, editor tasks) stay protected inside the lane. Pi's own files still ask. The sessions module refuses to start a worker inside another owner's lane (`forbidden`, `LanePaths.assertOwnLane`).
- **Scope alias.** `createPolicyModule({ scopeAlias })`: a lane's sessions share their project's approval rules and always-rules (`scopeOf(cwd)` answers the lane's `project_root`), and a lane is filed under its project in the sidebar (M9R104).
- **Issue lanes start tainted.** `lanes.create` with an issue calls `markTainted` for the primary session (sticky taint, ADR 0020). The issue text is fenced with `fenceText`, now in `packages/contracts/src/fence.ts` (pi-host re-exports it).
- **The tainted confirmation.** `lanes.runScript` and `lanes.archive` (when an archive script exists) answer `tainted` while any session of the lane, archived ones included, is tainted, until the call is repeated with `confirmTainted: true`. The fan-out test auto-run never runs in a lane with a tainted session. An unbound policy port counts as tainted.
- Taint does not gate extension event hooks: they see an issue's text (residual).
- Scripts, `gh` and installs run outside the policy pipeline (they are not tool calls); the unattended environment and the browser-only rule are their controls (`lanes.md`, ADR 0034).

## Pi resource loads never install (MC52)

- A Pi resource load installs a missing package (`npm install` with scripts, `git clone`) unless `PI_OFFLINE` is set. That would be code execution from a read, so every helper read op that loads resources or resolves packages runs with the switch on, for that call only: `skills.list`, `skills.setInvocation`, `plugins.list`, `trust.status`, the resource load of `mcp.test`, the model reads that open Pi's configuration (`loadRuntime`, `extension-load.ts`) and the subagent profile reads (`helper/ops/offline.ts:6`; skills list in `skills.md`). A missing package is not listed (or is in `unlisted` for trust) and the answer still comes. Only an explicit, step-up-gated install or update op may reach the network.
