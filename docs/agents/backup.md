# Backup

Decisions: ADR 0063; rulings M6bR1 to M6bR9, M6bR48 to M6bR50, M6bR55 in `docs/research/m6b-rulings.md`. `pap backup` needs no stopped daemon; `pap restore` does. Back up before an update (`update.md`).

## Plain backup: `pap backup`

`pap backup [--out <abs dir>] [--skip <attachments|agents|exports|pi>]... [--allow-large] [--keep N] [--encrypt [--secrets include] [--passphrase-stdin]] [--unit <name>] [--home <abs dir>]`

- One file, `pap-backup-<UTC yyyymmddThhmmssZ>.tar.gz`, mode 0600, in `$PAP_HOME/backups/` (0700) or `--out`. It is built as `<name>.<pid>.<random>.part` (two runs never share one) and published with a hard link on success, so a backup of the same name that appeared meanwhile is never replaced (a file system without hard links falls back to a rename); a name that exists is refused. A SIGINT or SIGTERM removes the `.part` and the stage folder before the process ends. `tar` is the one found on `PATH` (GNU tar required).
- Needs no instance lock and does not stop the daemon. `state.db` is a `VACUUM INTO` snapshot taken from a read-only connection (consistent). `pap backup` holds no instance lock, so it never deletes a `-wal` or `-shm`: with none present it reads through the immutable URI, and if a daemon starts during the read the snapshot is redone through a plain read-only connection. Only the callers that hold the lock (the update snapshot, the restore's kept copy) remove a sidecar their own read created. The other files are copied as they are, and a file that changes while tar reads it may be incomplete (for example a Pi transcript being appended). Hard-linked files (a `git clone --local` under `agents/`) are stored as separate regular files. GNU tar exit 1 ("file changed as we read it") is accepted and said in the summary; any other non-zero exit fails the backup.
- Members, in order: `manifest.json`, `state.db`, `attachments/`, `agents/`, `exports/`, then Pi's `sessions/` as `pi-agent/sessions/` (from `PI_CODING_AGENT_DIR`, default `~/.pi/agent`; `--skip pi` leaves it out).
- Never included unless `--secrets include --encrypt` (see below): `secrets/` (the vault key and scope files, `ref-salt`, `device.key`, `triggers/*.key`, `secrets/push/vapid.json`), `search.db*`, `worktrees/`, `lanes/`, `tmp/`, `logs/`, `backups/`, `update/`, `pap.lock`, Pi's `auth.json`, `models.json` and extensions. Unpushed lane work is not in the backup.
- `--keep N` (1 to 100) prunes every `pap-backup-*` file of the output folder, whichever home made it: do not share one `--out` folder between homes when you use `--keep`. It keeps the new backup and the N most recent older `pap-backup-*` files (`--keep 2` keeps the new backup and the 2 most recent older ones) of the output folder beside the new one and removes the rest. Only names of the exact form `pap-backup-<stamp>.tar.gz[.enc]` are touched.
- `update/last-backup.json` (`createdAt`, `file`, `encrypted`, `secrets`) is written on success, for `pap doctor`.

### What a plain backup is, and is not

- The summary says: "The secrets folder is not included. Transcripts and agent files may still contain secrets: treat this file as sensitive, and use --encrypt before copying it off this machine." Pi transcripts, agent folders (memory, prompts) and `state.db` (audit rows, push subscriptions) can hold a value someone pasted or a tool printed. A plain backup is allowed (one line of warning, nothing prompts); copy it off this machine, a backup on the same disk is not a backup.
- A plain backup detects corruption (gzip CRC, a database check), not tampering. Encryption (GCM) is what detects tampering. A swapped agent file in a plain backup restores silently.
- After a restore from a plain backup the vault, webhook keys, the known-device key and the push key are gone: re-enter or rotate them. Notifications: each device re-enables when it next opens pap.

### Gates

- Payload above 2 GiB: refused with the size of each folder, unless `--allow-large`. A single file above 8 GiB - 1 is refused always (the restore reader does not accept a pax `size`), naming the file.
- Free space at the output folder below `payload / 2 + state.db + 64 MB`: refused before anything is written. The home needs `state.db + 64 MB` free too (the stage holds the database snapshot there, for plain and encrypted backups alike). Unknown free space passes.
- What the walk leaves out is counted, never silent: symbolic links and special files (including links inside git working trees under `agents/`), names the restore reader would refuse (control characters, bidi marks, bytes that are not UTF-8), paths nested more than 128 parts deep, and folders without owner read and execute together with everything below them (the summary counts them as "names or folders the restore would refuse" and shows the first few; `chmod u+rx <folder>` and back up again to include them), and entries that vanished while the walk ran. Any other read error (`EACCES`) fails the backup.

### Which home and which unit

A unit with `EnvironmentFile=` or an empty `PAP_HOME=` cannot be read faithfully (the home may be set out of sight): it is "not a unit pap wrote", and `--home` is required.

`--unit` / `PAP_UNIT` (default `pap.service`) names the systemd user unit. The home is `--home`, else an explicit `PAP_HOME`, else the installed unit's `PAP_HOME`, else `~/.pap`; the summary prints it with its source. The backup is refused when the installed unit runs on another home than the resolved one and `--home` was not given, and when the unit's text is not one pap wrote (then pass `--home`).

## Encrypted backup: `--encrypt`

- Output name `pap-backup-<stamp>.tar.gz.enc`, mode 0600, created with `wx` and removed on any failure. The tar stream is encrypted as it is produced: no plain archive ever exists on disk, so it is not re-read at creation (`pap restore` re-validates everything). The stage (a plain `state.db` snapshot, the manifest and the member lists) lives in `$PAP_HOME/tmp/.backup-stage-*` (0700) and is removed on any exit, so no plain byte is ever written to the output folder, which may be removable or synced. A crash (SIGKILL, power) can leave that stage folder in the home's `tmp/`: delete it; a plain snapshot is in it.
- Container (`apps/daemon/src/cli/backup/crypto.ts`): `PAPB1\n`, scrypt cost bytes (log2 N 17, r 8, p 1), 16-byte salt, 12-byte IV, AES-256-GCM ciphertext, 16-byte tag. The whole header is the GCM additional data. The passphrase is normalized (NFKC) before the key is derived.
- Passphrase: 12 characters or more, no other rule. On a terminal it is asked twice ("This passphrase protects the backup file; pap cannot recover it."); with `--passphrase-stdin` (refused when standard input is a terminal) or any non-terminal stdin it is the first line of standard input. Never an argument or an environment variable, never in the manifest, the output or an error. A lost passphrase is unrecoverable.
- `--secrets include` (only with `--encrypt`; alone it is a usage error, exit 64) adds the whole `secrets/` folder, including `secrets/push/`. `--encrypt` alone encrypts and still leaves `secrets/` out. The manifest says `secrets: included`.
- Decryption (`decryptFile`) reads the cost from the header and refuses log2 N outside 14 to 18, r other than 8 and p other than 1 before deriving any key (at most 256 MiB and about 2 s). The ciphertext is read twice: the first pass only authenticates, so a wrong passphrase or one changed byte is refused before the output file exists; the second pass writes it (0600, `wx`) and removes it if the file changed in between. A wrong passphrase and a changed file give the same message, on purpose; a failing disk or a failing read gives its own message with the error code (`the decrypted archive could not be written: ENOSPC`). The input must be a regular file (a symbolic link or a FIFO is refused) and is opened once for both passes. There is no key-check value in the format (ruling M6b-C2): a wrong passphrase is found after one full pass over the file.
- What it does not do: anyone holding the file can try passphrases offline (scrypt makes each try cost about 0.4 s and 128 MiB); the file name, its size and the fact that it is a pap backup are visible.

## Restore reader: untrusted archive, three layers (Task 5a)

`pap restore` never trusts the archive. The reader, the stage walk and the placement live in `apps/daemon/src/cli/backup/`: `tar-list.ts`, `verify-stage.ts`, `place.ts`. None of the three layers is enough alone, and each has its own tests and mutation checks.

1. **`listMembers(file, limits)`** reads the gzip tar headers before anything is extracted (it extracts nothing). It accepts exactly what `tar --format=pax --owner=0 --group=0 --numeric-owner` writes for a backup: a header with the magic `ustar\0` and version `00`, a checksum field in ASCII (digits, NUL and spaces only: a no-break space or a byte order mark in it makes tar skip the header and read the member's content as headers) that matches, a size field of eleven octal digits, a folder mode that keeps owner read and execute, a type of regular file or folder, and an optional pax extended header whose only records are `path`, `mtime`, `atime` and `ctime` (each once). Anything else is a refusal, not an ignored field: a `size` record is how a hidden symbolic link member got past the first draft (GNU tar reads the pax size, a naive reader reads the ustar size, and the member's content is parsed as headers by one and skipped by the other). Also refused: links, devices, FIFOs, sparse and global headers, base-256 sizes, a regular-file header whose name ends in a slash (tar extracts it as a folder), names with `..`, absolute names, control characters, a name listed twice, a member below a file, data after the two zero blocks, an archive without them, a file listed where an earlier member implied a folder, folders nested more than 128 deep, more than 1 000 000 members or 64 GiB declared. A single file of 8 GiB or more makes GNU tar write a pax `size` record, which the reader refuses: such a file fails the backup's own check (`pap backup` says so and removes the file). `pap backup` runs the same reader over its own plain file before the rename.
2. **`tar -xzf`** with `--no-same-owner --no-same-permissions --no-overwrite-dir` into a private stage inside the home (Task 5b).
3. **`assertPlainTree(stage)`** lstat-walks the extracted stage before anything reads, chmods or places a file: anything that is not a regular file or a folder, and any file with another hard link, refuses the restore. **`ownerOnly(stage)`** then keeps the owner bits (`mode & 0o700`, so a script stays executable), makes files at least 0600 and folders 0700; it refuses a link, and a file with another name, instead of following it. A read error in the walk gives a fixed sentence with the error code, never a path from the archive.

`placeRestored(home, extracted, stamp, tops)` moves the verified tree into the home: the old `state.db` is kept as a `VACUUM INTO` snapshot `backups/pre-restore-<stamp>.db`, each replaced folder is renamed under `backups/pre-restore-<stamp>/`, and a failure moves every folder back (newest first). The database is the last step and is not undone by a rename; the snapshot is what remains. Nothing is deleted: the old `state.db` with its `-wal` and `-shm`, and the `search.db*` cache (rebuilt at boot), are renamed into the same folder, so a failure at any step puts everything back, and a failed undo says where the data is. A backup with no regular-file `state.db`, an unexpected folder name, or a stage or `backups/` on another file system than the home is refused before anything moves. A power cut between the folder renames and the `state.db` rename leaves a mixed home: the old data is under `backups/pre-restore-<stamp>*`.

## Restore: `pap restore` (Task 5b)

`pap restore <file> [--replace] [--passphrase-stdin] [--home <abs dir>] [--unit <name>]`. Code: `apps/daemon/src/cli/restore.ts` (command, summary) and `apps/daemon/src/cli/backup/restore.ts` (`restoreBackup`). It stops nothing: it refuses while the daemon runs (stop the unit first, `systemctl --user stop pap.service`, or `pap-preview` for the preview).

Order (each step refuses with a fixed sentence before the next one starts, and the home is as it was after any refusal):

1. Unit and home are resolved like `pap backup` (M6bR50); a unit whose home differs, with no `--home`, is refused.
2. `update/op.lock` (no update, rollback, recover or other restore at the same time), the home is prepared, the **instance lock** is taken (its text, `pap is already running ...`, is shown as it is).
3. An existing `state.db` without `--replace` is refused. With `--replace` the old data is kept (below).
4. A fresh 0700 stage `$PAP_HOME/tmp/.restore-XXXXXX` (same file system as the home). The input must be a regular file, not a symbolic link; it is copied (an encrypted one is decrypted, the passphrase is asked only then) into the stage, and everything below reads that private copy.
5. The reader (`listMembers`) lists the copy; the top-level names must be `manifest.json`, `state.db` (each once, as files), `attachments`, `agents`, `exports`, `secrets`, `pi-agent` (only `pi-agent/sessions`). The **disk gate** refuses when the free space at the home is below the declared bytes plus the copy plus 64 MB (the message gives the numbers).
6. `tar -xzf` into `stage/tree`. The child is reaped and a non-zero exit refuses ("tar could not extract the backup (exit N)").
7. `assertPlainTree`, then `ownerOnly`, with nothing reading an extracted file between them. The two have different messages ("the archive was not restored: ..." and "the extracted files could not be made private: ..."), so a test can tell which layer refused. A walk error is a fixed sentence and never names a path the archive chose.
8. Only now is an extracted file read: the extracted top-level names must equal the listing; the manifest (`format` other than 1 or an unknown key: "a newer pap"); `secrets/` only when the manifest says `included`; every folder listed in the manifest; the `state.db` size and sha256; `schemaIds` not null ("damaged"); every id known to this build ("written by a newer pap"); ids equal to the manifest's.
9. `placeRestored` (tops validated against `HOME_TOPS` and the manifest first; its test-only `rename` parameter is never passed), then the Pi sessions, then the stage is removed (folders the archive made unreadable are chmodded u+rwx after an lstat says they are folders) and both locks are released. This happens on every path, also after a failed placement.

What `--replace` keeps: the old database as `backups/pre-restore-<stamp>.db` and the old `state.db`, `-wal`, `-shm`, `search.db*` and replaced folders under `backups/pre-restore-<stamp>/`. Nothing is deleted and nothing prunes them; the summary prints both paths. A power cut between the folder renames and the `state.db` rename leaves a mixed home whose old data is under those paths. `search.db` is a cache and is never restored; it is rebuilt at the next start.

Pi sessions (M6bR8): files of `pi-agent/sessions/` are copied into `<realpath(PI_CODING_AGENT_DIR)>/sessions` with `COPYFILE_EXCL`, so a file that exists is kept (counted as skipped). A name whose existing parent is not a folder (a file, a symbolic link) is skipped and counted; nothing is written outside that folder. A symbolic link at `sessions` itself skips every file.

Summary: the backup file, `home: <path> (from <source>)`, what was restored, the kept paths, whether secrets were restored and, when not, which are missing ("re-enter agent secrets, rotate webhook secrets"), **"Notifications: each device re-enables when it next opens pap." whenever `secrets/push/vapid.json` was not restored**, the Pi session counts and `start pap: systemctl --user start <unit>`.

Cleanup after a restore removes the stage and the sidecars of the replaced database while both locks are held; do not start the daemon until the summary is printed. A failure of the directory `fsync` after the final rename is reported as a failed restore although `state.db` was replaced: check the summary's kept paths and the home before running it again.

Exit codes: 0 done, 1 a refusal, 64 usage. A wrong passphrase (or a changed file) is "wrong passphrase, or the backup was changed or damaged" and writes nothing: there is no key-check value in the format (M6b-C2), so a typo costs one full read of the backup.
