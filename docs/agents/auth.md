# Auth module

Code: `apps/daemon/src/modules/auth/`. Cookie policy: ADR 0004.

## Flow

- First start: no owner, so the daemon holds a one-time setup token in memory (a restart issues a new one) and `setupUrl()` returns `<publicOrigin>/setup#token=...`. The composition root prints it once with `logger.info("setup_url", { url })`; the field is `url`, never `token`, so the logger does not redact it. Nothing else may log it.
- `POST /auth/setup` verifies the token by SHA-256 digest in constant time, creates the single owner (12+ characters, scrypt N=2^15 r=8 p=3, parameters stored in the hash) and consumes the token.
- Sessions: opaque 32-byte id in `pap_session`, stored as SHA-256, 30-day expiry that slides at most once a day from `clock.now()`. `GET /auth/status` re-issues the cookie so the browser copy slides too.

## Open sockets and revocation

- `/ws` authenticates at the upgrade, and then again before every text frame and on every keepalive tick (`kernel/ws/ws-server.ts`; the check is the same session lookup the upgrade uses, `authenticateSession`). The socket keeps only the `pap_session` value of its upgrade, in memory (`sessionValueOf` picks it out of the `Cookie` header; the rest of the header is dropped): it is never logged, stored or sent.
- A failed check answers the request in flight `unauthenticated` (a malformed frame gets no answer), drops the socket's subscriptions at once, closes with code 4401 (`CLOSE_UNAUTHENTICATED`) and cuts the connection after the 1 s close grace if the peer does not answer. So `POST /auth/logout`, an expiry or a deleted session row end an open socket within one request or one 15 s tick.
- The web client needs nothing special: a dropped socket makes it probe `GET /ws`, which answers 401 for a dead session, and the connection goes to `signed-out`.
- A check that throws (database trouble) does not close the socket: the request is answered `internal` and not dispatched, a tick logs `ws_authenticate_failed` and tries again at the next one. Only request frames slide the session expiry, like any other request: the keepalive tick checks with `slide: false`, so an idle socket never keeps a session alive (it ends at its expiry, at the latest on the next tick after it). On a read-only database (a newer pap wrote it) the slide is skipped, not failed: `authenticate` ignores a read-only error from `extendSession` and the caller is still known, so frames and ticks keep working; any other write error still propagates.

## Step-up: `POST /auth/confirm`

- Body `{ "password": "..." }`, cookie `pap_session` required (401 without a live session). The password is checked like a sign-in (dummy hash path for timing, counted before the hash) but counted on the session's own key, so it neither depends on nor delays any sign-in. A good password answers 204 and marks that browser session for 5 minutes: `Caller.stepUpUntil`, kept in memory by session id hash and dropped at sign-out, revocation and passkey removal. A restart forgets every mark. An audit line `step_up` is written. Tokens never carry a mark.
- `auth.tokens.create` and `auth.passkeys.remove` answer `step_up_required` until the mark is live (and `forbidden` for a token caller). Device revocations need a browser session but no mark.

## Throttles

`createAuthThrottles(clock)` (`throttle.ts`) makes three tables of at most 10 000 keys each. A failure doubles the wait from 1 s to 60 s; a key is forgotten after 5 idle minutes or a success. A failure is counted before the scrypt or the verification, so parallel guesses queue behind the first.

| Table | Keys | When full | Used by |
| --- | --- | --- | --- |
| `password` | `ip:` and `user:` | refuses | password sign-in of a browser without a known-device cookie; a wrong setup token (`ip:` only) |
| `session` | `session:` and `device:` | refuses | `POST /auth/confirm`, `register/options` (the session key); password sign-in with a valid device cookie (the device key) |
| `passkey` | `session:`, `ip:`, `device:` | evicts the oldest failure | `register/verify` (the session key); `login/verify` (the device key, else the address) |

- `refuses`: only expired entries at the head are dropped, a live lockout is never evicted. When a new key does not fit, the attempt is refused before any hash with 429 and the longest wait, and `auth_throttle_full` is logged (no key, no address, at most once per 10 s). `evicts`: the passkey table drops the oldest failure, because nothing behind it is a guess to protect and a spray must not lock the recovery path; a spray can only loosen a limit there.
- `/auth/setup` answers 401 without counting once an owner exists, so a spray against it costs nothing and fills nothing.
- Keys are built in `throttle-keys.ts`. `ip:` is the socket address, never a forwarded header (R72): an IPv4 address as is, an IPv4-mapped IPv6 address as its IPv4, any other IPv6 address by its first 64 bits (`ip:2001:db8:1:2::/64`), since one host holds a whole /64. `user:` is the lower-cased account name. `session:` is the hash of the session's id hash, never the cookie. `device:` is the nonce of a known-device cookie, in hex.
- Why the tables are apart: a table that anybody can fill (the password table, by spraying addresses or names) must never hold keys that only a valid cookie can mint. If it did, its full-table refusal would lock the owner's own browser out. The session table is filled only by sessions and device cookies that exist, and the passkey table evicts. A lockout in one table never blocks another route: password failures do not block passkey sign-in, passkey failures do not block password sign-in, and neither blocks step-up or enrollment.
- Behind a reverse proxy every client shares the proxy's address, so one noisy client can hold the `ip:` key of the others until `trustProxy` exists. A known device is not behind that key.

## Known devices

Code: `known-device.ts`. Without it, anyone who knows the owner's username keeps the `user:` key armed and the owner's password sign-in nearly always lands on a throttled key.

- A successful sign-in (password, passkey or setup) gives the browser a `pap_device` cookie when the request carried no valid one for that account. Value: base64url of a 16-byte random nonce and the first 16 bytes of HMAC-SHA256(key, `"pap-known-device" 0x00 userId 0x00 nonce`), 43 characters. Attributes: `HttpOnly`, `SameSite=Strict`, `Path=/auth`, `Max-Age` 400 days, `Secure` by the session cookie's rule (ADR 0004, `--insecure-http` included).
- The key is 32 random bytes in `$PAP_HOME/secrets/device.key` (0600, created with `O_EXCL`, never logged). A file of another length, a symlink, or one that group or others can read (it may have leaked, and a leaked key mints unlimited cookies) is replaced and `device_key_replaced` is logged; every known device is forgotten with it. The key outlives restarts, so known devices do too. The cookie is compared in constant time.
- The cookie is not a credential. It never signs anybody in and never skips the password or the passkey check; it only chooses a throttle key. Password sign-in: a cookie valid for the account the request names uses the key `device:<nonce>` in the `session` table; otherwise the shared `ip:` and `user:` keys. Passkey sign-in: the account of the presented credential id is looked up before verification; a cookie valid for it uses `device:<nonce>` in the `passkey` table, otherwise `ip:`. A forged, truncated, expired-by-the-browser or other-account cookie, or an unknown name, falls back to the shared keys silently and answers exactly like no cookie. When the header repeats `pap_device` (a cookie planted from a narrower path is sent first) every value is tried, up to 16, and the first that validates counts.
- Effects: failures from other addresses or against the same username cannot lock a known browser; its own failures lock only itself (1 s doubling to 60 s), wherever it connects from. Step-up and enrollment need no cookie: they already use the session's own key. All four routes (sign-in, passkey sign-in, step-up, enrollment) are closed to the denial of service by a stranger; the one remaining risk is the used-nonce map of the passkey sign-in, which someone who knows a registered credential id can fill (see Passkeys, sign-in challenges).
- What a stolen cookie gives: a stream of password guesses, within its own `device:` key (doubling to 60 s), from any address, escaping the `user:` and `ip:` keys; and the ability to keep the owner's known browser locked by failing on that key until the browser's cookie is cleared or the key is reset (`pap passkey reset`, Task 18). It grants no access by itself. Only a successful sign-in mints a cookie, so the session table cannot be filled by someone without credentials.

## Events

- Warn events: `auth_login_failed`, `auth_setup_failed`, `auth_passkey_failed`, `auth_throttled` (at most once per address every 10 s), `auth_throttle_full` and `auth_login_challenges_full` (the used-nonce map below is full; both at most once per 10 s, no fields). The first four carry the socket address `ip` and `retryAfterMs`, nothing else: never the username (people paste passwords into it), the password, the token, a cookie or a credential id. `device_key_replaced` carries no field. A successful enrollment writes the info event `auth_passkey_enrolled` with `ip` only. A steady stream of `auth_throttled` is the sign of an attack.

## Devices and credentials

- Every browser session is a "device": a row of `auth_sessions` with a public id (random, shares nothing with the cookie, so it can be shown), the method that opened it (`password`, `passkey`, `setup`), the address, a coarse label of the user agent, and for a passkey sign-in `passkey_ref`, the short id of that passkey. `auth.devices.list`, `auth.devices.revoke` and `auth.devices.revokeOthers` (`auth:read` to list; `auth:admin` and a browser-session caller to revoke) work on them (the id is the public id) and drop the step-up marks of the sessions they delete. Open sockets of a revoked session close on their next frame or keepalive tick.
- `Caller.credentialId` is the credential the request came with: the session's public id for a cookie, the token id for a bearer. `Caller.kind` is `session` or `token`. The transport stamps both; nothing reads them from params.
- `passkey_ref` is the first 32 hex characters of the sha256 of the credential id (`passkeyRefOf`). `auth.passkeys.list` shows only that short id. Removing a passkey deletes every session whose `passkey_ref` is its short id, in the same transaction.
- API tokens (`pap_...`, `tokens.ts`) are stored hashed, with permissions and a mandatory expiry (7, 30, 90 or 365 days), at most 50, shown once, never carry `auth` or `policy:admin` permissions, and use no cookie. Creating one needs the step-up. `pap passkey reset` keeps them unless `--revoke-tokens`.
- Known limits: a persisted receipt of `auth.devices.revokeOthers` replays across two credentials of the same owner (it needs a `commandId` collision); `public_id` of `auth_sessions` is nullable in the migration and a later one makes it `NOT NULL`; `Caller.stepUpUntil` is lost at a restart (the person confirms again).

## Passkeys

Code: `passkeys.ts` (ceremonies), `login-challenge.ts` (stateless sign-in challenges), `passkey-http.ts` (routes), `passkey-store.ts` (table `passkeys`). The library is `@simplewebauthn/server`, pinned to 13.3.3 to match the `@simplewebauthn/browser` 13 the web app uses.

- RP ID is the host name of the public origin; the accepted origins are the allowed origins with that same host name, matched exactly (another port is another origin). An IP-address origin cannot carry passkeys (WebAuthn rejects IP RP IDs): `GET /auth/status` reports `passkeysAvailable: false` and every passkey route answers 404 (the enrollment routes answer 401 first when there is no session). Use a host name (or `localhost`) to enable them.
- `POST /auth/passkey/register/options` and `/register/verify` need a session. `POST /auth/passkey/login/options` and `/login/verify` do not; a successful verify always starts a new session (`startSession`) and sets a fresh cookie, so a cookie sent with the request is never reused or promoted.
- Enrollment needs the password as well as the session (R83). `register/options` takes `{ "password": "..." }` and checks it like a sign-in: the dummy-hash path for timing, counted on the session's own `session:` key in the `session` table (never the `ip:` and `user:` keys), the same fixed 401 `unauthenticated` and `auth_login_failed` log line on a miss, 429 while throttled. No enrollment flow exists until it passes. Why: `pap_session` reaches every server on localhost (ADR 0004), and without this step a stolen session could enroll a software passkey (attestation `none`) that survives logout and the 30-day expiry. Now a stolen session alone cannot add a permanent credential. The flow belongs to the browser session that created it (R85): it stores the sha256 of that session's cookie (its id hash), `register/verify` derives the same hash from the request's own cookie, another session is refused with the fixed 401, and the flow is consumed either way. Passkeys are listed and removed through `auth.passkeys.list` and `auth.passkeys.remove` (below). The web "Add passkey" dialog must ask for the password.
- User verification is required in both ceremonies (R81): `userVerification: "required"` in the options and `requireUserVerification: true` when verifying. A passkey replaces the password, so a stolen authenticator alone must not open the daemon. Consequence: an authenticator without PIN or biometrics (a security key with no PIN set) cannot be enrolled; the enrollment ends in a plain 401.
- Sign-in challenges keep no server state (R82). A challenge is base64url(nonce 16 bytes, expiry 8 bytes, HMAC-SHA256 of the label `pap-passkey-login`, the nonce and the expiry under a 32-byte key made at process start), and the flow id is that challenge. Verifying first looks the credential id up and checks the user handle, then recomputes the HMAC (constant time), checks the expiry (5 minutes) and refuses a nonce already taken; the library then checks that the authenticator signed exactly this challenge. Because nothing is stored per challenge issued, no number of unauthenticated `login/options` calls, from any address or through any proxy, can evict another client's pending sign-in or grow memory. The only memory is the set of nonces answered for a registered credential id (an answer naming an unknown credential is refused before the nonce is looked at, so a spray of garbage records nothing and leaves the challenge unused), kept until five minutes after they would have expired (R85: a clock stepped back by less cannot replay one) and capped at 10 000: when it is full of live entries a new answer is refused (the fixed 401), none is forgotten and `auth_login_challenges_full` is logged. Whoever knows a registered credential id can still fill it, and the passkey table evicts, so it is the log line that shows it. Each answer that fails counts against the sender's throttle. A restart makes a new key, so a challenge issued before it is refused (the page just asks again). A challenge is used up by the first answer for a registered credential, success or failure, and before the slow verification runs.
- Enrollment flows are stored (random id, the challenge, the user, the session id hash), single-use the same way, 5 minutes, at most 100 pending with the oldest evicted. Only a signed-in caller who gave the password can create one, so a flood cannot reach them.
- The signature counter is stored at enrollment and replaced after each sign-in. The library refuses an assertion whose counter did not advance when either side is non-zero (a cloned authenticator); authenticators that always report 0, such as synced passkeys, stay accepted (their replay protection is the single-use challenge). Two parallel sign-ins that present the same counter let one through: the loser finds the stored counter moved and is refused.
- A user handle in the assertion must be the credential's own user (WebAuthn level 2, 7.2 step 6); an assertion without one is accepted, a different one is refused.
- Only the transports WebAuthn defines (`usb`, `nfc`, `ble`, `hybrid`, `internal`, `smart-card`, `cable`) are stored; anything else in the registration response is dropped, and a damaged stored value reads as none.
- A credential id that is already registered is refused with 409 `conflict`; the first row is left untouched. That answer clears the enrollment backoff of the session (the credential was recognised, not guessed).
- Passkey verifications (either ceremony) count on the `passkey` table (see Throttles), never the password keys, in both directions (R80, R81). `register/verify` is keyed by the session, `login/verify` by the known device or else the socket address. Each failure is logged as `auth_passkey_failed` and doubles the wait from 1 s to 60 s; a request inside the wait gets 429 with `Retry-After` and no further log line. The attempt is counted before the slow verification (R85) and the count is cleared on a success or a `conflict`. Malformed bodies and 404s are not counted. The reason the library gave (wrong origin, no user verification, counter) is deliberately neither answered nor logged.
- Management (`passkey-manage.ts`, M5R76): `auth.passkeys.list` (`auth:read`) shows, newest first and at most 100 (so a passkey someone added last is never cut off), `{ id, createdAt, lastUsedAt, transports }` where `id` is `passkeyRefOf(credentialId)`, never the credential id; `lastUsedAt` is written with the counter at each sign-in (M5R78). `auth.passkeys.remove` (`auth:admin`, mutation) needs a browser-session caller and a live step-up (`step_up_required`), then deletes the passkey and every browser session whose `passkey_ref` is that id in one transaction, drops their step-up marks, answers `{ revoked }` (live sessions signed out) and audits `passkey_removed` with the short id and the count. All of it runs before the handler's first await. Open sockets of those sessions close on their next frame or keepalive tick. Another user's id and an unknown id both answer `not_found`, and only after the step-up. The last passkey can be removed: the password stays, and removal always needs the password step-up. Enrollment is audited as `passkey_enrolled`. Every sign-in that succeeds ends in `startSession`, which audits `signed_in` with `{ method, ip }` (password, passkey, setup); `setup` also audits `owner_created`; `policy.revokeRule` audits `rule_revoked { ruleId, tool }` with the caller as actor.
- Verification against the real library, with a software authenticator, is in `passkey-ceremony.test.ts` and `passkey-challenge.test.ts` (helpers in `modules/auth/testing/`, compiled out of the build); browser behaviour is covered by the Chromium virtual-authenticator journey in Task 27.

## Credentials on `/ws`

- One credential per connection: the `pap_session` cookie or `Authorization: Bearer pap_...` (read only from that header, never a query string). A bearer must be `Bearer` and one space and at most 128 non-blank characters; a malformed `Authorization` header counts as absent and cannot hide or replace a cookie. Two `Authorization` headers: 400.
- The upgrade checks in this order (`kernel/ws/ws-server.ts`): 400 or 404 for a bad URL or path; an `Origin` that is present must be allowed, whatever the credential (403, logged `origin_refused`); cookie and bearer together, or two `Authorization` headers: 400 (`conflict`); no `Origin` and no well-formed bearer: 403 (`origin_refused` logged): a browser always sends `Origin` and attaches its cookies by itself, a program presenting a token is not a CSRF vector, so only a bearer may come without one; a protocol other than the current one: 426; then authentication, 401 when the credential is unknown, expired or revoked. So a malformed bearer without `Origin` is a 403, not a 401.
- ADR 0021 records the deviation from spec C 4.4 (bearer tokens without `Origin`, step-up, the throttle keys).
- Every request frame and every keepalive tick re-checks the credential (the tick does not slide), so a revoked or expired token or session closes its socket with 4401. `GET /ws` accepts the same two credentials.

## Tokens and M8's files and terminals

- `TOKEN_PERMISSIONS` drops `auth:*`, `policy:admin`, `pi:admin` and `terminal:*` (`contracts/src/auth.ts:11-17`, M7R39, M8R2): a standing credential makes no code-running change. Every method that edits Pi's configuration, signs in, tests an MCP server, trusts a project or reads a masked Pi file is `pi:admin`, so a token answers `forbidden` and no handler runs; `security/pi-token.test.ts` calls each `pi:admin` method of the catalogue with a token holding every `TOKEN_PERMISSIONS` value and requires at least 35 of them (M7R152). `confirmProtected` is likewise never honoured for a token. A token may hold `files:read|operate`, `vcs:read` and `sessions:operate`.
- A token never sends `confirmProtected` (`forbidden` on any path), never writes a protected name, anything under `<agentDir>` or a `.pi/` folder, and never reads Pi's folder, a `.pi/mcp.json`, a `.mcp.json`, home's dot-entries (when a project is the home folder) or `/proc`, `/sys`, `/dev`, `/run`: those answer `not_found`, so a token cannot tell they exist. Pinned end to end in `apps/daemon/src/security/files-origin.int.test.ts`.
- The HTTP file routes (`GET` / `PUT /files/raw`, `POST /upload`) are cookie-only: a request with an `Authorization` header is `401`, whatever it holds (ADR 0031). A token uses `files.*` over `/ws`.
- A `vcs` subscription of a token is its own filtered stream (`token:<root>`), without the entries its boundary hides (ADR 0032).
- `step_up_required` also guards saves under Pi's folders and `.pi/` (the same 5-minute mark, `files.md`).

## Recovery commands

Code: `apps/daemon/src/cli/{user-add,passkey-reset,read-secret}.ts`, `modules/auth/cli.ts`. They run through the CLI, take the instance lock (M5R133) and so need the daemon stopped; for the preview service run `systemctl --user stop pap-preview` first (a running daemon makes them exit 1 with that hint and change nothing). The lock is taken before the password is asked and held until the command ends.

- `pap user add <username> [--password-stdin]`: creates the owner without the setup URL (a headless install). Refused (exit 1) when any user exists: pap v1 has one owner, and the insert is `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM users)`. The next `pap serve` prints no setup URL. Audit line `owner_created`, actor `cli`.
- `pap passkey reset [--revoke-tokens] [--keep-password] [--password-stdin]`: signs out everywhere. Deletes every passkey, every browser session and `secrets/device.key` (every known device is forgotten; the next daemon start makes a new key), in one transaction. **API tokens are kept unless `--revoke-tokens` is given**: an owner who fears a theft must pass it. A new password is asked unless `--keep-password`; it is checked before anything is deleted. Prints `removed N passkeys, M browser sessions[, K tokens]; password changed|kept`. One audit line `credentials_reset`, actor `cli`, with the counts and `passwordChanged`; no secret.
- The password never comes from argv. `--password-stdin`, or a standard input that is not a terminal: the first line, at most 1 024 bytes (an empty input is exit 1). On a terminal: asked twice, raw mode with nothing echoed, Backspace removes one code point, at most 1 024 characters, Ctrl-C exits 130; the terminal is restored on every path, a stream error included. On a terminal, `--password-stdin` reads a cooked line that the terminal echoes; use the prompt without the flag to hide it. It is 12 to 1 024 characters, like `/auth/setup`. Messages are fixed and never contain the password.
