# Auth module

Code: `apps/daemon/src/modules/auth/`. Cookie policy: ADR 0004.

## Flow

- First start: no owner, so the daemon holds a one-time setup token in memory (a restart issues a new one) and `setupUrl()` returns `<publicOrigin>/setup#token=...`. The composition root prints it once with `logger.info("setup_url", { url })`; the field is `url`, never `token`, so the logger does not redact it. Nothing else may log it.
- `POST /auth/setup` verifies the token by SHA-256 digest in constant time, creates the single owner (12+ characters, scrypt N=2^15 r=8 p=3, parameters stored in the hash) and consumes the token.
- Sessions: opaque 32-byte id in `pap_session`, stored as SHA-256, 30-day expiry that slides at most once a day from `clock.now()`. `GET /auth/status` re-issues the cookie so the browser copy slides too.

## Open sockets and revocation

- `/ws` authenticates at the upgrade, and then again before every text frame and on every keepalive tick (`kernel/ws/ws-server.ts`; the check is the same session lookup the upgrade uses, `authenticateSession`). The socket keeps only the `pap_session` value of its upgrade, in memory (`sessionValueOf` picks it out of the `Cookie` header; the rest of the header is dropped): it is never logged, stored or sent.
- A failed check answers the request in flight `unauthenticated` (a malformed frame gets no answer), drops the socket's subscriptions at once, closes with code 4401 (`CLOSE_UNAUTHENTICATED`) and cuts the connection after the 1 s close grace if the peer does not answer. So `POST /auth/logout`, an expiry or a deleted session row end an open socket within one request or one 15 s tick.
- The web client needs nothing special: a dropped socket makes it probe `GET /ws`, which answers 401 for a dead session, and the connection goes to `signed-out`.
- A check that throws (database trouble) does not close the socket: the request is answered `internal` and not dispatched, a tick logs `ws_authenticate_failed` and tries again at the next one. Only request frames slide the session expiry, like any other request: the keepalive tick checks with `slide: false`, so an idle socket never keeps a session alive (it ends at its expiry, at the latest on the next tick after it). On a read-only database (a newer pap wrote it) the slide is skipped, not failed: `authenticate` ignores a read-only error from `extendSession` and the caller is still known, so frames and ticks keep working; any other write error still propagates.

## Sign-in throttle and its trade-offs

- Keys: socket address (`ip:`) and lower-cased account name (`user:`). Failures double the wait from 1 s to 60 s; a key is forgotten after 5 idle minutes or a success. A failure is counted before the scrypt, so parallel guesses queue behind the first.
- Anyone who knows the owner's username can deny the owner password sign-in indefinitely. Every failure re-arms the `user:` key, and a poller that retries the moment each window reopens wins almost every window, so the owner's own attempt nearly always lands on a throttled key (at most 60 s per window, but a new one opens each time). The password is never bypassed, only made unusable while the attack lasts. Passkey sign-in is the recovery path: it has its own throttle and is never gated by the password keys, so enroll a passkey right after setup (and before you need it: enrolling asks for the password, which the same attack keeps throttled). The recovery path has one limit of its own: the passkey throttle is also keyed by socket address, and behind a reverse proxy or `tailscale serve` every client shares one address, so an attacker who keeps failing passkey verifications can hold that key too. Flooding `login/options` cannot (it keeps no state), failing verifications can.
- The IP key is the socket address. Behind a reverse proxy every client shares the proxy's address, so one noisy client can throttle all of them until `trustProxy` exists.
- Because the lockout is cheap and otherwise invisible, four warn events exist: `auth_login_failed`, `auth_setup_failed`, `auth_passkey_failed` and `auth_throttled`. Each carries the socket address `ip` and `retryAfterMs`, nothing else: never the username (people paste passwords into it), the password, the token or a credential id. A successful enrollment writes the info event `auth_passkey_enrolled` with `ip` only. `auth_throttled` is written at most once per address every 10 s, so a client retrying every few milliseconds cannot flood the log; a steady stream of it is the sign of an attack.

## Passkeys

Code: `passkeys.ts` (ceremonies), `login-challenge.ts` (stateless sign-in challenges), `passkey-http.ts` (routes), `passkey-store.ts` (table `passkeys`). The library is `@simplewebauthn/server`, pinned to 13.3.3 to match the `@simplewebauthn/browser` 13 the web app uses.

- RP ID is the host name of the public origin; the accepted origins are the allowed origins with that same host name, matched exactly (another port is another origin). An IP-address origin cannot carry passkeys (WebAuthn rejects IP RP IDs): `GET /auth/status` reports `passkeysAvailable: false` and every passkey route answers 404 (the enrollment routes answer 401 first when there is no session). Use a host name (or `localhost`) to enable them.
- `POST /auth/passkey/register/options` and `/register/verify` need a session. `POST /auth/passkey/login/options` and `/login/verify` do not; a successful verify always starts a new session (`startSession`) and sets a fresh cookie, so a cookie sent with the request is never reused or promoted.
- Enrollment needs the password as well as the session (R83). `register/options` takes `{ "password": "..." }` and checks it exactly like a sign-in: the dummy-hash path for timing, counted on the password throttle keys (`ip:` and `user:`), the same fixed 401 `unauthenticated` and `auth_login_failed` log line on a miss, 429 while throttled. No enrollment flow exists until it passes. Why: `pap_session` reaches every server on localhost (ADR 0004), and without this step a stolen session could enroll a software passkey (attestation `none`) that survives logout and the 30-day expiry. Now a stolen session alone cannot add a permanent credential. The flow belongs to the browser session that created it (R85): it stores that session's id hash, `register/verify` from another session is refused with the fixed 401, and the flow is consumed either way. Passkeys are listed and removed through `auth.passkeys.list` and `auth.passkeys.remove` (below). The web "Add passkey" dialog must ask for the password.
- User verification is required in both ceremonies (R81): `userVerification: "required"` in the options and `requireUserVerification: true` when verifying. A passkey replaces the password, so a stolen authenticator alone must not open the daemon. Consequence: an authenticator without PIN or biometrics (a security key with no PIN set) cannot be enrolled; the enrollment ends in a plain 401.
- Sign-in challenges keep no server state (R82). A challenge is base64url(nonce 16 bytes, expiry 8 bytes, HMAC-SHA256 of the label `pap-passkey-login`, the nonce and the expiry under a 32-byte key made at process start), and the flow id is that challenge. Verifying recomputes the HMAC (constant time), checks the expiry (5 minutes) and refuses a nonce already taken; the library then checks that the authenticator signed exactly this challenge. Because nothing is stored per challenge issued, no number of unauthenticated `login/options` calls, from any address or through any proxy, can evict another client's pending sign-in or grow memory. The only memory is the set of nonces somebody answered, kept until five minutes after they would have expired (R85: a clock stepped back by less cannot replay one), and each answer that fails counts against the sender's throttle. A restart makes a new key, so a challenge issued before it is refused (the page just asks again). A challenge is used up by the first answer, success or failure.
- Enrollment flows are stored (random id, the challenge, the user), single-use the same way, 5 minutes, at most 100 pending with the oldest evicted. Only a signed-in caller who gave the password can create one, so a flood cannot reach them.
- The signature counter is stored at enrollment and replaced after each sign-in. The library refuses an assertion whose counter did not advance when either side is non-zero (a cloned authenticator); authenticators that always report 0, such as synced passkeys, stay accepted (their replay protection is the single-use challenge). Two parallel sign-ins that present the same counter let one through: the loser finds the stored counter moved and is refused.
- A user handle in the assertion must be the credential's own user (WebAuthn level 2, 7.2 step 6); an assertion without one is accepted, a different one is refused.
- Only the transports WebAuthn defines (`usb`, `nfc`, `ble`, `hybrid`, `internal`, `smart-card`, `cable`) are stored; anything else in the registration response is dropped, and a damaged stored value reads as none.
- A credential id that is already registered is refused with 409 `conflict`; the first row is left untouched.
- Passkey verifications (either ceremony) count on a throttle of their own, keyed by the socket address only, never by account and never shared with the password keys, in both directions (R80, R81): password failures do not block passkey sign-in, passkey failures do not block password sign-in. Each failure is logged as `auth_passkey_failed` and doubles the wait from 1 s to 60 s like the password throttle; a request inside the wait gets 429 with `Retry-After` and no further log line, so the failure lines are the whole signal. The attempt is counted before the slow verification runs (R85: parallel guesses queue behind the first, as for passwords) and the count is cleared on a success. Malformed bodies and 404s are not counted. The reason the library gave (wrong origin, no user verification, counter) is deliberately neither answered nor logged.
- Management (`passkey-manage.ts`, M5R76): `auth.passkeys.list` (`auth:read`) shows `{ id, createdAt, lastUsedAt, transports }` where `id` is `passkeyRefOf(credentialId)`, never the credential id; `lastUsedAt` is written with the counter at each sign-in (M5R78). `auth.passkeys.remove` (`auth:admin`, mutation) needs a browser-session caller and a live step-up (`step_up_required`), then deletes the passkey and every browser session whose `passkey_ref` is that id in one transaction, drops their step-up marks, answers `{ revoked }` (live sessions signed out) and audits `passkey_removed` with the short id and the count. All of it runs before the handler's first await. Open sockets of those sessions close on their next frame or keepalive tick. Another user's id and an unknown id both answer `not_found`, and only after the step-up. The last passkey can be removed: the password stays, and removal always needs the password step-up. Enrollment is audited as `passkey_enrolled`.
- Verification against the real library, with a software authenticator, is in `passkey-ceremony.test.ts` and `passkey-challenge.test.ts` (helpers in `modules/auth/testing/`, compiled out of the build); browser behaviour is covered by the Chromium virtual-authenticator journey in Task 27.

## Credentials on `/ws`

- One credential per connection: the `pap_session` cookie or `Authorization: Bearer pap_…` (read only from that header, never a query string). Both: 400.
- An `Origin` that is present must be allowed whatever the credential (403, `origin_refused`). Without `Origin` only a bearer is accepted (a browser always sends it; a program presenting a token is not a CSRF vector). ADR 0021 records the deviation from spec C 4.4.
- Every request frame and every keepalive tick re-checks the credential (the tick does not slide), so a revoked or expired token closes its socket with 4401. `GET /ws` accepts the same two credentials.
