# Sessions module

Code: `apps/daemon/src/modules/sessions/`. Identity of a session and its Pi file: ADR 0005. Worker protocol: ADR 0001.

## Pieces

- `service.ts`: the one place that knows which workers are up (`live`), which are coming up (`starting`, `reopening`) and when a session's Pi file is remembered. RPC handlers (`rpc.ts`) only decode, call it and let `PapError` through.
- `live-session.ts`: one worker's session. Sends `init`, tracks status, dialogs, run boundaries and the run's messages; everything it knows leaves through `publish` (stream) and `record` (table `session_events`).
- `run-tracker.ts` (run start/end), `dialogs.ts` (cards), `run-view.ts` + `snapshot.ts` + `transcript.ts` (what a subscriber starts from), `pi-files.ts`, `cwd.ts`, `store.ts`.
- `testing/` helpers are for tests only (the build and the lint keep them out of production code): `service-bed.ts` (real database and hub, fake workers), `live-bed.ts`, `helpers.ts`. A helper in `testing/` may import a module only through its `index.ts`, so the test files import `service.ts`, `store.ts` and `live-session.ts` themselves and pass the factories in.

## Protocol v2 (ADR 0008)

- `PROTOCOL_VERSION` is 2 (`packages/contracts/src/frames.ts`). The snapshot (`streams.ts`) carries `status`, `rows`, `dialogs` (+ `hiddenDialogs`), `partial`, `queue`, `statuses`, `widgets`, `title`, `panels`, `notices` (+ `decorationsTruncated`), `history`, `activity`, `leafId` and `name`.
- A transcript row is `TranscriptRow {entryId | null, message}`: the Pi message and the id of the Pi entry it came from, once known. Rows are live (from `message_end`, bound to their entry by the `entry` event) or read from the file; a summary (compaction, branch) is a row too.
- Pap's own notices and status causes carry a `code` (`SERVER_CODES` in `streams.ts`, optional on the wire) and `params` beside the English text; extension-written text has none. A new fixed sentence needs a code, and an English and French entry in the web's `catalog/server.ts`.
- Stream events: `snapshot`, `status`, `pi`, `dialog_open`/`dialog_closed`, `notice`, `row`, `entry`, `queue`, `status_bar`, `widget`, `title`, `editor_text`, `panel`/`panel_closed`, `name`, `activity`. Extension UI limits live in `UI_LIMITS` (`streams.ts`); the daemon rebuilds every decoration from the fields it knows and cuts them to it.
- Run origin on the wire: `run_start {origin}` is recorded `user` or `extension` today; spec C also names `trigger` and `task`, which have no producer yet.

## Capacity

A worker counts against `maxWorkers` from the moment it is forked: `starting` is a set, checked and filled in the same tick, so concurrent creates cannot both pass (R9). It leaves `starting` only after the session is in `live`. `minFreeMemMb` is checked at the same place. Both refuse with `capacity`; nothing waits in a queue. After `shutdownAll` every new start is refused with `capacity` too. The `capacity` error carries `workers: { used, max }` (`modules/sessions/service.ts:56`), daemon-wide rather than per owner; the session screen shows it as "n / n workers". After a worker crash, the crash banner's Retry calls `sessions.reopen {sessionId}` (`sessions:operate`, owner check, `not_found` for another owner's): it goes through the same `ensureLive` path as `prompt`, so it respects the cap, and concurrent reopens share one start.

A worker that does not say `ready` within 30 s (`READY_TIMEOUT_MS`) is stopped and the start fails with `worker_failed`. A worker that exits before `ready` (exit 70 for a bad init, policy or `PI_CODING_AGENT_DIR`) gives the same fixed `worker_failed`; the log has its exit and the last 2000 characters of its output, never the client.

A failed start of a new session leaves nothing: the row is inserted only when the worker is ready, and nothing is published or recorded for a row that is not stored (the hub keeps a channel for every key it is asked to publish for, so a ghost key would stay). What the worker says before that point (an extension failing at start-up, a policy audit line) is held in a bounded buffer (`pre-ready-buffer.ts`: 32 items, 256 KB, earliest kept, the rest counted in a `session_start_events_dropped` warning) and replayed right after the insert (events to the hub and the journal; a policy audit line goes to the audit module, which stores it in the `audit` table, not in `session_events`); a failed start drops it with the rest. The status at `ready` is not held, a snapshot carries it. Like the events of a reopened session, the replayed ones reach a subscriber that resumes from the start of the stream (`after.seq` 0 of this epoch); a cursor-less first subscriber gets a snapshot, which carries the last 20 notices (the live session records every notice it publishes, start-up ones included, in `notices.ts`'s ring).

## Runs

- A run starts at `agent_start` and ends when `agent_settled` is confirmed by up to three `get_state` probes 100 ms apart; new input cancels the probes. Spec C §2.4 says what happens when no probe sees Pi idle: the run stays open until the next `agent_settled`.
- Abort is a mutation (R110): it carries a `commandId`, so a client that did not see the answer and sends the same command again gets the receipt back and does not stop a newer run. `get_state` first; compaction, or no answer within 2 s, terminates the worker. If Pi shows nothing running, the run the daemon still holds open ends (`run_end {aborted: true}`, status `idle`) and the worker is left alone (R111); `abort` is sent to Pi all the same, fire-and-forget, because the answer can be stale: Node delivers each record before the continuation of the response before it, so an idle `get_state`, the prompt's `started` and `agent_start` can arrive together and `abort()` resume after all three. The run generation (bumped by every `agent_start`) is read before `get_state` is sent and `finish` ends nothing if it changed, so the status never reads `idle` while Pi streams (R111b). Otherwise `abort` is sent and the worker is terminated if the run has not settled 5 s later. One deadline, not two.
- A run left open by input Pi rejected or handled without an agent turn (no `agent_settled` will come) is closed without anyone pressing Stop: when a prompt is answered rejected or `handled` while the tracker has a run open, the daemon probes `get_state` (not awaited, so the answer to the client does not wait) and ends the run if Pi is idle, unless an `agent_start` came in meanwhile (R111b).
- `prompt` has no timeout (R99): an extension command answers only when it ends, possibly after a dialog the user takes minutes to answer. The pending request ends with the worker (`worker_failed`). Dialog answers do not wait for it. `get_state` and `abort` are internal and their timeouts are handled where they happen; the methods that wait for an answer from the worker (`clearQueue`, `rename`, `autoName`, `exportHtml`) can answer `timeout`, and so could any future one. A `timeout` means "outcome unknown" (R105): the dispatcher stores no receipt for an error, nothing retries, and the client has to look at the session's state before it sends the command again.
- Stop before the run exists (R113, `live-run.ts`): while a prompt is on its way or was answered `started` and has no `agent_start` yet, `abort()` cannot find a run. It sends one `abort` at once (a no-op if Pi is idle), sets `abortAtStart` and sends a second when `agent_start` arrives (idempotent). The wait for `agent_start` is bounded by `ABORT_SETTLE_MS` (5 s); past it the flag is dropped (`abort_at_start_expired`), so a late Stop never hits an unrelated run. `promptPending()` is the same window.
- Run origin (`run_start {origin}`): `user` if a prompt is in flight or was answered `started` when `agent_start` came, otherwise `extension` (logged `run_started_by_extension`). Nothing produces `trigger` or `task` yet.
- `starting` on reopen (R112): a cold session whose worker is being brought up again publishes `status starting` to whoever watches it, and the service reports `starting` while the reopen is pending (`reopening` map; two commands that arrive together share one start). A new session has no subscriber yet, so it publishes nothing.
- Stop while a navigation or compaction has no answer stops the worker (Task 17a, see "Session commands").
- A crash closes every open dialog, records `run_end {interrupted: cause}` and `worker_exit`, publishes `status cold` with a readable cause and removes the worker from `live`. Nothing restarts it; the next prompt does, on the same Pi file (or a new Pi session for a draft).

## Dialogs

At most 64 open dialogs and 8 MiB per session; extra ones are answered `cancelled` at once. Methods other than `select`, `confirm`, `input` and `editor` are decorations (`setStatus`, `setWidget`, `setTitle`, `set_editor_text`, `notify`: rebuilt by `decorations.ts` into their own stream events, never forwarded as `pi` events; a malformed one is dropped, logged as `decoration_refused` once every 10 s with the count) or, if unknown, cancelled. The worker's text is untrusted: a dialog is rebuilt from the fields we know, text is cut to the limits of `Dialog` and then to 1 000 000 bytes as serialised (a character can take up to six bytes once escaped), so one dialog is never more than one frame. A `select` whose options do not fit (more than 100, or one longer than 4096 characters) is cancelled instead of cut, because the extension is waiting for one of those exact strings. Every cancelled dialog is answered, but the log line and the `notice` for a cancel (by size or by the limit) come once every 10 s per reason and session, the log line carrying how many it left out (R111): an extension that asks in a loop cannot flood the screen or the log. Extension errors reach the client as a fixed sentence with, at most, the event name when it looks like one; the worker's text only goes to the log, clipped to 2000 characters (R66).

## What a subscriber starts from

- `snapshot` is the current status, the open dialogs and about the last 75 messages, held under 1 MB: approvals first, then the other dialogs (a decoration, a panel or the partial message and the rows come after, in that order of claim on the budget), then messages newest first, contiguous. A row over 256 KB goes in as a placeholder `{role, timestamp, omitted: true, bytes}`, so a huge tool result never empties the snapshot (R109). An unknown session id is `not_found` (R79), so a client cannot make the hub create channels.
- Messages come from the Pi file through the SDK helpers (never written, never migrated on disk), and only as many bytes of it as are needed. Pi writes an entry after its subscribers saw it, so during a run the file is read only up to its size when the run began, and the run's own messages (from `message_end`) follow it (R38); the run keeps at most 75 of them and 1 MiB (a message over 256 KB as its placeholder), measured before it is kept. Once the run has settled the file is complete. A hot session's snapshot also comes from the file, where spec C §3.3 says `get_entries{since}`; that is M2.
- Entry ids and the leaf (Task 10b, ADR 0007): the file is not read for them. pi-host (`entry-tracker.ts`) checks `SessionManager.getLeafId()` one macrotask after an event that may have appended and sends the new entries as slim `entry_appended` records (up to 4096 per walk, 128 per macrotask), or a `leaf` record. The live session turns an entry into an `entry` stream event (the client binds the id to the newest unbound message with the same role and timestamp, or the same `toolCallId`) and a compaction or a branch summary also into a `row`; Pi's own `entry_appended` is never forwarded. `leafId()` follows `ready`, entries and `leaf` records; during a run the snapshot reads the file along the leaf the run began at (`leafAtStart`). A `leaf` record with `resync` (a walk of more than 4096 entries) means the run's rows keep no id until a client subscribes again after the run (only logged).
- Reads (Task 11), all `sessions:read`, idempotent and owner-checked (`not_found` for another user's session): `sessions.history {before, limit}` gives older rows of the branch above `before` (default 50, at most 100 rows and 900 000 JSON bytes; the oldest rows go first and `oldestEntryId`/`turnsBefore` follow); `sessions.toolOutput {toolCallId}` gives the whole result found along the active branch (text at most 800 000 JSON bytes, `truncated` says when it was cut; arguments at most 64 KiB); `sessions.branches` gives the leaf and the fork points under 900 000 JSON bytes (oldest points first out; a choice whose id is over 128 characters is skipped; `truncated` says when anything was left out). Sizes are JSON bytes (`clipJsonText` in `service-reads.ts`), never characters. The web view counts snapshots in `SessionView.generation`; `prependHistory` drops a page asked for another generation or cursor (M2-RT-12).
- Steering queue (Task 12): `queue-guard.ts` counts what Pi holds (its `queue_update`: previews, count, bytes) plus the prompts still on their way, and refuses a prompt past 128 messages or 32 MiB with `queue_full` before anything reaches the worker (it may refuse a little early, never late). A `queue_update` becomes `{kind: "queue", queue}` (the raw event is not forwarded; previews cut to 2000 characters and kept as a contiguous prefix under 64 KiB of JSON, so they never crowd the snapshot's approvals), and the snapshot carries the same view; a dead worker empties it. `sessions.clearQueue` (`sessions:operate`, mutation with `commandId`, errors `not_found`/`worker_failed`/`timeout`: after a `timeout` the outcome is unknown and is not retried) returns the cleared texts, re-fitted by the daemon in JSON bytes with `truncated`; a cold session answers empty lists without a worker. Stop is `clearQueue`, then `abort`.
- Pi puts its system prompt in the file as the first message (`role: "system"`, about 9 KB in the default prompt, and it may embed the user's AGENTS.md). It is internal: the daemon leaves it out of the snapshot and of the `message_start`/`message_end` events (R107). M2 may add an explicit "show the system prompt" request.
- Text, thinking and tool-call deltas are merged per content block and sent at most every 50 ms (`coalescer.ts`, on the kernel `Clock`); a tool's progress keeps only its latest update and is dropped when the tool ends; 256 KiB of pending text or 256 pending items send at once. Every event the live session publishes (status, dialogs, notices, other Pi events) sends the pending deltas first, so text never arrives after what follows it, and a worker exit sends them before the `cold` status. The snapshot's `partial` reply (`partial.ts`) is rebuilt from published events only, never from pending deltas, so a snapshot plus the frames after it give the reply exactly once (M2R43). A reply past 256 KiB leaves the snapshot until the next assistant message (M2R42); a client then has it whole from `message_end`. Merging loses no field: no `message_update` ever carries Pi's running `message` (pi-host strips it), so a merged event is the delta plus the latest `usage`. Before it is sent, a tool's result is cut to 8 000 characters (progress to its last 2 000, arguments to 8 000 per string, details over 8 KiB dropped) with `papTruncated` saying how much there was, a nested tool's progress is not sent, and `text_end` / `thinking_end` lose their `content` (`wire-clip.ts`, M2R44-45); the whole output is to be fetched with `sessions.toolOutput`.
- `agent_end` and `turn_end` reach the daemon without `messages` and `toolResults` (R103, `toWireEvent` in pi-host): they grow with the run. Each message is in its `message_end` and each tool result in the `toolResult` message of its `message_end`; `tool_execution_end` carries no result. `turn_end` keeps its assistant `message`, clipped like a `message_end` (a 900 KB `write` call is not sent twice).
- Events are sent whole or not at all: every Pi event is measured after it is clipped (`wire-clip.ts`: a `text_end` has no `content`, a `toolcall_end` has its arguments cut to 8 000 characters per string), and one still over 1 MB (a huge `text_delta`, a message with thousands of large arguments) is dropped with a `notice`, at most one notice and log line every 10 s.
- The SDK that reads the files is loaded the first time a client subscribes, not with the module (R108): `subscribe.session` first awaits `prepareSubscription` (owner check and the memoized `import()`), then opens the subscription, and the hub's synchronous snapshot provider reads what that loaded (without it, `snapshot` answers `internal` rather than an empty transcript). Measured on this machine: importing the sessions module takes the process from 44 to 96 MB resident in about 0.1 s (it was 163 MB and 0.65 s with the SDK imported statically; the 52 MB left is zod and `node:sqlite`); the first subscription pays about 90 MB and 0.55 s once.

## Sidebar marks and the `shell` stream (M4)

- Columns added by `202610121500_session_marks.sql`: `project_id`, `preview` (the start of the first user message, at most 120 characters, written once), `pin_rank` (1..50), `archived_at`, `settled_at`, `settled_auto` (the 3-day rule settled it, not the person), `unsettled_at` (when the person last un-settled it or a snooze woke), `snoozed_until`, `pending_pi_session_id`.
- `pending_pi_session_id` (RT-01): the first Pi session id a worker reported at `ready` for a row that has no Pi file yet (a draft); a later id never replaces it (M4R60). Every id reported (at most 32 per draft) is also in `session_pending_ids`, which `findByPendingPiId` reads: a draft prompted again after a crash gets a new worker with a new id, and the first worker's file still binds back to the draft under its own owner, not to the instance owner as a new session. It is stored by `setPendingPiId`, only `WHERE pi_path IS NULL`, and is not `pi_session_id` because the table's CHECK pairs that column with `pi_path`. After a restart the scan port finds the draft by `findByPendingPiId` and binds the new file to it, under the draft's own owner, so a draft never becomes a second adopted session. A failed write is logged (`session_pending_id_not_stored`) and costs only that restart case. **The store is not owner-checked; the service is:** `marks-store.ts` reads and writes by session id, and every path from a client goes through `owned(sessionId, caller)` in the service (`not_found` for another user's session).
- Marks and their rules are `applyMark` in `packages/contracts/src/marks.ts`, the one rule set: the daemon writes with it and the browser shows the change with it before the answer. Pinning clears archived and settled; archive, settle and snooze unpin; archive and settle clear a snooze; a snooze is 1 minute to 366 days and refused on an archived session (`bad_request`); 50 pins at most (`limit_reached`); `restore` puts a `MarkState` back (Undo). `sessions.mark` changes state synchronously, before its first `await` (M4R126).
- `shell` stream (`subscribe.shell`, `sessions:read`): the key is the caller, never a param. The snapshot holds the owner's pinned sessions then the newest not archived (at most 550), every project of the owner with an active session (up to 500, in the person's order), `more`, `moreProjects` and `archived`; it is fitted under `PAGE_BYTES`. Events: `session`, `project`, `counts`. `createShellPublisher` batches what changed in one turn of the loop (sessions, then projects, then counts) and contains a failing item (`shell_publish_failed`, rate-limited). `sessions.listArchived` pages the archive.
- Auto-settle (owner Q2): `organiser.ts` sweeps every hour (batches of 500) and settles a session idle 3 days or more that is not pinned, snoozed, settled or archived, and was not un-settled in the last 3 days. The first boot after the install settles every such session at once. Any pap or CLI write un-settles it (`activity`, called by the worker path and by the scan port's `touched` when entries were read on). A wake timer follows the earliest snooze and clears it. Both are off in read-only mode, and a SQLite error in a timer is logged (rate-limited) and re-armed.
- Scan port (`scan-port.ts`, `SessionsScanPort`): `claim(path, header)` is synchronous, so one Pi file never becomes two sessions. Order: a row already bound to the path; a row bound to the header's Pi id (a different path: `duplicate_id`); a path outside the agent's `sessions/` (`not_pi_file`); a live worker that reported this Pi id; a draft with this pending id; otherwise adopt, owned by `ownerId()` (the oldest user; none yet: `wait`). The adopting insert, the project assignment and `onAdopted` run in one transaction; a failure leaves no row and the next pass tries again. `onAdopted(sessionId)` is wired in `daemon.ts` to `policy.markTainted(owner, id, 0)`: an adopted session starts tainted, and a failure rolls the adoption back. In read-only mode `claim` answers `wait`.

## Outside writes (Task 29, owner Q13)

- `outside-writes.ts` and `scan-port.ts` remember, per session (1024 at most, oldest dropped), the latest write the scanner saw that pap did not make. `outsideWrite` is true while that write is under `OUTSIDE_WRITE_MS` (2 minutes) old; the snapshot carries it as `outsideWrite` and the session screen shows a notice. It is not a lock: nothing stops a second writer. Tool results added outside pap taint the session (decision 75 Q5, M7R27, MC19; `outside-taint.ts`, `outside-tail.ts`). `processFile` passes `toolResults` to `touched` when a chunk read on from a stored cursor (or from a replaced file) holds a `message` entry whose message has `role: "toolResult"`, or a line it could not read (bad JSON, over the line cap: fail closed). It does so BEFORE it saves the position: when the taint cannot be stored, `touched` throws, the position stays, and the next pass (the watcher, or the 60 s reconcile) reads the same bytes again. For the taint, a write is outside when no pap worker is live or starting and its mtime is after the session's last worker end and after `sessions.pap_wrote_at` (stamped at every worker exit and when a fork or clone makes a file, with the file's size in `pap_wrote_size`); there is no `startedAt` term, so an append made while the daemon was down taints at the next scan, and pap's own last writes before a restart do not. The notice of the previous paragraph keeps its own test (after the daemon's start). The module raises the taint with no epoch (a late outside write after a Clear taints again), logs `session_tainted_outside` and audits `policy` / `tainted_outside` (actor `system`) when it raised. A session whose taint failed is remembered (at most 1024, never evicted, a full set drops the new one with a rate-limited log) and tainted on the next touch even if a worker holds it by then. Before a cold session's worker is spawned (`beforeStart` in `service-adopt.ts`) an owed taint is made, then the file's mtime is compared with the later of `sessions.updated_at` (the scanner has decided up to there; a Clear does not move it) and `pap_wrote_at`: at or below it, nothing is read, so a Clear made while the session is closed survives the next start, and old sessions the scanner has caught up on are not tainted. Above it, a row with no stamp is tainted (nothing says where pap's bytes end), and a stamped row has the bytes from `pap_wrote_size` on read (at most 16 MiB): tool results, an unreadable or unfinished line, a shorter file or an unopenable one taint the session. A link or a non-file is always `changed`. A taint that cannot be stored refuses the start (`internal`). Residuals: mtime granularity (a write in the same millisecond as the mark, or an mtime set back by `cp -p`, `rsync -t` or a sync tool, counts as unchanged); after a Clear, a text-only append re-reads from the old stamp and taints again if tool results lie there. Not covered: text-only continuations; writes made while a pap worker held the session; a crash leaves pap's own unscanned tool results to taint after the restart (one Clear); a first index or a rebuilt index (the history is read whole, so a CLI continuation made before a rebuild is lost to it); `bashExecution`, `custom` and `custom_message` messages, `context_edit` replacements and `system` messages that add tools.
- A write is pap's own, and does not count, when it comes from: a live worker (`live` has the session); a starting worker (between the spawn and `live`); a worker that has ended (writes up to its end time, `workerEnded`); a fork or clone file (`onMade` in `forks.ts` marks the new file as if a worker had just ended on it); or anything before the daemon started (`startedAt`); this is the notice's rule only, the taint has no `startedAt` term (below).
- The full warning (a banner before sending, not only a notice) stays M13.
- Known gap (Task 3 N10): the first time the scanner indexes a file it already holds on disk (`known` is undefined and the file is not `replaced`), `toolResults` is false by construction (`search/scanner-file.ts:156-157`) and `touched` still moves `updated_at` to the file's mtime (`sessions/scan-port.ts:173-175`). The pre-start check of a cold session then reads that mtime as "the scanner has decided up to here" and skips the file, so outside tool results that were already in a file at its first index are never judged. Fix this before any `SEARCH_SCHEMA_VERSION` bump (`search/index-db.ts:7`): a bump rebuilds the index and every file is a first index again.

## Traps

- `ready.sessionFile` of a draft does not exist; do not treat a missing file as an error anywhere (reads give an empty transcript).
- Never read the Pi file because of a `message_end`.
- `sessions.abort` needs a `commandId` like the other mutations (13 in `methods.ts`); the web client's mutation helper has to send one (a missing one is `bad_request`).
- Never import the Pi SDK statically in the daemon: `transcript.lazy.test.ts` fails if anything in the module loads it.
- A worker's `sessionId` is Pi's, not the session's. The session's id is the pap id everywhere a client or the hub sees it.
- Tests use fake workers with the fake clock; the tests that fork the real `pi-host` are `sessions.int.test.ts`, `sessions.transcript.int.test.ts` (built on `testing/int-bed.ts`, which collects each worker's exit and fails `dispose()` on a network refusal) and `live-session.leaf.int.test.ts` (scripted model, network guard, temporary agent directory, home and pap home).
- Approvals (`approval_request`, ADR 0008): never cut. A record the schema refuses (no category, bad answers, tool over 256, bad key, title over 4096 or message over 65 536 characters) but that has an id becomes `approval_request_invalid` in `parseWorkerRecord`, and the session answers it `{ answer: "deny", cancelled: true }` with a rate-limited notice (own limiter key); one without a usable id is dropped (`worker_record_dropped`). The same answer goes for an approval over the dialog limits. The policy sees a closed question, not a refusal. A second approval under the id of an open one withdraws the open card (answered cancelled) and opens the new; an approval and an extension dialog never share an id (the newcomer is cancelled, the open one stays). `sessions.respondDialog` checks the answer before taking the dialog: an answer the card does not offer (also the `once` or `deny` a `confirmed` maps to) is `bad_request` and the card stays open; `{ answer }` on an extension dialog is `bad_request`; `{ cancelled: true }` (a dismissed card) is a plain deny, the person's own answer. Tests that need a worker's record to cross the schema use `worker.emitRaw`.
- Grants (Task 14b, `grants.ts`, pi-host `policy/extension.ts`): a grant is the tool name plus the sha256 of the exact payload. "Session" grants live in the worker (at most 1000, oldest dropped). An "always" answer is saved with `addAlways` and never written into the session grants: the worker holds it as provisional, stamped with the rules version read when the question was asked, and every `policy_update` (valid or malformed) that the worker takes after that ends it, so only `rules.alwaysAllow` allows the call afterwards and a revoke bites the live worker, even one that lands before the answer is processed. When `addAlways` answers "full" or throws, no rule exists: the call the person allowed proceeds, the grant lasts until the project's next rule change, the worker's exit, or the 1000-entry cap dropping it as the oldest, and a rate-limited notice says so (a throw is also logged as `always_rule_not_saved`). A rule added or revoked reaches every live or starting worker of that owner and project (the row and project scope sit in a WeakMap beside the `LiveSession`). Each update carries the whole list and a live worker gets it synchronously, inside the call that changed the rules (M5R7, carry #30: a request handled after the change, even in the same socket read, reaches the worker after the update; a burst is one update per change); a worker still starting gets one update right after `ready` (it holds at most 128 records before then, and exits 70 past that). A worker that cannot be told is stopped. A stored rule outside the `AlwaysRule` schema is skipped and logged `policy_rule_invalid`; a list over 1000 rules or 2 MiB (`MAX_POLICY_BYTES`, a defence of its own: nothing caps what a worker receives) is sent as no rule at all and logged `policy_rules_too_large`. The `onChange` listener is removed by `shutdownAll`.

## Policy link (M5, `policy-link.ts`)

- `createPolicyLink` is the one place where the sessions module meets the policy module. `compose(row, scope)` builds a worker's whole `PolicyRules` (owner settings, always rules, the session's mode override or the owner's default, taint and epoch, guard); a bug in a part yields read-only rules, never none. It is sent in `init` and in every `policy_update`; a refused update stops the worker (`onPolicyRefused`), so the next prompt starts with fresh rules.
- The snapshot carries `policy` (`SessionPolicyView`: the mode in force, whether the session chose it, `tainted`) and the stream a `policy` event when it changes. `Dialog` gains `tainted` and `guard` (copied from `approval_request`), which the card shows as "external content" and the guard line.
- The worker's `taint` record goes to `markTainted` (epoch rule in `policy.md`, ADR 0020). `audit` records go to the audit module; the daemon adds the worker-scope fact to stage 05. A record the worker could not redact never leaves it (`redacting-ipc.ts`).
- A fork or clone copies the mode and the taint (`inherit` inside `adopt`; a failure removes the file and the row). Sessions adopted by M4's scanner start tainted (`onAdopted` is wired to `markTainted` inside the adopting transaction); so does every session that exists when the M5 policy migration runs (nothing before M5 fenced external content). A token answers an approval with `deny` or `once` only (`always` and `session` answer `forbidden`), and the call's audit row names the answering credential (`actor` `user` or `token`, `actorId`), matched on the tool call id the question carries.
- The session-header always-rule list stays (owner MQ7) with a "Manage approvals" link.

## Session commands (Task 17a)

- `sessions.navigate {sessionId, targetId}` and `sessions.compact {sessionId, customInstructions?}` are `sessions:operate` mutations (`commandId`, owner check). Neither has a daemon timeout (the worker answers when Pi has, or the worker is gone: `worker_failed`); were a timeout ever added, it would mean the outcome is unknown and must not be retried (R105).
- Busy rule (M2R88), `LiveSession.busy()`: a run is open, Pi compacts, a prompt is on its way or was answered `started` and has no `agent_start` yet, or a navigation or compaction is in flight. `service-commands.ts` checks it before `ensureLive` and again after, with no `await` between the second check and `session.command(...)`, which puts the request on the wire synchronously and counts it (`live-commands.ts`). Pi's `compact()` aborts the current operation, so a missed check costs a user's prompt.
- The other way (M2R89): `LiveRun.prompt` throws `session_busy` before counting or sending when Pi compacts or a navigation or compaction is in flight (Pi would throw "Cannot submit a prompt while compaction is in progress"). A prompt during a navigation is refused too: it could land on either branch.
- A worker that refuses a command is `command_failed` (`session_empty` for a compaction with "Nothing to compact", `refusalOf`). Its text is logged clipped (`command_refused {command, error}`) and never returned (R66, M2R87).
- After a navigation the daemon sets the leaf from the answer (`navigated`, an id over 128 characters counts as unknown) and publishes one `snapshot` of the new branch (none when Pi cancelled). The worker navigates with `summarize: false`, so no branch summary entry is written today; the snapshot is read from the file along the new leaf and would carry one.
- Stop (`LiveRun.abort`) while a navigation or compaction has no answer (`promptBlocked()`) stops the worker, as it does during a compaction: a hook that never ends would otherwise refuse every prompt for good. The pending command settles with `worker_failed` and the next prompt starts a fresh worker.
- pi-host refuses `compact` and `navigate_tree` when `session.isIdle === false` (response `error: WORKER_BUSY`, mapped to `session_busy`). It covers what the daemon cannot see: a compact landing after the 5 s start deadline of an answered prompt, or a run an extension started once Pi marks it active (`sessions.commands.int.test.ts` holds one with the extension's own `agent_start` hook). It does NOT cover the `before_agent_start` hooks of a run an extension started: Pi marks that run active only after its hooks, so `isIdle` is still true meanwhile and a compact or navigate can land in that window. The user's own prompt is covered on the daemon side (a prompt in flight or answered `started` is busy).
- The assistant message's own `errorMessage` (the model or provider failure) is not Pi failure text in the sense of R66: the user must see it, it is already clipped to 500 characters in the transcript, and it stays in messages and rows.
- Pi's failure text (`compaction_end.errorMessage`, `auto_retry_start.errorMessage`, `auto_retry_end.finalError`, `summarization_retry_scheduled.errorMessage`) never reaches subscribers: `clipPiEvent` drops it (`failed: true` on `compaction_end` and `auto_retry_end`) and the daemon logs it clipped (`pi_error_text`). A navigation whose answer is unreadable, or whose snapshot cannot be built, publishes the "Reload the page" notice.
- Names (M2R92-94): `nameOf` (`names.ts`) is the one clip: lone surrogates replaced, whitespace runs (NEL and U+2028/9 included) collapsed, `\p{Cc}` and `\p{Cf}` removed (the BOM too) except the zero width joiner, which keeps emoji sequences whole; a name of only joiners and selectors is `null`, cut to 256 code points (never inside a pair), empty is `null`. It guards `ready.sessionName`, `session_info_changed` (never forwarded as a Pi event: `{kind: "name"}`, only when the name changed), the rename input and `sessions.name` (CHECK `length(name) <= 256`, counted in characters). The contract's `SessionName` counts code points too (`.max` alone counts UTF-16 units, so 256 emoji would fail the list). The column is a cache of Pi's `session_info`: refreshed from `ready` (after the row exists; a name that differs from the cached one is announced with a `name` event to whoever watched the cold session) and `session_info_changed`; `rename` does not write it, Pi's event does. Migration `202610110200_session_name.sql` sorts after the policy migration on purpose (the migrator refuses a pending one that sorts before an applied one); later M2 stamps stay below M3's `202610111000`.
- `sessions.rename` and `sessions.autoName` (`sessions:operate`, mutations, owner check) are not under the busy rule: Pi's `setSessionName` appends one `session_info` entry to the current branch and forks nothing (Pi's leaf does advance to it: pi-host asks the entry tracker to look after a successful `set_session_name` and after `auto_name`, so the `entry` event and `leafId` follow without waiting for the next message), and the title request runs outside the conversation. A cold session's worker is started for either (single writer). `timeout` (auto-name waits 120 s, rename 30 s) means the outcome is unknown and is not retried (R105). Two `autoName` asks at once share one model call. A worker refusal is `command_failed` (`session_empty` for pi-host's "nothing to name"); its text is never returned.
- `activity {compacting, retry}` follows Pi's `compaction_*`, `auto_retry_*` and `agent_start`; an `activity` event is published only when it changes, the snapshot carries it, and a worker that is gone has none.

## Model and reasoning level (M7 Task 7, M7R41-M7R45)

- The worker commands `get_available_models`, `set_model` and `set_thinking_level` (`pi-host/src/model-commands.ts`) back `sessions.models` (`sessions:read`), `sessions.setModel` and `sessions.setThinking` (`sessions:operate`, mutations); the daemon side is `service-models.ts`. The list comes from the live worker's own runtime in Pi's order, never re-sorted and cut at 500 (`truncated`): `session.scopedModels`, else the scope `enabledModels` names (resolved with `resolveModelScopeWithDiagnostics`), else `modelRuntime.getAvailable()`. So a cold session's menu starts its worker (`ensureLive`, capacity applies) and extension providers show up.
- A pick is session-scoped: `setModel` is never given `persist`, so `settings.json` stays byte-identical (pinned by `host.models.int.test.ts`). A model change while a run goes on is `session_busy` (the daemon's `busy()` after `ensureLive`, then the worker's `isIdle`, `WORKER_BUSY`). A reasoning change is allowed at any time and applies from the next model request (pinned with the scripted provider's `captureThinking`). Pi clamps a level the model lacks; a model without reasoning offers only `off`.
- `loadout` (`SessionLoadout`: model, thinking level, the levels the model allows, preset, up to 256 tool names): the worker sends it after `ready`, after each of the three commands and from the inline `pap-loadout` extension on `model_select` / `thinking_level_select` (an extension may switch models itself). The payload travels as unknown; `loadout-view.ts` parses it with the contract, drops an invalid one with one rate-limited `loadout_invalid` warn (no worker text) and publishes a `loadout` event only when it changed. The snapshot carries `loadout` (null for a session without a worker); `LiveSession.loadout()` is its source. The preset in it is the worker's own (`presetOf`), see Tool presets below.

- Accepted Pi SDK residual: `setModel` awaits `checkAuth` for the provider before it switches (`model-commands.ts:86` calls it), and Pi's `checkAuth` runs a `!command` stored in `auth.json`. A session's own model change therefore can run the owner's own key command, as a prompt to that provider would. Settings never does (`models.md`).

## Decorations, panels and notices

- Status, widget and title events go through one keyed throttle (`keyed-throttle.ts`, kernel `Clock`): the first change of a key is published at once, later ones within 50 ms fold into the latest; at most 64 open windows, one more key goes out unthrottled. `decorations.ts` refuses new keys past `UI_LIMITS` (32 statuses, 8 widgets). `editor_text` goes out at once and is not stored.
- Extension notices (`notify`, extension errors) pass `notices.ts`'s limiter: 10 per 10 s per session, the rest counted and one pap-worded "N more notices from extensions were not shown." published directly when the window ends (it is never limited itself). A `notify` carries `source: "extension"`; pap's own notices (and the extension-error sentence) carry none. `stop()` (worker exit) publishes the pending summary. The ring keeps the last 20 of every source for the snapshot. The web treats the level as the lifetime: `info` is transient like Pi's TUI `notify` (a toast when the `notice` event arrives live, never from the snapshot), `warning` and `error` are persistent lines with a client-side dismiss (no daemon state).
- Panels (`panels.ts`): at most 4 open; a fifth `custom_render` is answered with `custom_cancel` and a rate-limited notice. A `custom_close` for an id the daemon never saw (e.g. after that cancel) is ignored silently. The last 64 closed ids are remembered: a late `custom_render` for one is ignored (log `panel_record_ignored`, once per 10 s) instead of reopening a ghost panel. `stop()` sends `custom_cancel` for every open panel before the shutdown; a worker exit clears decorations and panels and publishes `panel_closed` for each (clients clear theirs on `cold`).
- `sessions.panelInput` is `idempotent: true` with no `commandId`, the one exception to R65b (keystrokes are never retried; a receipt per key would cost an fsync per key). It still needs `sessions:operate` and the owner check; `data` is 1..4096 characters; a session without a worker or a panel that is not open is `not_found`.
- `fitSnapshot` clamps statuses, widgets, notices and panels to `UI_LIMITS` (setting `decorationsTruncated`) and counts the dialogs it could not fit in `hiddenDialogs`. Open panels have their own 256 KiB budget (`PANEL_BYTES`) beside the 256 KiB of statuses, widgets and notices.

## HTML export (Task 18, ADR 0006)
- `exports.ts` holds the pending exports (16, 10 min, in memory); `export-http.ts` is the one download route; `export-patch.ts` makes Pi's three recursive template helpers iterative.
- The route is the only user of `ownCsp` (kernel `app.ts`). A new header for it needs an exact test in `export-http.test.ts`.
- `exportHtml` prepares the entry before it brings the worker up; only a `timeout` after the command was sent keeps the entry (the worker may still write).
- A Pi upgrade can change the template: `export-patch.test.ts` runs the anchors against the installed Pi, so it fails first.
- The patch reads and rewrites the whole file synchronously-ish: at the 64 MiB bound it holds the event loop about 270 ms and about 0.5 GB of transient heap. The bound is a conscious choice; lower `MAX_PATCH_BYTES` if that matters.
- The boot purge only removes regular `<uuid>.html` / `<uuid>.html.patching` files in `$PAP_HOME/exports`; anything else is kept and counted in an `export_purge_kept` warning.
- HEAD on the export URL answers 404 and spends nothing (Hono would otherwise run the GET handler for it).
- `sessions.fork {sessionId, entryId}` and `sessions.clone {sessionId}` (Task 19, ADR 0009; `sessions:operate`, mutations, owner check, `not_found` for another owner's) create a cold session on a new Pi file written by Pi's `SessionManager` over a **private copy** of the source's complete lines (`pi-writer.ts`; `open()` would append to a torn last line and rewrite an old or empty file). Copies are `<uuid>.jsonl` files (0600) in `$PAP_HOME/fork-tmp` (0700), removed after each call; at boot `purgeForkTmp` deletes only regular files with that name (`lstat`, no link followed, no folder entered) and logs the count of anything else it kept. The source is opened `O_NONBLOCK` and must be a regular file (a FIFO is `unreadable`, not a hang); only its finished lines (up to the last newline) are copied. After branching the new file's header must name the real source (`parentSession`), else the file is deleted and `internal` is logged as `fork_lineage_mismatch`. Blocking cost: opening and branching run synchronously on the daemon's thread; measured about 0.2 to 0.8 s at the 32 MiB cap depending on entry count (about 0.2 s for 8 000 large entries, about 0.8 s for 160 000 small ones). Over 32 MiB: `capacity`; empty branch: `session_empty`; not a user message: `bad_request`; unreadable header or a new file outside Pi's folder: `internal`. A fork at the first message is a draft row with no file. The fork's text is clipped to 800 000 JSON bytes. `cloneName` (`forks.ts`) names a clone "<title cut to 40 code points> · xxxx". `session_before_fork` hooks do not run.

## Idle release (Task 20, spec C 2.1)
- A worker is released after `Config.workerIdleMs` (30 minutes; `0` turns it off) with nothing pending: `idle-release.ts` (timer, kernel `Clock`), `live-idle.ts` (the stop and the refusal of commands), `LiveSession.state()` (what is pending). **Busy** = status not `idle`, a run, a prompt in flight or answered `started`, an open dialog or panel, Pi's queue not empty, a command in flight, a compaction or an automatic retry. **Background** = nothing busy but `health.descendants > 0`: the agent left processes running; the worker is released anyway `BACKGROUND_RELEASE_MS` (8 h, owner R2-2) after its last activity, and at that very moment, not at the next multiple of `workerIdleMs`.
- **What re-arms it (M2R108):** client commands (prompt, abort, respondDialog, panelInput, clearQueue, the session commands; at their start and at their end) and `pi_event`, a dialog `extension_ui_request` that opened (a decoration, or a dialog the daemon cancelled, does not), `approval_request` and `custom_render`. Never `health`, `audit`, decorations, `extension_error` or the keyed throttle's publishes, so a clock in the status bar or pi-host's 30 s `health` cannot keep a worker for ever. A touch only moves the last activity; one timer at most, and it sleeps what is left of the quiet period when it fires, so a stream of events costs no timers. What an extension does on its own timers is invisible and does not keep the worker (M2R109).
- `countAgentProcesses` (`packages/pi-host/src/descendants.ts`, every 30 s in `health`) counts the processes the agent started that still run, outside the worker's own process group (Pi's bash tool starts each command in a group of its own; MCP helpers share the worker's). It is the union of three sources: (1) the worker's descendants, which is all there is while a tool call still runs; (2) **what the tool's shell left behind**: `cmd &` and `nohup cmd &` outlive the shell, Linux gives them to pid 1 and they are no descendant any more (measured with the real bash tool, review of Task 20). In a worker scoped by pap they stay in the scope, so its `cgroup.procs` members outside the group are counted. The scope is the worker's only if its cgroup leaf equals `PAP_WORKER_UNIT`, which the daemon puts in the scope launch environment (`workerEnv` strips inherited `PAP_*`) and pi-host reads and deletes at boot: a worker started by an agent inside another pap worker sits in that worker's scope and is on the marker path; (3) **without a pap scope** (scopes off, no linger, no systemd) pi-host sets `PAP_WORKER_TOKEN` (random per worker) in its own environment before Pi starts, the shells inherit it, and the processes whose `/proc/<pid>/environ` carries that exact entry are counted (same-user processes only are readable; a process that clears its environment, or a daemon that detaches and re-execs with a clean one, is not seen). One pass over `/proc` (at most `MAX_TABLE_ENTRIES` = 32768 processes read; zombies skipped), a walk by parent that visits each pid once (at most `MAX_COUNTED_PROCESSES` = 4096 and `MAX_COUNT_DEPTH` = 32), at most 4096 scope members, and for the marker at most `MAX_ENVIRON_BYTES` = 256 KiB per process and `MAX_ENVIRON_TOTAL_BYTES` = 16 MiB in all (bytes, not characters). 0 off Linux, when the worker does not lead its group, or on any error (one stderr line). Cost without a scope: about 2 ms per call for 183 processes for the walk; the marker adds one small read per process outside the worker's group. A process that exits mid-read is simply missing, a pid reused between two reads is read once. The count can be up to 30 s old when the timer looks at it. Tests: `descendants.orphans.test.ts` (fixtures: scope, marker, bounds), `descendants.scope.int.test.ts` (a real scope: skipped locally without a user manager, required in CI) and `host.descendants.int.test.ts` (the real bash tool, no scope).
- **Release (race-free):** `release()` publishes `releasing`, stops the worker (the `shutdown` record; pi-host tells extensions with `session_shutdown`), and the exit publishes `cold` with no `cause`. A stop the daemon asked for (release, `shutdownAll`, a policy update that could not be sent) never shows a cause, except `oom`, which keeps its own (M2R111). The service keeps a releasing session in `live` until its exit has been handled, so `list` shows `releasing`.
- While a session is `releasing`: `prompt`, `navigate`, `compact`, `rename`, `autoName`, `exportHtml` wait in `ensureLive` for the exit (no deadline of their own: the kill ladder ends the worker) and then start a new worker on the same Pi file; two commands that arrive together share one start. Whether a worker is closing is `LiveSession.stopping()` (the service never asks the status, which an extension can move to `running` meanwhile). `LiveSession` itself refuses `prompt` and `command` with `worker_failed` and sends nothing. `abort` answers ok and `clearQueue` answers empty lists without asking the closing worker (M2R112: a quiet session has no run and no queue, and a closing pi-host drops requests). `respondDialog` and `panelInput` answer `not_found` (the dialogs closed with the worker). `fork` and `clone` read the file and need no worker. A `policy_update` is not sent to a releasing worker (`grants.ts`): the next worker starts with the current rules in its `init`. After `shutdownAll` begins, a command waiting for a release exit gets `capacity` and starts nothing.
- A navigation nobody continued is lost at release (M2R110, ADR 0007, owner M2-Q11): Pi's leaf lives in its memory and the release does not restore it.

## ANSI colours and the extension label (web)

- Extension text is parsed by `apps/web/src/features/sessions/ansi.ts` into spans with token classes (never HTML): SGR 30-37 and 90-97 map black to `text-dim`, red to `error`, green to `ok`, yellow to `human`, blue and cyan to `agent`, magenta to `attention`, white to `text`; bold, faint, italic and underline are kept; backgrounds, inverse, 256-colour and truecolor are ignored. ## Prompts with attachments (M8, ADR 0031)

- `sessions.prompt` takes `attachments: [id]` (ids of `POST /upload`, at most 10); the text may be empty when there is at least one. `prompt-attachments.ts` claims them for this session and owner **before** the worker is asked (`not_found` for another owner's or session's id; a duplicate is `bad_request`). Files are copied under `$PAP_HOME/attachments/<session>/` and announced in the message as an `Attached files:` list of paths: the agent reads them with its own tools (M8R42). Images stay in `attachments/pending/` and travel in the `prompt` record as `images: [{ path, mimeType }]` (`PromptCommand.images`); once Pi has taken the prompt `accepted()` releases the pending images. Nothing the owner attaches taints the session (M8R99).
- The worker reads the image itself (`packages/pi-host/src/prompt-images.ts`): only a real path inside `<papHome>/attachments/pending`, `nlink` 1, at most 10 MiB, the header's pixel count at most 50 million (checked before decoding, `image-size.ts`), then Pi's `resizeImage`. A prompt goes with all of its images or none: otherwise the worker answers `pap:image_unreadable`.
- **The prompt queue** (`prompt-queue.ts`, `commands.ts:55`): prompts reach Pi in arrival order although an image prompt prepares asynchronously. A text prompt with nothing ahead starts at once, as before M8. An image prompt waits for the ones before it to be prepared, and the prompts behind it wait until Pi has *answered* it (the preflight response, never the end of the turn), because Pi normalises images again before it takes a prompt; M2's steering is unchanged. Stop (`handleAbort` -> `dropWaiting()`) ends every wait, including the in-flight one, and answers the dropped prompts `pap:aborted`.
- Residuals: an image sent to an extension command blocks the queue until the command ends or Stop is pressed. The daemon maps every failed `prompt` response to the one code `prompt_rejected` (`live-run.ts:172`), so a text prompt dropped by Stop reads like a rejected one; the log line keeps the worker's reason.
- **Echoes stay small.** Pi's echo of the user message and tool results with images would cross the 4 MiB IPC record cap (a 12 MB message was dropped with two `extension_error` notices). `toWireEvent` (`wire-events.ts`) replaces every image block, in echoes and in tool results (depth-bounded walk), with `{ type: "image", mimeType, omitted: true, bytes }`; `wire-clip` keeps `bytes` when there is no data.

## Lanes seams (M9, ADR 0033)

- `lane-port.ts` (`SessionsModule.lanes`) is the only way the lanes module touches sessions: `create` (the session's folder is the worktree; a model Pi refuses leaves its default), `prompt`, `activityIn` (busy = running, starting or a prompt pending, including one held in the lane hooks), `sessionIdsIn` (archived ones too, for the taint check), `runState` (idle and live leaf, for the re-check under the lane lock), `archiveIn`, `releaseIn` (loops over `releaseIdle`), `lastAgentText`, `branchPath` (the branch from root to leaf, at most 10 000 entries) and `suggestCommit`. `live-session.ts` is not edited.
- `releaseIdle(ownerId, sessionId)` answers `released`, `busy` or `cold`. It adds no dialog, panel or queue of its own and leaves a worker with a dialog, panel, queued message or command in flight alone.
- `lane-hooks.ts` is a slot the lanes module fills once (`setLaneHooks`). `closed(cwd)`: an `archiving` lane refuses prompts (`session_busy`), an `archived` one answers `not_found`. `holdsFiles(cwd)`: a prompt waits for a running restore with no cap. `beforePrompt`: for an idle session the prompt waits at most 15 s for the `before` checkpoint and answers `undefined` synchronously when there is nothing to do, so the busy rule (M2R88) is kept; a prompt to a busy worker does not wait. `afterRun`: the session went from `running` to `idle`, which takes the `after` checkpoint and may start the fan-out test auto-run. `assertOwn` runs before a worker starts.
- `suggestCommit` and Pi's `auto_name` are side calls: no run is registered and M10's daily budget does not count them (C1).
- A session belongs to a lane by folder (its real cwd is the worktree or inside it), never by a stored link.

## Scopes (see daemon.md)

- The service passes `scopes` to each worker spawn; with scopes on, the worker's cgroup is `MemoryMax`-bounded and `oom` is the one exit cause a release never hides. `PAP_WORKER_SCOPE=off` (every test bed) runs workers as in M1.

## Traps found in M2

- **Pi's leaf is memory only** (M2R110, owner M2-Q11, ADR 0007): `navigate_tree` writes nothing. A navigation nobody continued (no prompt after "Edit from here") is lost at idle release, at a crash and at a restart. The composer keeps the text put there; the branch does not come back.
- **Approvals vs extension dialogs**: an approval is `Dialog.method "approval"` over the approvals channel (`approval_request`/`approval_response`), answered with `answer`; an extension's `confirm` is answered with `confirmed` and can never carry a policy answer. They never share an id. The web renders them with different cards, and extension ones always say "extension".
- **ws delivers several frames per read**: the client can get a stream frame in the same tick as the reply that names its `sub` (`runtime/subscriptions.ts` holds those until the reply is handled, then drops what no request claims), and a pi-host worker can read an answer and the next `policy_update` in one read (`extension.grants.test.ts`). Code must not assume one record or frame per event-loop turn.
- **`HEAD` on the export route** answers 404 and spends nothing: Hono runs the GET handler for HEAD, which would eat the single-use token (`export-http.ts`).
- **Fork and clone never open the live file**: they copy the source's finished lines to a private file in `$PAP_HOME/fork-tmp` and branch that copy (ADR 0009); `SessionManager.open()` on the live file would append a newline to a line a worker is writing or rewrite an old file.
- **Background detection** (`packages/pi-host/src/descendants.ts`): in a pap scope, processes in the scope's `cgroup.procs` outside the worker's group count, but only if the cgroup leaf equals `PAP_WORKER_UNIT`; without a scope, processes whose `/proc/<pid>/environ` carries this worker's `PAP_WORKER_TOKEN` count. A process that clears its environment is not seen.
- **Worker memory**: workers always start with `--max-semi-space-size=16` (`workerExecArgv`); `WORKER_BUDGET_MB` = 285 was measured with it over a 300-turn scripted session with compaction on (`docs/spikes/s4-m2-long-session.md`). 285 is a 300-turn figure, not a ceiling: with the flag alone RSS keeps rising about 0.18 MB per turn (Task 23 review), and a session that never compacts reaches 666-695 MB regardless of the flag.
- **`sessions.panelInput` has no `commandId`** (R65b exception) and `abort` has one: the web mutation helper must send it.
- **`/` is 404 without `apps/web/dist`**: build before `pnpm smoke` or a manual run.
- **Taint is the daemon's** (M5R60, `policy-link.ts`): the worker's `taint` record carries its taint epoch, and `markTainted(owner, session, observedEpoch)` raises only when no clear came after it (`taint_epoch <= observedEpoch`). Second path: an audit entry with `kind: "result"` and `external: true` (checked before the full audit schema) raises with no epoch, so a late one after a clear taints again (a nuisance, never unsafe). It is the safeguard for external content a worker reads between a Clear and the new epoch reaching it: never add an epoch check to this path, that would make it fail open. A restart keeps the taint: `compose` sends it in `init`. Forks and clones call `inherit` inside `adopt`; a failure there removes the file and the new row. `inherit` never lowers an epoch.

## M10: runs hooks, task sessions, fork caps

- Two hooks into the module, both wrapped so a throw never reaches a session: `LiveSessionDeps.observe(event)` (one line in `live-session.ts`, after `run.onPiEvent`; the raw Pi event, before clipping) and `record` in `service-launch.ts` calling `deps.runs?.onRecord(row, kind, data, loadout)` at `run_start`/`run_end`. They feed the runs registry (`finops.md`).
- `SessionsAutomationPort` (`automation-port.ts`, `sessions.automation`) is the only way the automation and runs modules reach sessions: `createTaskSession` (inserts the row and `setTaskPolicy` in one transaction; refuses `capacity` unless one worker stays free, `disk_low` below the floor), `prompt`, `abort`, `answerUnattended` (denies open approvals as actor `system`), `releaseIdle` (M9's rule through `SessionsService.releaseIdle`: quiet means idle, not busy, no prompt held in the lane hooks, no dialog, panel or queue; answers `released`, `busy` or `cold`), `archive`, `deleteTaskSession` (refuses a live worker; session row, then the Pi file only inside Pi's sessions folder), `onAttention`, `workers()`, `admits()`, `promptPending` (a reopen, a prompt held in M9's `beforePrompt` window, or a busy worker). A task session's in-memory row carries its `TaskSessionPolicy` until the `session_policy` row exists, so there is no window without the allowlist.
- Fork caps: `fork-quota.ts`, at most 30 forks and clones per owner in any 10 minutes (`rate_limited` for the 31st); `fork`/`clone` and task creation also check the disk floor (`PAP_MIN_FREE_DISK_MB`, `disk_low`).
- A fork or clone copies the allowlist but never `unattended`: a fork is the owner's, attended, until "Use my normal tools". Details of the profile: `automation.md`, `policy.md`.

## Projects: `projects.add` (decision 85)

- `projects.add { root }` (`sessions:operate`, idempotent, no audit): the projects service resolves the folder with `resolveSessionCwd` (`invalid_cwd`), files it under `policy.scopeOf` (its git root, else itself) exactly as `sessions.create` does (PH1), refuses the real path or the scope inside `$PAP_HOME` or Pi's agent folder (`bad_request`, a link into them included), and calls `ensure`; a full table (2000) answers `capacity`, a database a newer pap wrote `read_only` (PH15). The composition (`daemon.ts`) passes `ProjectFolders` (`resolve`, `scopeOf`, `stateDirs`); without them `add` fails closed (`internal`).
- The `shell` snapshot lists every project with an active session and every project no session files under yet, flagged `unused: true` (`MarksStore.projectsInUse`, `ProjectsPort.all`); a `project` event carries the flag until the first session. Residual: a project whose sessions are all archived is not listed by the snapshot, so re-adding it holds for the page only.

## M11a: session kinds, agent sessions and the launch gate

Details of the agent side: `agents.md`, ADRs 0047 to 0050.

- **Kinds.** `sessions` has `agent_id`, `agent_role` (`thread`, `task`, `child`) and `parent_session_id` (migration `202610151100_session_kinds.sql`) and, for the owner's tool choice on an agent session, `owner_preset` (`202610151152_owner_preset.sql`). `session-kind.ts` makes the platform's `kindOf` from the row: type (`sessionTypeOf`), owner, taint, agent id, and `autonomous` (trusted autonomy on in the worker's start-time profile and in the registry now). An M10 task row counts as `task` through the in-memory policy before its `session_policy` row exists, so it never gets `subagent`.
- **Ports.** `setAgentPorts({platform, inLane, agents})` (`agent-surface.ts`, called more than once; the pieces are merged) binds what the sessions module needs from the other modules late: the platform dispatcher, the lane test, and `agents` (the registry's `profileOf`, `vaultOf`, `onceOf`, the sandbox probe, the egress proxy and the owner's host list). No registry bound means `not_found` for an agent row: fail closed. `SessionsModule.agentSessions` (`SessionsAgentPort`) is the only way agents, automation and secrets reach agent sessions: `createAgentSession`, `threadState`, `releaseIdle`, `applyLive` (a model or thinking change to a live thread; never wakes a cold worker), `sendToAgent` (vault updates to live workers of the agent, thread and task, sandbox on, optionally one session), `sandboxed`, `precheckSandbox`, `precheckEgress`, `lastText`, `activeTools`.
- **The bridge.** A worker handle has three `onRecord` listeners: the live session's, `platform-bridge.ts` (`platform_call`, `platform_cancel`, `secret_used` re-validated; a throw is logged `platform_bridge_failed`, and the dispatcher is told when the worker exits) and `egress-link.ts` (`egress_open`, `egress_close`). The platform reply goes back with `handle.send`. A new worker of a session ends the earlier worker's calls.
- **Approved calls.** `approved-calls.ts` holds the browser's Allow once for a tainted `ask` op, keyed by session, tool call id and tool (4 096 entries, 10 minutes, spent once). `guardAnswer` refuses a token's answer and the automation caller's on a platform card before the worker sees it; `host` answers (`network_request`) are for a browser on an agent thread's card of that tool only.
- **The launch gate** (`agent-gate.ts`) is the first awaited step of `launch` for every row with an `agent_id` (new, reopened, after an idle release, a crash or an unarchive, a `sessions.prompt` on a cold thread): the agent exists and is the owner's, its profile parses (`not_found`), not quarantined (`agent_paused`), the home check (`invalid_cwd`), the probe (`sandbox_unavailable`), and for a networked profile the egress proxy. It returns the init facts (`SandboxSpec`, vault, once values, agent, memory). Nothing awaits between the gate, the capacity check and the spawn, and the last worker is kept free for the owner inside `launch` (`keepFreeFor`, `worker-room.ts`). Plain sessions get no extra tick. A launch marked sandbox-only (a5 auto-resume of a full-access agent) refuses a profile without the sandbox: a warm worker whose start-time profile had it off, or a cold start.
- **Rules.** `agent-rules.ts` adds the agent profile fields after `taskRules` in `policy-link.ts`'s `compose`: mode (thread: the stricter of the agent's and the session's, W5-R23), hosts (agent's list, else the owner's), blocked commands (the owner's then the agent's, at most 128), `agentHome`, `agentScratch` (a task's cwd), `sandbox`, `autonomy`, `trustedSources`, `hostGrants` (thread only). Every compose of a running worker uses the profile snapshot it started with (W5-R26). The tool preset is the narrower of the start-time profile's and `owner_preset` (W5-R28, `preset-clamp.ts`): `setTools` stores the choice only when the change took effect.
- **What an agent session is not.** No `sessions.fork` or `sessions.clone` (`bad_request`); `sessions.create` in `$PAP_HOME/agents` is `invalid_cwd` (`cwd.ts`); out of the `shell` snapshot, counts, archived page, `session` events and project filing (`marks-store.ts`, `sidebar-hub.ts`), while attention (an open dialog) still reaches the agents module; project trust is never given (`inside-pap-home` for a folder under `$PAP_HOME`).
- **Errors.** About 16 existing methods that start or relaunch a worker declare `sandbox_unavailable`, `agent_paused` and `invalid_cwd` (`AGENT_GATE_ERRORS`), so a refused relaunch shows its code and not `internal`.
- **Host grants** (`host-grants.ts`): `sessionId → hosts`, at most 64, memory only, dropped when the thread's session is archived.
- Pi's context-file discovery is off for agent sessions (`open-session.ts`), and `agent-prompt.ts` appends the agent's fixed prompt (name, home, sandbox state, role) once.
