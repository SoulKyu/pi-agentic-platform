# Sessions module

Code: `apps/daemon/src/modules/sessions/`. Identity of a session and its Pi file: ADR 0005. Worker protocol: ADR 0001.

## Pieces

- `service.ts`: the one place that knows which workers are up (`live`), which are coming up (`starting`, `reopening`) and when a session's Pi file is remembered. RPC handlers (`rpc.ts`) only decode, call it and let `PapError` through.
- `live-session.ts`: one worker's session. Sends `init`, tracks status, dialogs, run boundaries and the run's messages; everything it knows leaves through `publish` (stream) and `record` (table `session_events`).
- `run-tracker.ts` (run start/end), `dialogs.ts` (cards), `run-view.ts` + `snapshot.ts` + `transcript.ts` (what a subscriber starts from), `pi-files.ts`, `cwd.ts`, `store.ts`.
- `testing/` helpers are for tests only (the build and the lint keep them out of production code): `service-bed.ts` (real database and hub, fake workers), `live-bed.ts`, `helpers.ts`. A helper in `testing/` may import a module only through its `index.ts`, so the test files import `service.ts`, `store.ts` and `live-session.ts` themselves and pass the factories in.

## Capacity

A worker counts against `maxWorkers` from the moment it is forked: `starting` is a set, checked and filled in the same tick, so concurrent creates cannot both pass (R9). It leaves `starting` only after the session is in `live`. `minFreeMemMb` is checked at the same place. Both refuse with `capacity`; nothing waits in a queue. After `shutdownAll` every new start is refused with `capacity` too.

A worker that does not say `ready` within 30 s (`READY_TIMEOUT_MS`) is stopped and the start fails with `worker_failed`. A worker that exits before `ready` (exit 70 for a bad init, policy or `PI_CODING_AGENT_DIR`) gives the same fixed `worker_failed`; the log has its exit and the last 2000 characters of its output, never the client.

A failed start of a new session leaves nothing: the row is inserted only when the worker is ready, and nothing is published or recorded for a row that is not stored (the hub keeps a channel for every key it is asked to publish for, so a ghost key would stay). What the worker says before that point (an extension failing at start-up, a policy audit line) is held in a bounded buffer (`pre-ready-buffer.ts`: 32 items, 256 KB, earliest kept, the rest counted in a `session_start_events_dropped` warning) and replayed to the hub and the journal right after the insert; a failed start drops it with the rest. The status at `ready` is not held, a snapshot carries it. Like the events of a reopened session, the replayed ones reach a subscriber that resumes from the start of the stream (`after.seq` 0 of this epoch); a cursor-less first subscriber gets a snapshot, which does not carry notices (M2: recent notices in the snapshot).

## Runs

- A run starts at `agent_start` and ends when `agent_settled` is confirmed by up to three `get_state` probes 100 ms apart; new input cancels the probes. Spec C §2.4 says what happens when no probe sees Pi idle: the run stays open until the next `agent_settled`.
- Abort is a mutation (R110): it carries a `commandId`, so a client that did not see the answer and sends the same command again gets the receipt back and does not stop a newer run. `get_state` first; compaction, or no answer within 2 s, terminates the worker. If Pi shows nothing running, the run the daemon still holds open ends (`run_end {aborted: true}`, status `idle`) and the worker is left alone (R111); `abort` is sent to Pi all the same, fire-and-forget, because the answer can be stale: Node delivers each record before the continuation of the response before it, so an idle `get_state`, the prompt's `started` and `agent_start` can arrive together and `abort()` resume after all three. The run generation (bumped by every `agent_start`) is read before `get_state` is sent and `finish` ends nothing if it changed, so the status never reads `idle` while Pi streams (R111b). Otherwise `abort` is sent and the worker is terminated if the run has not settled 5 s later. One deadline, not two.
- A run left open by input Pi rejected or handled without an agent turn (no `agent_settled` will come) is closed without anyone pressing Stop: when a prompt is answered rejected or `handled` while the tracker has a run open, the daemon probes `get_state` (not awaited, so the answer to the client does not wait) and ends the run if Pi is idle, unless an `agent_start` came in meanwhile (R111b).
- `prompt` has no timeout (R99): an extension command answers only when it ends, possibly after a dialog the user takes minutes to answer. The pending request ends with the worker (`worker_failed`). Dialog answers do not wait for it. No sessions method can answer `timeout`: `get_state` and `abort` are internal and their timeouts are handled where they happen. If one ever did, it would mean "outcome unknown" (R105): the dispatcher stores no receipt for an error, nothing retries, and the client has to look at the session's state before it sends the command again.
- A crash closes every open dialog, records `run_end {interrupted: cause}` and `worker_exit`, publishes `status cold` with a readable cause and removes the worker from `live`. Nothing restarts it; the next prompt does, on the same Pi file (or a new Pi session for a draft).

## Dialogs

At most 64 open dialogs and 8 MiB per session; extra ones are answered `cancelled` at once. Methods other than `select`, `confirm`, `input` and `editor` are decorations (passed on as `pi` events) or, if unknown, cancelled. The worker's text is untrusted: a dialog is rebuilt from the fields we know, text is cut to the limits of `Dialog` and then to 1 000 000 bytes as serialised (a character can take up to six bytes once escaped), so one dialog is never more than one frame. A `select` whose options do not fit (more than 100, or one longer than 4096 characters) is cancelled instead of cut, because the extension is waiting for one of those exact strings. Every cancelled dialog is answered, but the log line and the `notice` for a cancel (by size or by the limit) come once every 10 s per reason and session, the log line carrying how many it left out (R111): an extension that asks in a loop cannot flood the screen or the log. Extension errors reach the client as a fixed sentence with, at most, the event name when it looks like one; the worker's text only goes to the log, clipped to 2000 characters (R66).

## What a subscriber starts from

- `snapshot` is the current status, the open dialogs and about the last 75 messages, held under 1 MB: dialogs first (oldest first), then messages newest first, contiguous. A row over 256 KB goes in as a placeholder `{role, timestamp, omitted: true, bytes}`, so a huge tool result never empties the snapshot (R109). An unknown session id is `not_found` (R79), so a client cannot make the hub create channels.
- Messages come from the Pi file through the SDK helpers (never written, never migrated on disk), and only as many bytes of it as are needed. Pi writes an entry after its subscribers saw it, so during a run the file is read only up to its size when the run began, and the run's own messages (from `message_end`) follow it (R38); the run keeps at most 75 of them and 1 MiB (a message over 256 KB as its placeholder), measured before it is kept. Once the run has settled the file is complete. A hot session's snapshot also comes from the file, where spec C §3.3 says `get_entries{since}`; that is M2.
- Entry ids and the leaf (Task 10b, ADR 0007): the file is not read for them. pi-host (`entry-tracker.ts`) checks `SessionManager.getLeafId()` one macrotask after an event that may have appended and sends the new entries as slim `entry_appended` records (up to 4096 per walk, 128 per macrotask), or a `leaf` record. The live session turns an entry into an `entry` stream event (the client binds the id to the newest unbound message with the same role and timestamp, or the same `toolCallId`) and a compaction or a branch summary also into a `row`; Pi's own `entry_appended` is never forwarded. `leafId()` follows `ready`, entries and `leaf` records; during a run the snapshot reads the file along the leaf the run began at (`leafAtStart`). A `leaf` record with `resync` (a walk of more than 4096 entries) means the run's rows keep no id until a client subscribes again after the run (only logged).
- Pi puts its system prompt in the file as the first message (`role: "system"`, about 9 KB in the default prompt, and it may embed the user's AGENTS.md). It is internal: the daemon leaves it out of the snapshot and of the `message_start`/`message_end` events (R107). M2 may add an explicit "show the system prompt" request.
- Text, thinking and tool-call deltas are merged per content block and sent at most every 50 ms (`coalescer.ts`, on the kernel `Clock`); a tool's progress keeps only its latest update and is dropped when the tool ends; 256 KiB of pending text or 256 pending items send at once. Every event the live session publishes (status, dialogs, notices, other Pi events) sends the pending deltas first, so text never arrives after what follows it, and a worker exit sends them before the `cold` status. The snapshot's `partial` reply (`partial.ts`) is rebuilt from published events only, never from pending deltas, so a snapshot plus the frames after it give the reply exactly once (M2R43). A reply past 256 KiB leaves the snapshot until the next assistant message (M2R42); a client then has it whole from `message_end`. Merging loses no field: no `message_update` ever carries Pi's running `message` (pi-host strips it), so a merged event is the delta plus the latest `usage`. Before it is sent, a tool's result is cut to 8 000 characters (progress to its last 2 000, arguments to 8 000 per string, details over 8 KiB dropped) with `papTruncated` saying how much there was, a nested tool's progress is not sent, and `text_end` / `thinking_end` lose their `content` (`wire-clip.ts`, M2R44-45); the whole output is to be fetched with `sessions.toolOutput` (not built yet).
- `agent_end` and `turn_end` reach the daemon without `messages` and `toolResults` (R103, `toWireEvent` in pi-host): they grow with the run. Each message is in its `message_end` and each tool result in the `toolResult` message of its `message_end`; `tool_execution_end` carries no result. `turn_end` keeps its assistant `message`, clipped like a `message_end` (a 900 KB `write` call is not sent twice).
- Events are sent whole or not at all: every Pi event is measured after it is clipped (`wire-clip.ts`: a `text_end` has no `content`, a `toolcall_end` has its arguments cut to 8 000 characters per string), and one still over 1 MB (a huge `text_delta`, a message with thousands of large arguments) is dropped with a `notice`, at most one notice and log line every 10 s.
- The SDK that reads the files is loaded the first time a client subscribes, not with the module (R108): `subscribe.session` first awaits `prepareSubscription` (owner check and the memoized `import()`), then opens the subscription, and the hub's synchronous snapshot provider reads what that loaded (without it, `snapshot` answers `internal` rather than an empty transcript). Measured on this machine: importing the sessions module takes the process from 44 to 96 MB resident in about 0.1 s (it was 163 MB and 0.65 s with the SDK imported statically; the 52 MB left is zod and `node:sqlite`); the first subscription pays about 90 MB and 0.55 s once.

## Traps

- `ready.sessionFile` of a draft does not exist; do not treat a missing file as an error anywhere (reads give an empty transcript).
- Never read the Pi file because of a `message_end`.
- `sessions.abort` needs a `commandId` like the other three mutations; the web client's mutation helper has to send one (a missing one is `bad_request`).
- Never import the Pi SDK statically in the daemon: `transcript.lazy.test.ts` fails if anything in the module loads it.
- A worker's `sessionId` is Pi's, not the session's. The session's id is the pap id everywhere a client or the hub sees it.
- Tests use fake workers with the fake clock; the tests that fork the real `pi-host` are `sessions.int.test.ts`, `sessions.transcript.int.test.ts` (built on `testing/int-bed.ts`, which collects each worker's exit and fails `dispose()` on a network refusal) and `live-session.leaf.int.test.ts` (scripted model, network guard, temporary agent directory, home and pap home).
