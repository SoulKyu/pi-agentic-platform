# Agents and project boxes in microVMs (sub-projects 1 to 3, boxes lot B1)

An agent runs in its own Kata Containers microVM (Cloud Hypervisor) with its own disk, CPU and memory. Pi's worker and a bubblewrap shell run inside it, and no provider credential is ever in the VM. Since sub-project 3 this is the only agent runtime: there is no switch, and a host without KVM or without `sudo pap vm setup` has no agents (see "The switch"). The host sandbox of ADR 0048 is gone for agents.

Decisions: ADR 0078 (the runtime), 0079 (network and files), 0081 (the VM as the only runtime). Spec of sub-project 3: `docs/specs/2026-10-22-agents-vm-only-design.md`. Spec: `docs/specs/2026-10-19-agents-microvm-runtime-design.md`. Plan and rulings R1 to R38: `docs/plans/2026-10-19-agents-microvm-runtime.md`. Measurements of the real stack: `docs/research/agents-vm-risk-checks.md` (linked, not copied). Install: `install.md` ("Agent VMs"). Checks: `doctor.md` ("Agent VM checks").

Code: `apps/daemon/src/modules/agent-vm/` (gateway, runtime, mirrors, relay link, images, status, trash), `apps/daemon/src/compose-agents-vm*.ts`, `apps/vmd/` (pap-vmd), `packages/pi-host/src/{guest,relay,vm-shell,vm-files}/`, contracts `packages/contracts/src/{agents-vm,agents-vm-methods,agents-net,agents-resources,relay-ipc,vmd}.ts`.

## Settings

| Env | Meaning |
|---|---|
| `PAP_AGENTS_RUNTIME` | Gone. Not read; when it is set the daemon logs one warning (`agents_runtime_ignored`, "PAP_AGENTS_RUNTIME is gone: agents always run in microVMs") and boots. `pap doctor` (`vm.runtimeVar`) also warns. |
| `PAP_AGENTS_MEMORY_MAX_MB` | Cap on the memory of all running boxes together, agents' and projects' ("Project boxes"). Default `max(1024, half of the RAM)`; an integer of at least 1024 or the boot stops. Each VM counts its `memoryMb` plus 512 (`VM_OVERHEAD_MB`). |
| `PAP_TEST_AGENT_RUNTIME` | `process`, tests only: the guest runs as a local process over the same gateway. Needs `PAP_TEST_PROVIDER_SCRIPT`, else the boot stops. Never set it outside tests. |
| `PAP_TEST_VMD_SOCKET` | Tests only: the pap-vmd socket a test daemon dials. Needs `PAP_TEST_PROVIDER_SCRIPT`, else the boot stops. A daemon with the scripted provider must name its pap-vmd (a fake client, a seam or this variable), so a test never reaches the real `/run/pap-vm/vmd.sock`. Never set it outside tests. |
| `PAP_DEV_VMD` | `1` lets a `--dev` daemon (`pnpm --filter @pap/daemon dev`) dial the real pap-vmd. Without it a dev daemon names an unreachable socket under its own home and has no agents: pap-vmd's boot `stopAll` stops every VM it lists, which are the running pap's. Set it only when no live pap runs on this host. |
| `PAP_MIN_FREE_DISK_MB` | As elsewhere (1024). `agents.vmStatus` offers an agent's disk the free space of pap-vmd's state folder less this floor. |

Needs KVM: see "Setup" below.

## The switch

- Agents always run in a microVM. There is no host runtime and no setting that selects one.
- **No KVM, no pap-vmd, a held port: no agents, the rest of pap boots.** The daemon never throws at boot for a missing VM stack. When pap-vmd does not answer or `pap0` never appears, it listens on loopback with an unusable status and stops no VM; a held gateway or proxy port does the same. Sessions, lanes, terminals and triggers that target no agent work as before. Down mode lasts until pap restarts.
- **What the owner sees.** Settings › Agents (and the phone Agents tab, and the New agent dialog) show an EmptyState, "Agents run in microVMs: this machine needs KVM and `sudo pap vm setup`." with a pointer to `pap doctor`. `agents.create` and every start of an agent are refused with the typed error `sandbox_unavailable`; the web maps it to that sentence. Agent rows are kept untouched and come back with the stack. A trigger that fires for an agent, or a VM that dies, while the stack is gone takes the paths a failed VM start takes already (the thread's failure state, the run's failure and its notification).
- **Stale code in the VM** (`vm_bundle_stale`): see "Bundle skew".

## Existing agents: no migration

pap ships no migration. Agents made in host mode are deleted and created again: a VM agent gets a fresh disk at its first start (`disk.create`), and an old agent's recorded thread then fails with "the VM lost this conversation's file; the copy is kept". Delete the agent from its screen, then create it again.

- `pap doctor` lists such agents by name (the host-made agents check: an agent whose recorded thread file is outside the mirrors folder): delete it and create it again. Do not open a host-made agent's thread in the meantime.
- A VM agent's session file is its mirror (`$PAP_HOME/agents/.mirrors/<id>/`).
- Each boot purges the trashed homes (`$PAP_HOME/agents/.trash/<id>-<stamp>` and the `.runs` entries) older than 7 days.

## Architecture in one page

- **pap-vmd** (`apps/vmd`, root, systemd system unit) is the only caller of pap's own containerd, Kata and BuildKit. It reads one typed request per connection on `/run/pap-vm/vmd.sock` (owned by pap's uid, 0600, at most 64 KiB, `VmdRequest` in `vmd.ts`). The daemon never sends a path, a command, an environment or Dockerfile text: pap-vmd builds them. `apps/vmd` imports only `@pap/contracts` and Node built-ins.
- **Disks** live in `/var/lib/pap-vm/<pap uid>/agents/<id>/disk.img` (root, 0700); the daemon never reads them and never parses an image a guest wrote. An isolated task gets a blank disk of pap-vmd's own at `tasks/<key>/disk.img`, deleted when the task's VM stops.
- **Disks stay sparse** (Kata 4.3.1, Cloud Hypervisor v54). A box disk is created sparse (`ftruncate`, then `mkfs.ext4`), and Cloud Hypervisor attaches it with `sparse=on`, so the host holds roughly the blocks the guest used, not `diskMb`. Kata 4.2.0 attached a direct volume with `sparse=off` and Cloud Hypervisor `fallocate`d the whole file at VM start (kata-containers#13864, fixed in 4.3.0). The disk is mounted in the guest with the `discard` option (`options` of the direct-volume info, passed on by runtime-rs to the guest mount), so a deleted file punches a hole in the host file. When a box's VM is confirmed gone (`vm.stop`, container removed and absent from `nerdctl ps`), pap-vmd answers the stop, then copies the box disk with `cp --sparse=always` beside it (`disk.img.reclaim`), checks the size, syncs and renames it over the disk, as its own job under the box lock (10 minute limit; skipped with `no_room` unless the folder has the disk's allocated size plus 256 MiB free; the original is untouched until the rename). A plain `fallocate --dig-holes` does not work here: Cloud Hypervisor pre-allocated with unwritten extents, which it takes for holes, after checking again that `nerdctl ps` shows no live VM of the box and that no process has the file open (`vmd_disk_reclaim_skipped {reason: file_held}` otherwise). It logs `vmd_disk_reclaimed {before, after, reclaimed}` in bytes (`vmd_disk_reclaim_failed {reason}` on a failure, which never fails the stop). A disk pre-allocated by Kata 4.2.0 therefore shrinks at its box's next stop. Run `sudo pap vm setup` after the update to install Kata 4.3.1.
- **Guest** (`pap-guest`, `packages/pi-host/src/guest/`): the VM's entrypoint. It parks the gateway token in a file and re-executes itself without it in its environment, seeds `/agent/.pi/agent` from the image's `/opt/pap/pi-agent`, grows the file system online (`EXT4_IOC_RESIZE_FS`) and starts pi-host workers when the daemon asks, handing each the token on fd 3. Layout: `/agent/{home,knowledge,inbox,.pi}`; Pi runs with `PI_CODING_AGENT_DIR=/agent/.pi/agent` and `GIT_CEILING_DIRECTORIES=/agent`. One VM per agent: the thread, its children and thread tasks are workers in it. The guest seeds `/agent/knowledge` (OKF `index.md` and `log.md`) at every start when absent; the thread and its children are told about it in the prompt, a task VM is not (`knowledge.md`).
- **Gateway** (`gateway.ts`): the daemon listens on `10.213.0.1:7841` and takes length-prefixed JSON frames (4 KiB until the hello is accepted, 4 MiB after; 10 s to say hello, 60 s for a cold boot). Hello checks the agent id, the launch, the token and the protocol. A pap-vmd or guest whose protocol differs is refused.
- **Mirror** (`mirror*.ts`): the daemon keeps a copy of each session file under `$PAP_HOME/agents/.mirrors/<agent id>/` (0700/0600), fed by `session_append` chunks (at most 2 MiB each) and checked line by line (shape, duplicate entry ids, 32 MiB a line, a quota within the agent's disk). Every reader (snapshot, history, the outside-write check) reads the mirror. Opening history never starts a VM. A user entry pap did not send is kept and shown "not sent from pap". A VM rewrite that is not an extension of the mirror keeps the old copy as `replaced/<name>.<stamp>` for 7 days, posts a notice and taints the session (ADR 0074's path).
- **Relay** (`pap-relay`, `packages/pi-host/src/relay/`): a daemon child process, the only holder of provider credentials, listening on `10.213.0.1:7842`. The VM's Pi talks to `http://llm.internal:7842/<provider>/...` and `http://claude.internal:7842/...`. Per request: fixed route table (POST, known paths and queries only), the launch's relay key (bound to the VM's address), the agent's models (the picker's list) and its state (not paused, not over budget); then it forwards over TLS with the credential Pi's auth storage resolves on the host. Every 60 s it reports requests, bytes and refusals per agent (attribution).
- **Network** (`agents-net.ts`, loaded by pap-vmd's unit): a VM reaches the gateway, relay and proxy ports (7841, 7842, 7843) on the bridge address and nothing else. The inet table answers those ports to `pap0` only and drops everything forwarded to or from `pap0`; the bridge table drops any frame from a VM port whose MAC, IPv4 or ARP sender is not its own, all IPv6, and VM to VM. `pap0` is `isGateway: false`: pap does not turn on IPv4 forwarding. The guest has no default route (`ENETUNREACH` for any address off the bridge), and the host firewall would drop a route added by guest root anyway.
- **The VM shell** (`packages/pi-host/src/vm-shell/`): pap's `bash` runs in bwrap as guest root with a seccomp filter (no new namespaces, mounts, `ptrace`, `bpf`, `io_uring`, keys; `clone3` answers `ENOSYS`; `socket` only for AF_UNIX, AF_INET, AF_INET6 and AF_NETLINK, `socketpair` only for AF_UNIX, any other family answers `EPERM`, and another architecture or an x32 call kills the process; with the network off the shell has no route and the INET families reach nothing; with it on they reach the proxy), every capability dropped but seven, the image root read-only, `/agent/.pi` hidden, one overlay-less shell per worker at a time. It is registered for every VM session (the profile's old "sandbox required" switch is ignored; a stored profile keeps parsing with the field present), and is judged like an edit of the agent's own folder whether or not it uses the network (see "Network"). With `sandbox.network` off it has no network (`--unshare-net`); with it on, it shares the VM's network, which reaches only the three bridge ports.
- **Pi's file tools** (`vm-files`): `read`, `write`, `edit` and `ls` open every path component without following a link (`O_NOFOLLOW`); a path Pi would rewrite (`~`, `@`, `file:`, a Unicode space) is refused. `grep` and `find` stay Pi's, and their root is judged by the same rule.
- **Images** (`kata-images.ts`, `image-policy.ts`): three layers built by pap-vmd (base from a pinned Node digest, profile, agent), tags `pap-agent-<layer>-<64 hex>`. The Dockerfile is rendered by pap-vmd; only apt names and pap tags are data. The base is rebuilt with `apt-get upgrade` and no cache once per ISO week (checked hourly, retry an hour after a failure); an agent whose image is being rebuilt keeps running on the old one and gets the notice "a new image is being prepared; this agent runs on the old one". A tag whose guest speaks another protocol is refused. After a successful build and on the weekly tick the daemon calls pap-vmd's `image.prune`, keeping the base, the newest profile, each agent's newest image, every image a VM runs on and, until they start again, the recorded images of agents not started since the boot (pap-vmd also skips any image a container uses); a failed prune is logged, never thrown into a launch. `vm.disk` does not count the image store (pap-vmd reports no size for it); `/var/lib/pap-vm` is where to look. The Pi profile is prepared (copy, secret scan, digest) in a worker thread, once per change: it is skipped when the names, sizes and mtimes of the agent folder's top-level files, the package folders and every copied root equal those of the last good preparation (a file modified in the last 2 seconds is not trusted). Measured on a synthetic profile of 23,210 files and 861 MB with 40 needles: about 5 s on the event loop before, 0 ms of loop time now, about 0.3 s when nothing changed.

## What a VM agent cannot do

- **The network is the proxy's and nothing else, and only when `sandbox.network` is on** (see "Network"): HTTP and HTTPS to hosts on the agent's list. No `apt install` at run time (the VM root is read-only), no `git` over ssh, no database ports.
- **No prechecks.** The owner does not use them, so they were not brought into the VM. Since lot B1 prechecks are removed for every trigger: a stored one is refused at fire time with the journal word `precheck_removed` (formerly `precheck_agent` for agents), never ignored, and the dry-run answers the same word (`automation.md`).
- **`export_html` is refused `sandbox_unavailable`** (it would write a host path from inside the VM).
- The owner's "always allow" grants made for host calls do not cross into a VM.
- Attachments reach `/agent/inbox/` in chunks, one file at a time. A name is sanitised, not refused (NFKD, marks dropped, other characters `_`, 128 characters keeping the extension), so the VM file can differ from the uploaded name; the prompt shows the VM path. A name that already exists is retried once with a `-<4 hex>` suffix and the whole file is sent again; any other failure is `prompt_rejected`.

## Network

Sub-project 2 (ADR 0079, spec `docs/specs/2026-10-21-agents-vm-egress-design.md`). A simple filtering proxy: it reads no content, decrypts no TLS and injects nothing. It guarantees which hosts and ports an agent reaches, not what it sends there.

- **Proxy**: pap's egress proxy (`modules/egress/`) with one more TCP listener on `10.213.0.1:7843`, owned by the daemon like the gateway. It speaks HTTP `CONNECT` and plain HTTP forward requests. No `https://` interception, no other protocol.
- **Who is asking**: the VM's source address, mapped to its running launch (pap-vmd's anti-spoofing pins each VM to its address). No credential rides in the proxy URL. An address with no running launch gets `403` (`x-pap-deny: unknown_source`) and no card.
- **Host list**: the agent's `allowHosts` (`null` = the owner's list from Settings › Approvals). An entry is `host[:port]`: a name (optional leading `*.`) or an IPv4/IPv6 literal (an IPv6 is bare without a port, `fd00::5`, and in brackets with one, `[fd00::5]:6443`; a malformed form is refused). No port means 80 and 443. Widening the list (a port, an IP, a new host) asks the step-up, as before; a `*.` entry never covers an exact entry (an exact entry reaches private ranges a wildcard cannot), so adding `nas.home.lan` under `*.home.lan` asks it too.
- **Address policy**, on every address the name resolves to (the connection uses the addresses it checked; one refused answer refuses the name): loopback, link-local (including `169.254.169.254`), CGNAT, multicast, unspecified, the `pap0` subnet and every address of the host itself are always refused, whatever the list says. Private ranges (RFC 1918, ULA) pass only for an exact name entry or an IP entry, never through a `*.` wildcard (someone else's DNS can point a wildcard's subdomains at your LAN).
- **Answers**: `403` for a refusal, with `x-pap-deny: not_listed` or `blocked_ip` and a one-line body naming the host, the port and the reason (`not_listed`, `private_wildcard`, `blocked_address`) that the client prints. `502` with reason `resolve` when a listed name does not resolve: a failure, not a refusal, so no card.
- **Inside the VM**: workers, Pi and its extensions, MCP servers and the shell get `HTTP_PROXY`, `HTTPS_PROXY` (and lower-case forms) set to the proxy, `NO_PROXY` for `llm.internal`, `claude.internal`, the gateway and loopback, and `NODE_USE_ENV_PROXY=1` (Node's `fetch` follows the variables only with it). The shell's network follows `sandbox.network`, read when its session opens: a later change reaches the shell with a new session. The shell's environment holds no `PAP_*` key and cannot read the gateway token.
- **No approval card for network in a VM**: a shell command is judged like an edit of the agent's own folder, tainted or not. The host list is the only barrier at the exit. A shell command run with `sandbox.network` on is external: the worker taints its own session at the first result (sticky, the "external content" chip; no egress report is read any more, so a trusted source does not clean it); with it off nothing taints. The daemon's own mark comes from the proxy (see "Taint the daemon sees"). Platform ops keep their own rules.
- **A refused host** shows a card in the agent's thread (solid frame, `BLOCKED` chip) whose button opens a dialog: the host and port, the attempts (count, last time, "thread" or the task's name), a line when the address is private, the scope ("this agent only, from its next request") and `ADD TO LIST`, which asks the step-up. An agent on the owner's list gets its own copy plus the entry; the owner's list and other agents are untouched. Nothing is retried for the agent. A host that resolves to an always-refused address has no button. The card comes with one Inbox item (`agent_egress`) and one push. At most one card, item and push per agent and host:port per hour; later refusals in that hour raise the card's count. At most 20 new cards per agent per hour (the rest are logged `egress_refusal_card_cap`). The dedupe is in memory: a daemon restart can raise one more card per host:port.
- **Counts and logs**: per launch every 60 s (a task's VM and the thread's VM count apart), requests, bytes and refusals (`egress_vm_usage`). Refusals of a card update it at most once a minute (the count in memory is exact and flushed), and the card-cap and unknown-agent log lines come once per agent a minute with the number they stand for. A refused host is logged as written when the owner wrote it, else `h:<12 hex> (len N)`.

Limits:

- Tunnels have limits: 32 connections per agent, 120 s idle, 30 min life (a long idle `kubectl watch` is cut), no byte cap. DNS lookups are bounded (2 in flight for all VMs, 1 per VM).
- HTTP and HTTPS only. `git` over ssh, database ports and other protocols have no path. `git clone https://...`, `npm`, `pip --user`, `npx` and static binaries work when `sandbox.network` is on, their hosts are listed and the tool follows `HTTP_PROXY`/`HTTPS_PROXY`; one that ignores them (a raw socket client) has no path.
- A listed host gets whatever the agent sends: scope credentials at the source (a read-only RBAC service account, an OAuth read-only scope). pap does not restrict methods or content.
- A name the agent chose can resolve to a LAN address only through an exact or IP entry; the dialog says so.
- With the network on, the shell shares the VM's loopback and abstract-socket namespace with the worker, Pi and MCP servers: any local listener in the VM (an MCP server with an HTTP transport, say) is reachable from the shell. pap has none today. The relay (`10.213.0.1:7842`) is reachable too; its per-launch key, which the shell cannot read, is the barrier.
- Counting is by VM: a task VM's requests are the task's, the thread's VM serves the thread, its children and thread tasks.

## Taint the daemon sees

Sub-project 3 (ADR 0081). A VM worker also reports its own taint, but a compromised VM can simply not report, so the daemon marks from what it sees itself.

- **The proxy marks.** Each time the VM proxy (`modules/egress/vm-listener.ts`) opens a tunnel, or forwards a request, for a VM to a host that does not keep content clean, it tells the sessions module. A host keeps content clean only when it is one of the agent's trusted sources reached over `CONNECT` 443 (`cleansContent` in `@pap/contracts`, one rule for the worker and the daemon). A refused request (listed or not, a failed resolve included) marks nothing: nothing came in.
- **The mark belongs to the launch.** What came in stays in the VM's memory and disk, so every session that runs in that launch is tainted: the ones live at that moment and the ones that start later in it (the thread, its children and its thread tasks share the thread's VM; a task VM is its own launch). The record is the policy module's (`session_policy`, which `PlatformKind.tainted` reads for `whenTainted`, delegation isolation and trusted autonomy), reached through the daemon-side `sessions.mirror.taint(sessionId)` with no epoch, so a worker's clear cannot race it. One audit row (`tainted_outside`) per session, once.
- **Sticky.** The worker's own reports (a networked shell's first result, an external tool result) can add taint and never clear it. A new launch starts clean. The mirror-resync taint stays.
- **Project boxes.** The same launch rule holds for a project's box, but the mark also comes from the sessions themselves: when the policy module records a taint for a box session (a worker's report, a task created tainted) the daemon marks the session's launch, taints every session joined to it and every one that starts later in it. A session that joins a launch while already tainted marks it as it starts. Agent boxes are unchanged (the proxy marks, a worker's report taints its own session only).

## The vault in the VM

Sub-project 3 (ADR 0081, extending ADR 0079). The vault's values the agent may use, and its one-use values, reach a VM session the way they reached a host-sandboxed one: in the worker's `init.vault` and `init.once` and its live `vault_update` frames (a value the owner adds mid-thread reaches the next shell command). A child never holds the vault (RT-07).

- The VM shell gets them in its environment; the fixed names (`PATH`, `HOME`, `LANG`, `TERM`) and the proxy variables win, and no worker credential is passed. A one-use value goes to the first command that names it, then `secret_used` tells the daemon.
- `secret.request` (the card where the agent asks the owner for a value) works from a VM session.
- Redaction is unchanged: the worker redacts the vault's values from everything it sends, from the first byte. ADR 0049's limits apply inside the VM: a command the agent runs can print a value, the redactor misses values under 8 characters and encoded ones, and a process in the VM can read the shell's environment. Provider keys and the Claude token never enter the VM.
- The stored profile's "sandbox required" switch is retired: every started agent session counts as sandboxed for the vault.

## Bundle skew

Sub-project 3. The code that runs in a VM is the agent bundle (built into a `dist-agent` folder under `packages/pi-host` by `scripts/build-agent-bundle.ts`), which `pap vm setup` installs as `/opt/pap-vm/agent-bundle`. The Kata base image's tag is a digest of that installed folder (`kata-images.ts`).

- At its first check the daemon takes the same digest of the bundle built with it (its own tree's `dist-agent`) and keeps it for the life of the process: that is the code it runs with, so rebuilding the tree while pap runs does not flip the verdict.
- Before a VM start the installed digest is compared (a mismatch is confirmed with a fresh read, so a `pap vm setup` since the one-hour cache is seen). When it differs, no VM starts and the thread shows `vm_bundle_stale`: "The code inside this agent's VM is older than pap. Run `sudo pap vm setup`, then open the thread again. Nothing was lost." The log gets `vm_bundle_stale` once per agent and boot. The check also fires on a spawn into an already running thread VM; a VM already running old code keeps running after `pap vm setup` until it restarts.
- A change to the web app or the daemon alone does not change the bundle and asks for no root step. When the daemon has no bundle of its own to compare (an install without the tree), the check is skipped with one `vm_bundle_unchecked` info log. `pap doctor` (`vm.bundle`) says the same.
- **A silent `worker_exited` is no longer silent.** When the wire closes, the daemon waits up to 2 s on the kernel `Clock` for the guest's `exited` frame, so `worker_exited.output` carries the worker's last words (the failing schema paths, never a value). The policy-rules refusal names its failing paths (`policy.<path>`, at most 8).

## Prompt chips

`agents.prompts` and `agents.prompt` read the `.md` files the owner imported directly under `prompts/` in the agent's files (the host copy of the Files tab, same bounds as before: no link followed, a regular file, 16 KiB, UTF-8). Files the agent writes itself in its VM are not listed: the daemon never reads a VM disk.

## Providers and the Claude token

- The relay serves providers whose Pi `api` is `anthropic-messages`, `openai-completions`, `openai-responses` or `google-generative-ai`, with an API key. The credential comes from Pi's auth storage on the host (`auth.json`, `models.json`), read through `$VAR` and `!command` references like Pi does; answers are kept 60 seconds, so a `!command` key runs once per (provider, model) per 60 seconds and concurrent misses are not merged.
- **OAuth providers are refused** (no request is forwarded). T0b could not test one: the owner's `auth.json` held only an API-key provider, so the relay's header rule for an OAuth login is unverified. `cloudflare-ai-gateway` is unsupported (its key rides in headers behind placeholder base URLs). A model with duplicate top-level `model` keys in its JSON body names no model and is refused.
- **pi-claude-bridge** goes through `claude.internal`. The token is the user's own `claude setup-token`, set in Settings › Agents (`agents.vm.setClaudeToken`, `settings:operate`, step-up, browser only) and stored in that user's vault as `CLAUDE_TOKEN` (M14; before it, one file `$PAP_HOME/secrets/claude-token`, which moves to the owner's vault at first start and is then removed). The daemon sends it to the relay child inside `box_policy` as `claudeToken`; the VM never holds it. T0b: `claude` 2.1.289 works through the relay (Bearer upstream, 200). `agents.vmStatus` reports the caller's own status, `set` or `missing`, never the value. A bad token file is a fixed word in the log, never its content.
- pap sets the bridge's Claude Code environment per agent, for agents that use pi-claude-bridge only (its provider, or its package among the picks; ADR 0080). In a VM: `IS_SANDBOX=1` (the CLI refuses `--dangerously-skip-permissions` as guest root otherwise) and `CLAUDE_CONFIG_DIR=/agent/home/.claude` (`HOME` is `/root`, on a read-only root). The daemon sends them in the spawn command; the guest applies a closed allowlist (`IS_SANDBOX` equal to `1`, `CLAUDE_CONFIG_DIR` under the home without `..`) and logs and drops the rest. The image holds no `IS_SANDBOX`. The bridge's own Claude Code tools run as VM root without pap's per-command shell policy: the VM boundary and the egress proxy still apply.
- A launch right after boot waits up to 30 seconds for the relay to report ready on `10.213.0.1:7842`, then is refused `sandbox_unavailable`. The daemon also checks that the sockets on `10.213.0.1:7841` and `:7842` are its own (`/proc/net/tcp` and `tcp6` against the process's fds); a foreign holder refuses the launch (`relay_listener_foreign`).

## Secrets in the profile

Before an image is built, pap scans the Pi profile files it would copy for the owner's known values: every string of 8 characters or more in `auth.json` (through Pi's auth storage), the vault's values, the Claude token and literal provider header values. A hit stops the build with "a Pi profile file holds a secret; it does not enter the image" and names the file, never the value. The same set masks the relay's stderr before it is logged. Limits (same as ADR 0049's redactor):

- values under 8 characters are never needles;
- encoded values (base64, split, reversed) are missed; the scan matches the literal and its JSON-escaped form;
- Pi references (`$VAR`, `!command`) are not needles: they hold no value;
- OAuth metadata in `auth.json` (an email, say) is a needle and can cause a refusal;
- more than 4096 needles, or an unreadable `auth.json`, refuses the build rather than skipping the scan.

Key handling in the profile (`!command` keys, `cloudflare-ai-gateway`, the 8-character minimum, encoded values) is described in "Providers and the Claude token" and in this section.

## Packages and resources

- `AgentInput` gains `resources` (`memoryMb` 512 and up, default 1024; `cpus`, default 1; `diskMb` 1024 to 65 536, default 4096), `systemPackages` (Debian names, 64 at most) and `packages` (the owner's Pi packages picked in the form, 64 at most). Memory and cores are checked against the host at save (`bad_request`, the field is logged as `agent_resources_refused`); the disk only grows.
- Packages are stored as plugin ids. Packages saved earlier as source strings read as input `null` (no data migration; the branch was unreleased): pick them again in the form.
- A 4 GiB agent disk takes about 330 MB on the host after its first boot (sparse file, lazy ext4 init). Cold start is about 6 s; a running VM costs about 200 MB of host memory beside its own. Details: `docs/research/agents-vm-risk-checks.md`.

## Files

A VM agent can hold its own credentials as files in its home (ADR 0079): a kubeconfig at `.kube/config`, an `~/.netrc`, a scoped token file. The owner imports them in the agent's **Files** tab; provider keys and the Claude token never go this way.

- **Limits.** 1 MiB per file, 32 files per agent. A path is relative to the agent's home (`/agent/home`, the shell's `$HOME`): 1 to 8 segments of letters, digits, `.`, `_` and `-`, no `.` or `..` segment, 512 characters at most. The tab lists path, size and import date, never the content. Importing to an existing path replaces the file.
- **Import and remove.** Import is `PUT /agent-files?agentId=<id>&path=<path>` with the raw body (browser cookie only, `agents:admin`, never a token, the app's Origin check; 2 imports in flight per owner). Remove is `agents.files.remove`, list is `agents.files.list` (same permission). Each import or removal writes one audit row (`agent file imported`, `agent file removed`) with the agent, path and size, never the content.
- **On the host.** `$PAP_HOME/secrets/agent-files/<agentId>/<path>`: folders 0700, files 0600 (written to a temporary name, then renamed), the import date is the file's mtime. A removal that the VM has not applied yet is kept in `agent-files/.removals/<agentId>.json` (0600) until the VM confirms it.
- **In the VM.** At every VM start, the thread VM and each task VM alike, pap writes the files into the home through the worker (parents opened one by one without following a link, file written 0600 through a temporary name, folders 0700, a path re-checked by the worker). Removals are sent first. A change or removal reaches a running thread VM at once when it has a live worker; with none (the VM idles between prompts) it is kept and sent to the next worker that starts in that VM, as it is at the next VM start (a task VM gets it at its next start). A file the agent edited is overwritten by a later import or start. The agent can read its files, as can anything running in the VM, and can send them to any host on its list: scope the credential at its source (read-only service account, narrow token). Quarantine does not delete the files; it lists their paths (`filePaths`, step `files`) so you can revoke them at the source.
- **Delete and trash.** Deleting the agent moves `agent-files/<agentId>` to `agent-files/.trash/<id>-<stamp>`, kept 7 days like the disk and the mirrors; "Purge now" removes it at once; the daily sweep removes the expired ones. The trash is inside `secrets/`, so a plain backup excludes it too.
- **Backup.** A plain `pap backup` excludes `secrets/`, so imported files, pending removals and the files trash are not in it, and `pap restore` leaves the Files tab empty: import them again (a file already in a VM's home stays there until the VM's disk goes). `pap backup --encrypt --secrets include` carries them; treat that file as holding credentials. See `backup.md`.
- **Known limits.** No password step-up on import or remove. A file is delivered after the worker starts, so a first prompt can in theory run before the last file lands (milliseconds against a first model turn of seconds). The VM status is read when the agent screen opens: after a runtime change, reload.

## Delete, trash, purge

Delete moves the agent's disk to pap-vmd's trash, its mirrors to `$PAP_HOME/agents/.trash/<id>-<stamp>.mirrors` and its imported files to `$PAP_HOME/secrets/agent-files/.trash/<id>-<stamp>` ("Files"), all kept 7 days. "Purge now" (`agents.purgeTrash`, `agents:admin`) removes the disk, the mirrors and the files trash at once but leaves the trashed home and `.runs` folder for their 7 days (the sweep removes them at boot and daily).

## Setup

`sudo pap vm setup --user <name>` and `sudo pap vm uninstall [--purge]`: `install.md`, "Agent VMs". Needs `/dev/kvm` and x86_64 (the pinned artefacts are amd64). pap-vmd runs from `/opt/pap-vm`, installed from pinned artefacts; `pap update` does not update it, so after an update `pap doctor` says `vm.vmd` fails until you run `sudo pap vm setup` again. `agents.vmStatus` and the Settings › Agents page show the same sentence, and creating or starting an agent is refused `sandbox_unavailable` while the stack is unusable. The doctor checks are in `doctor.md`.

| "A new image is being prepared" | A base or profile rebuild runs; the agent keeps its old image. A failed weekly upgrade retries after an hour. |

## Project boxes (lot B1, ADR 0083)

A project made from a name (`projects.create`) has a box: a Kata microVM like an agent's, one per project. Its sessions, subagent children and trigger tasks run in it, one trust zone: taint is per launch, so a tainted session taints every session of that launch (tasks included) until a new launch (an idle stop, then a start, or Restart box). The daemon marks the launch from any taint of one of its sessions (a worker's report, a task that starts tainted such as a webhook or feed task, the proxy), not from the proxy alone; agent boxes keep their own rule below. Specs: `docs/specs/2026-10-23-boxes-b1-design.md`, `docs/specs/2026-10-23-boxes-design.md`. The host's file and git helpers never receive a box path, and neither do Pi's configuration helpers: project-scoped MCP, skills, plugins and trust are not available for a box project in B1 (the daemon answers `invalid_cwd` for a box root, the web sends no folder for it and says "Not available in a box yet."). Fork and Duplicate of a box session are refused (`sandbox_unavailable`, before the host's Pi opens anything) and hidden in the web: the session file is the VM's. Host projects (made from a folder) keep working as before until lot B4.

- **Layout.** The disk is mounted at `/boxes/<projectId>`: `project/` (the repository and the sessions' cwd), `home/` (`HOME`), `inbox/` (attachments), `.pi/sessions` and `.pi/agent`. **The guest path is pap's path**: a box project's `root` in pap is `/boxes/<projectId>/project`, and the same string appears in transcripts, Files, Changes and triggers. The daemon routes any path at or under that root to the box, whether or not it exists on the host, and judges it as text (no `realpath`): `/boxes/<id>/project/../x`, `/boxes/<id>/projectX` and another id are not box paths. The process backend (tests) uses the same names under `$PAP_HOME/tmp/boxes/<projectId>`. pap-vmd keeps the disk at `/var/lib/pap-vm/<uid>/projects/<projectId>/disk.img`.
- **Identity.** `PAP_BOX` (`agent:<id>` or `project:<uuid>`) replaces `PAP_AGENT_ID` in the guest and the worker. `AGENT_VM_PROTOCOL` was 2 in lot B1 and is 3 since lot B2: an older hello is refused (`protocol`), so `sudo pap vm setup` is needed after the update. Launch tokens, the relay, the proxy, the crash log and the bundle-skew check are keyed by box.
- **Creation and defaults.** `projects.create {name}` inserts the project and starts nothing. Defaults: 2048 MB, 2 CPUs, 8192 MB of disk (the disk only grows); at most 2000 projects. At the first start the guest seeds the layout and runs `git init -b main` in `project/` when there is no `.git`. A Scratch project (`projects.scratch`, one per user, renamable) serves sessions outside any project; it cannot be deleted while it holds sessions.
- **Policy profile `project`.** pap's VM shell and VM file tools; writable roots `project/`, `home/`, `inbox/`; own folder `project/`; `sandbox {required: true, network: true}` (the proxy decides what is reached); no "always" grants carried in. The shell is judged as an edit of the own folder (not asked in auto-accept-edits, asked in supervised, blocked in read-only). A `project` rule without a VM is blocked. No agent prompt; the OKF section is added when the worker finds `project/knowledge/index.md` itself. Context files (`AGENTS.md`) load; the repository's own `.pi/` resources (extensions, skills, MCP configuration, settings) do not (see Known limits). The owner's models and budgets apply through the relay; `export_html` is refused (`sandbox_unavailable`).
- **Guest operations.** The guest link carries `op {id, name, args}` and `op_result {id, ok, value | code}`. Names: `fs.list`, `fs.read`, `fs.write` (atomic, etag), `fs.put` (upload chunks, `skip` or `replace`), `fs.get` (download chunks), `fs.search` (`@` mentions: git's file list, ripgrep), `git.status`, `git.blob`, `knowledge.state`, `knowledge.enable`, `project.config`. At most 8 in flight per box, 30 s each, frames within 4 MiB (`BOX_OP_LIMITS`); results respect `FILE_LIMITS` and `VCS_LIMITS` (an oversized result answers `payload_too_large`). Every path is judged in the guest under `project/` without following links; `.git` is never listed and never written; `home/`, `inbox/` and `.pi/` are not shown. git runs in the guest with the neutralised command line (no fsmonitor, hooks, filters or external diff; `contracts` holds the shared argv). The daemon judges names and protected paths itself (`box_stopped` aside, the rules of `files.md` apply). `BoxOps.call` resets the idle wait; **`BoxOps.poll`** does not and never starts a box (the `vcs` poll and subscriptions use it). A box that is not running answers `box_stopped` at once; browsing never starts a VM.
- **Image and packages.** The project image is the agent layer's mechanism with the Debian packages of `.pi/project.yaml` `packages` (at most 64, `SystemPackage` rule). At each start the guest reads the file and reports the list. When it differs from the list the image was built from, the project page shows PACKAGES CHANGED and **Rebuild** (`projects.rebuild`, `sessions:admin`). The project page lists both the packages the image was built from and the ones the file asks for, so the owner sees what a rebuild installs. A rebuild never starts by itself and runs behind running sessions; the new image applies at the next start or at Restart box, and a notice says so. State: `$PAP_HOME/vm/project-images.json`.
- **Lifecycle.** A box starts on a session launch, a trigger task or **Start** (`projects.startBox`); **Restart box** (`projects.restartBox`) stops it and starts a new launch (clears taint, applies a rebuilt image, resumes a crash-paused box). It stops after `PAP_WORKER_IDLE_MINUTES` with no worker and no guest operation. A refused start shows its code: `capacity`, `vm_bundle_stale`, `agent_paused`, `sandbox_unavailable` (or `disk_low`); no box is stopped to make room for another. After 3 crashes in 10 minutes launches pause and the Inbox gets a **`box_paused`** item (`refId` = the project id, one per project, removed when the project is deleted; a restart resumes the box but does not remove the item).
- **Delete and trash.** `projects.delete` (`sessions:admin`, password step-up) stops running workers and tasks (a running task ends `cancelled`), removes the project's sessions, search rows and triggers, stops the box, moves the disk to pap-vmd's trash (`project_<id>-<stamp>`) and the mirrors to `$PAP_HOME/boxes/.trash/<id>-<stamp>.mirrors`, kept 7 days (swept daily); recovery is by hand. A `deleting` box answers `not_found` to new work; a failed delete leaves the mark and a retry finishes it. When the rows are gone the shell stream publishes `projectRemoved {projectId}`: every client drops the project and its sessions at once, and the settings dialog of the deleting client closes and goes home.
- **Mirrors.** A project session's file is mirrored under `$PAP_HOME/boxes/.mirrors/<projectId>/` (0700/0600), the agents' shape, with a quota of the project's `diskMb`. Search watches both mirror roots (`search.md`).
- **Network.** A box reaches the owner's host list plus its project's list (at most 256 `host[:port]` or IP entries, edited in the project's settings). The list belongs to the project and the box reaches it on top of the owner's list, which it never changes (the settings field says so). The proxy reads the project's list on every connection. **`network.request`** is callable by box sessions (agent threads, plain sessions of a box, tasks, children); "Allow this host" adds exactly that host to that project's list (audit `project_host_added`, detail `{projectId}`, no raw host; a full list answers `limit_reached`). A host session cannot call it; an unattended task's request is the existing unattended question (no answer means deny). 10 requests per hour per session.
- **Memory cap.** `PAP_AGENTS_MEMORY_MAX_MB` keeps its name and covers every running box, agents' and projects' (each counts `memoryMb` + 512).
- **Log field rename.** The gateway, relay, guest-link, runtime, bundle-skew and egress log lines print `box` (`agent:<id>` or `project:<uuid>`) where they printed `agentId`. Outside queries and alerts that match `agentId` must follow.
- **Permissions.** `projects.create`, `scratch`, `startBox`, `restartBox`: `sessions:operate`; `projects.box`: `sessions:read`; `setBox`, `rebuild`, `delete`: `sessions:admin`, which is never granted to an API token (a token must not widen a box's egress or delete one).
- **Tests.** The process backend runs project boxes with the real guest and worker over the scripted provider (`testing/box-bed.ts`; `boxes.int.test.ts`, `boxes.network.int.test.ts`, `boxes.delete.int.test.ts`, `boxes.host-reads.int.test.ts`, which fails if the daemon's file system or git helpers ever receive a path under a box root). `createFakeVmd` covers box requests; `createFakeBoxOps`, `createFakeBoxControl` and `createFakeProjectBoxSource` (`kernel/testing/fake-boxes.ts`) serve unit tests. The Kata journey is `modules/agent-vm/project-box.kata.int.test.ts` (local only, `CI=1 pnpm vitest run --project kata`). Tests never reach the real pap-vmd.

## The terminal and GitHub in a box (lot B2, ADR 0084)

Specs: `docs/specs/2026-10-24-boxes-b2-design.md`. Code: daemon `modules/terminal/remote-pty.ts` and `modules/agent-vm/{guest-ptys,box-terminals}.ts`, `modules/github/` (App, tokens, projects, lists), guest `packages/pi-host/src/guest/ops/{github,git-remote,github-env}.ts` and `packages/pi-host/bin/{gh,pap-git-credential}`. Web: `web.md`.

- **Protocol 3.** `AGENT_VM_PROTOCOL` is 3 (a `terminal` hello role, the `git.clone`, `git.commit`, `git.push`, `git.link`, `git.unlink`, `github.token`, `github.identity`, and `github.forgetKey` ops, pty frames; no op runs `gh`). A protocol-2 guest is refused: run `sudo pap vm setup` after the update. The base image also changes (node-pty, `openssh-client`, `gh` at `/usr/local/bin/gh`; image salt `pap-base-2`), so the first start after setup rebuilds it.
- **Terminal.** A terminal whose folder is at or under a box project's root runs in that box (`boxCwdOf`, the same text judgement as Files), as the guest's root user without bwrap (it is the owner's shell), with `HOME = home/`, the proxy variables and the git identity below. Each terminal is its own gateway connection (a pty hello with the slot the daemon asked for); the guest stops reading the pty while more than 1 MiB is unacknowledged; one output frame carries at most 64 KiB raw. The daemon keeps its terminal module (ring, replay, attach, `PAP_MAX_TERMINALS`, binary frames); a remote pty replaces the host pid, so the kill ladder sends SIGHUP, then SIGKILL after 2 s through `pty_signal`. Opening a terminal starts a stopped box (an explicit action); a box that cannot start answers its start code. Stopping or restarting the box, a lost gateway link or a daemon restart ends its terminals (`exited`). Host projects keep the host terminal until lot B4. Details: `terminal.md`.
- **Idle.** A terminal counts as a worker for the idle stop only while a browser is attached or it printed within `PAP_WORKER_IDLE_MINUTES`. A new terminal counts as output for one window, so a detached, silent terminal frees the box after up to about twice the idle time. A shell left open in a closed tab does not keep a 2 GiB box running.
- **The App.** One GitHub App per pap, created from Settings › GitHub (`auth.md`, "GitHub callbacks"; `install.md`, "GitHub"). Its file is `$PAP_HOME/secrets/github-app.json` (0600, no links followed, at most 16 KiB). Each user's own token and refresh token are in that user's vault scope as `GITHUB_USER_TOKEN` and `GITHUB_REFRESH_TOKEN`, with `GITHUB_TOKEN_META` (expiry and the reconnect flag). The App is public (`APP_PUBLIC` is true in `modules/github/manifest.ts`, Q1 of M14): each member installs it on their own GitHub account. A backup of the whole `$PAP_HOME` holds all of this, like the vault key.
- **Tokens.** The host mints a box token for the project's repository only: `{contents: write, pull_requests: write}`, never `administration`, and checks the answer names exactly that repository. It sends it at each box start and every 45 minutes while the box runs (`github.token`); the guest writes `/run/pap-github/token` (tmpfs, 0600; line 1 the token, line 2 its expiry). A git credential helper (by absolute path in `home/.gitconfig`, answering only the GitHub web host) and the `gh` wrapper read it. The project's VM shell mounts `/run/pap-github` read-only. **The token is readable inside the box**: every process there, the model included, can read it, so a session can push, and a session driven by an API token can push too (the push and PR methods refuse a token; the box cannot tell who drives it). Its reach is one repository for one hour; the proxy keeps the box to the project's hosts. The GitHub tab's lists and a check's log use read-only installation tokens, cached 60 s (50 items per list, releases the latest 20). A user's token (8 hours; refreshed once at a time, the new pair written to the vault first) does the user-only calls: the repository picker, fork, adding and removing signing keys.
- **Identity and signing keys (R5).** The box's `home/.gitconfig` holds `user.name` (the GitHub login), `user.email` (`<id>+<login>@users.noreply.github.com`), `gpg.format ssh`, `user.signingkey` (the public key, `home/.ssh/pap_signing.pub`), `gpg.ssh.program` (`pap-ssh-sign`, in the bundle's `bin` and linked at `/usr/local/bin`), `commit.gpgsign true` and the credential helper. The key is an ed25519 pair made in the box; the private key is in `/boxes/<id>/.pap/signing/` (0600, guest root), outside every session bind (R8). Guest root runs an `ssh-agent` (socket `/run/pap-github/agent.sock`, started at delivery and at box boot when the key exists, stopped on unlink and delete) that holds the key; `pap-ssh-sign` sets `SSH_AUTH_SOCK` and runs `ssh-keygen`. The key never leaves the box. Known limit: while the box runs and the project is linked, a session can ask the agent to sign, so it can make commits GitHub shows as Verified for the owner; it cannot copy the key. The guest writes `home/.gitconfig` and `home/.ssh/pap_signing.pub` by a temporary file and a rename and refuses a link in place of `.ssh`. The host adds the public key to the owner's account as `pap <project name> <first 8 of the project id>` and keeps its GitHub id; deleting or unlinking the project removes it, and a removal that fails is retried at the daily sweep. A project's repository config is not used for this: daemon ops run with `GIT_CONFIG_GLOBAL=/dev/null` and pass the identity and signing settings on their command line, from `/boxes/<id>/.pap/github.gitconfig`, and one project owns the box. A repository cloned by hand in the same box also signs as the owner. The guest's network git ops (clone, push) refuse a repository whose own config sets `core.sshCommand`, `credential.*`, `url.*.insteadOf`, `http.*` and similar keys (`conflict`).
- **Projects from GitHub.** `projects.createFromGithub` clones or forks (the owner picks); a fork waits up to 60 s for GitHub, then fails `github_unavailable`. The project gets the hosts github.com, api.github.com, codeload.github.com and objects.githubusercontent.com on its host list, visible and removable. The clone runs in the guest into a temporary sibling folder and is moved into `project/` on success: a failed clone leaves `project/` empty and the project intact (`projects.cloneAgain` retries when the folder is empty; otherwise `conflict`). `projects.linkGithub` adds `origin` to an existing project; `projects.unlinkGithub` removes `origin` and the key. State is in the `project_github` table.
- **Push and pull request.** `projects.commitPush` (message, the current branch) runs `git.commit` and `git.push`; `projects.prCreate` (title, body, base) pushes, then the daemon calls `POST /repos/{repo}/pulls` with a one-use installation token for the repository with `{pull_requests: write}` only (head = the pushed branch, base = the given or the default branch; an existing pull request is `conflict`; R9). They are the owner's action and do not ask under taint. Delivery (token, identity, clone) uses `BoxOps.poll`: `BoxOps.call` resets the idle wait, delivery never does. The box token last delivered is revoked (`DELETE /installation/token`) on unlink and delete. For a fork project, Open a pull request pushes and returns GitHub's compare page (`https://github.com/<upstream>/compare/<base>...<login>:<branch>`): pap never calls the upstream's API. Op timeouts: `git.clone` 600 s, `git.push` 120 s, others 30 s.
- **The GitHub section.** `projects.github` lists open pull requests with their checks, open issues and the latest releases; `projects.checkLog` returns the last 64 KiB of a failed job's log. GitHub answers the log call with one redirect: pap follows it once, only to `*.actions.githubusercontent.com` or `*.blob.core.windows.net` over https (no userinfo, no IP literal, the same DNS guard), without an Authorization header, and caps the download at 32 MiB. `projects.sendToSession` hands a log or an issue to a session of the project, fenced as `UNTRUSTED · github actions` or `github issue`, and the session is tainted. All text from GitHub is data.
- **Permissions.** `github.status`: `settings:read`. `github.startCreate`, `authorizeUrl`, `disconnect`: `settings:admin`; `github.forget`: `settings:admin` with step-up; `github.repositories`: `sessions:operate`. `projects.createFromGithub`, `linkGithub`, `unlinkGithub`, `cloneAgain`, `commitPush`, `prCreate`, `sendToSession`: `sessions:operate`. `projects.github` and `projects.checkLog`: `sessions:read`. Browser only (a token gets `forbidden`): everything except `github.status`, `projects.github` and `projects.checkLog`. `settings:admin` is never granted to a token (R3).
- **Secrets.** The App key, client secret, user and refresh tokens and live box tokens reach no log, audit row or response; the owner-secrets collector learns them (`GithubTokens.liveValues()` for box tokens). Only `secrets/github-app.json` and the tmpfs token file hold them on disk.
- **Tests.** The fake GitHub (`kernel/testing/fake-github.ts` and `fake-github-git.ts`: API, git smart HTTP, a fake `gh`) stands in for github.com and api.github.com. A test daemon reaches it through `PAP_TEST_GITHUB_ORIGIN` (tests only; needs `PAP_TEST_PROVIDER_SCRIPT`; stops the boot without it; a loopback `http` origin only). Journeys: `apps/daemon/src/boxes-b2.*.int.test.ts` (terminal, App and state refusals, clone, fork, signed push and PR, the GitHub section, `no secret in logs`). The Kata journey is `modules/agent-vm/box-terminal.kata.int.test.ts` (local only). No test contacts a public host. `pnpm build` passes the pnpm store root to `deploy` (R7), whatever the `v10` or `v11` suffix of `pnpm store path`.

## Members: boxes and the host gate (M14, ADR 0085)

Code: `apps/daemon/src/modules/users/`, `apps/daemon/src/modules/agent-vm/{claude-tokens,claude-token-service,relay-link}.ts`, `apps/daemon/src/modules/github/{access,keys,deliver}.ts`, `apps/daemon/src/kernel/box-path.ts`, `apps/daemon/src/kernel/ws/client-path-gate.ts`, `apps/daemon/src/compose-users.ts`. Run `sudo pap vm setup` after the update: the relay in the bundle changed.

- **A member's work is in boxes only.** No host project, worker, terminal, lane or lane script. The dispatcher refuses any path or cwd that is not at or under one of their box project roots (`forbidden`) before any fs call, for Files, Changes and the raw routes. `assertBoxOnly` returns the `{projectId, root}` it matched and the caller routes with that, so a box removed between the gate and the routing never falls through to a host `realpath`. Background code asks `auth.isMember(ownerId)`. Unknown ids are gated like members.
- **The Claude token is per user.** `policyOf` and `policyOfProject` compute `claudeToken` for the box's owner and send it in `box_policy`; `replay()` resends it and the revoke's empty policy clears it. `ClaudeTokens.onChange` calls `relay.refreshAll()`. A box whose owner has none gets `claudeToken: null` and the relay's `no_claude_token` refusal. Another user's token is never used, and there is no fallback to the owner's. A vault failure is not reported as "missing" (one warning, a distinct state); with `vault_key_lost` the legacy file is kept and the daemon still boots.
- **Shared providers.** A member's box policy models, `sessions.models` and `sessions.availableModels` drop providers the owner has not shared (`finops.md`, "Members: budget line and shared providers"). `claude-bridge` is exempt and goes through the user's token.
- **Budget and pause at the relay.** `policyOf` answers `blocked: "budget"` once the member line reaches the `budget_usd` column, and `blocked: "paused"` for a disabled owner. A policy refresh is pushed on `onRunEnd` for project boxes as well as agents.
- **The launch gate for a disabled owner.** `status.require()` and `BoxControl.start` refuse their box or agent with `account_disabled`, so a worker restart or a queued start cannot boot it. The gate fails closed before `bindLate` (`sandbox_unavailable`) and is checked again right before the spawn (`guardedLaunch.spawn`), so a disable during an await does not slip through. Disabling stops their boxes and agent VMs; data stays.
- **GitHub per member.** Each user authorizes the same App on their own account (`auth.md`, "Roles, invitations and disabled accounts"). Every installation-token mint (the box token, list tokens, the pull-request token) goes through `mintFor(ownerId, repo, perms)`, which runs the access check first: does the project owner's own user token reach the repository with push (OQ3, RT-01)? The answer is cached 10 minutes; if GitHub cannot be asked, the last answer holds for at most 60 minutes and then access is refused; a 401 on the user token counts as lost access and revokes the last box token. Linking and cloning check fresh, with no cache. A repository only the owner's installation reaches is therefore not reachable by a member. The signing key is added to, and removed from, the member's own account.
- **Delete.** Box projects go to the project trash and agents to the agent trash; box disks and agent homes wait for the 7-day sweep of vmd, so the trash keeps data. GitHub signing keys are released first. A key whose removal GitHub refuses is logged (`user_delete_github_keys_left`) and the delete goes on.
- **Memory cap.** One global cap for every box, first come (`PAP_AGENTS_MEMORY_MAX_MB`); there is no per-user VM quota.

## Known limits

- **The boundary is KVM's.** A guest kernel or Cloud Hypervisor escape is the residual. x86_64 only.
- **Network is HTTP(S) through the proxy only** ("Network"): no content filtering, no per-method rules, no ssh, no TLS inspection.
- **OAuth providers** are refused (R9); the relay's header rule for one is unverified (T0b, above).
- **pap-vmd lags `pap update`** until `sudo pap vm setup` (R6): `vm.vmd` fails and launches are refused meanwhile.
- **`sudo pap vm setup` runs pap's own program as root** (RT-22). Without `--dev-from-tree` setup refuses unless its entry file and folder, its `vm-assets.json` and the running Node are owned by root and not writable by group or others, so a compromise of pap's user cannot plant code that the next routine setup runs as root: run it from a release archive unpacked as root. `--dev-from-tree` copies user-writable code that then runs as root (R19) and is exactly the case where such a compromise becomes root at the next setup; it prints the warning and is for testing only. The check also covers every folder above each of those paths up to `/` (each must be root-owned and not group- or other-writable, with no sticky-bit exemption, like `--assets`). `sudo pap vm uninstall` also runs pap's program as root and is not checked: the same rule applies to it by convention, so run it from the same root-owned copy. The pins (`vm-assets.json`, `--assets`) are checked by SHA-256 either way.
- **The existence oracle by a race.** `grep`, `find` and `ls` roots are judged before the walk (R26): the agent's shell can flip `home/a` between a folder and a link to `/` while a read is judged, which reveals whether a path exists, never its content; the ops open component by component with `O_NOFOLLOW`. Inside a VM "the outside" is the VM's own root (pi-host, the agent's other workers). An fd-relative judge is not planned (sub-project 3 left it out).
- **MCP stdio servers and extension subprocesses** start outside bwrap and the file rule; only `GIT_CEILING_DIRECTORIES=/agent` is set. Sub-project 3 chose not to confine them inside the VM (ADR 0081): the exits trust nothing the VM says, so what they could read inside the VM (the gateway token file, the Pi profile, which holds no provider key) gives them nothing the agent does not already have, and pap does not control how a third-party extension starts its children. The VM is the boundary.
- **`export_html` is unavailable for agents and box sessions; prechecks are removed everywhere** (`automation.md`). Credentials a VM agent needs are its own, scoped at the source (ADR 0079), or vault values the owner allowed it ("The vault in the VM"); provider keys and the Claude token never enter the VM. Vault values reach the VM shell's environment: ADR 0049's limits apply inside the VM.
- **The first stop of a pre-allocated disk is slow.** The copy reads the whole allocated file (minutes for an 8 GiB disk Kata 4.2 filled), and a start of that box waits on the box lock until it ends. Later stops are quick. A pap-vmd exit during a copy is harmless: the original is untouched until the rename, and a stale `disk.img.reclaim` is removed by the next reclaim.
- **Sparse disks and a full host.** `diskMb` is a ceiling, not a reservation: boxes whose guests fill their disks together can exhaust the host's free space (`PAP_MIN_FREE_DISK_MB` is checked at create and grow only). Discard returns space only for files the guest deletes; blocks a guest wrote once and never freed stay allocated.
- **`pap backup` holds mirrors, not disks** (disks are in root-owned `/var/lib/pap-vm`; backups are sub-project 4). A backup of `$PAP_HOME` is still sensitive.
- **The approval engine runs in the worker.** The approval mode, the blocked commands and the tool rules are the agent's own policy inside the VM: in a compromised VM they are its own choice. At the exits the daemon enforces the host list (proxy), the models and budget (relay), and the platform ops' callers and taint rule (gateway). The taint the daemon uses is the one it sees ("Taint the daemon sees"); the worker's own reports can add taint and never clear it. A reopened VM thread session is tainted (the mirror resync), so its tools ask once.
- **Provider-side tools are an egress and spend path.** The relay forwards request bodies and `anthropic-beta` verbatim, so a tool the provider runs (Anthropic `mcp_servers` and web fetch, OpenAI Responses `web_search` and `mcp`) lets code in the worker reach hosts through the provider and spend on it.
- **The pause and budget gate rests on the cost the VM worker reports.** The relay counts requests for attribution only (a mismatch is logged, not acted on); a compromised worker can under-report its cost.
- **A notice posted "now" is live-only.** A mirror notice that no start follows is shown to whoever watches the session at that moment and are not kept for a later start.
- **A plain restore drops every VM agent's package picks.** The plugin-id key lives in `secrets/plugin-id.key`, which a plain backup excludes (`backup.md`); the ids change and `sourcesOf` drops each pick with a log line (`agent_plugin_pick_gone`) and no notice, so agents start without their packages, the Claude bridge included. Pick them again in the form.
- **The relay-restart window.** The listener check runs at relay ready and after each restart. A local user who binds `10.213.0.1:7841` or `:7842` during a restart window while VMs run receives their provider requests (the firewall filters by interface, not by socket owner). It never gets a credential: VMs hold only a relay key, which is worth nothing off the relay.
- **`vm.listeners` warns briefly at boot** before the relay binds (run doctor again).
- **Boxes (lot B1).** No backup of a box disk: a project's files live only in its box (the project page says so; push is B2). A repository's own `.pi/` resources (extensions, skills, MCP configuration, settings) are not loaded in a box session: the worker's Pi folder holds no project trust, so loading fails closed; Settings › MCP and Skills show the global lists only for a box project, and the trust banner is not offered. No Fork or Duplicate of a box session. One box is one trust zone: a tainted session taints every session of the launch. No lanes and no Fan-out in a box until B3 (the terminal and GitHub came with B2, below). Browsing Files, Changes or knowledge of a stopped box shows START, never starts it. A box that crashed three times needs Restart box; its `box_paused` item stays until the project is deleted. The "image is being rebuilt" notices are French only. A "Allow this host" card for a host already on the list still appears in another session. The Files tree of a box hides `.git`.
- **Purge leaves the trashed home and `.runs`** for 7 days.
- **The forward chain** has no end-to-end test (above).
- **Boxes (lot B2).** The box token is readable by every process in the box and a session can push with it ("The terminal and GitHub in a box"). The App is public: any GitHub account can install it on its own repositories, and each member connects theirs ("Members: boxes and the host gate"). Commits in a box are the box owner's, signed by the project's key, whoever or whatever typed them; a second repository cloned by hand in the same box signs as the owner too. A fork's pull request is opened on GitHub's compare page. A detached, silent terminal keeps a box up for up to about twice `PAP_WORKER_IDLE_MINUTES`. A terminal in a box ends with the box; `kill` signals only the shell's own process group, so a `setsid` job survives a Close until the box stops. Unlink or delete waits behind a running clone (up to 600 s). Reading the real GitHub flow end to end (App creation, key upload, the log redirect) is the owner's check after the merge: tests use the fake. The check chips' states follow GitHub's check runs; one failing check-runs call fails the pull request list.
- **Members (M14).** A member is root in their box, so the cost the VM reports, the provider label on a run and the relay key in their worker are theirs: the budget is a guard against mistakes, not a hard cap (OQ5, ADR 0085). Relay-side metering is a later lot. Box tokens delivered before a daemon restart are not revoked by the new daemon; they expire within an hour. While GitHub access is lost, the same warning repeats every 60 s. A member's box and agents share the one memory cap with the owner's.
