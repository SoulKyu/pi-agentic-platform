# Terminal module (M8)

Code: `apps/daemon/src/kernel/pty/` (spawn, environment, kill ladder), `modules/terminal/` (`registry.ts`, `terminal.ts`, `flow.ts`, `ring.ts`, `service.ts`, `launch.ts`), `kernel/ws/binary-streams.ts` (the binary channel), `kernel/supervisor/scope.ts` (terminal scopes). Contracts: `packages/contracts/src/{terminal,binary-frames}.ts`. Web: `apps/web/src/runtime/terminal-channel.ts`, `features/terminal/`, `web.md`. Rulings: `docs/research/m8-rulings.md`. `files.md` has the path boundary a terminal's folder goes through.

## Who, how many, how long

- Browser sessions only. A token never holds `terminal:*` (`TOKEN_PERMISSIONS` drops it, `contracts/src/auth.ts:10`; M8R91): a standing credential makes no code-running change, and the terminal is exactly that. No extra password.
- **The terminal is the owner's shell, not a sandbox.** It runs as the daemon's user with the daemon's rights; pap's policy pipeline, taint and approvals do not apply to what is typed there (they judge the agent's tool calls). Terminal and save traces go to the daemon log only (no audit rows, M8R96).
- `terminal.create { cwd, sessionId?, cols, rows, requestId }` judges `cwd` as a `list` of a folder inside the caller's roots (`not_found` for anything else, `service.ts:77`) and starts the shell there. A repeated `requestId` returns the same terminal while it is listed (idempotent). `terminal.attach`, `detach`, `resize` and `close` are idempotent too; another owner's terminal answers `not_found`.
- A terminal lives until it is closed, its shell exits, or pap stops (a restart loses every terminal; the pane then says it ended). At most `PAP_MAX_TERMINALS` **running** terminals per owner (default 8, 1 to 64); the next `create` answers `capacity`, as does a free memory under `PAP_MIN_FREE_MEM_MB` (`registry.ts:127`). Nothing is killed to make room. An exited terminal stays listed for its output, at most 8 per owner, the oldest dropped first (`MAX_EXITED_KEPT`). A hidden browser tab never pauses a terminal (below).
- `terminal_unavailable` is answered when node-pty did not load (boot probe `loadNodePty`, logged; the daemon boots without it) or the spawn failed (`launch.ts`); the message is fixed, the errno goes to the log (`terminal_spawn_failed`).
- **Memory and tasks.** A terminal scope is a sibling of the workers' scopes under the same home slice and has the same `MemoryMax` and `TasksMax` (`PAP_WORKER_MEMORY_MAX_MB`, `PAP_WORKER_TASKS_MAX`, `daemon.md`), each scope on its own: eight terminals running builds plus the workers compete for the host, not for one shared budget. The shell's `oom_score_adj` is 800, so the kernel's OOM killer takes it before the daemon (`spawn.ts:78`; workers carry the same `oom_score_adj`).

## The shell

- Command: `/bin/sh -c 'umask "$1" && shift && exec "$@"' pap-shell <mask> <shell> [-l]` (`spawn.ts:13`), so the shell has the daemon's **starting** umask (R114), not the 077 the daemon sets for itself, and its pid is the shell's. `<shell>` is `$SHELL` when it is an absolute path to an executable file, else `/bin/sh` (`shellOf`); known shells (`sh bash zsh dash ksh mksh fish`) get `-l`. With a scope the whole command is wrapped in `systemd-run --user --scope --unit=pap-<h>-term-<id>-<n>.scope --slice=...` (M8R54).
- Environment (`kernel/pty/env.ts`, `supervisor/env.ts`): the daemon's environment without `PAP_*`, `NODE_OPTIONS` and the service manager's variables (`NOTIFY_SOCKET`, `LISTEN_*`, `INVOCATION_ID`, `JOURNAL_STREAM`, `MANAGERPID`, `MAINPID`, `WATCHDOG_*`, `CREDENTIALS_DIRECTORY`, `MEMORY_PRESSURE_*`, ...; the same `isDaemonOnly` filter as workers and M7's helpers); `TERM=xterm-256color`, `COLORTERM=truecolor`, `LANG=C.UTF-8` when no locale is set. node-pty opens the shell on a pty slave as stdin, stdout and stderr; no daemon descriptor reaches it but its sibling terminals' masters (residual below; the first terminal is probed in `terminal-boundary.int.test.ts`).
- Size is clamped to 2 to 500 columns and 2 to 200 rows (`PTY_COLS`, `PTY_ROWS`).

## Wire

Terminal bytes travel as binary frames on `/ws` (spec C §4.2): a 16-byte header then the payload. Byte 0 magic `0x70`, 1 version `1`, 2 op (server to client: `1` output, `2` reset, `3` exit; client to server: `16` input, `17` ack), 3 flags `0`, 4-7 stream id (u32 LE, given by `terminal.attach` to this connection only), 8-15 seq (a u64 as two u32, high word at most `0x1FFFFF`: a byte offset of the terminal's output for output, reset, exit and ack; a counter that only grows for input), then at most 64 KiB (exit carries JSON `{ "code": n | null, "signal": "SIGHUP" | null }`). Anything else is dropped and counted (`ws_binary_dropped`, logged at 1, 2, 4, 8, ...). `HandlerContext.binary` is optional; `CAPABILITIES` gains `terminal`; `PROTOCOL_VERSION` stays 2. A connection holds at most 16 streams (`capacity`), a terminal at most 8 (`MAX_STREAMS_PER_TERMINAL`). A stream starts sending only after the `terminal.attach` answer has gone out (`commit`), and the answer's `start`/`end` say where the replay begins and ends; the first frame is authoritative.

## Output ring, replay, flow control

- Each terminal keeps a ring of its output: 4 MiB and 5 000 lines at most, evicting whole chunks from the front (`ring.ts`). A new attach starts with `reset` and the ring from a line boundary (`safeStart`); an attach with `after` inside the ring continues at that byte, with no gap and no duplicate; an `after` that fell out of the ring gets `reset` and the ring.
- Flow control per stream (`flow.ts`): at most 512 KiB sent past the last ack (`window` pause), resumed when an ack brings the lag to 256 KiB or less. A frame the socket refuses (more than 1 MiB buffered, `STREAM_BUFFER_LIMIT`) pauses the stream (`buffer`) and is retried every 50 ms on the clock; the socket itself is never closed for it. An ack beyond what was sent, or one that moves nothing, is ignored.
- **Stale streams.** A stream paused for 2 s, counted **from the start of the pause**, is stale: still attached, no longer holding the PTY. An ack that does not resume the stream only advances `acked` and never restarts the count; a stream leaves `stale` only when an ack actually resumes it (MC27). The PTY is paused only while at least one attached stream is not stale and every such stream is paused (`reconcile`, `terminal.ts:181`). So a hidden tab, whose timers are throttled and whose acks stop, never stalls a build for more than 2 s, and a client that stops acking never stalls the shell (owner f2). A paused PTY whose shell dies would lose its last bytes (node-pty destroys a paused socket 200 ms before it reports the exit), so while paused the shell is polled every 50 ms (`ALIVE_POLL_MS`, `/proc/<pid>/stat` start time against the one read at spawn) and the PTY resumes as soon as it is gone; the `exit` frame follows the last output byte after 100 ms of quiet (at most 1 s).
- **Replay protection is client-side.** Replayed output holds device queries (cursor position, colours) that xterm would answer into the shell. The pane drops everything xterm sends (`onData`, `onBinary`) from `attached()` until the bytes up to the answer's `end` are written, and ignores typing before then (`use-terminal.ts`). The daemon does not filter input.
- **Hidden tab.** The web channel detaches a terminal's stream 5 s after the page becomes hidden (`HIDDEN_DETACH_MS`) and attaches again with `after` = the offset it finished writing as soon as the page is visible; a shorter hide keeps the stream. Reconnects attach again the same way, so a terminal survives a browser reconnect within one daemon lifetime (`terminal.reconnect.int.test.ts`).
- Sizes: the last `terminal.resize` wins for every client; the pane throttles resizes to 100 ms.

## Closing and the kill ladder

`terminal.close` of a running terminal and a stop of the daemon run `ptyKill` (`kernel/pty/kill.ts:129`) on the shell (closing an exited terminal, or evicting the oldest one, only reaps its scope):

1. SIGHUP to the shell's process group and to **every process of the shell's session** (read from `/proc`: an interactive shell gives each job a group of its own, so a group signal misses them; a pid whose start time changed is never signalled).
2. After 2 s (`PTY_HANGUP_GRACE_MS`), unless the shell exited and its session is empty: SIGKILL to the same, repeated up to 8 passes while a fresh read still finds members (a job that forks outruns one pass); a member that refuses the signal (EPERM, for example under `sudo`) is skipped and logged once per step (`pty_kill_denied`).
3. Wait for the shell's exit, at most 5 s more (`PTY_EXIT_WAIT_MS`), then log `pty_kill_timeout`.
4. With a scope, `reap()` kills the unit's whole cgroup, stops and resets it. `sweep()` at boot also resets failed `pap-<h>-term-*` units.

The daemon's stop closes every terminal in parallel after the workers' ladder (`daemon.md`); a `create` that arrives once the stop began is refused (`capacity`), also when it was waiting on the folder judgement (MC28).

Residuals (accepted):

- **Without a scope** (no lingering user manager) a job that left the session (`setsid`, a daemonizing tool) survives Close. A fork storm faster than 8 SIGKILL passes also survives; the scope reap covers it where scopes exist.
- **With a scope**, Close and a natural shell exit kill everything in the scope, so a `nohup` job started in the terminal is killed (by the SIGKILL pass at 2 s on Close, by the reap when the shell exits on its own). Jobs started with `systemd-run --user` live outside the scope by design: that is the escape hatch for work that must outlive the terminal.
- **Two attached clients** (two browsers on one terminal) both answer a live device query, so the shell can receive the answer twice.
- **Descriptors.** node-pty leaves the master of every terminal without close-on-exec, so any process the daemon starts afterwards inherits it. Workers close every inherited descriptor that leads to `/dev/ptmx` or `/dev/pts/*` as the **first import** of `main.ts` (`packages/pi-host/src/close-inherited-fds.ts`, `close-pty-fds.ts`; MC29), before any agent, extension or tool code. Git's children are masked (MC38): `kernel/git/runner.ts` spawns git with `maskedStdio` (`kernel/pty/fd-mask.ts`), a dense `stdio` array that maps each PTY master the daemon holds (read from `/proc/self/fd` in the same tick as the spawn; Linux only, a no-op elsewhere) to a `/dev/null` descriptor and every gap to `"ignore"` (a sparse array is compacted by Node and masks nothing); a repository-local filter driver therefore sees `/dev/null` where the master was (`kernel/git/fd-mask.int.test.ts`). Residual: a shell inherits its sibling shells' masters (the owner's own shells, same user), and any other child still unmasked (`systemd-run`, `systemctl`, `loginctl`, M7's helpers before their first import) can type into an open terminal. That is more than same-user code execution: sudo's default `timestamp_type=tty` makes a shell with cached credentials worth root, and an open `ssh` session reaches other hosts. For git, planting a filter driver needs an approved write to `.git/config`, and the git runner empties a repository's own filter drivers before it runs `status`, `diff` and the other subcommands that filter (MC13, `kernel/git/filters.ts`). Spawn sites of the daemon, for the next person who adds one: workers (`kernel/supervisor/worker.ts:89,100`), git (`kernel/git/runner.ts`, masked), `systemd-run` / `systemctl` / `loginctl` (`kernel/which.ts:26,40`), and the PTYs (`kernel/pty/spawn.ts:109`). A new child process that can run agent or user code must close the PTY descriptors too, or be started before the first terminal.
- Terminals are in memory: no persistence, no audit row, and the ring is lost with the process.
