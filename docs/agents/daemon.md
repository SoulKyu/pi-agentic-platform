# Daemon composition

Code: `apps/daemon/src/daemon.ts` (composition root), `main.ts` (`pap serve`), `shutdown.ts`, `kernel/home.ts`. The test harness is `apps/daemon/src/testing/harness.ts`.

## Start and stop

- `createDaemon(config, deps)` builds everything in one place: home and lock, migrations, receipt purge, auth, sessions, ws, http. Each thing that must be undone is pushed on a list; a start that fails half-way (port taken, migration refused) and `stop()` both run it in reverse, so nothing is left locked or open. `deps` carries the injected clock, logger and worker environment, plus `onFatal` and `announceSetupUrl`.
- Stop order (R104), in `DaemonHandle.stop()`, idempotent (the second call returns the first call's promise): `sessions.shutdownAll()` first, so every worker climbs its kill ladder (shutdown request, SIGTERM, SIGKILL; at most 10 s) and pi-host kills Pi's bash trees on the way; in parallel with `pi.stopAll()` (the M7 helpers), then `wk.shutdown()` (the M8 workspace: every terminal climbs its own ladder in parallel, SIGHUP, 2 s, SIGKILL, up to 5 s, then the scope reap; then the `vcs` poll and the files stores stop; a throw in one is logged as `workspace_shutdown_failed` and never skips the next step); only then `killAllWorkerGroups()`; then ws, http, receipt purge, database, instance lock (`daemon.ts:315`). A terminal `create` that arrives once the workspace started stopping is refused. The order matters: Pi starts every command in a group of its own, out of reach of a SIGKILL to the worker's group, so killing the groups first leaks those trees. `daemon.boot.int.test.ts` runs a real `sleep` under a worker and fails when the order is swapped.
- `main.ts` turns SIGTERM, SIGINT and SIGHUP into that stop (`shutdown.ts`). A second signal, a failed stop, or `STOP_DEADLINE_MS` (22 s: the worker ladder 10 s, the terminal ladder 7 s, 5 s for the rest; `shutdown.ts:10`) without a result calls `forceKill` (SIGKILL of the worker groups, then `killAllNow` of the home slice's scopes) and exits 1: nothing can keep the process alive. Exit 0 only after a clean stop.
- `--tls-cert` and `--tls-key` are read once, in `loadConfig` (`Config.tls` holds the PEM bytes; the server never reads the files again). Each file is checked with the TLS stack's own parser (`tls.createSecureContext`, so a DER certificate or a key with a passphrase is refused here too, not at listen time), then the pair. A file that cannot be read, a certificate or key that fails that and a key that does not belong to the certificate each end in a `ConfigError` that names the flag and, for a read, only the errno code (`--tls-cert cannot be read (ENOENT)`): one line, exit 64, never a stack trace from the HTTPS server.
- `pap serve` exits 64 on a bad command line and 1 on a startup refusal an operator can fix (`InstanceLockError`, `HomeError`, `MigrationError`, `EADDRINUSE`/`EACCES`/`EADDRNOTAVAIL`), with one line `pap: <message>`. Anything else keeps its stack trace.

## Server errors

- `startServer` requires `onError`: Node throws an `'error'` that no listener handles (accept failing on EMFILE, say) as an uncaught exception. The daemon logs `server_error` with the error `code` and nothing else, then calls `deps.onFatal("server_error")`; `main.ts` answers with the graceful stop and exit code 1, so the service manager restarts it.
- A database written by a newer pap opens read-only (`read_only_mode` warning at boot). A write that SQLite then refuses (a sign-in; a session's daily slide is skipped instead) is `503 {"error":{"code":"read_only"}}` on HTTP, the same code the RPC answers, logged as the warn line `http_read_only` instead of an `http_error` stack. `kernel/db/read-only.ts` (`isReadOnlyError`) is the one test for it. The page reads that code from a failed `/auth/status` too, so the gate says the database is read-only instead of "unreachable".
- `onFatal` fires once (R115). A later error is only logged: a second `shutdown.trigger` would count as a second signal and SIGKILL the worker groups before pi-host cleaned up.

## Home, permissions, umask

- `prepareHome` runs before the database is opened: `$PAP_HOME`, `backups/`, `secrets/` and `logs/` are 0700, and `state.db`, `-wal` and `-shm` are 0600 (R68). SQLite gives the WAL and shared-memory file the mode of the database file; snapshots are chmod-ed explicitly. A home or database file an earlier run left more open is tightened at boot (R117); a path that cannot be made private is a `HomeError` naming it. The database files are checked with `lstat` and a symlink among them is skipped, so a chmod never lands on whatever it points to; a symlinked `$PAP_HOME` itself and its directories are followed.
- A home that cannot be chmod-ed refuses to boot (R119): on a volume that ignores or forbids chmod (some container volume drivers, FAT/exFAT, some network file systems) `prepareHome` throws a `HomeError`, and the daemon exits 1 instead of running with a state directory the OS cannot protect. Mount a volume that honours Unix modes, or run with a user that owns it.
- The process umask is 077 from then on, so any file the daemon creates later is private by default.
- Workers do not inherit it (R114). `prepareHome` returns the umask the process had before its first call (module-level, captured once, R114b), the sessions module puts it in every `InitRecord.umask`, and pi-host applies it with `process.umask()` before it opens the Pi session. Files Pi's tools and bash children create in a project get the user's usual modes; state files stay 0600. A worker started without `umask`, or with one outside 0..0o777, refuses to start.

## One daemon per home

- `acquireInstanceLock` (R70) creates `pap.lock` in `$PAP_HOME` before migrating. The file holds `<pid> <start time>` and appears with its content already in it (hard link of a written temp file), so a second instance never reads an empty file. A second daemon exits with `pap is already running on <home> (pid N)`.
- A lock is stale, and replaced, when its pid is gone, when the process now at that pid started at another time (Linux: field 22 of `/proc/<pid>/stat`; this catches a reboot or a pid that wrapped), when its content is unreadable, or when it names our own pid and this process does not hold that path (R116: in an OCI container the daemon is pid 1 every time, so "alive" would be true for ever after a restart).
- Limits: taking over a stale lock is not atomic, so two instances started in the same instant after a crash could both win. Where there is no `/proc` only the pid is compared. A file system without hard links gives an `InstanceLockError` saying so; the hint appears only for the errors a missing `link()` produces (`EPERM`, `ENOTSUP`, `EOPNOTSUPP`, `EXDEV`, `ENOSYS`, `EMLINK`), any other code (`EACCES`, `ENOSPC`, `EROFS`...) is reported as plain `(CODE)`.
- The lock is a pid, so it only works inside one PID namespace: one daemon per `$PAP_HOME`, and never one home on a volume shared by daemons in different PID namespaces (two containers on one volume, a container and the host). Each would see the other's pid as dead or as its own and take the lock over; they would then migrate and write the same database. Give every daemon its own home.

## HTTP headers

- Every response carries the CSP of R74 (`default-src 'self'` and the rest, no inline script) from `secureHeaders`, API and static alike. `connect-src 'self'` covers same-origin ws/wss; if a library needs more, relax one directive and write an ADR.
- HSTS (`max-age=15552000`, no `includeSubDomains`) only when the daemon itself serves TLS: `createHttpApp({ servesTls })` is `config.tls !== null`. Plain HTTP never sends it, because it would pin `localhost` and every other local port for 180 days. A reverse proxy that terminates TLS adds its own.
- A request refused for its Origin (an unsafe-method HTTP request, or a `/ws` upgrade) is answered 403 and logged as the warn line `origin_refused`: `via` (`http` or `ws`), the Origin clipped to 100 characters (`(none)` when absent), `suppressed` (refusals the window swallowed) and a hint naming `PAP_PUBLIC_ORIGIN`. One line per path every 10 s (`createOriginRefusalLog`), never a cookie, header or path. The case it exists for: `--host 0.0.0.0` with no `PAP_PUBLIC_ORIGIN` only accepts the loopback origins, so a browser on the LAN gets a bare "forbidden" otherwise. The startup warning `plain_http_on_network` names `PAP_PUBLIC_ORIGIN` for the same reason.
- `GET /ws?proto=N` is a plain request answering 426 (another protocol), 401 (no session) or 200: the browser cannot read the status of a failed upgrade.

## Setup address

- The one-time setup URL is logged once, as `setup_url` with the field `url` (the logger redacts keys called `token`, not `url`). `main.ts` announces it through a logger fixed at info, so `PAP_LOG_LEVEL=error` does not hide the only way to create the owner (R117); with no `announceSetupUrl` it goes through the daemon's own logger.
- In `--dev` the address and `DaemonHandle.setupUrl` carry the Vite origin (`http://localhost:5173`), because that is where the browser is (R31).
- After the owner exists a restart prints no `setup_url`.

## Settings (`modules/settings/`)

- Account-scope documents: one JSON text per owner and key (`appearance`, `keybindings`) in the `settings` table. `settings.get` returns `{ value, revision }` (`null`, 0 when nothing is stored); `settings.set` takes `{ key, value, baseRevision }`. The RPC layer decodes the value against the contracts schema before the service sees it.
- Compare-and-set (owner R3-4): `store.put` is one statement. `baseRevision` 0 inserts and does nothing when a row exists; any other value updates only `WHERE revision = $baseRevision`. No row returned means `conflict`, and nothing is written. The client re-reads, merges and retries once (see `docs/agents/web.md`).
- A document over `MAX_SETTING_BYTES` (128 KiB of UTF-8 JSON) is `payload_too_large`.
- A stored row that no longer parses reads as "no setting" (`value: null`, the row's revision) and logs the warn line `settings_row_unreadable` with the key only. The client falls back to its defaults and its next write, based on that revision, replaces the row.
- The migration `202610111000_settings.sql` sorts after M2's `202610110100_policy.sql`. Re-stamp it only if another milestone's newest stamp sorts after it, and never for a home that already applied it: an applied id missing from the sources is `database_newer_than_binary` and the daemon opens read-only. Such a home needs a reset.

## Projects and search modules (M4)

- `modules/projects/` (`createProjectsModule`): table `projects` (`202610121510_projects.sql`, listed in `PROJECTS_MIGRATIONS`, sorted by stamp before the sessions marks migration), RPCs `projects.update` (rename, move) and `projects.add` (decision 85, see `sessions.md`), and the `ProjectsPort` the sessions module uses (`ensure` one project per session folder scope, `list`, `all`, `onChange`). A project is the git root of a session's folder (the policy scope), named and ordered by the person (fractional `position`: a move writes one row).
- `ownerId`: `AuthModule.ownerId()` is the one definition of the instance owner, the oldest user (`store.firstUserId()`). `createDaemon` passes `ownerId: () => auth.ownerId()` to sessions; adopted Pi sessions belong to that user, and none exists until the owner is set up (the scan port answers `wait`).
- `modules/search/` (`createSearchModule`, details in `docs/agents/search.md`): `search.db` in `$PAP_HOME`, the scanner and the query thread. `createDaemon` builds it with `installedAt` (`ensureInstallTimestamp`, the cutoff), `readOnly` and the sessions scan port, registers `search.rpc`, and calls `search.start()` only after the HTTP server listens, so a first scan never delays the boot. A damaged index is rebuilt at runtime by the module itself (at most 3 times an hour). Its closer is pushed after the database's, so `stop()` runs it first: the scanner and the thread end, and only then does the database close.
- `testCaller()` (`testing/caller.ts`): every daemon test builds its callers with it instead of a `{ userId, permissions }` literal, so fields M5 adds to `Caller` compile after the merge.

## Audit (`modules/audit/`)

- The `audit` table is append-only (migration `202610122000_audit.sql`): triggers refuse UPDATE, DELETE outside a prune of a month older than 12 months, and an INSERT onto an existing id (REPLACE would skip the DELETE triggers; `recursive_triggers` stays off, it is kernel-wide). `month` and the `at` range are CHECKed. The triggers stop a bug, not a person editing the file.
- A worker's entry arrives as `unknown` (the sessions `service-sync.ts` calls `audit.fromWorker` with the session row and the containment). It is parsed with `PolicyAuditEntry`; NUL becomes U+FFFD in every string; `args` and `reason` lose well-known token formats (`scrub.ts`); stage reasons are clipped until the JSON fits the column, the daemon's "worker scope on/off" fact always ends stage 05. A malformed entry is an `invalid` row (100 per session). Valid rows are budgeted at 600 per session per minute. The first drop of a window writes one marker row (`audit rows dropped: rate limit`, no count), where the gap starts, so a session that goes quiet still leaves its trace; at most one per session per window. The running count is in the `audit_rows_dropped` log line: `dropped: 1` at the first drop, the window's total when it ends or the session is forgotten.
- An answered call's row: `actor` / `actorId` name the person (`user`, the browser session's device id) or the token that answered; its content (decision, stages, args) is still the worker's report. The daemon matches the answer to the row by tool call id, once; a rogue worker can move one real answer onto another call row of the same session, once.
- `audit.list` (`audit:read`) answers the caller's rows and the system's, newest first, under `PAGE_BYTES`. Each row is decoded with `AuditView`; a row the contract refuses is shown repaired (`audit_row_degraded`), never failing the page.
- `append` never throws: a failure logs `audit_append_failed` (kind and a `suppressed` count, once a minute). At boot `audit_prunable` says when months can be pruned (`pap audit prune`).
- Size: about 0.5 KB per call row, so 1 000 tool calls a day is about 180 MB a year; nothing but the monthly prune removes rows (ADR 0022, `policy.md`). There is no per-session volume cap beyond the 600 rows a minute: a hostile session can add about 10 MB a minute until stopped.
- `MIGRATION_SOURCES` (`daemon.ts`, exported) is the only list of migration sources; `createDaemon` and the CLI both pass exactly that constant to `migrate`, so a home the daemon created never looks newer than the CLI (`cli/open-home.int.test.ts` opens one a real daemon created). Whoever merges second adds the other milestone's sources to it.

## CLI (`apps/daemon/src/cli/`)

- `main.ts` answers `pap serve`; every other command goes to `runCli` (`run-cli.ts`, table `COMMANDS`, parsed with `node:util` `parseArgs`, strict): `pap audit prune [--month YYYY-MM] [--dry-run]`, `pap user add <username> [--password-stdin]`, `pap passkey reset [--revoke-tokens] [--keep-password] [--password-stdin]`. `usage.ts` holds `USAGE` and the `systemctl --user stop pap-preview` hint; extend `USAGE` and `COMMANDS` together.
- `openHomeForCli` (`open-home.ts`) takes the instance lock, prepares the home and migrates with `MIGRATION_SOURCES`; the lock is taken before a password is asked and held until the command ends, so these commands need the daemon stopped. A running daemon makes them exit 1 with `pap is already running ...` and the stop hint, and change nothing. A killed prune leaves a stale lock that the next run replaces (the pid is gone).
- `pap service install|uninstall|url` (`cli/service/`) manage the systemd user unit and the `~/.local/bin/pap` launcher; they take no instance lock and never open `$PAP_HOME`, so they work while pap runs. Guide: `docs/agents/install.md`.
- `pap backup`, `pap restore`, `pap update check|install|apply|rollback|recover` and `pap doctor` (M6b, `cli/backup*`, `cli/update/`, `cli/doctor/`) open nothing through `openHomeForCli`: backup and doctor work while pap runs, restore refuses while it runs, update stops and restarts the unit itself. Guides: `backup.md`, `update.md`, `doctor.md`; `install.md` for the image, npm and releases.
- Exit codes: 0 done, 1 refusal an operator can fix (`CliError`, lock, home, migration, config errors; one line `pap: <message>`), 64 a bad command line (message and usage), 130 Ctrl-C at a password prompt. Anything else keeps its stack trace.
- `audit prune` removes whole months older than 12 months (`--month` names one, `--dry-run` only counts) and leaves its own row in `audit_prunes`. `user add` and `passkey reset` are in `auth.md`.

## Tests

- `startTestDaemon(script, { tls?, config?, deps? })` boots a daemon on a free port in a temporary home, on the scripted provider and under the network guard (R94); the worker gets a minimal environment, never the outer process's `PI_*` or `HOME`. It removes its temporary directory when the start fails. Its client rejects a call that gets no response within 30 s and never retries a mutation (R105).
- Workers inherit the daemon's `--conditions=` node flags and nothing else, plus `--max-semi-space-size=16` which `workerExecArgv` (`kernel/config.ts`) always appends and never takes from the daemon's own flags: `WORKER_BUDGET_MB` (285) was measured with it (`docs/spikes/s4-m2-long-session.md`). `sessions.budgets.int.test.ts` reads it back from a worker's `/proc/<pid>/cmdline` and `pnpm smoke` from the real daemon's workers. Never `--import`: a worker starts in the session's project, so a relative or bare specifier would load that project's code (`./x.mjs`, a `node_modules` package) before init and the policy, and a project without it would break every worker (R130). The one way to preload something into workers is test-only: `PAP_TEST_WORKER_IMPORT=<absolute path>` (a relative or bare value is a `ConfigError`), honoured only when `PAP_TEST_PROVIDER_SCRIPT` is set too, added as `--import=<path>` after the daemon's own flags. The smoke test uses it for the network guard.
- `pnpm smoke` (`scripts/smoke-dist.ts`, a step of the CI `build` job after `pnpm build`) runs the built `apps/daemon/dist/main.js` with no `--conditions` against the built `packages/pi-host/dist/main.js`: temporary `HOME`, `PAP_HOME` and `PI_CODING_AGENT_DIR`, `PI_OFFLINE=1`, the scripted provider and the network guard in the daemon (its own `--import=`) and in every worker (`PAP_TEST_WORKER_IMPORT`). It sets the owner up, signs in, opens `/ws`, creates a session, prompts, approves the card, waits for the tool output and `agent_settled`, then (`scripts/smoke-search.ts`) writes a Pi session file by hand under its agent folder, waits up to 10 s for its `session` event on the `shell` stream and searches the smoke session's own marker, which only works if the built search thread starts; helpers are in `scripts/smoke-lib.ts`. It then sends SIGTERM and expects exit 0 and no process left under its `HOME`. Run `pnpm build` first; it prints the daemon's last lines when a step fails. Linux only (it reads `/proc`).
- `main.int.test.ts` runs the real entry point in a child process with a throwaway home.
- Crash tests (`security/automation-crash.int.test.ts`, M10R79) run that entry point and kill it with SIGKILL where `PAP_TEST_OUTBOX_HOLD` freezes it, then boot the same home again: `<kind>` leaves the row leased with its handler not called, `<kind>:sent` stops the handler right after its sent mark (before the prompt it was about to send), `cancel` stops a task's Cancel after its commit and before its abort. Honoured only beside `PAP_TEST_PROVIDER_SCRIPT` (otherwise a `ConfigError`, M10R80); a production daemon never holds an effect. The scripted provider's `captureUserMessages` (a file name in the script) appends the user messages of each request, one JSON line per call. Long timers of a test daemon can be parked and moved by `security/testing/steppable-clock.ts`.
- PATH differs between `pnpm exec vitest` (puts `./node_modules/.bin` on PATH) and `pnpm test:int` / `pnpm run` (absolute entries only). `coverCommand` refuses coverage when any PATH entry is relative, so a read-only command such as `echo hi` asks under `pnpm exec` and runs unasked under `pnpm test:int`. A test or a mutation run that depends on such a command asking must use a command outside `READ_ONLY_COMMANDS` (the security suite uses `curl` or `touch`) and be run through `pnpm test:int`.
- Worker scopes (`kernel/supervisor/scope.ts`, wired in `createDaemon`: `probeScopes` at boot, then `scopes.sweep()` before any worker can start, `DaemonHandle.killScopes` = `scopes.killAllNow()`): `probeScopes` wraps each worker in `systemd-run --user --scope` inside a slice of its own, nested under the home's slice (`app-pap-<sha8(real home)>.slice` > `app-pap-<sha8>-<id>.slice`; units `pap-<sha8>-worker-<rand>-<n>.scope`, `n` counts per probe), `MemoryMax = max(2 GiB, 50 % RAM)`, `TasksMax`, `OOMPolicy=continue`, no `MemoryHigh`. Sweep and `killAllNow` act on the home slice and so cover the nested ones. Linger off, `loginctl` missing or no user manager: scopes off, one boot warning. `spawnWorker({ scope })` holds the exit report for `scope.reap()` (at most `REAP_TIMEOUT_MS`): one `systemctl show` of the unit and its slice, then SIGKILL of the unit's cgroup (Pi's detached bash trees, R100), stop and reset-failed of the unit, stop of the worker's slice; a unit systemd already collected (`LoadState=not-found`) is not touched. `oom` = the worker died of SIGKILL and its own slice's `memory.events` counts `oom_kill` > 0: with `OOMPolicy=continue` the unit is gone at reap time (no `Result=oom-kill`, no cgroup to read) while the slice still counts, and the slice holds one worker, so a sibling's OOM never reads as this worker's and no baseline is needed. Cost of the slice per worker, measured: one more cgroup, spawn time unchanged (about 10 ms either way), one `systemctl stop` (about 8 ms) at reap. Tests use their own temporary home (own slice, swept in `afterEach`), `MemorySwapMax=0`, never the owner's slice; `scope.int.test.ts` fails in CI without a lingering user manager.

## Worker settings and scopes

- Env settings (`kernel/config.ts`): `PAP_MAX_WORKERS`, `PAP_MIN_FREE_MEM_MB` (512 by default), `PAP_MIN_FREE_DISK_MB` (1024 by default, `0` is off; `statfs` of Pi's sessions folder below it refuses `fork`, `clone` and a task session's creation with `disk_low`, and `statfs` of the lane paths (`kernel/disk.ts` `createPathDiskGuard`, wired by `compose-lanes.ts`) refuses `lanes.create`, `lanes.restore`, `lanes.review`, `lanes.checkpointStatus`, `lanes.suggestCommit` and `lanes.compare` with `disk_low` too (`0` turns the lanes floor off as well); a failing `statfs` lets the action through and logs `disk_free_unknown` once), `PAP_WORKER_IDLE_MINUTES` (30; `0` never releases), `PAP_WORKER_SCOPE` (`auto` or `off`; anything else is a `ConfigError`), `PAP_WORKER_MEMORY_MAX_MB` (default `max(2 GiB, 50 % of RAM)`, at least 1024: a command near the worker's own memory would get the worker killed, since tool children inherit its `oom_score_adj`), `PAP_WORKER_TASKS_MAX` (4096, at least 64), `PAP_MAX_TERMINALS` (running terminals per owner, default 8, 1 to 64; a terminal also needs `PAP_MIN_FREE_MEM_MB` free memory), `PAP_HELPERS_MAX` (4, 1 to 16; a run past the cap is refused with `capacity`, never queued). Terminal scopes use the same limits as workers' (`terminal.md`). The default worker cap is `floor(RAM x 0.5 / 285)` clamped to 2-16.
- `PAP_WORKER_SCOPE=auto` needs a lingering user manager: `loginctl enable-linger <user>` once on the host, and `XDG_RUNTIME_DIR` set in the daemon's environment. Without `XDG_RUNTIME_DIR`, `systemd-run` or `systemctl` (info), or with `loginctl` missing or linger off (warn), `probeScopes` returns `NO_SCOPES` and logs `worker_scopes {enabled: false, reason}` (the `warn` is the boot warning). Workers then run as in M1 (no memory cap). With linger the probe runs a `systemd-run --user --scope` miniature with the real limits; a user manager older than systemd 253 gets plain scopes without `OOMPolicy` and logs `worker_scopes_oom_policy_missing`.
- Per-home slice: units sit in a slice named from the real `PAP_HOME`, so two daemons of different homes never sweep each other. Boot sweep (`scopes.sweep()`) kills what an earlier daemon of this home left; a forced exit (`killAllNow`, the second-signal and `STOP_DEADLINE_MS` paths) kills the home slice synchronously. Normal stop is the kill ladder first (R104).
- OOM attribution: see the scopes bullet under "Tests". A session whose worker was OOM-killed shows the `oom` cause; a stop the daemon asked for never shows a cause.
- `PAP_WORKER_UNIT` (the worker's cgroup leaf, set in the scope launch environment) and `PAP_WORKER_TOKEN` (random per worker, set by pi-host when there is no scope) are internal: they feed background-process detection (sessions.md, Traps). `workerEnv` strips inherited `PAP_*`, so a worker never sees the daemon's settings.

## Workspace: files, vcs, terminal (M8)

- `compose-workspace.ts` (`createWorkspaceModules`) builds what the three M8 modules share, so `daemon.ts` grows by a handful of lines (the file must stay under 400 lines after both M7 and M8): the boundary configuration (`boundaryConfigOf`: pap's home, Pi's agent folder, the daemon user's home, `$XDG_RUNTIME_DIR`, each in both spellings), the one deny set (warmed at boot, deadline 15 s), the git runner, then `files`, `vcs` and `terminal`. It also probes `loadNodePty` once so a missing node-pty build is logged at boot (the daemon boots without it; `terminal.create` then answers `terminal_unavailable`). Details: `files.md`, `terminal.md`.
- `Config.userHome` (`kernel/config.ts`) is the daemon user's home folder (from `os.homedir()`, injected in tests); it is what the boundary treats as "home" for the dot-entry rule.
- The HTTP routes `GET` / `PUT /files/raw` and `POST /upload` are mounted by `wk.mount(hono, auth.authenticateCookieHeader)` and are cookie-only. `kernel/http/server.ts` sets `requestTimeout` to 300 000 ms explicitly (`UPLOAD_REQUEST_TIMEOUT_MS`): an upload that takes longer is cut.
- Log lines worth knowing: `attachments_size {bytes, entries, truncated}` at boot (the daily `attachment.cleanup` removes folders idle for 30 days), `deny_walk_failed`, `deny_walk_link_followed` (debug), `file_written`, `file_uploaded` (protection and caller kind, never the path), `terminal_spawn_failed {code}`, `pty_kill_denied`, `pty_kill_timeout`, `workspace_shutdown_failed`.
- Error codes M8 added: `protected_path` and `terminal_unavailable` (both have messages in the eager `catalog/shell.ts`). `too_large` and `attachments_size` are not error codes.
- M8 adds no table and no migration; `MIGRATION_SOURCES` is unchanged. `PAP_MAX_TERMINALS` is in the settings list below.

## Lanes, worktrees and forges (M9)

- `compose-lanes.ts` (`composeLanes`) builds the `worktrees` and `lanes` modules and the forge port, so `daemon.ts` grows by about ten lines (M9 added 10 against `main`; the file is 339 lines, limit 355). It returns `rpc` (the 23 `lanes.*` methods and `subscribe.lane`), `paths` (`LanePaths`: `scopeOf` for the policy's `scopeAlias`, `roots` for the file roots), `recover`, `bind` and `shutdown`, and exports `LANE_MIGRATIONS` for `MIGRATION_SOURCES`.
- Order in `createDaemon`: `composeLanes` after the workspace modules; `await lanes.recover()` before the server listens (script orphans are killed first, then worktree recovery, bounded to 60 s, then lane recovery; skipped on a read-only database); `lanes.bind({ sessions, trust, policy, hub })` once those exist (sets the lane hooks on sessions, registers the `lane` stream, resumes interrupted archives). Stop: `lanes.shutdown()` runs in the same `Promise.all` as `pi.stopAll()` and `sessions.shutdownAll()` (a running script is stopped; a `worktree add` in flight is waited for).
- Home: `$PAP_HOME/worktrees` (0700; the worktrees), `lanes/<laneId>/*.log` (script logs, 0600), `tmp/git-index/` (temporary indexes; the runner's `indexDir`; each file is removed when its capture ends, a crash can leave one), `tmp/forge/` (the empty folder `gh` runs in, 0700, created at boot).
- Migrations: `modules/worktrees/migrations/202610141000_worktrees.sql` and `modules/lanes/migrations/202610141010_lanes.sql`. M10's are `2026101420xx`. `yaml` 2.9.0 is a daemon dependency (the SDK already installs it).
- Settings: `PAP_TEST_GIT_PROTOCOLS` is test-only (`file`, `https`, `ssh`, colon-separated; it needs `PAP_TEST_PROVIDER_SCRIPT`, else `ConfigError`): it lets a push reach a local bare repository. Never set it in production.
- Log lines worth knowing: `lane_script_started`, `lane_script_ended`, `worktree_undo_failed`, `worktree_folder_unusable`, `worktree_disk_refused`, `worktree_folder_refused`, `push_refused {reason, keys, count}` (key shapes only, never URLs), `checkpoints_full`, `lane_trust_inherit_failed`, `lane_auto_test_failed`, `lane_archive_remove_failed`. Fuller story: `lanes.md`.
- Error codes: M9 adds none (refusals a person acts on are typed results). `lanes.create`, `lanes.restore`, `lanes.review`, `lanes.checkpointStatus`, `lanes.suggestCommit` and `lanes.compare` declare M10's `disk_low` (the disk floor, `PAP_MIN_FREE_DISK_MB`); a floor that fails any other way is still `capacity`.
- Unattended children (lane scripts, `gh`, M7 installs, M10's precheck) share `unattendedEnv` (`packages/contracts/src/child-env.ts`, re-exported by `kernel/child-env.ts`); the git runner keeps its own narrower allowlist (`kernel/git/exec.ts`).

## Policy module and exports

- `modules/policy/` (`createPolicyModule`): table `approval_rules` (`202610110100_policy.sql`: one row per owner, project and exact call; `grant_key` is the sha256 of the tool and its exact payload), table `session_policy` (`202610122010_session_policy.sql`: per session the mode override, `tainted_at`, `taint_epoch`; every statement names the owner), the owner's global settings (default mode, blocked-command patterns, built-in preset switch, host list; `settings-store.ts`, compare-and-set with `baseRevision`, 64 KiB cap), RPC `policy.listRules`, `policy.revokeRule` (`policy:read` / `policy:admin`), `policy.getSettings`, `policy.setSettings`, `policy.setSessionMode`, `policy.clearTaint` (`policy:admin`; tokens never hold it), and the `PolicyPort` the sessions module uses. Rules, modes, taint and the matrix: `policy.md`; the sessions side: `sessions.md`. Project = the git root of the session's folder (`project-scope.ts`: `.git` folder or file, at most 64 levels, real paths; the folder itself outside git; unreadable cases are their own project, never wider). - `compose-pi.ts` (`composePi`, called once by `createDaemon`) builds the helper pool, the one Pi write queue and the modules that use them: `models` (Settings › Models, `models.md`), `mcp` (Settings › MCP, `mcp.md`) and `trust` (project trust, ADR 0027), plus `skills` (Settings › Skills, `skills.md`, `compose-pi.ts:87`). It returns their merged `rpc` tables (`compose-pi.ts:95`) and `stopAll()`.
- Every method of these modules is `pi:admin` unless `models.md` or `mcp.md` says otherwise (`skills.md` has no exception: `skills.search` is `pi:admin` too, MC59), so a token is `forbidden`; `security/pi-token.test.ts` calls each `pi:admin` method of the catalogue as a token (M7R152) and requires at least 35 of them.
- Migrations M7 added (all in sources already listed in `MIGRATION_SOURCES`): `policy/migrations/202610131000_pattern_rules.sql`, `sessions/migrations/202610131020_pap_wrote_at.sql` (MC19) and `sessions/migrations/202610131030_tool_preset.sql` (MC20).

- The shared Pi write queue (`kernel/pi-write-queue.ts`, 8 in flight or waiting) is also held by plugin installs, removals, updates and switches. An install or update waits for the helper for up to 330 s (`modules/skills/service.ts:22`), and every other Pi settings write queues behind it meanwhile (MC54, accepted for M7; Pi re-reads `settings.json` under its own lock, so no save is lost). - Helper failures log `tail` (the clipped end of the helper's output) only for `skills.install`, whose output the helper masks, on every failure path (answer, timeout, exit, malformed record). Any other op logs code and clipped detail, since Pi's npm and git children write unmasked output (MC57, MC59, `kernel/helper/pool.ts`).
- `GET /metrics` (M10R95-R97, `compose-runs.ts` `composeMetrics`): off (404 JSON, like any reserved path) unless `PAP_METRICS_TOKEN` is set; a set value outside 32-256 of `A-Za-z0-9._~+/=-` is a `ConfigError` that names the variable, never the value. Own bearer only (compared on SHA-256 digests, `modules/runs/metrics-auth.ts`): wrong or missing is 401 with `WWW-Authenticate: Bearer` and `Cache-Control: no-store`; a cookie or a pap token is never accepted. Families come from `kernel/observability/prometheus.ts` (a collector that throws drops its family and logs once a minute). Runs families read the `runs` table (finished runs only, cached 15 s) so counters never go back; labels are closed sets, `provider` and `model` go through `labelValue`, and `model` keeps the 100 most expensive (`topLabels`), the rest `other`. `pap_trigger_fires_total` is an in-process counter incremented at each journal write (from 0 at the daemon's start); `pap_otlp_dropped_spans_total` counts spans the tracer refused (a line over 1 KiB, a full queue) plus those the OTLP exporter dropped.

## Agents and the sandbox (M11a)

- `daemon.ts` builds M11 through `compose-m11.ts` (`composeM11(core, modules)`, after `composeM10`, which the agents module needs), serves `m11.rpc` beside the other methods, and calls `m11.stop()` first in its stop, so the platform dispatcher answers `unavailable` before the sessions' workers stop. Migration stamps `2026101511xx`: sessions `1100` (kinds) and `1152` (owner preset), agents `1110`, automation `1120`, `1131` and `1153`, runs `1130`, inbox `1140`, lanes `1150`. Details: `agents.md`.
- Environment: `PAP_BWRAP` (`kernel/config.ts`): an absolute path or unset (a relative value stops the boot); it must pass the same test as the system `bwrap` (root-owned real path, every folder above it root-owned and writable by root alone). Not set by the service unit: a non-standard path is a drop-in (`systemctl --user edit pap`). The probe also reads `XDG_RUNTIME_DIR` for the egress folder (through the composition, `core.env`).
- The probe (`kernel/sandbox/probe.ts`) runs at boot in the background and never delays it past its 5 s; the canary folder is made under `$PAP_HOME` (hidden by a tmpfs inside the probe), and stale `pap-probe-*` folders (or links, which are unlinked and not followed) are removed at boot. A change of state logs `sandbox_probe {usable, reason}` (`missing`, `unsafe_path`, `refused`, `timeout`); a failed cleanup logs `sandbox_probe_cleanup_failed`. Other lines: `agent_sandbox_refused {agentId, reason}` (a launch refused), `agent_sandbox_spec_invalid`, `agent_egress_refused`, `agent_home_mode_repaired`, `agent_profile_unreadable`.
- The egress proxy: root `$XDG_RUNTIME_DIR/pap/<6 hex of sha256(real $PAP_HOME)>/egress` when `XDG_RUNTIME_DIR` is a real folder owned by the daemon's user with mode 0700 (the contract of that folder), else `$PAP_HOME/run/egress`; the first whose longest socket path (`<root>/<session>/<command>.s`) fits 107 bytes, else the proxy is unusable (`socket_path`). Under it: one folder per agent session, one socket per command, all 0700/0600, and the forwarder file `fwd.py` written at boot. Boot removes what a dead daemon left under its own root only (another daemon on the same `XDG_RUNTIME_DIR` keeps its own; `egress_boot_foreign` counts what is not pap's). The forwarder needs a root-owned `python3` under `/usr/bin`, `/usr/local/bin` or `/bin` (real path inside the sandbox's system folders) that answers a nonce; none: `no_python` or `unsafe_path`, and every launch of a networked agent answers `sandbox_unavailable` (Settings › Agents shows the line). Install `python3` system-wide for networked agents.
- The proxy resolves with `dns.lookup` (so `/etc/hosts` and nsswitch apply), two lookups at once daemon-wide and one per command, 5 s each. A machine that reaches the internet only through an upstream proxy has no networked agents in M11a (the proxy connects directly, ports 80 and 443 only).
- Egress log lines: `egress_status {usable, python, reason}` at boot and on "Check again", `egress_command {sessionId, agentId, allowed, refused, up, down, hosts}` when a command ends, `egress_limit {what, agentId, sessionId}` (rate-limited to one a minute), `egress_listen_failed`, `egress_session_failed`, `egress_handler_failed`, `egress_root_unusable`, `egress_probe_failed`. Hosts in `egress_command` are written as is only when they equal an entry the owner wrote (the list in force, a trusted source, a grant); every other host is `h:<first 12 hex of sha256(host)> (len N)`. `printf %s the-host.example | sha256sum | cut -c1-12` gives the hash to look for (lower case, no final dot). The hash is unsalted, 48 bits and logged with the length: it cannot name a host to a reader, but a low-entropy value placed in a host name can be guessed offline from a shared log. Command arguments and stage 02 reasons are not covered by this: the worker's value-based redactor protects them, and it skips values under 8 characters.
- Platform and vault lines: `platform_call_invalid`, `platform_op_failed`, `platform_result_invalid`, `platform_dispatch_failed`, `platform_bridge_failed`, `vault_key_lost`, `vault_unreadable`, `vault_failed`, `vault_update_not_sent`, `secret_audit_failed`, `agent_row_unlistable`, `agent_delete_incomplete`, `agent_quarantine_step_failed`.
- Reinstalling the service (`pap service install`) restarts the daemon: agent runs end, pending agent and secret requests expire, "use once" values are dropped and host grants are lost (`install.md`).
