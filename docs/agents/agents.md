## Agents

- An agent runs in its own Kata microVM, always (`agents-vm.md`; ADRs 0078, 0079, 0081). A machine without KVM or without `sudo pap vm setup` has no agents: creating or starting one is refused `sandbox_unavailable`, the rest of pap works. Platform ops, cards, requests, the vault and quarantine here apply to those agents; the VM's network is the proxy on `10.213.0.1:7843` filtered by the agent's host list.
- `AgentInput` (contracts) is the trust boundary; the row keeps the parsed JSON and parses it again at every read (`unreadable` otherwise). 32 per owner, `@Name` unique per owner whatever the case, id `<slug>-<4 hex>`. Methods: `agents.list|get|create|update|delete|openThread|resetThread|markRead|setPaused|queueTask|answerApproval|events|status|prompts|prompt|permissions|quarantine|vmStatus`, `subscribe.agents`. `agents:admin` and `secrets:*` are never a token's (`forbidden`); a token may read, open the thread, mark it read, pause or resume (M11R4) and fire an agent trigger whose target is `isolated`; it never makes an agent's session run (`sessions.prompt`, `compact`, `navigate`, `autoName`, `usage.resumeNow` answer `forbidden`, W5-R64).
- An agent's model may be one an extension registers (pi-claude-bridge, for one): the form's picker lists it after "Show models added by extensions" (`models.md`, "Extension providers"); the worker loads the owner's global extensions and applies it at start; a model it does not offer leaves the run on the model it has, logs `agent_profile_not_applied` and puts a notice in the session naming both (`agent_model_refused`), with the way to Settings › Models › Available models, where "My selection" can switch an extension's models on. An agent in Chat only loads no extension: its form's picker lists none and says why (the line under the field too), and when its saved model's provider is one the worker lacks the notice says Chat only is the reason (`agent_model_refused_chat`, from the worker's `MODEL_PROVIDER_UNKNOWN`); a model of Pi's own providers gets the regular notice; a change that failed otherwise is `agent_model_not_applied`.
- Edits are compare-and-set; the password is asked when `widensReach` says the agent can do more (ADR 0050). A running worker keeps the profile it started with; the owner's session mode and tool preset can narrow it, never widen it (W5-R23, W5-R26, W5-R28).
- Home: `$PAP_HOME/agents/<id>/` (0700, git repository, `prompts/`; a `MEMORY.md` from before sub-project 5 stays and is no longer read by pap), checked with `O_NOFOLLOW` at every launch (`agent-home.ts`). Scratch folders of isolated tasks: `$PAP_HOME/agents/.runs/<agent>/<task uuid>/`. Deleted homes: `$PAP_HOME/agents/.trash/<id>-<stamp>`. `sessions.create` below `agents/` is `invalid_cwd`. A VM agent's home is the VM disk's `/agent/home`; the host folder keeps `prompts/` and the trash. Its knowledge is the OKF bundle `/agent/knowledge` on the VM disk (`knowledge.md`).
- Delete: pause, busy check (`session_busy`), triggers, queued tasks, thread, vault scope, home move, one-use values, Inbox items, row. A failure after the move leaves the agent quarantined (`agent_delete_incomplete`).
- A row whose id is not a valid agent id is skipped from the list and logged (`agent_row_unlistable`); it cannot be seen or deleted in the UI.

## Threads, cards, unread

- `agents.openThread` is the only way a thread is made (`createAgentSession`, the launch gate runs in `launch`). The thread is the session `agent_role = 'thread'`; a reset archives it and the next open starts a new one. No fork or clone of an agent session. Agent sessions are out of the sidebar and the counts.
- Cards (`agent_events`, 500 newest per agent): `schedule`, `task`, `isolated`, `delegation`, `reminder`, `notify`. Written by pap before the prompt (`runCard`, state `running`), moved when the task ends; a failed task counts as unread again. Text from outside is stripped and clipped, and shown as text.
- Unread +1 per completed thread run and per card; `agents.markRead` clears it. Rail state: `needs_input` > `running` > `failed` > `paused` > `idle`, `quarantined` instead of all. `agents` stream: 32 agents, 200 requests, batched 250 ms; the `event` hint tells an open tab to read the cards again.
- `agents.status`: today against the budget, 7 and 30 days from `runs`, the newest 10 tasks, up to 20 triggers.

## Platform calls

- Session type is read from the session row (ADR 0047). `compose-m11.ts` registers seven handlers: `lane.note`, `agent.notify`, `agent.approve`, `network.request`, `secret.request`, `agent.delegate`, `agent.remind`. `subagent.run` is registered by `compose-subagents.ts` (M11b). `preview.start` and `preview.stop` are registered by `compose-previews.ts` (UX-2). A switch (`registry.available`) can turn an op off per owner.
- `agent.notify`: an Inbox info item and a solid card, 30 an hour per agent. `agent.approve`: a pending request (4 open per agent), a to-handle item, waits 25 minutes less 2 s, then `{approved: false}` and the request is `expired`; an abort cancels it.
- `agent.delegate`: refusals in this order: unknown caller, itself, unknown target, target not opted in, a tainted request to a `chat` or `none` target, depth (a run that was itself delegated delegates no further), target paused or quarantined, 10 an hour, 20 already waiting for the target (`limit_reached`), target over budget. Untainted: a thread task for the target. Tainted (after the owner's Allow once): an isolated, tainted task. The result comes back as a card in the requester's thread (`delegation`) and a `delegation_done` Inbox item; the target's thread also gets a request card while it runs.
- `agent.remind`: `when` is an ISO time with offset or `<n>m|h|d`, 15 minutes to 30 days ahead; 5 pending, 24 a day; moved to the end of the owner's quiet hours; a reminder set inside a delegated run stays delegated. It is a thread task on the agent's own thread, due on a guarded Clock timer (`due-timer.ts`, dedup `due:<id>`). A tainted reminder fires into its setter's session only (W5-R44, W5-R46).
- Every call writes one audit row; a call whose audit slot cannot be reserved (120 a minute per session) answers `rate_limited` and runs nothing (W5-R16). A worker in flight with 8 calls gets `rate_limited` for the ninth.
- `lane.note` writes the lane's one-line note (2 000 characters, 60 an hour per lane) and publishes the lane.
- `preview.start` and `preview.stop` (tools `preview_start`, `preview_stop`; UX-2, ADR 0088) are registered by `compose-previews.ts` once the sessions and the VM stack exist (`modules/previews/platform-ops.ts`). Callers `agent-thread` and `plain` (a project box's session only; the daemon refuses any other row `forbidden`, reading the box from its own records). `whenTainted: "run"`, deadlines 60 s and 10 s, no exfiltration. `preview.start {name, command, port}` starts a named service in the VM and answers `{id, name, port, status, reason}`, never an address; the service gets the network the session's shell has (an agent's `sandbox.network` read when the thread opened; a box session's the project's), decided by the daemon, never by the worker. It is a command that runs in the guest's own bwrap, so it is an `edit` for the approval matrix (read-only blocks it, supervised and the read-only preset ask Deny / Allow once, never "always") and is exempt from stage 02's "only pap's bash runs a command" through `runsACommand` (`packages/pi-host/src/policy/preview-start-plan.ts`); any other op with a `command` is still blocked there. The daemon refuses a read-only session whatever the worker planned. `preview.stop {name}` answers `{stopped}`. Limits, supervisor and tunnel: `agents-vm.md` ("Previews").

## Requests, the vault and secret requests

- Requests (`agent_requests`): `approve` and `secret`, states `pending`, `approved`, `denied`, `answered`, `declined`, `expired`, `cancelled`. At boot every pending request becomes `expired`. The owner answers with `agents.answerApproval` (approve), `secrets.answerRequest` / `secrets.declineRequest` (secret); a token is `forbidden`, a read-only database is `read_only`.
- Vault: ADR 0049. `secrets.list|set|delete`; values reach the worker as `init.vault` and `vault_update` (also in a VM, where the shell gets them in its environment: `agents-vm.md`, "The vault in the VM"), never to a child. A set while a worker boots reaches it (`vaultDrift`). Lost key: `secrets.set` answers `command_failed` and logs `vault_key_lost`; the list reads `unreadable`.
- `secret.request`: works from a VM session (a started agent session counts as sandboxed). The answer is audited, then kept, then the request closes with the ref's hash. A failed keep writes a second audit row "secret answer failed" with the code only. A one-use value waits 24 hours, 3 per agent, in the daemon and in the asking worker; it goes to the first command that names `$NAME` or `${NAME}` exactly. `vault_update.once` is authoritative: the worker replaces its whole set at each record and drops an expired value by its own clock (W5-R37). A reset, a quarantine and an agent delete drop them; a restart does too.
- The card for a secret request shows the asking thread's current taint (W5-R38): `AgentRequestView` carries no taint, the web reads the thread's session.

## The VM, the launch gate and egress

- Every agent runs in its own microVM (ADR 0081, which supersedes ADR 0048's host sandbox for agents): `agents-vm.md` for the runtime, the proxy, the taint the daemon sees, the vault in the VM and the bundle check. There is no probe, no bubblewrap on the host and no `python3` requirement. Settings › Agents shows the VM stack's status (`agents.vmStatus`), not a sandbox probe.
- The launch gate (`sessions/agent-gate.ts` and `vm-gate.ts`) runs for every agent launch: the agent exists and parses, quarantine (`agent_paused`), the home check (`invalid_cwd`), the VM layout (no VM stack on this machine: `sandbox_unavailable`, logged `agent_vm_unavailable`), then the vault and the owner's waiting one-use values for a thread or a task (never a child). `guardedLaunch` adds the VM stack check (`sandbox_unavailable`) and the bundle check (`vm_bundle_stale`) before any VM starts.
- The egress proxy is the VM proxy on `10.213.0.1:7843` (`agents-vm.md`, "Network"): it filters by the agent's host list, not by content. The proxy and the report lines it writes (`egress_vm_usage`, `egress_limit`) are in `modules/egress/`; a host the agent chose is logged as `h:<12 hex> (len N)` unless the owner wrote it. To find the host behind a hash: `printf %s the-host.example | sha256sum | cut -c1-12` (lower case, no final dot). The hash is unsalted and 48 bits: a low-entropy secret placed in a host name can be recovered offline from a shared log. Shell command arguments and stage 02 reasons carry what the agent wrote and rely on the worker's value-based redactor.
- A networked shell's first result taints the worker's session, and the daemon marks the launch's sessions from what the proxy saw: `agents-vm.md`, "Taint the daemon sees".

## Quarantine and permissions

- `agents.quarantine` steps (`QUARANTINE_STEPS`): pause with `quarantined_at`; `tasks`: cancel running and queued tasks (10 s); `subagents`: abort the running children of its threads (M11b); `thread`: abort, archive and clear the thread (this drops its host grants, W5-R52); `requests`: cancel pending requests; `once_values`: drop one-use values; `triggers`: rotate the agent's webhook secrets (shown once); `vault`: list vault names; `files`: list the paths of its imported files. Each step reports `{step, code}`. Replay answers `conflict` (the secrets are shown once). Resume from quarantine needs the password.
- `agents.permissions` (browser only): tools (preset, `active` only from a live loadout, else `unknown-until-start`), the shell (a microVM), hosts, blocked count, vault names, triggers, trusted sources, autonomy, the egress line, and the three legs of the trifecta. `tools.active` is `unknown-until-start` until a worker has started, and the sheet then says "may" instead of "can".
- `agents.prompts` / `agents.prompt` read the `.md` files the owner imported under `prompts/` in the agent's files (the host copy; `agents-vm.md`, "Prompt chips"): no link followed, a regular file, 16 KiB, fatal UTF-8. Files the agent writes in its VM are not listed.

## Subagents (M11b)

ADR 0053; sessions side in `sessions.md` ("Subagents"), spend in `finops.md`. Code: `modules/subagents/` (the op, the rows, stop, profiles), `modules/sessions/child-port.ts` and `children.ts`.

- The `subagent` tool (`subagent.run`) is registered on the platform port by `compose-subagents.ts` with the owner's switch (`agents.subagents.enabled`, default on; `maxConcurrent` 1 to 4, default 2). Callers: `plain`, `lane`, `agent-thread`. A child, a task and an agent's isolated task have no platform op, so depth is 1. A third-party subagent tool is an unknown external tool and asks or is blocked.
- A call refuses, in order: switch off (`unavailable`), `maxConcurrent` running children of this parent (`limit_reached`), 30 starts an hour per owner (`rate_limited`, failed starts count), parent archived (`not_found`), no capacity (`unavailable`), the agent over its own daily budget (`budget`). Then the row (`subagent_runs`), the child session, the prompt (fenced as `subagent-task` when the parent is tainted), and the wait for the child's run end (at most the op's 240 minutes). The answer is the child's last assistant text, at most 51 200 characters, `clipped`; `tainted` is the child's taint at the end, and a tainted answer is fenced in the parent. A finished child's worker is released at once.
- Profiles (`subagents.profiles {sessionId}`, `sessions:read`; read-only, owner m13): `<Pi agent dir>/agents/*.md`, and `<project>/.pi/agents/*.md` only while Pi trusts the project (the daemon passes the folder only when trusted, the helper checks again; never for an agent's session: its home is not a project, W5-R27, W5-R29), read by the helper offline; 64 files per folder, 32 KiB each, `longTerm` skipped, a project file wins over a user file of the same name. The result counts what it skipped (`parse`, `refused`, `tooLarge`; log `subagent_profiles_skipped`). The call reads the chosen file whole (`subagents.profile`; two files with one name in a folder: `conflict`, call `bad_request`; none: `not_found`; helper failure: `unavailable`). Without a `profile` the child takes the parent's preset and no extra prompt.
- The child is held to its parent: tools = the profile's list narrowed to the parent worker's live active tools (no loadout: nothing kept, so a profile list gives `bad_request`); mode = the parent's, `full-access` becomes `auto-accept-edits`; taint = the parent's, sticky. A child of an agent thread keeps `agent_id` with role `child`: the launch gate, the agent's hosts, blocked commands, sandbox and home, the agent's mode (capped as above) and preset at every start (a reopen narrows, never widens), the agent's budget. It has no vault (not in `init.vault`, skipped by `sendToAgent`), no host grants, no autonomy, no platform op and memory closed. Its file tools follow the thread's allow-list: its home, the agent's own runs folder (external content), attached files, the system folders, Pi's skills read-only (W5-R63, W5-R65, W5-R66). A child of a plain or lane session is an attended session with the owner's rules.
- The profile's prompt is a file, `$PAP_HOME/subagents/<child id>.prompt` (0600 in a 0700 folder, W5-R62), written before the session row and read at each launch. Deleted with the child session, kept on archive, swept at boot when no row has it. A missing file logs `child_prompt_missing`; the child still starts.
- Stop: see `sessions.md` (five causes, the owner's `subagents.cancel`, boot marks live rows `interrupted`). Log lines: `subagent_prompt_failed`, `subagent_profile_failed`, `subagent_child_failed`, `subagent_release_failed`, `subagent_abort_failed`, `subagent_row_not_ended`, `subagent_runs_interrupted`, `child_prompt_missing`, `child_model_not_applied`.
- Not done: no delete path for an ordinary parent yet (`parent_deleted` comes through `deleteTaskSession` only); a stop that arrives before a child's guard exists is only caught by the parent-open checks and the launch gate; the roll-up cost on a chip refreshes at status changes.

## Known limits (in one place; ADR 0049 and ADR 0081 carry the reasons)

- **Inherited descriptors.** A daemon started by a parent that leaks non-CLOEXEC descriptors (GitHub's Actions runner does) passes them to terminals and workers. Systemd starts it with 0 to 2 only. CI runs `test:int` through `scripts/ci/without-inherited-fds.sh` (M13-C13); closing inherited descriptors at boot comes after v1.
- An agent thread's `read`, `grep`, `find` and `ls` are blocked (no question, every mode) outside its home, its own runs folder (`agents/.runs/<id>/`, read as external content: fenced and tainting, W5-R65), the files attached to the thread, Pi's skills folder (`<Pi agent dir>/skills/`, read-only, neither fenced nor tainting: instructions you installed, W5-R66) and the system folders (W5-R63: "outside this agent's folder"); its edits stay in its home, and a write under the skills folder is refused like any write outside it. Your home, the rest of `$PAP_HOME`, other agents' homes and the runs folders are out of reach. These are pap's path rules, and they run in the worker (inside the VM, bwrap confines the shell to the VM's home besides).
- "Use once" bounds how long a value is available, not who sees it.
- Values under 8 characters are never redacted; encodings (base64, split, reversed) bypass literal redaction.
- After a worker restart the redactor no longer knows a one-use value that was used.
- The proxy guarantees hosts, not content; exfiltration through any reachable host remains.
- In a VM, the approval mode, blocked commands and tool rules run in the worker: in a compromised VM they are the agent's own policy. MCP stdio servers and extension subprocesses are not confined inside the VM (ADR 0081).
- A backup of the whole `$PAP_HOME` holds the vault key (RT-13); a lost key leaves the vault unreadable.
- The worker (Pi, extensions, MCP stdio) is not confined inside the VM; the VM is the boundary (ADR 0081). An owner session's worker (outside agents) is not sandboxed; R101's residual stays.
- Host grants and one-use values are lost at a daemon restart.
- The key write needs hard links (Linux).
- CI: under `CI=1` `pi-search.symlinks.int.test.ts` makes ripgrep and `fd` hard requirements, and the pi-host VM shell test (`vm-shell/ops.bwrap.int.test.ts`) throws without a working root-owned `/usr/bin/bwrap`; locally they skip with one warning.

## Test seams

- Int tests that start agent workers use the VM bed on the process backend (`PAP_TEST_AGENT_RUNTIME=process`, harness `vm: true`, `testing/vm-bed.ts`; `agents-vm.md`, "Tests"): no bwrap, no KVM, no pap-vmd. They use a temporary `PAP_HOME`, the scripted provider (`PAP_TEST_PROVIDER_SCRIPT`; its `prices` option gives runs a cost), and the steppable clock of `security/testing/steppable-clock.ts`.
- `modules/egress/testing/` is the only place that reaches `127.0.0.1`: the proxy factory takes `resolve` and `denies` as required dependencies and the production wiring passes `dns.lookup` and `blockedStrict` (`kernel/net/address-strict.ts`, the check push uses too: it also refuses the documentation, benchmarking, ORCHID, SRv6, Teredo, discard and 6to4-relay ranges). No egress test names a public address or a real host; bypass targets are listeners on the loopback and the test asserts they saw nothing;; the Kata suite checks interface isolation from inside a VM.
- Beds: `agents/testing/bed.ts`, `agents/testing/requests-bed.ts`, `secrets/testing/secret-requests-bed.ts`, `platform/testing/dispatch-bed.ts`, `sessions/testing/int-bed.ts`.
