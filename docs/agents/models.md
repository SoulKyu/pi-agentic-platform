# Models (Settings › Models, the session's model bar)

Code: `apps/daemon/src/modules/models/`, helper ops `packages/pi-host/src/helper/ops/models-*.ts` and `auth*.ts`, worker side `packages/pi-host/src/model-commands.ts`, web `apps/web/src/features/models/` (see `web.md`). Contracts: `packages/contracts/src/models-*.ts`. ADRs 0023, 0026, 0029, 0068 to 0070. Rulings: `docs/research/m7-rulings.md`, `docs/research/models-batch-rulings.md`. The helper pool and `compose-pi.ts` are in `daemon.md`; the session's own model commands are in `sessions.md`.

## Rules that hold across the module

- Pi's configuration (`auth.json`, `models.json`, `settings.json`) is read and written only in a helper (ADR 0023), masked. Every method is `pi:admin`, so a token is `forbidden` (`security/pi-token.test.ts`), except three `pi:read` methods: `models.overview`, the masked provider and model list (`contracts/src/models-methods.ts`), `models.available`, the models a context may use (next section), and `models.pricing`, which answers `forbidden` while the models.dev switch is off (`contracts/src/models-provider.ts`).
- Changes that run code or add a credential take the password step-up (sign-in, API key, `models.json` save, provider save and remove, discover); switches, defaults, sign-out and cancels never ask (M7R133).
- `$HOME`-wide dotfiles latitude (owner m13, M7R146): the `models.json` editor follows a symlink anywhere inside `$HOME` as well as inside the agent directory (`helper/ops/models-json-shared.ts:30`, roots `[agentDir, home]`). Only a process of the same user can plant such a link, and it can already write the target. A link to `/etc/x`, a dangling link, a FIFO, a folder or a file over 1 MiB is refused (`config_path_refused`). `mcp.json` has the same latitude (`mcp.md`).
- Zero telemetry: the requests pap starts are the ones the owner clicks for (catalog refresh, sign-in, discover, Test, and the models.dev lookup once its switch is on).

## Models module (Settings › Models)

- `modules/models/` calls the helper ops `models.overview`, `models.setDefault`, `models.setDefaultThinking` and `models.refreshCatalog` (`packages/pi-host/src/helper/ops/models-*.ts`; schemas `HELPER_OPS` in contracts). Every helper result is parsed with the contract's strict schema before it goes on: an unknown field fails the call `helper_failed`, so a key cannot ride along.
- The overview opens Pi's `ModelRuntime` with `refreshOnCreate: false, allowModelNetwork: false`: built-in and `models.json` providers only, no extension, no request, no key command run. A `!command` value is code execution: Pi's `checkAuth` does not run one in a `models.json` key, but DOES run one in a stored `auth.json` credential, so the overview never calls `checkAuth` or `listCredentials` (MC25). Sign-in state comes only from pap's own bounded read of `auth.json` and `models.json` (leading BOM stripped like Pi; `readSignInFacts`): a stored credential or a `models.json` key means configured, and a file that is unreadable or does not parse sets the provider's `auth` status to `unknown` (all providers for `auth.json`, the `models.json` providers for `models.json`). Sign-in through an environment variable is not a stored sign-in and does not make a provider `configured`; the `env` list of `auth` (MC26) gives, for a built-in provider, the variable NAMES Pi reads a key from and whether each is set in the helper's environment (the daemon's, without `PAP_*`): presence only, nothing executed, no value in the answer. The table is a constant in `helper/ops/env-sign-in.ts` (Pi 1.1.0 keeps its own private); its test fails when a listed provider is no longer one Pi ships. Overview, `setDefault` and `setDefaultThinking` never run a command in a models.json `apiKey` or header, nor in `auth.json` (`models-commands.test.ts`, a marker file per field). `auth` says which kinds exist and whether one is stored or configured, never a value. The answer is cut at 300 providers, 2000 models each and 800 000 bytes (`truncated`, `modelsTruncated`).
- Defaults are written with Pi's `SettingsManager` into the global `settings.json` (flush, then `drainErrors()`). A model outside the resolved `enabledModels` is refused (`bad_request`); a trusted project whose `.pi/settings.json` sets the same key gives `project_scope` (the file goes to the log, the client message is fixed). An unreadable settings file is `config_invalid` and is never written over; a link or non-regular file is `config_path_refused` (Task 6b boundary).
- `models.setEnabled` edits `enabledModels` minimally (`helper/ops/enabled-models.ts`): Pi's own `resolveModelScopeWithDiagnostics` decides what every entry enables, only the entry covering a switched-off model is rewritten, and the finished list is re-resolved before it is written (mismatch: `failed`, nothing written). Refusals answer `conflict`: the last enabled model, or a list over the contract's 256 entries.
- Settings writes are serialised in the service (MC28): one chain, a write waits for the previous, at most `WRITE_QUEUE_MAX` (8) in flight or waiting (`kernel/pi-write-queue.ts:4`), then `capacity`. Reads are not queued. The queue is the daemon's one chain for every write of Pi's `settings.json` and models/MCP files (MC29): `apps/daemon/src/compose-pi.ts` creates it and hands it to the models and MCP services; the trust service keeps a queue of its own (`trust.json` is not `settings.json`).
- Deviation from "every Pi write goes through `writePiFile`": `settings.json` is written by Pi's `SettingsManager` (its lock, field-level merge, in place, not atomic). `guardSettingsWrite` repeats the link/root check and refuses a file with another hard link (`config_path_refused`, `hard-link`) immediately before each write. Residual: a same-user swap between that check and Pi's write. ADR 0029.
- `cwd` of the overview and the writes must be a project root of the caller or a folder inside one (`ProjectsPort.covers`), else `invalid_cwd`.
- `models.refreshCatalog` is the only request pap starts for the catalog, on the owner's click. With `PI_OFFLINE` set (any value; it passes to the helper) the answer is `{ offline: true }` with no request. The refresh is an explicit `pi:admin` action and may run the owner's own `!command` keys (the agent directory's config) as Pi does when it calls a provider; Pi reads no project's `models.json`, so a project's command is never run (tested with an untrusted and a trusted project). It answers `failedProviders` (ids only); it fails `helper_failed` only when every provider asked (dynamic, with a sign-in) failed and nothing changed.
- The `cwd` check is lexical: a symlink inside a project folder that points outside passes `covers` (same-user only; the helper reads a project's settings only when the trust store says trusted).

## Sign-in and API keys (Settings › Models, Task 11)

- Helper ops `auth.login`, `auth.setApiKey`, `auth.logout` (`helper/ops/auth.ts`) run Pi's own `ModelRuntime.login` / `logout` (M7R57) over a credential store of pap's (`auth-store.ts`) instead of Pi's file store. Every read and write of `auth.json` goes through the Pi file boundary: no link out of the folders, no dangling link, a regular file, mode 0600 on every write, and a file with another hard link is refused with its own code `config_hard_link` (fixed en/fr message, R66). The store holds Pi's lock folder (`auth.json.lock`, stale after 30 s) around each read-modify-write; a file that does not parse is `config_invalid` and is never written over; other providers' entries are rewritten as they were.
- No `!command` runs. Pi's own `login` and `logout` call `checkAuth` for the provider they work on; pap's own code never does (the overview neither, MC25). Nothing resolves a stored key all the same: the store's `read` returns what is stored without resolving it (Pi's own store resolves a command on read), and Pi's composed check does not resolve a stored key. A credential whose key or env value starts with `!` is refused (`bad_params`) in the contract, the sign-in prompt and the store. The runtime is opened with `refreshOnCreate: false`, so no provider is checked at open. A `!command` in `models.json` for the provider being signed in or out is not run either (marker tests).
- `models.login` and `models.setApiKey` require the password step-up (`requireStepUp`, a browser session only; owner c3). `models.logout` does not (removals never ask, M7R133). All six methods are `pi:admin`, so a token is `forbidden`; `pi-token.test.ts` and `login-flow.int.test.ts` pin it.
- `models.login` starts a flow (`login-flows.ts`): at most 2 live per owner (`capacity`), 1 per provider (`conflict`), never evicting; ended after `done`, a cancel, 10 minutes, or 60 s without a subscriber (a `subscribe.login` counts; when the last subscription of the flow closes, a reload or a lost connection, the hub's `onLastSubscriberLeft` calls `flows.detach` and the 60 s start again, MC31; a reload that comes back within the minute re-attaches). A flow belongs to its starter (`not_found` for anyone else). Helper events are parsed with `LoginEvent` (https links, or http on loopback); a helper cannot announce a prompt or `done`; the 8th refused event ends the flow `helper_failed`. The `login` stream is keyed by the flow id; its snapshot holds the last 64 events (`login-publisher.ts`).
- Keys and answers go to the helper and nowhere else: not logged, not in the audit (`provider_signed_in {provider, method}`, `provider_key_set {provider}`, `provider_signed_out {provider}`), not in a result. A receipt normally keeps the SHA-256 of the request params (R69); for `models.setApiKey`, `models.loginAnswer`, `models.config.save` and `sessions.respondDialog` the method definition lists `sensitiveParams` (the non-secret selector fields: `provider`; `flowId` + `promptId`; `baseRevision`; `sessionId` + `dialogId`; MC30, MC43) and the dispatcher hashes only those, so a replay must name the same target (another selector under one command id is `bad_request`) and `state.db` holds nothing to guess a key from.
- If Pi commits the credential but its follow-up model sync fails (`CredentialSynchronizationError`), the op answers ok: the credential is stored or removed, and the owner is told so (MC31). Any ok helper result is audited, even after a cancel or an idle abort raced it; the stream still gets one `done`. `models.cancelLogin { provider }` cancels the caller's own live flow for a provider (no step-up; another user's flow is `not_found`), so a reload that lost the flow id does not lock the provider for 10 minutes.

## The models.json editor and the Pi file boundary (Settings › Models, Task 12a)

- Methods `models.config.get` and `models.config.save` (both `pi:admin`: browser sessions only, never a token, because masking is best effort and the masked text can still show the residuals below, MC33; the save also takes the password step-up, owner c3, and is a mutation) over the helper ops of the same names (`helper/ops/models-json.ts`). The file is always `<agentDir>/models.json`; the client sends text and a revision, never a path. The daemon parses each helper result with the strict contract schema (`models-config.ts`), so a field that is not listed cannot carry a secret out.
- Revision (MC32): an HMAC-SHA-256 of the file text under 32 random bytes the service makes at each boot and hands to the helper (the client never sees or sends it). It is not a hash anyone can test a guessed secret against. After a daemon restart the first save answers `conflict` and the editor reloads.
- A file that does not parse (a missing comma or colon, a single quote, a block comment, an unterminated string, over 64 levels) is not shown: `get` answers `text: null` with `issues`, each a line and column (of the text with comments and trailing commas removed) and a fixed phrase, never a value. Fix it in a terminal, or replace the whole content from the editor (a replacement holds no placeholder, since none can come from a file that was never shown).
- Masking (`helper/models-json-mask.ts`, scanner `scanJsonc` in `helper/jsonc.ts`; `parseJsonc` stays Pi's exact tolerance and the only validator): a string value is masked as `"<redacted:N>"` (N in document order) when any key above it, or a `headers` key, contains `key`, `token`, `secret`, `password`, `passwd`, `auth`, `bearer`, `credential`, `cookie`, `pwd`, `passphrase`, `session` or `signature` once reduced to lowercase letters (the shared list of `helper/credential-words.ts`, MC41, which the MCP masker uses too) (`openaiApiKey`, `X-Api-Key`, `client_secret`, `api key ` all match), or when it is a URL with user information (`https://user:pw@host`); unless it is `$NAME`, `${NAME}` or starts with `!`. In a comment, from right after the first credential word (inside its identifier: `token_sk-...` is cut after `token`) to the end of that line is masked the same way (a closing block marker stays); only a whole quoted reference or command (`"$NAME"`, `"!op read x"`) or a bare reference is kept, so `// apiKey: !important sk-...` is masked. Over-masking (`monkey`, `keyboard`, `author`) is accepted: a restore is exact.
- Still shown (named residuals, shown to the owner's browser session): a `!command` that embeds a literal (`!echo sk-...`; it is shown so the owner sees what runs); a secret under a name with none of the words; a non-string value under a credential key; a comment whose value is on a different line than its credential word, comes before the word (`// sk-... is the old key`), or has no credential word (`// sk-abc`); a spelling with a separator inside the word (`pass_word`) in a comment; a literal key with a trailing space is masked, a URL with credentials in a query string is not.
- A save re-reads the file, compares the revision (`conflict`), masks the current file again, and puts an original back only at the exact key path (object keys and array indices) it was masked at, or into a comment that would mask it again. A placeholder that is unknown, used twice or moved answers a refusal `masked_value_moved at line L, column C`, so a moved placeholder can never be read back as text. Then it validates: `parseJsonc` (block comments are refused as Pi does), a lenient zod shape, Pi's own loader on a private copy in `$PAP_HOME/models-check` (0700, removed after, swept at daemon boot, a failed removal is logged) with `getError()` empty. A refusal for content is a result `{ code: "config_invalid", issues }` with at most 20 JSON paths or positions of plain characters, never a parser or Pi message. The revision is checked again right before the write; an outside writer (an editor, the `pi` CLI) can still land between that check and the rename, and the rename then replaces its change.
- The write is `writePiFile` (temp beside the real file, mode 0600, rename). A link must lead inside the agent directory or the home (a dotfiles link anywhere in `$HOME` is followed, owner m13, M7R146: only a process of the same user can plant it, and it can already write the target); `/etc/x` is `config_path_refused`; a dangling link, a FIFO, a folder or a file over 1 MiB are refused. A hard-linked file is refused with `config_hard_link` (a fixed message: no path, no errno text).
- After a save the helper re-asserts `enabledModels` for the providers named in the old or new file whose models were all enabled before (`resync`, computed from the same matching as the overview's `enabled` flags, after the final revision check and just before the write). The answer says `enabledModelsSynced`; when settings.json cannot be read or updated the save still stands and the flag is false. Renamed models are not tracked: the owner prunes. The save goes through the models service's write queue (MC28, MC29; `service.queue.test.ts` pins it). The audit line is `models_config_saved` with no detail. A receipt normally keeps the SHA-256 of the request params, which would hold any new literal typed into the text: `models.config.save` lists `sensitiveParams: ["baseRevision"]` (`contracts/src/models-config.ts`), so the dispatcher hashes only the revision and a replay must name the same one.
- `pi-file.ts` residuals: (1) the hard-link check and the rename are two steps, so a hard link made by another process of the same user in between is split by the rename (the other name keeps the old text); (2) a folder swapped for a link between the descriptor check and the rename (same user); (3) a folder sync that fails after a successful rename does not fail the write: the new file is in place, the helper emits `folder_sync_failed {code}` and the service logs `models_config_save_event` with the code only (for `auth.json` the helper writes a `pap-helper: auth.json folder sync failed (CODE)` line on stderr). A root is compared by its real path: `//`, `/.`, `/tmp/..` or a link to `/` is refused.

## Provider discover, test and pricing (Settings › Models, Task 12b)

- `models.discover { provider }` (`pi:admin`, password step-up: it sends the provider's key to its base URL, on the owner's Q3(a) list, M7R133) and `models.test { provider, modelId }` (`pi:admin`, no step-up: a model Test is not on that list) run helper ops of the same names (`helper/ops/models-discover.ts`). Both start only on the owner's click and resolve the provider's key on the runtime, so a `!command` key of the owner's own `models.json` runs in the helper (as it does whenever a session prompts that provider). Discover is one `GET <baseUrl>/models`; test is one completion through Pi's provider code with `maxTokens` 16, no retry. Both wait 15 s at most, follow no redirect and send no cookie (`provider-request.ts`: a key must not travel to another host; the test op hands Pi `strictFetch`, pinned by cross-origin 307 tests for openai-completions and anthropic-messages).
- A failed request is reduced to a status class in the answer (`code`: `http_4xx`, `http_5xx`, `network`, `timeout`), never a provider body or message (M7R66). The class of a completion comes from the HTTP status only, never from a number in text. Discover then answers `{ models: [], code }`: `code` is an addition to the planned `{ models }` shape so the owner can tell a refused key from a dead URL. Only `id`, `contextWindow`, `maxTokens` and `reasoning: true` are copied from a discovered entry (pi-web #856); at most 2000 and 800 000 serialised bytes (`truncated: true` when cut), duplicates dropped, a body over 4 MiB is `network`. A key Pi cannot resolve (a failing `!command`, none) is asked without; the helper writes `pap-helper: auth_unavailable` to stderr.
- Known no-op (plan-mandated, M7R66): discover appends `/models` to the base URL for every provider. For the built-in Anthropic (`/v1/models` is the real path) and Google (key in a query) it answers `http_4xx`. The web UI hides the button for them (`discoverSupported` in `apps/web/src/features/models/models-json.vm.ts`).
- `models.pricing { provider?, modelId }` (`pi:read`) is the models.dev opt-in (M7R138, MC3, MC34). The service reads the owner's `models` setting through `SettingsPort.models(ownerId)` first; off (the default, no row, a damaged row or a wrong-typed value) it answers `forbidden` before any helper or request, cached data included. On, one helper run fetches `https://models.dev/api.json` (8 MiB cap, declared length checked first, stream cancelled at the cap; 15 s; no header, cookie or redirect) and returns the entries asked for plus the extracted map of every model's finite numeric prices. The daemon keeps that map for 1 hour (`pricing-cache.ts`, one map, replaced) and answers every later question from it, so models.dev is downloaded at most once an hour whatever a caller asks. A map over 900 000 bytes (helper) or 1 MiB (daemon) is not kept: each call then downloads again. A token holding `settings:operate` and `pi:read` can switch the lookup on and trigger the fixed-URL download without a click; no data is sent.
- `models.usage { providerId }` (`pi:admin`, idempotent, Task 18, M10R109 to M10R111) shows a provider's quotas on the owner's click. Ten providers (`PROVIDER_USAGE_IDS`), one pinned https URL each (`helper/ops/models-usage.ts`). Before it resolves any credential the helper loads Pi's configuration the way a session does: **the owner's global extension code runs in the helper on each click** (global `extensions/` and the enabled packages of the global settings, offline with `PI_OFFLINE` on, `projectTrusted: false`, no project scope), so an extension that repoints the provider's base URL is seen. The helper refuses a provider whose *effective* base URL (provider, first model, or the credential's own) is not on the official origin (`provider_overridden`), and refuses when an extension fails to load (`extensions_failed`, fail closed); no step-up. Pi's `ModelRuntime` resolves the key over `createAuthFileStore`, so an expired OAuth token is refreshed by Pi under the store's lock and written with Pi's own temp-and-rename (mode 0600); the 15 s deadline bounds the HTTP request only, never credential resolution or the refresh (only the daemon's cancel signal reaches it). The request has no redirect, no cookie, 15 s and a 64 KiB body cap; the answer is normalised and parsed with the strict `UsageReport` (at most 32 buckets and 32 metrics, labels cleaned of control and bidi characters). A failure is a status with no text: `auth_unavailable`, `query_failed`, `unsupported`, `provider_overridden` or `extensions_failed` (fixed en and fr copy in the UI). The daemon keeps one answer per provider for 60 s (`usage.ts`, failed queries included, helper errors not) and shares a run in flight. Web: the "Check usage" button in the provider detail (`ProviderUsage.tsx`); nothing is asked before the click.
- A helper failure of any of the three is `helper_failed` with a fixed message; the helper's own text goes to no client. A discovery writes the audit line `provider_discovered {provider}` once the request ran; test and pricing write none.

## Which models a context may use (picker, `models.available`; ADR 0068)

- **Three rules, one function.** (1) `listAvailable(runtime, patterns, sessionScope?)` (`pi-host/src/available-models.ts`) is the only code that decides: the session's scope, else the models `enabledModels` resolves to when that is non-empty, else every model of a provider with a key. Patterns that match only unsigned providers fall back to the signed-in list, never an empty picker. (2) A read that has no session (the helper) opens Pi's runtime over pap's credential store with `refreshOnCreate: false` and no model network, so it runs no `!command` and makes no request. (3) A worker re-reads before it lists. `models.overview`'s `enabled` flag stays "not switched off, among all models", for the Settings switches only.
- **The worker's freshness (MPR25).** `freshAvailable` (`handleGetAvailableModels`, `handleSetModel`) reloads the settings (`SettingsManager` `reload`) and calls `runtime.refresh({ allowNetwork: false })` before it lists, so a warm worker sees a provider or an `enabledModels` change the owner made meanwhile (`host.models.int.test.ts`, "sessions.models and the helper agree after a write"). While the session runs it lists from the snapshot its run started with; a model switch is refused during a run anyway (`session_busy`).
- **`models.available { cwd? }`** (`pi:read`, idempotent; `cwd` must be a project of the caller, checked before the cache is asked) is the helper op `models.available`: `ModelSummary` rows, provider names and `origin` (`scope` | `signed-in`), nothing secret, at most 2000 models, 300 providers and 600 000 bytes (`truncated`). After the same offline `refresh` as the worker, so a catalog cached by "Refresh catalog" is listed too. Pi's one write there: it creates `models-store.json` when the file is missing, before it takes its own lock; otherwise the refresh only reads it.
- **The daemon cache** (`modules/models/available.ts`): 10 s TTL per `cwd` (none counts as one key), at most 32 keys (expired ones are swept before the cap is judged; a new key is answered but not stored when full), one helper run for concurrent reads, and a generation counter so a read that started before a write never stores its result. `clear()` runs when each write of Pi's files settles, success or failure: `setEnabled`, `setDefault`, `setDefaultThinking`, `config.save`, provider `save` and `remove`, `refreshCatalog`, `setApiKey`, `logout` and a login's `onSignedIn`. What it cannot see shows when the 10 s end: a trust change (the `trust` module owns it), a hand edit, the `pi` CLI, and a helper killed mid-write by a deadline or a cancel that lands its file after the clear. Worst case memory: 32 keys of at most 600 000 bytes, about 19 MB.
- **A lane can see another list.** The New lane dialog asks with the project root, but the lane runs in a worktree whose Pi trust is inherited only under conditions (`lanes.md`, "Trust inheritance"): a lane on a foreign base can list different models than the dialog showed.
- **A damaged file.** With a corrupt `settings.json` the helper shows the full signed-in list, while a warm worker keeps the selection it last read well. With a corrupt `models.json` both drop the custom providers.
- **Extension models differ.** The helper loads no extension, so a model an extension's provider registers appears in a session's menu (`sessions.models`) and not in a no-session picker. The picker footnote says so.
- **The `!command` exception (MPR1).** The worker's default store resolves a `!command` key; the helper reports such a provider configured without running it. Both list it, and it may fail when used. The footnote says so. `available.marker.no-command` proves the helper runs none for `auth.json`, `models.json` keys or headers.
- **The picker** (`apps/web/src/features/models/picker/`, `web.md`): one field for the agent form and the new-lane dialog; the session menu shares its list. Pickers read `models.available` or `sessions.models`, never `models.overview` (a source scan pins it). A saved choice that is not offered stays visible, first model row after Pi's default, as "saved, no longer offered", and re-picking it keeps the thinking level. No run-start check exists: the run fails with Pi's own error.
- **Backups.** M6b leaves `models.json`, `auth.json` and `settings.json` out of the backup (M6bR3). After a restore, set the providers, the model selection and the keys again.

## Provider form (Settings › Models › Add a provider, ADR 0069)

What the owner can do: add, edit and remove one provider of `models.json` from Settings, with preset cards (Ollama, LM Studio, vLLM, OpenRouter, three compatible APIs, custom) and one short form: name or id, API type (`openai-completions`, `openai-responses`, `anthropic-messages`, `google-generative-ai`, `mistral-conversations`), base URL, key or auth (stored, an environment variable, none, keep), up to 8 headers, up to 500 models by hand or by discovery. Bedrock, Vertex, Azure, Codex and `pi-messages` stay in the raw editor. Code: helper ops `packages/pi-host/src/helper/ops/models-provider.ts` (merge in `provider-apply.ts`, the form's view in `provider-view.ts`, the shared write tail `commitText` in `models-json-shared.ts`), daemon `modules/models/provider-config.ts`, contracts `models-provider-form.ts` and `base-url.ts`, web `features/models/provider/` (lazy chunk).

- **Methods.** `models.provider.get { id? }`, `save { mode, id, provider, baseRevision }`, `remove { id, baseRevision, alsoRemoveKey }`, all `pi:admin` (a token is `forbidden`); `save` and `remove` take the password step-up and are not idempotent; `save` lists `sensitiveParams: ["id","mode","baseRevision"]` and `remove` `["id","baseRevision","alsoRemoveKey"]`, so a replay under one command id must name the same target. Audit `provider_saved`, `provider_removed` (and `provider_signed_out` when the key goes), ids only. `provider-config.int.test.ts` walks the temp root for a marker key and a header literal: the key is in `auth.json` once, a header literal only in `models.json`, nothing in a log, the audit, the receipts or any answer.
- **Write rules** (ADR 0026, MPR11): strict JSON, unowned keys kept, revision checked in the one write queue and again before the write, Pi's loader validates a private copy (not on remove), `writePiFile` 0600, `enabledModels` resync. Every write clears the `models.available` cache.
- **`get`** answers `editable: true` with the provider, a revision and `advanced` (the entry holds fields the form keeps), or `editable: false` with a reason (`not_in_file`, `builtin`, `api_unsupported`, `url_unsupported`, `needs_raw_editor`) for a provider outside the form's grammar; such a provider can still be removed. Literal header values come back as `keep`; the name of a `keep` header is locked until Replace; Replace on a credential-named header switches to an environment reference.
- **A stored key outranks the environment variable and "No key".** Pi uses a credential stored in `auth.json` before the `apiKey` of `models.json` (probed on Pi 1.1.0: the stored credential wins over `$NAME`, over `local-no-key` and over no `apiKey`). So switching a provider from a stored key to an environment variable or to no key does not remove the key: the form says so and points to Sign out on the provider's page. `get` tells the form: `keyStored` for the edited provider, and, with no id, `storedKeys` (the ids `auth.json` holds a credential for, never a value; a damaged `auth.json` gives none), so the add form warns when a new provider reuses an identifier that still has a key, which would otherwise send an old key to the new base URL. A remove with the box unticked leaves the key by design. The helper reads its own store and resolves nothing.
- **The key** is typed only in the existing `ApiKeyForm`, offered after a save of a stored-key provider ("Provider saved. Add the key."); the form has no key field. An environment variable is `"$NAME"` in the file, a keyless server gets the dummy literal `local-no-key`, a `!command` is never written by the form. After a remove with the key box ticked and no key stored, the sign-out answers `not_found`: that is "no key", the removal stands and no `provider_signed_out` row is written. After a remove with the box ticked, a failed log-out leaves an orphaned key: the form reloads with `get` and, on `not_in_file`, offers "Remove the stored key" (`models.logout`).
- **Base URL policy** (owner q4): `https:` anywhere, `http:` only to this machine. One constant, `HTTP_PLAINTEXT_POLICY` in `packages/contracts/src/base-url.ts`, and one table, `BASE_URL_TABLE`. To allow `http:` to any host, set the constant to `"any"` and change the two sentences of the `settings-providers` catalog (the policy text and the clear-text warning); the tests run both columns and need no change. The raw editor accepts any URL Pi accepts behind the same step-up, so the loopback rule is not a barrier.
- A create whose id is already in the file (while the revision is current) answers `config_invalid` at `$.provider.id`, not a conflict.
- **Discover** in the form appends discovered ids to the draft (at most 500 minus the rows already there, ticked by the owner) and saves nothing; the button is off until the provider is saved, and every first save closes the form: open it again with Edit to discover.
- **A save or remove racing a change** (another tab, the raw editor, a hand edit) answers `conflict`: the form reloads with `get`, keeps the draft, and shows the file's version only on request. A dirty draft asks before it is dropped (select, Edit, Add).

## Available models view (Settings › Models, ADR 0070)

What the owner can do: choose "All the models of the connected providers" or "My selection", switch providers and models on and off, see the preview of what the pickers will offer, clean up patterns that match nothing. Code: web `features/models/availability/` (lazy chunk, nothing eager), catalog `settings-availability.ts`.

- It writes only through `models.setEnabled` (no step-up) and previews only with `models.available`, so the preview is the picker's list. The preview count line is a live region (`role="status"`).
- Choosing "All models" deletes the saved list (globs and patterns for providers not connected now included) with no undo: the question names the entries it removes and takes the focus.
- A project selection (a trusted project's `.pi/settings.json`) shows as text with the path; switches are read-only.
- **Two preview reads per write is deliberate.** `useModelWrites` reloads the overview and asks for a preview when the last write ends, success or failure; the changed overview asks for a preview again. One read runs at a time and a request during a read becomes one trailing read, an answer older than the newest request is dropped (MP-RT-14). The cost is one extra helper run per write; the benefit is that the preview never shows a list older than the last write. Do not "fix" it by dropping one of the two: the reload after a failed write is how the screen learns what the file really holds.
- It claims nothing about per-person, project or agent restrictions: those come after v1 (owner answer q11) and are only a design paragraph (next sections).

## Extension providers (read-only list, ADR 0070)

- `models.extensions` (`pi:admin`, idempotent, no step-up, 60 s) is a helper op that loads the owner's global extensions the way `models.usage` does (`ops/extension-load.ts`: offline flag on, no project scope, `projectTrusted: false` and a trust resolver that refuses, so each gate holds alone). The daemon shares one run among concurrent calls and keeps nothing. Web: a button in the availability view ("Read providers added by extensions"); nothing is asked before the click.
- Built-in ids are left out; a provider of `models.json` that an extension re-registers is listed and marked "overrides" (the mark needs the overview's provider list: when the overview is `truncated`, the view says an override may be unmarked). No base URL, header or key is read. Provider and model ids and names are cleaned in the web view (`stripHidden`, `apps/web/src/lib/untrusted-text.ts`) and shown as text.
- Caps: 300 providers, 500 models per provider, 600 000 bytes. `truncated` (top level) is set by the provider cap, the byte budget (the list stops at the first hit) and a provider id over 128 characters (left out, never clipped); `modelsTruncated` by the model cap, the budget, and a model whose id is over 256 characters (left out).
- **Virtual-only providers are not listed.** The op reads `getRegisteredProviderIds`: a provider an extension registers only later (from an event handler or a command during a live session) is not there. A session's model menu shows it once the session has it.
- The copy never says the load has no network: Pi's offline flag stops Pi's installs and refresh, not an extension's own fetch. Extension code runs in the helper process and can read the agent directory, like `models.usage` (same exposure; mitigations are the click, `pi:admin`, offline, no project scope).

## The policy hook (C, design only)

Per-person, per-project or per-agent restrictions come after v1 (owner answer q11) and are not built: there is no table, no method and no UI. The design is in ADR 0070 and the spec (section 8): an allow-list would be a filter over the single source (`listAvailable`), applied in the daemon after the helper or the worker answered, never inside Pi, and it would only narrow Pi's list. The interface line, not built: `ModelPolicy.filter(models, { userId, projectId?, agentId? })`. Do not describe it as a feature.

## Residuals

- `redactLine` (comment masking, `helper/models-json-mask.ts`): a comment line keeps a quoted reference or command only when the quoted value contains no other quote. The earlier regex let `// "apiKey": "!op read x" "sk-abc"` keep the second value; it is masked now (`models-json-mask.test.ts`, "redacts a literal that follows a kept command"). Other comment shapes are listed under "Still shown" above.
- Redirects: the model Test and discover send Pi's providers a `fetch` that never follows a redirect (`strictFetch`, `helper/ops/provider-request.ts:69`); cross-origin 307 tests pin it for `openai-completions` and `anthropic-messages` (`models-discover.test.ts:228`, `:245`) and for discover (`:194`). Nothing pins it for the Google and Bedrock provider APIs: whether their SDK paths use the supplied `fetch` is not tested. The models.dev lookup does its own `fetch` with `redirect: "error"` (`models-pricing.ts:100`, `models-pricing.test.ts:58`).
- Pi's `setModel` awaits `checkAuth` before it switches (SDK behaviour, called by `handleSetModel` at `packages/pi-host/src/model-commands.ts:76`), and `checkAuth` runs a `!command` stored in `auth.json`. pap accepts that for a session's own model change: the key is the owner's, the session is the owner's, and Pi does the same when it prompts the provider. The overview and the defaults never call it (MC25).
- Settings writes use Pi's `SettingsManager`, not `writePiFile`: ADR 0029.
- Provider usage (`models.usage`) residuals: the helper sees only what Pi registers at load time, so "Check usage" may send the stored key to the official host for a provider the owner meant to repoint when (1) an extension registers the provider later, from an event handler or a command during a live session; (2) a *trusted project's* `.pi/extensions` or project packages would repoint it (the helper has no cwd and reads no project scope); (3) a package is declared in settings but not installed (a session online installs it, the offline helper does not). A daemon stop (or an RPC-level cancel) during an OAuth refresh already started can kill the helper before Pi persists the rotated token: the file stays intact (temp and rename) but that refresh token can be lost and the owner signs in again. A failing extension makes the check refuse (`extensions_failed`, cached 60 s).
- Built-in Anthropic and Google discover answers `http_4xx` (known no-op); the UI hides the button for them.
- **Models batch residuals** (provider form, availability view, pickers):
  - A `models.json` with comments or trailing commas needs the raw editor: the form never rewrites it (MPR11) and says so.
  - A LAN `http:` server needs the raw editor under the loopback policy (owner q4); the one-line flip is above.
  - The strict-JSON rewrite may change formatting, and an integer-like provider id (`"123"`) moves ahead of the others, as JavaScript orders keys. A digit run of 16 or more (a fraction too) is refused, so such a file also goes to the raw editor.
  - Providers (`models.json`), the selection (`settings.json`) and keys (`auth.json`) are not restored by M6b (MPR29): set them again after a restore.
  - Extension models are missing from no-session pickers (the footnote says it); virtual-only providers are missing from the extension list (above).
  - There is no server-side membership check when an agent or a lane names a model: a saved model that is no longer offered stays visible and the run fails with Pi's own error.
  - The dummy key literal `local-no-key` sits in `models.json` for keyless servers (masked in the raw editor because the key is named `apiKey`; not a secret).
  - A trust change reaches the pickers within the 10 s cache TTL (the `trust` module is not wired to the cache).
  - A model whose id is over 256 characters cannot be a `ModelSummary`: `models.extensions` flags it (`modelsTruncated`); `models.available` and `models.overview` leave it out without a flag.
  - The credential vocabulary shared by the maskers and the header rule (`credential-words.ts`) has gaps: `X-Pass`, `X-Creds`, `JWT`, `HMAC` are not credential names. A header named that way takes a literal in the form. Widening the list also widens the masking of models.json and MCP text (MC40), so it needs a ruling of its own.
  - Phone, hardware Escape: a bottom sheet reopened while the previous one is still closing (about 300 ms) once let one Escape reach the parent dialog (controller C2 note); not reproduced with the layers settled.
