# Files module (M8)

Code: `apps/daemon/src/kernel/fs/` (the path boundary), `apps/daemon/src/kernel/git/` (the git runner), `modules/files/` (`files.*`, the HTTP routes, attachments), `compose-workspace.ts` (builds the boundary, the one deny set and the modules). Contracts: `packages/contracts/src/{files,protected-paths}.ts`. ADR 0031. Rulings: `docs/research/m8-rulings.md`. Git status and diffs (`modules/vcs/`): ADR 0032. Lanes' git (worktrees, checkpoints, push): `lanes.md`, ADR 0033. The terminal: `terminal.md`.

## The boundary at a glance

A path is an absolute, canonical string (no `.`, `..` or empty segment, no NUL, at most 4 096 bytes: `canonical`, `kernel/fs/boundary.ts:62`). The caller's roots are its project roots (M4). A path is inside when **both** its spelling and its real path (symlinks followed) are inside a root, and every name rule is judged on both spellings (`judgePath`, `boundary.ts:139`). The judge never reads the filesystem for a name rule and never reads the environment: `boundaryConfigOf` (`compose-workspace.ts:40`) hands it pap's home, Pi's agent folder, the daemon user's home and `$XDG_RUNTIME_DIR`, each in both spellings (a link on either side cannot hide it; a path that does not exist yet is resolved through its nearest existing parent).

| Path class | list | read | write: browser session | write: token |
| --- | --- | --- | --- | --- |

| protected name (M5's lists: `.git`, `.agents`, `.husky`, `.vscode`, `.idea`, `.zed`, `.devcontainer`, `.lefthook`, `.mise` segments; `.envrc`, `.pre-commit-config.yaml`; lefthook and mise configs) | yes | yes | `protected_path` unless `confirmProtected` ("Save anyway?") | `forbidden` |

- A token additionally gets `token_hidden` (so `not_found`) for anything under `/proc`, `/sys`, `/dev`, `/run` and `$XDG_RUNTIME_DIR` (`judgeName`, `boundary.ts:93`; MC7), whatever the roots.
- Write gate (`gateWrite`, `boundary.ts:162`): a token never confirms and never writes a protected path (`forbidden`); a browser session with `protection: confirm` needs `confirmProtected`; `step_up` (Pi's folders and every `.pi/`) needs it and a live step-up (`Caller.stepUpUntil`, `auth.md`). Protection is the stricter of the two spellings (`protectionOf`, `:118`).
- **Pi's configuration has one writer.** The five JSON files are `pi_private` for every intent here (the explorer shows them as locked); M7's Settings is their only reader and writer, masked and behind the step-up. Other writes under `<agentDir>` and `.pi/` take the confirmation and the step-up.
- **The home-folder rule** (owner f8): when a project is the home folder or `/`, dot-files and dot-folders directly in the home are protected (confirm on save; `not_found` for tokens). The rest of the home is ordinary. The deny set also covers the owner's secret stores (below).
- Errors: a refusal answers `not_found` with a fixed message and says nothing about why (`judged`, `modules/files/access.ts:59`); `refusal` maps every `BoundaryError` and every "not there or not yours" errno (`ENOENT`, `ENOTDIR`, `ELOOP`, `EACCES`, `EPERM`, `EISDIR`, `ENXIO`, `ENAMETOOLONG`, `ENODEV`) to it. Anything else (`EMFILE`, `EIO`) is left to the dispatcher (`internal`). The lists are copies in contracts (`PROTECTED_SEGMENTS`, `PROTECTED_BASENAMES`, `HOOK_CONFIG_NAME`, `PAP_SENSITIVE_NAMES`); `packages/pi-host/src/policy/protected-lists.test.ts` proves, in one direction, that every entry is also protected by pi-host's own checks. A name added to pi-host and not to contracts is not caught by that test: add it to both.

## The checked open and write (`kernel/fs/safe-open.ts`)

- Every open goes through `openRegularFile`, `openFolder` or `writeAtomic` (`O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`; a PTY slave never becomes the daemon's controlling terminal, `:26`). After the open the descriptor is judged again: its real place from `/proc/self/fd/N` must be inside the judged root and pass the name rules; a failed `readlink` on Linux is `moved`. Where `/proc` is absent (tier 2) only the name is checked (`PROC_EXPECTED`, `:34`).
- The opened file's `(dev, ino, birthtime)` must not be one of the **deny set**'s private files. A folder listing is read through the held descriptor (`/proc/self/fd/N`), so a folder swapped for a link meanwhile is not listed.
- `writeAtomic` (`:142`): a `.pap-<12 hex>.tmp` file in the target's folder, created `O_EXCL` with mode 0600, checked as the file it will become, written with a byte cap, `fsync`ed, then `rename` (replace) or `link` (create; `EEXIST` is `exists`). The target is checked against the deny set again right before the rename. The folder is `fsync`ed best effort. No temporary file is left on any path. A new file gets `0o666 & ~workerUmask` (R114), an existing one keeps its mode.
- `uploadName` (`names.ts`): one segment, NFC, no surrogate, no control, bidi, zero-width or default-ignorable character (MC9), not a `.pap-*.tmp` name, no surrounding blank, at most 255 bytes.

## The deny set (`kernel/fs/deny-set.ts`)

Hard links, swapped folders and renamed backups keep a private inode reachable under an allowed name, so the name rules are not enough.

- Sources (`denySourcesOf`, `compose-workspace.ts:68`): the five Pi JSON files, `state.db`, `-wal`, `-shm` and `pap.lock`; the folders `<agentDir>/sessions`, `secrets`, `backups`, `exports`, `fork-tmp`, then **all of `$PAP_HOME`** (so `search.db` and its `-wal` / `-shm`), minus `attachments/` and `papHomeOpen` (skipped by inode, not by spelling; MC21); and the owner's usual secret stores in the home: `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/gh`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.git-credentials` (MC10). Symlinks met in the walk are followed once (a visited set against cycles, counted in the cap, logged as `deny_walk_link_followed`).
- Keys are `dev:ino:birthtimeNs`. Every key a walk finds is **remembered for the daemon's lifetime** (cap 100 000, `DENY_KEYS_MAX`; never evicts): a private file renamed away or a rotated backup stays refused.
- `has()` (`:184`): a known key is private. A file with one link is otherwise not private. A file with `nlink >= 2` whose ctime is newer than the last walk (2 s slack) triggers a refresh, up to twice. When the set cannot vouch (the last walk was cut at 50 000 entries or could not read something other than `ENOENT`, the keys are full, or no walk has finished) every linked file is refused (fail closed).
- The first walk starts at boot (`deny.warm()`), with a 15 s deadline on the clock (`DENY_WALK_DEADLINE_MS`); until a walk completes the set refuses every file, linked or not (reads and lists answer `not_found`; up to 15 s after boot, or longer on a slow walk such as a big `~/.kube/cache`), and again whenever a walk outruns its deadline. A late first walk logs `deny_first_walk_late` once. A walk that outruns the deadline leaves the set unable to vouch.
- Before closing `state.db` and `search.db` the daemon runs `PRAGMA wal_checkpoint(TRUNCATE)` (`kernel/db/database.ts:64`), so an alias of a `-wal` file does not outlive its content.

Residuals (accepted; each needs an unusual filesystem or a race with the owner's own account):

- **Filter drivers (MC13, closed at the M7 rebase; the choice is to run with overrides, not to ask).** `git status` and `git diff` compare files, and a repository-local `filter.<name>.{clean,smudge,process}` driver would run. `compose-workspace.ts` wraps the runner in `guardFilters` (`kernel/git/filters.ts`): before `status` or `diff` it runs `git config --null --show-scope --get-regexp '^filter\.'` (the one `config` call the runner accepts), names every driver of the repository's own scopes (local, worktree, includes; a scope it does not know counts as the repository's), and runs the real command with `GIT_CONFIG_COUNT` entries that empty `clean`, `smudge`, `process` and set `required=false` for each (env entries carry any name, `=` and dots included; only `GIT_CONFIG_COUNT/KEY_n/VALUE_n` may be added to git's environment). The Review pane keeps working, with raw file content compared. Why not "repository config needs review": it would need a new error state, UI and catalog entries for a case that is harmless once the drivers are empty, and M7's guard lives in pi-host, which the daemon may not import. Left alone: the owner's own system and global config (his, as in M7's guard), and the exact standard git-lfs entries (`git-lfs clean -- %f`, `git-lfs smudge -- %f`, `git-lfs filter-process`: they run the git-lfs binary, not what the repository chose; any other value on the `lfs` driver is emptied). A repository with more than 64 drivers is refused (`failed`). `status` and `diff` also pass `--ignore-submodules=dirty`: without it git runs `git status` inside each nested repository with that repository's own drivers, which the scan of the top repository does not see (MC43 I1). An empty driver name (`[filter ""]`) is emptied too. `gitEnv` drops relative `PATH` entries so the standard git-lfs entries cannot find the repository's own `git-lfs`. **Git floor:** the overrides are `GIT_CONFIG_COUNT` variables, which git before 2.31 ignores silently, and the scan needs 2.26. `guardFilters` asks `git --version` once: from 2.31 it runs as described; on 2.26 to 2.30 `status` and `diff` refuse with `git_too_old` (shown as `failed`) when the repository defines a non-lfs driver; below 2.26 they always refuse. Debian 11 ships 2.30. **Accepted residuals (MC43):** (M3) the scan and the command are two git processes, so a driver added to the config between them runs; the writer already runs code as the user. (M7) each `status` or `diff` costs a scan, so a poll tick starts 4 git processes instead of 2; `ponytail:` comment in `filters.ts` names the upgrade (scan once per tick, or cache by config mtime). The list is `LFS_ENTRIES` in `@pap/contracts`, shared with M7's `git-config.ts`. The raw runner (`createGitRunner`) still runs drivers: its tests use them to prove the process-group kill and the PTY mask (MC38).
- **Attachments and the agent (MC38 I3, closed at the M7 rebase).** pi-host's read check (`policy/read-target.ts`) asks before the agent reads `$PAP_HOME/attachments/pending/**` (the worker reads pending images itself) or `attachments/<sid>/**` of any session but its own, and before a `grep` / `find` rooted at `attachments/`. The session's own claimed attachments read unasked. Residual: the agent's own `bash` outside the read-only commands (a plain `cat` in full access, any script) is not judged by this check; taint and the egress card still apply.
- **Non-Linux.** Without `/proc` the descriptor's place is not re-checked, only the name (tier 2).
- **Folder swap.** Between the check of the temporary file's place and the `rename` by path, the target folder can be swapped for a link and the file lands where the link points.
- **`lstat` then `rename`** on a filesystem without hard links (`EPERM`, `ENOTSUP`, `EOPNOTSUPP`, `ENOSYS` from `link`): a file created between the two is replaced (`safe-open.ts:114`).
- **Case-insensitive spelling** of a Pi session file created since the last walk: its alias has one link and is not a known key until a walk sees the file.
- **After a restart** the remembered keys are gone: a private file renamed away while the daemon was stopped (an alias with one link) is served until it is a known key again. Where libuv has no `statx` (a seccomp filter) the birth time equals the ctime and the key changes with any write: the remembered keys do not hold there.
- **Past 100 000 keys** a one-link alias of a later private file is not refused.
- **Hard links to secrets outside pap** (the home stores above are covered; `~/.local/share/...`, a password manager's file) placed in a project are served.
- **A link to a big folder inside `$PAP_HOME`** (for example to `~`) puts the first 50 000 entries in walk order into the set: fail closed, silent apart from the debug log.
- **A FUSE or hung-network mount** inside a project: an `open` has no deadline and four hung libuv threads starve the pool. Walks are not rate limited: a hard-linked file kept fresh makes a check run up to two walks, and a freshly linked ordinary file is refused for about 2 s.
- **A literal backslash** in a name is a character like any other: it is created inside the root (`files.write` / upload), never a separator.

## Listing, reading, saving (`modules/files/`)

- `files.list` (`list.ts`): opens the folder through the guard, `lstat`s entries 32 at a time, folders first then by lower-cased name; at most 5 000 entries and a page under 900 000 JSON bytes, `truncated` says when more exist; at most 20 000 names are read from one folder. An entry carries `protected` (the caller may not open it), `link` (`inside`, `outside`, `broken`) and `hidden`. Ignored names (`.gitignore` rules) are hidden unless `showIgnored`: `git check-ignore -z --stdin --no-index` over the folder's names (5 s), minus names holding a tracked path; `.git` and `.DS_Store` never show.
  - **Inner repositories.** The listing runs git at the **project root**. A project that is a sub-folder of a bigger repository (git cannot climb above the root) or holds a nested repository gets the fixed name list instead (`node_modules`, `dist`, `build`, `out`, `target`, `coverage`, `.next`, `.nuxt`, `.venv`, `venv`, `__pycache__`, `.cache`, `.turbo`, `.parcel-cache`; `visibility.ts:10`), not the repository's rules. The same list applies when git fails or times out.
- `files.read` (`read.ts:54`): up to 256 KiB per call (`readChunkBytes`) and under the page size, cut at a UTF-8 boundary, `nextOffset` when more follows. A NUL in the first 8 KiB makes a file `binary` (no text). `st_size` is never trusted (procfs reports 0). A file up to 384 KiB is read whole: `etag` is the first 32 hex digits of its SHA-256 and `editable` is true only when it is UTF-8 and its JSON fits a page. **A file that is not valid UTF-8 opens with `editable: false`.** `protection` tells the editor what a save needs.
- `files.write` (`write.ts:57`): text up to 384 KiB and under 900 000 JSON bytes (`payload_too_large` above; a frame over 1 MiB would close the whole socket), `baseEtag` of what the editor read (`null` for a new file), then judge, write gate, base check (`conflict` when the disk differs or the file vanished), `writeAtomic`. A save logs `file_written` with the protection and the caller's kind, never the path.
- `GET /files/raw` (`raw-http.ts`): cookie only; an image inline up to 20 MiB, everything else an `octet-stream` attachment with a safe name, under the route's own sandbox CSP. `HEAD` answers the headers and closes the file at once.
- `files.search` (`search-index.ts`, `rank.ts`): the `@` index of one root, built at most every 30 s (16 roots cached): `git ls-files -z --cached --others --exclude-standard` (8 MiB) or, outside git, a bounded walk (depth 16, 20 000 files, 5 000 folders, 10 000 entries per folder, 5 s deadline on the clock), paths without any invisible character, filtered by what the caller may read. Ranking scores only the last 256 characters of a path, with a budget of 25 million cells and 200 000 paths; past either the answer says `truncated`. Up to 50 results.

## Uploads and attachments

- `PUT /files/raw` (explorer upload, `upload-http.ts`, `upload.ts`) and `POST /upload` (composer attachments, `attachments-http.ts`): the order of refusals and the caps are in ADR 0031. Both are cookie-only, read the declared length first and refuse before the first body byte: read-only database 503, more than 4 in flight for the owner 503 `capacity`, length missing 400, above 25 MiB 413.
- **The deadline is 5 minutes.** `kernel/http/server.ts:30` sets `requestTimeout` to 300 000 ms explicitly; 25 MiB needs about 700 kbit/s. A slower link is cut and the web says the upload stopped before the end.
- The success answer of `PUT /files/raw` is `UploadAnswer` (contracts `files.ts`, decoded by the web's `uploadFile`): `{ written: false }` for a `skip` that found the file, else `{ written: true, meta }` with `etag: null`, `editable: false`, `binary: false`. **M8 has no explorer upload UI**: `uploadFile` has no production caller yet, so a client that wants the etag or the kind asks `files.read`.
- **One writer at a time per file (MC38 m1).** `path-lock.ts` keeps one promise chain per real path (after the judge's `realpath`), shared by `files.write` and `PUT /files/raw`, around the base check and the atomic replace; the entry is deleted when its chain settles. Two saves on one base etag: the second answers `conflict` and the file holds the first. Not covered: a write by the agent's own tools, or by a shell, that lands between the check and the `rename` (milliseconds, `fsync` included) is overwritten; the lock only orders pap's own writers. An upload holds its path's chain while the body streams (at most the 5 minute request deadline).
- Listings never show a `.pap-<12 hex>.tmp` file (a crash mid-write leaves one, up to 25 MiB), `showIgnored` included.
- Pending attachments (`attachments-store.ts`): `$PAP_HOME/attachments/pending/<id>`, per owner at most 32 and 200 MiB counted at the declared length before the body is read, 1 hour expiry (swept every 5 minutes on the clock; a claim renews it, so a prompt that waits behind an extension command still finds its image), index in memory and the folder emptied at boot. Claimed files are copied to `attachments/<session>/<id>/<name>` and stay until the daily `attachment.cleanup` (`attachments-cleanup.ts`: a session folder goes after 30 days without activity (and only when no file in it is younger than 30 days: a copy into a long idle session lands before its `updated_at` moves), or, with no row (a deleted task session included), when the folder itself is 30 days old; the daily effect is enqueued by the automation housekeeping (receipt `attachments:<day>`); 50 folders a pass, `defer` one minute while more remain; links are never followed; log `attachments_cleanup {removed, kept}`; residual: a fork reads its parent's `attachments/<parent>/`, so a parent idle for 30 days loses the folder under an active fork); once Pi accepts the prompt, the pending images and the copied files are forgotten and their share of the budget is released (`release`, MC38 m3); the boot line `attachments_size` logs the folder's size (bytes, entries, `truncated` past 10 000 entries). A claim is bound to the session and owner (`not_found` otherwise), takes duplicates as `bad_request`, and re-opens the pending file through the deny set. Prompts: `sessions.md`.

## Limits and cost

| What | Value |
| --- | --- |
| listing | 5 000 entries, 20 000 names read, 900 000 JSON bytes |
| read chunk / editable / upload | 256 KiB / 384 KiB / 25 MiB |
| `@` search | 50 results, 100 000 paths, 5 s |
| pending attachments | 32 and 200 MiB per owner, 1 h, 10 per prompt, images 10 MiB |
| in-flight uploads | 4 per owner per route |
| git | 4 processes at once, 64 waiting, 10 s, 8 MiB of output |

- **CPU of the poll.** The files module polls nothing. The `vcs` module runs one `git status` and one `git diff --numstat` per watched root every 15 s (ADR 0032), at most four git processes at once for every root, and 200 line-count reads per run.
- **Git's flags.** Every call is `git --no-optional-locks --literal-pathspecs -c <safe config> -C <root> <subcommand> …` with an allowlist of nine subcommands (`rev-parse`, `status`, `diff`, `log`, `show`, `cat-file`, `ls-files`, `check-ignore`, `hash-object`) and an exact option list for each (`kernel/git/runner.ts:179`; `--no-ext-diff --no-textconv` are added by the runner to `diff`, `log` and `show`; `check-ignore` runs without `--literal-pathspecs`, its names start with `./`). Config switched off: fsmonitor, hooks, pager, external diff, protocols, credential helpers, signature programs, submodule diffs, bare repositories, alternate-ref commands (`kernel/git/exec.ts:10`). The environment is an allowlist (`PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `TMPDIR`, `XDG_CONFIG_HOME`) plus `GIT_CEILING_DIRECTORIES` set to the root's parent, `GIT_ALLOW_PROTOCOL` blank and `GIT_NO_LAZY_FETCH`. Git leads its own process group, killed on timeout and at exit. Failures carry a fixed message; git's stderr is clipped and logged only.
- **Git for lanes (M9, `kernel/git/allowlist-lanes.ts`, `exec.ts`).** The nine subcommands above are the read set; M9 adds the lane set with exact option lists and exact call shapes (the full table is in `lanes.md`). A call must match its shape: the `--` rule keeps paths after `--` (a commit's paths are `./`-prefixed, so one cannot parse as an option or a pathspec magic such as `:(glob)x`); `check-ignore` is the only call without `--literal-pathspecs`. Two profiles: `local` (default, no transport) and `remote` (`push` only: the owner's credential helpers and SSH agent, `https` and `ssh` only, `push.pushOption=` empty; `PAP_TEST_GIT_PROTOCOLS` may add `file` in tests). A lane call names its git dir (`--git-dir=<common>/worktrees/<name>`, from pap's record) and always pins `--work-tree`. Extra environment is checked name by name: `GIT_CONFIG_COUNT/KEY_n/VALUE_n`, `GIT_INDEX_FILE` as `<indexDir>/idx-<32 hex>` (`indexDir` is `$PAP_HOME/tmp/git-index`, the runner's `indexDir` option), pap's fixed author and committer, `GIT_LFS_SKIP_SMUDGE=1`; anything else refuses the call before git starts. `keepStderr` returns git's stderr (64 KiB) to the caller to classify; it is never logged beyond 300 characters. The filter guard (`guardFilters`) also runs for `add`, `commit`, `restore`, `reset` and `worktree`.
- **Branch names.** `BRANCH_PATTERN` (contracts `lanes.ts`) refuses `@` anywhere: git 2.53's `check-ref-format --branch` prints `@` back as the previous branch, so a name containing `@{...}` could mean another ref. It also refuses `..`, `//`, `/.`, `.lock`, a leading dash and `HEAD`, `FETCH_HEAD`, `ORIG_HEAD`, `MERGE_HEAD`. The daemon additionally runs `check-ref-format --branch` and requires the same name back.
