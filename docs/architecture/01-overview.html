2 · Layout du repo & règles anti-sprawl

pi-agentic-platform/
├─ apps/
│  ├─ daemon/          pap : CLI + serve, composition root
│  │  └─ src/
│  │     ├─ kernel/     db, outbox, scheduler, supervisor, exec…
│  │     ├─ modules/
│  │     │  └─ sessions/  index.ts (API publique)
│  │     │     ├─ service.ts   logique
│  │     │     ├─ store.ts     SQL
│  │     │     ├─ rpc.ts       handlers
│  │     │     └─ *.test.ts
│  │     └─ main.ts      câblage uniquement
│  └─ web/             SPA React + PWA
│     └─ src/features/<domaine>/  miroir des modules
├─ packages/
│  ├─ contracts/       zod : catalogue RPC, events, erreurs
│  ├─ pi-host/         worker de session + extensions policy
│  └─ ui/              design system E1 : tokens, primitives,
│                       composants IA (message, tool, approval)
└─ docs/  DESIGN.md, specs/, adr/, agents/
  1. Un module = un domaine (D01–D21). Il n'expose que son index.ts. Ses imports possibles : contracts, kernel, et l'index.ts d'un autre module. Vérifié par lint en CI.
  2. Plafond de 400 lignes par fichier, en échec dur, sans baseline ni exception. T3 et Orca ont des fichiers de 12k lignes, c'est exactement ce qu'on évite.
  3. Un handler RPC décode, appelle une seule méthode de service et mappe une erreur typée. Aucune logique dans le transport (règle T3).
  4. Chaque méthode RPC déclare sa permission dans contracts. Un oubli est une erreur de type (T3/Orca).
  5. Le front reflète les modules : features/<domaine>. Les primitives de ui gèrent leur propre apparence. Pas de couleur brute, pas de valeur arbitraire (lint, règle T3).
  6. Pas de 4ᵉ package tant qu'un besoin réel n'apparaît pas. Les modules restent des dossiers plutôt que 20 packages npm : la frontière est assurée par le lint.
