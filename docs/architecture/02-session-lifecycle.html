Spec C · Architecture · Section 2 / 9

Cycle de vie d'une session et protocole pi-host

Une session Pi active = un process pi-host (Node) qui embarque le SDK Pi. Le daemon le lance à la demande, le surveille, le libère quand il dort, et ne le ressuscite jamais tout seul après un crash. Le transcript reste le fichier JSONL de Pi : le worker est jetable, la session non.

1 · États du worker

cold

Aucun process. La session existe (fichier Pi + ligne SQLite). État normal de la plupart des sessions.

starting

fork(pi-host) + scope systemd, ouverture du fichier de session, puis ready (chemin, version Pi).

idle

Prêt. Accepte prompts, changement de modèle, navigation d'arbre, export.

running

Run en cours, de agent_start à agent_settled confirmé par sonde get_state.

releasing

30 min idle, sans dialogue en attente, file vide, pas de travail de fond, alors shutdown.

cold

Prochaine commande : relance paresseuse sur le même fichier de session.

idle ⇄ running · prompt pendant un run = steer ou followUp (préférence) ; file plafonnée à 128 messages / 32 MiB
tout état → crashed → cold · run terminé interrupted avec cause (OOM, signal, code de sortie, échec de spawn), dialogues annulés
abort · abort, et si compaction en cours ou pas de settle en 5 s : arrêt du process (règle T3)

2 · Protocole daemon ⇄ pi-host

Transport : canal IPC de Node (child_process.fork), qui découpe déjà les messages, d'où aucun parseur JSONL à écrire. stdout/stderr ne servent qu'aux logs : seuls les 8 derniers KiB sont gardés, jamais logués en entier (ils peuvent contenir des secrets). Les records reprennent les formes de pi --mode rpc. Pour basculer une session vers le vrai Pi RPC, il suffit de changer d'adaptateur de transport.

3 · Règles de run et d'isolation

Fin de run
  • agent_settled est le seul signal de fin. agent_end ne suffit pas (retries, compaction).
  • Il est confirmé par get_state : pas de streaming, pas de compaction, file vide. Jusqu'à 3 essais à 100 ms, et une nouvelle entrée annule la sonde.
  • Chaque run porte son origine : user, trigger, task ou extension.

T3 adapter.ts · Orca rpc-idle-check.ts

Confinement
  • Si systemd user est présent : systemd-run --user --scope avec MemoryHigh, MemoryMax et TasksMax (réglages).
  • Au démarrage, le worker se met à oom_score_adj=800 : le noyau tue un agent, pas le daemon.
  • Groupe de process dédié. Le worker surveille son parent et s'arrête si le daemon meurt.
  • Arrêt progressif : shutdown, puis 2 s, puis SIGTERM au groupe, puis 3 s, puis SIGKILL.
  • Le bash des agents passe par bwrap selon leur profil (pi-web).

T3 agentScope.ts · Orca provider-process-supervisor.ts

Environnement & capacité
  • Session interactive : l'env du daemon moins PAP_* et les secrets plateforme.
  • Session d'agent : une liste blanche d'env plus le coffre de secrets de l'agent (pi-web).
  • Plafond de workers actifs et plancher de mémoire libre (réglages pi-web). Au-delà, refus explicite avec la raison, jamais de file silencieuse.
  • Le SDK Pi est épinglé dans pi-host. pap doctor signale un écart avec le CLI pi installé, puisque les fichiers de session sont partagés.

4 · Appels plateforme (outils agent_*, lane_note, request_secret)

Un outil plateforme s'exécute dans le daemon, jamais dans le worker. Le worker envoie platform_call{op,args}. Le daemon identifie l'appelant grâce au type de session qu'il a lui-même lancée (session interactive, thread de confiance d'un agent, tâche isolée) et non grâce aux paramètres. Il vérifie que op est autorisé pour ce type d'appelant, exécute, puis répond platform_result.

« Les paramètres choisissent la cible, l'appelant fixe les limites » (T3 McpToolAccess). Pas de jeton MCP à émettre : le canal IPC est privé au couple daemon-worker.

Ops v1
  • agent.notify agent.approve agent.delegate agent.remind : threads de confiance seulement
  • lane.note : sessions de lane
  • secret.request : la valeur va dans le coffre, seule une référence à usage unique entre dans le transcript
  • audit.append : tous les appelants, dans un journal append-only

5 · Ce qui se passe quand…

le worker crashe / OOM
Run en interrupted avec cause lisible (bannière : « Agent process killed: out of memory (MemoryMax 2 GB) »). Dialogues en attente annulés. Aucun redémarrage automatique : la prochaine commande relance le worker sur le même fichier.
le daemon redémarre
Les workers s'arrêtent seuls (surveillance du parent). Au boot, les runs encore running passent en interrupted. Les tâches et triggers sont rejoués ou non selon l'outbox (section 6).
le client se déconnecte
Aucun effet sur le worker. Au retour : reprise par curseur, et le message partiel en cours est renvoyé en snapshot (section 4).
une extension lance un run
Accepté (intégration Pi profonde), attribué à l'origine extension, visible dans le transcript et audité. T3 et Orca tuent la session dans ce cas ; nous non, car tout passe par le daemon.
Pi demande un dialogue
Carte d'approbation ou d'input dans le chat. Au plus 64 dialogues ou 8 MiB. Une méthode inconnue est annulée automatiquement. Après 60 s sans réponse et sans onglet ouvert : push (pi-web).
