Pipeline de politiques et outils plateforme

Toutes les politiques de pi-web (denylist, egress, sandbox, coffre, masquage, audit, isolation du contenu non fiable) deviennent une extension pap-policy évaluée en dernier dans pi-host, après les extensions de l'utilisateur, pour juger l'appel final (amendement, ADR 0002). Le daemon reste la source de vérité des règles : il les compile, les envoie au démarrage du worker et à chaud via policy_update. Règle absolue : une erreur d'évaluation bloque l'appel, jamais l'inverse.

Quatre réponses (T3) : once, session (en mémoire du worker), always (règle enregistrée par projet ou par agent, visible et révocable dans Réglages), deny avec raison renvoyée au modèle. Sans « always », le mode auto-accept edits deviendrait vite pénible.

Profils de politique (choisis par le daemon, jamais par le worker)
  • interactive : session d'un utilisateur. Mode d'approbation, règles « always » du projet, denylist globale optionnelle.
  • agent-thread : thread de confiance d'un agent long-terme. Profil de l'agent (sandbox, egress, denylist, coffre), outils agent.* autorisés.
  • isolated-task : run d'un trigger. Allowlist d'outils fermée par trigger (pi-web), chemins limités au home, contenu du déclencheur clôturé, aucun outil agent.* sensible.

Limite assumée (v1)

L'allowlist d'hôtes contrôle les outils qui portent une URL. Un bash avec réseau autorisé peut joindre n'importe quel hôte : la vraie barrière, c'est bwrap sans réseau (sandbox_network: false). Un proxy d'egress par agent (allowlist appliquée au niveau réseau) part en roadmap.

Compatibilité extensions

pap-policy passe en dernier : elle voit l'appel tel qu'il sera exécuté, et ne peut pas être contournée, car un seul block suffit à bloquer. Les extensions de l'utilisateur gardent le même ctx que dans le CLI (principe pi-web).
