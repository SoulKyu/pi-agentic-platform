Q1 · Installer les prérequis (root)

containerd, Kata (avec Cloud Hypervisor et son noyau invité), nerdctl et BuildKit, plus l'unité pap-vmd, le bridge et les règles nftables.

A · sudo pap vm setup : installe des archives officielles aux versions et SHA-256 épinglés par la release de paprecoIdempotent, pap vm uninstall pour revenir en arrière ; même principe que l'archive d'install de pap (SHA-256 épinglé). Kata : son archive statique ; containerd, nerdctl, BuildKit : l'archive « nerdctl-full ».
B · Un guide d'installation manuelle ; pap ne fait que vérifierPas de code root dans pap hors pap-vmd, mais chaque auto-hébergeur assemble la pile à la main.
C · Paquets de la distribution (apt)Mises à jour par le système, mais versions de Kata très variables d'une distribution à l'autre.

Q2 · Les tests

Ce VPS n'a pas KVM. Les runners Linux de GitHub l'exposent (à vérifier en premier, comme le volume direct de la section 1).

A · Unitaires et intégration sur le faux runtime partout ; tests Kata réels en CI, sautés localement avec un avertissementrecoMême règle que les tests bwrap aujourd'hui : sous CI=1 ils échouent sans KVM au lieu de sauter. Couvre : démarrage, canal, copie de transcription, disque, réseau (VM ↔ VM bloqué, rien hors passerelle et proxy), suppression.
B · Tests Kata réels seulement dans un job de nuitCI plus rapide, mais une régression d'isolation peut rester un jour sur main.

Q3 · Migrer CyberLooker (et tout agent existant)

Règle de la section 1 : l'hôte ne monte jamais le disque d'un agent. mkfs.ext4 -d <dossier> remplit un disque neuf depuis un dossier, sans le monter.

A · Au premier démarrage en VM, pap-vmd crée le disque avec mkfs.ext4 -d depuis l'ancien home + la session du thread en coursrecoL'agent reprend sa conversation et son state/ là où il en était ; l'ancien home part à la corbeille 7 jours. Ses souvenirs mem0 seront convertis en knowledge/ par le sous-projet 5.
B · Disque neuf avec l'ancien home seulement ; nouveau threadPlus simple, mais l'agent perd le fil de sa conversation.

Q4 · La bascule de l'ancien mode au nouveau

Les sous-projets 1, 2 et 3 doivent tous être là pour qu'un agent en VM soit utilisable (réseau par le proxy, plus de demandes dans la boîte).

A · Le mode VM arrive derrière PAP_AGENTS_RUNTIME=vm ; l'ancien mode reste le défaut jusqu'à la fin du sous-projet 3, qui bascule le défaut et supprime l'ancien coderecoTu peux essayer CyberLooker en VM dès le sous-projet 1 ; aucune période sans agents ; l'ancien code n'est supprimé qu'une fois le nouveau prouvé.
B · Une seule grosse bascule à la fin des sous-projets 1 à 3Pas de double chemin à maintenir, mais rien d'essayable avant la fin.
