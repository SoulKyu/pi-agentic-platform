L'image de l'agent, générée par pap

pap construit l'image à partir de ton ~/.pi/agent : tes packages, tes skills, tes réglages. Aucun secret n'y entre : ce sont les adresses internes du proxy qui portent les identifiants. Une seule image partagée sert de base ; chaque agent n'y ajoute que ce qui lui est propre.

1 · Ce qui entre dans l'image · par liste blanche, jamais par liste noire

Entre (copié depuis l'hôte, versions figées)
  • Base Debian slim épinglée par digest dans la release de pap, Node 24 à la même version que l'hôte
  • Outils : bwrap, git, curl, jq, python3, ripgrep, fd, ca-certificates
  • pi-host (dist de pap) + le SDK Pi de pap
  • Packages de settings.json : npm (depuis ~/.pi/agent/npm), git (depuis ~/.pi/agent/git), chemins locaux (copiés)
  • Skills (~/.pi/agent/skills + celles des packages), en lecture seule
  • Réglages assainis : compaction, niveaux de réflexion, modèles activés, la liste des packages
  • Fournisseurs : URL de base → http://llm.internal/<fournisseur>, clé → valeur factice
  • CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
N'entre jamais
  • auth.json, ~/.claude/.credentials.json, toute clé de fournisseur
  • Les sessions, mem0/, les index et l'état de pi-web
  • Les fichiers de config des extensions tels quels (ex. la config de recherche de pi-web-access : elle contient des clés)
  • Tout ce qui n'est pas dans la liste blanche : un nouveau fichier dans ~/.pi/agent n'entre pas tant que pap ne le connaît pas
Adaptateurs pour 3 packages connus
pi-claude-bridgeANTHROPIC_BASE_URL=http://claude.internal + jeton factice (spike 0)
pi-web-accessconfig régénérée : clés factices, URLs des fournisseurs de recherche → adresses internes
pi-mcp-adapterserveurs MCP stdio : binaires dans l'image ; MCP HTTP : URL interne, jeton injecté

Un package inconnu entre sans sa config : s'il a besoin d'une clé, il échoue proprement dans la VM.

2 · Les couches

BaseDebian + Node + outils + pi-host + SDK Pi. Change avec une release de pap.
Profil Pites packages, skills, réglages assainis, adaptateurs. Partagée par tous les agents. Change quand ton ~/.pi/agent change.
Agentce qui est propre à l'agent (voir Q2). Petite, optionnelle.

Tag = sha256 des entrées de chaque couche : rien ne se reconstruit si rien n'a changé. Les couches partagées ne coûtent leur place disque qu'une fois.

3 · Les choix · clique ta réponse sur chacun

Q1 · Comment l'image est construite

pap-vmd (root) est déjà le seul à parler à containerd ; la construction a besoin du réseau de l'hôte pour l'image de base et les paquets Debian.

A · Un Dockerfile généré par pap, construit par pap-vmd avec BuildKitrecoUne image Docker classique : lisible, reproductible, et tu peux la reconstruire ailleurs (ta CI) avec le même Dockerfile.
B · pap assemble lui-même les couches OCI (tar + manifeste)Pas de BuildKit, mais du code de construction d'images à maintenir dans pap.
C · pap génère le Dockerfile, ta CI construit et pousse, pap tire l'imageIl faut un registre et une CI ; chaque changement de ton Pi passe par elle.

Q2 · Les outils système qu'un agent installe

L'agent est root dans sa VM, mais le système de fichiers racine vient de l'image : ce qu'il installe à la main disparaît au redémarrage. CyberLooker, par exemple, a besoin de curl, jq, python3.

A · Une liste « paquets système » dans la config de l'agent → la couche AgentrecoDéclaratif, reconstruit proprement ; l'agent peut aussi installer à chaud pour essayer, puis demander à l'ajouter à sa liste.
B · Rien de persistant : il réinstalle à chaque démarrageZéro config, mais lent et fragile à chaque démarrage à froid.
C · Racine persistante (overlay sur son disque)Il garde tout, y compris ce qu'il a cassé ; seuls les backups permettent de revenir en arrière.

Q3 · Quand l'image est reconstruite

Tu installes un package Pi, ou pap passe à une nouvelle version : les entrées changent.

A · Automatiquement, au prochain démarrage d'un agentrecoL'agent démarre sur l'ancienne image en attendant la nouvelle, avec une note dans son thread. Une image dont le protocole pap n'est plus compatible est refusée, et on attend la nouvelle.
B · Seulement sur un bouton « Reconstruire »Contrôle total, mais un agent peut tourner longtemps sur une image périmée.

Q4 · Les packages Pi d'un agent

Moins de code dans la VM = moins de surface d'attaque ; CyberLooker n'a pas besoin de plannotator.

A · Une image Profil Pi partagée ; chaque agent coche ses packages, appliqués au démarragerecoUne seule image à construire ; par défaut, tous les packages de l'image.
B · Une image par agent, avec seulement ses packagesLe code non coché n'est même pas présent, mais une construction par agent.

Q5 · Mises à jour de sécurité de la base

La base Debian reçoit des correctifs ; une image figée vieillit.

A · Reconstruction hebdomadaire de la base, appliquée au prochain démarragerecoLe digest épinglé par la release de pap reste le point de départ ; apt upgrade à la construction.
B · Seulement à chaque release de papReproductible au bit près, mais les correctifs attendent une release.
