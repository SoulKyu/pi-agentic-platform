Agents en microVM · Sous-projet 1 · Runtime d'agent · Section 1 / 5

Architecture et frontières de confiance

Un agent vit dans sa propre microVM : liberté totale dedans, aucune vue sur l'hôte, des garde-fous seulement sur ce qui sort. Si l'agent est compromis, on le supprime : rien d'autre n'est touché. Cette section fixe les pièces et qui a le droit de parler à qui.

1 · Spike 0 · pi-claude-bridge sans identifiant dans la VM

Résultatconcluant

Binaire claude du bridge, HOME vide, ANTHROPIC_BASE_URL vers le proxy + jeton factice : le proxy injecte Bearer <OAuth> → 200 (Haiku, Sonnet). Aucun en-tête OAuth en plus.

Hôtes contactés1 seul

api.anthropic.com. Sans CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 : 2 tentatives de télémétrie, refusées, sans effet sur la réponse → variable mise dans l'image.

Risquerenouvellement

Le jeton d'accès expire en quelques heures ; deux renouveleurs (ton Claude Code + pap) se casseraient. Reco : claude setup-token (jeton longue durée) rangé dans le vault de pap, injecté par le proxy. Non testé : interactif.

3 · Les choix structurants · clique ta réponse sur chacun

Q1 · Qui a les droits root sur la machine ?

Accéder à la socket de containerd équivaut à être root. Si le daemon y a accès, une faille de pap devient une prise de contrôle de l'hôte.

A · Un service root séparé, pap-vmdrecoUne API étroite et vérifiée. Le daemon reste un utilisateur normal.
B · Le daemon dans le groupe de la socket containerdPlus simple, mais le daemon devient équivalent à root.
C · Une règle sudoers pour nerdctlToujours équivalent à root : nerdctl run peut tout monter.

Q2 · Comment le daemon pilote les VM

Cette machine n'a pas KVM, et les tests doivent tourner partout (en CI, les runners Linux de GitHub ont /dev/kvm).

A · L'interface AgentRuntime avec deux implémentations : Kata et un faux runtime de testrecoLe faux lance le worker comme un simple processus, avec le même canal. Seulement par PAP_TEST_*, jamais en production. Kubernetes viendra comme 3ᵉ implémentation.
B · Kata seulementPas de faux runtime : les tests d'intégration ne tournent qu'en CI ou sur une machine avec KVM.

Q3 · Le canal entre le worker et le daemon

L'IPC de Node ne traverse pas une VM. Le protocole DaemonToWorker ne change pas, seul le transport change.

A · Le worker se connecte à une passerelle sur le bridge, avec un jeton par lancementrecoIdentique sous Kubernetes (un Service). Jeton révoqué à l'arrêt.
B · vsock (une socket unix côté hôte)Pas de réseau à filtrer, mais propre à Kata et à cet hôte : à refaire pour Kubernetes.

Q4 · Ce que le réseau d'une VM peut atteindre

C'est la protection contre le mouvement latéral entre agents et vers l'hôte.

A · Seulement la passerelle et le proxy ; VM ↔ VM bloqué ; tout le reste refusérecoRègles nftables posées par pap-vmd (NetworkPolicy plus tard sous Kubernetes).
B · Seulement le proxy, et le canal passe par vsockVa avec Q3 = B.

Q5 · Le disque de l'agent

L'hôte ne monte jamais le disque : aucun fichier de l'agent n'est lu sur l'hôte pendant que la VM tourne.

A · Volume passé directement par Kata (virtio-blk)recoà vérifier en tout premier sur une machine avec KVM : c'est le 1ᵉʳ risque du plan.
B · Monter le disque sur l'hôte (loop) puis le partager avec la VMRefusé par principe : l'hôte monterait des fichiers écrits par l'agent.
