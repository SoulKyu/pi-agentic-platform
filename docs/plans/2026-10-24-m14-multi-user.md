# M14 (owner and members) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** pap gets members. The owner invites trusted people. Each member has their own box projects, sessions, agents, triggers, budget, Claude token and GitHub account. The owner keeps the installation, sees members' usage but never their content.

**Architecture:**
- **S1 writes the shared contracts:**
  - the `users` permission domain and the role permission sets;
  - the `users.*` RPCs and their views;
  - the invitation HTTP shapes;
  - `ClientPath`, the one branded schema of every client path field;
  - `sessions.availableModels` and `agents.packages`;
  - the permission moves (fonts, GitHub, ops events, the GitHub HTTP routes);
  - four error codes.
- **Lane A is the daemon:**
  - roles in the auth module (A1) and invitations (A2);
  - the deny-by-default host gate (A3);
  - the GitHub access check (A6);
  - the per-user Claude token (A4a), shared providers (A4b), the budget cap and the member spend line (A4c);
  - the users module (A5a) and the delete cascade (A5b).
- **Lane B is the web (B1 to B3):** role plumbing and hiding; Settings › Users; the invitation page.
- **Join:**
  - wiring;
  - two-user journeys, with an isolation test driven from a typed method table and a route table;
  - ADR 0085;
  - one Opus final review;
  - the post-merge `sudo pap vm setup`, needed because the relay (in the agent bundle) changes.

**Tech Stack:** TypeScript (erasable), Node 24, zod, vitest, SQLite migrations, React, the relay (`packages/pi-host/src/relay`), the vault.

**Roles:**
- `users.role` is `owner` or `member`, and there is exactly one owner (a partial unique index).
- The migration makes the oldest user (`ORDER BY created_at, id LIMIT 1`) the owner.
- The owner holds every permission.
- A member holds every permission except `system:admin`, `pi:*`, `users:*` and `lanes:*` (members have no lanes in M14, since lanes in boxes are a later lot; the gate's lane call sites are defence in depth).
- Cookie sessions get `permissionsOf(role)`. Tokens get the intersection of the token row's permissions, `TOKEN_PERMISSIONS` and `permissionsOf(role)`.
- A token is created with at most its creator's permissions.
- `system:admin` and `users:*` are never-for-tokens.
- **One source of a user's role:** `auth.roleOf(userId)` and `auth.isMember(userId)`. There is no `Caller.role`; background Callers (`automationCaller`, `ownerCaller`, lanes `callerFor`) are untouched. A unit test (A3) greps non-test daemon code for `caller.role` and `role: "owner"` and finds none.

**Permission moves (S1):**
- `github.startCreate` and `github.forget` become `system:admin`. `GET /github/app/new` follows (`system:admin`).
- `github.authorizeUrl` and `github.disconnect` become `settings:operate`. They stay in `GITHUB_BROWSER_ONLY`. `GET /github/app/authorize` follows (`settings:operate`).
- `agents.vm.setClaudeToken` and `agents.vm.clearClaudeToken` become `settings:operate`. They stay browser-only, with their step-up.
- `ops.events.list` and `subscribe.ops` become `system:read`. They are already per owner, so a member keeps their own failures and Health stays visible.
- `fonts.add` and `fonts.remove` become `system:admin` (fonts are shared by every user).
- `users.invite` is `users:admin`, step-up, `secretResult: true`. `users.setDisabled {disabled:false}` also takes a step-up.
- New: `agents.packages` (`agents:read`) and `sessions.availableModels` (`sessions:read`).

**Client path fields (S1, A3):**
- Every client path field uses one branded zod schema, `ClientPath` (absolute, the existing path rules): `FilePath`, `Cwd`, the local `AbsolutePath`s in `shell.ts`, `skills-methods.ts`, `trust-methods.ts`, `mcp-methods.ts`, `models-methods.ts`, `pi-helper.ts`, and `projectRoot`.
- zod's brand is type-only, so `ClientPath` also records each parsed value into an active collector: `collectClientPaths(fn)` returns the paths seen during a synchronous parse.
- The dispatcher, after the params parse and only for a member caller (`auth.isMember(caller.userId)`), runs `assertBoxOnly` on every collected path before the handler. This is deny-by-default: a new path-taking method is gated when its schema uses `ClientPath`. A contracts test greps `*-methods.ts` and `*.ts` param schemas for a raw `z.string()` path field named `path`, `cwd`, `root` or `projectRoot` that does not use `ClientPath`.
- `httpCaller`'s path routes (`/files/raw` GET and PUT, `/upload`, `/agent-files`) do the same.
- The A3 call sites stay as defence in depth.
- `deps.isMember` is REQUIRED in every dependency type that takes it.

**Invitations:**
- An invitation is a token of 32 random bytes, base64url.
- Only `sha256Hex(token)` is stored. `users.invite` is `secretResult`, so the raw token never reaches `receipts`.
- It is valid 24 hours and used once.
- The link is `<origin>/invite#token=<token>`, where `<origin>` is the caller's origin checked against `allowedOrigins`. This replaces the spec's `/auth/invite/<token>` (ruling: a hash never reaches a server log or a Referer). `isSpaRoute` already serves `/invite`.
- Accepting it uses the setup rules: username `^[A-Za-z0-9_.-]{1,64}$`, password 12 to 1024 characters. It creates a member and starts a session with method `password`. If the request carries a live session cookie, that session is revoked first.
- Failures (unknown token, 404, and 409 `username_taken`) are counted on `ipKey(ip)` in a throttle table of its own (`invite_throttle`), never the setup throttle, so invite failures from a shared address never delay the owner's password sign-in.
- Accept and passkey `login/verify` refuse a disabled account with `account_disabled`.

**Budgets:**
- A member's cap is `users.budget_usd` (REAL, USD per day, 0 to 1000). The default for a new member is `5`, the install default.
- There are two lines. The **automation budget** (`SettingsService.automation(ownerId).dailyBudgetUsd`) is clamped to the cap. The **member line** is the member's whole API spend.
- Automation clamp: for a member, a stored or written `null` means the cap (`null` is "no budget" today); otherwise `min(stored, cap)`. `settings.set` refuses an `automation.dailyBudgetUsd` above the cap, and `null`, with `budget_cap`. `settings.get` returns the effective value, and Settings › Automation shows a "capped at {cap}" line.
- Member line (OQ1, owner, decision 129): counts every run of the member billed `api` or `unknown`, interactive included, finished and live. Subscription runs through the member's own Claude token cost the owner nothing and are not counted. The day is the owner's time zone, never the member's writable `automation.timezone` (the clamp's day too).
- The relay policy (`policyOf`, `policyOfProject`) answers `blocked: "budget"` once the member line is at or above `users.budget_usd`. A policy refresh is pushed on `onRunEnd` for project boxes as well as agents.
- `UserView.spentTodayUsd` shows the member line.
- The owner has no cap.
- Known limit (OQ5, owner, decision 129): the line rests on the cost the VM reports, so against a member (root in their box) it is a guard against mistakes, not a hard cap. ADR 0085 says so.

**Shared providers:**
- The table is `provider_sharing(provider TEXT PRIMARY KEY, shared INTEGER NOT NULL)`, in the new users module's migrations (`modules/users/migrations`), not auth and not models.
- The default row is written the first time a provider is seen (never derived on each read): shared when its auth is `api_key` by the relay's own rule (`R/credentials.ts:122`, `checkAuth().type === "api_key"`, so `models.json` literal and `$VAR` keys count), otherwise not shared.
- A member's box policy models, `sessions.models` and `sessions.availableModels` drop unshared providers. `modelsOf` reads the auth kind from a cached `models.overview`, cleared on `models.onChanged`.
- **`claude-bridge` is exempt from sharing**: it has no stored auth, and it is gated by the box owner's own token (`policy.claudeToken`).
- OAuth (subscription) providers are never served to boxes: the relay already refuses them. Their sharing switch is shown disabled with the subscription copy (OQ6, owner, decision 129). Subscription use goes through each user's own Claude token.
- `setProviderShared` calls `relay.refreshAll()`.

**Claude token:**
- Each user's token is in the vault's user scope under the name `CLAUDE_TOKEN`.
- At the first start, the legacy file `$PAP_HOME/secrets/claude-token` moves to the owner's vault and the file is removed. With no owner yet, the file is left alone. If a crash left both, the vault wins and the file goes. If the vault is unreadable (`vault_key_lost`), the file is kept, a warning is logged and the daemon boots. The read-only database mode only reads the owner id.
- The token travels inside `box_policy` as `claudeToken: string | null`, computed with the box's owner (`policyOf` / `policyOfProject`), replayed by `replay()` and cleared by the revoke's empty policy. There is no separate token message and no token map in the relay. `ClaudeTokens.onChange` calls `relay.refreshAll()`.
- A box whose owner has no token gets `claudeToken: null` and the relay's existing `no_claude_token` refusal. Another user's token is never used.
- `agents.vmStatus` reports the caller's own token status.

**Host gate:**
- For a member, any path or cwd that is not at or under one of their box project roots (`boxOfPath(source, ownerId, path) !== null`) is refused with `forbidden` before any host file-system call, including Files, Changes and the raw routes.
- `assertBoxOnly` returns the `{projectId, root}` it matched, and the caller routes with it, so a box removed between the gate and the routing never falls through to a host `realpath`.
- Members never get a host project, a host worker, a host terminal, a host lane or a lane script.
- Background code checks `auth.isMember(ownerId)` because it has no `Caller`.

**GitHub access:**
- A project's repository must be one the project owner's own token reaches with push (OQ3, owner, decision 129). See A6.

**Disable and delete:**
- **Disable** sets `users.disabled_at`. Both `authenticate` paths then refuse, so the next WebSocket frame fails and tokens answer 401. It is deny-by-default through three chokepoints, with no per-path list:
  1. `SettingsService.automation(id).paused` is true for a disabled user (the seam of the budget clamp: it covers fire, resume, queued and thread tasks, reminders, feed polls and limits);
  2. the VM launch gate (`status.require()` and `BoxControl.start`) refuses a disabled owner's box or agent with `account_disabled`, so a worker restart or a queued box start cannot boot it;
  3. `policyOf` and `policyOfProject` answer `blocked: "paused"` for a disabled owner.
  Their boxes and agent VMs stop. Data stays.
- **Enable** clears `users.disabled_at` (step-up).
- **Delete** starts with the disable path, so a crash mid-delete leaves a disabled account, never an enabled half-deleted one. Then it asks the step-up (before anything), and:
  - stops everything;
  - box projects go to the trash as a project delete does;
  - agents go to the agent trash;
  - triggers, sessions, the vault (every scope of the owner, after the GitHub signing keys are released and awaited), push subscriptions and deliveries, the member's search index rows, attachments and exports on disk, and every `owner_id` / `user_id` row are deleted, except `runs` and `audit` (OQ2, owner, decision 129: they hold costs and the misuse trail, no content);
  - finally the `users` row is deleted, which cascades to sessions, passkeys and tokens.
- The owner can be neither disabled nor deleted: `forbidden`.

**CLI:**
- `pap user add <username> [--password-stdin] [--role owner|member]`:
  - with no user, it creates the owner;
  - once an owner exists, it creates a member;
  - `--role owner` is refused when an owner exists (exit 1, "an owner already exists").
- `pap passkey reset [<username>] [--revoke-tokens] [--keep-password] [--password-stdin]`:
  - the default user is the owner;
  - every delete is scoped to that user;
  - `secrets/device.key` is removed only for the owner.

## Review Focus

1. A member reaching an owner's row, file or repository by id or path through any RPC or HTTP route, including a host path the gate must refuse before any host fs call, and a repository only the owner's App installation reaches (RT-01). Tests: J1 `every method and route is classified and a member never reads or changes the owner's rows`; A3 `the dispatcher refuses a member's host path before the handler`; A6 `a member cannot clone or link a repository only the owner's installation reaches`.
2. A disabled member who keeps a live WebSocket, a token, a firing trigger, a resume effect, a queued task, a reminder or a restarting box. Test: J1 `disabling a member stops their boxes and agents, closes their socket, refuses their token, and no resume, queued task or reminder starts work`.
3. One invitation accepted twice (two concurrent accepts, expired, revoked), or its token stored in plaintext. Tests: A2 `two concurrent accepts create one member`; A5a `users.invite leaves no token in receipts`.
4. The relay serving a member's box with the owner's Claude token or an unshared provider. Tests: A4a `a member's box gets the member's token or none` and J1 `the relay uses each owner's Claude token`.
5. A member spending the owner's API keys past the cap: raising the budget through `settings.set`, a token or an import, or chatting interactively once the line is spent (RT-02). Tests: A4c `a member cannot raise the budget past the cap` and `an interactive box session of a member is refused budget once the cap is spent`.
