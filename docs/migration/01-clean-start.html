Spec D · Migration (décision 24)

Départ propre

Aucun import depuis pi-web. pap démarre avec un ~/.pap vide et recrée ses agents, triggers et lanes. Pi reste partagé : pas de re-login des providers, extensions et skills inchangés. pi-web n'est jamais touché, donc le rollback se résume à rouvrir pi-web.

1 · Qui voit quoi

~/.pap · neuf
  • Owner créé via l'URL de setup + passkey.
  • Agents, triggers, lanes, réglages, coûts : tout part de zéro.
  • Historique FinOps à partir du premier run dans pap.
~/.pi/agent · partagé
  • Comptes providers, models.json, settings.json, extensions, skills, subagents, mem0, mcp.json : réutilisés tels quels.
  • Sessions : pap n'indexe que celles créées après son installation, CLI pi compris. Les anciennes restent dans Pi et pi-web.
Fichiers propres à pi-web · ignorés
  • pi-web-session-*.json, agent-ops/, agent-spaces/, agents-home/, agents-secrets/ : pap ne les lit jamais.
  • Les profils .md des agents long-terme de pi-web, rangés dans ~/.pi/agent/agents/, sont vus par Pi comme des subagents. Une note de nettoyage le signale.

Gel

pi-web : lanes Lot B terminé, puis plus que des bugfixes (décision 9).

1
Installation

pap installé à côté sur 127.0.0.1:7777. Il démarre vide et devient l'outil des nouvelles sessions.

pi-web reste ouvert pour l'historique et les agents existants.

2
Recréation

Tu recrées dans pap les agents et triggers que tu veux garder (formulaires + dry-run). Pour chaque webhook : nouvelle URL et nouveau secret dans Alertmanager ou Grafana.

Chaque trigger recréé dans pap est désactivé dans pi-web, pour ne jamais tirer deux fois.

3
Arrêt de pi-web

Quand plus rien ne tourne dans pi-web : arrêt du service, et pap prend son host et son port (ou le reverse proxy pointe vers pap).

pi-web reste installé 30 jours, puis le repo est archivé. Nettoyage de ~/.pi/agent à la main, avec une liste documentée.

Risques restants
  • Même session ouverte dans les deux apps : pi-web voit aussi les nouvelles sessions de pap (fichiers Pi partagés), sans verrou. Pendant la cohabitation, ne pas reprendre dans pi-web une session de pap. pap avertit si un fichier change sans que son worker y ait écrit.
  • Double tir d'un trigger recréé : évité par la règle de l'étape 2.
Ce que ça simplifie
  • Pas de pap import pi-web, pas de rapport d'import, pas de fixtures du format pi-web à maintenir.
  • Pas de route alias pour les anciens webhooks.
  • Scan initial léger : seulement les sessions postérieures à l'installation.
  • Aucun format de pi-web ne contraint le design de pap.
