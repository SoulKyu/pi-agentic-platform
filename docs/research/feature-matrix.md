# Feature matrix: pi-web vs T3 Code vs Orca

Built 2026-10-10 from `pi-web-inventory.md` (rows), `t3code.md` and `orca.md` (columns). Feeds spec A (scope), C (architecture), D (migration).
Paths: `T3:` = `_refs/t3code`, `Orca:` = `_refs/orca`, `pw:` = pi-web (`local` + `feat/lanes`).

Verdicts:
- **KEEP**: pi-web's behaviour is better or unique; port the behaviour (not the code).
- **ADOPT**: take the reference's pattern.
- **ADAPT**: pi-web's feature set + a reference pattern for the mechanism.
- **DROP**: do not port / do not build.
- **NEW?**: not in pi-web; candidate needing a user decision (listed in §3).

## 2. Cross-cutting findings for spec C (architecture)

### 2.1 Pi process model: the key decision
Both refs run **one Pi child per session** (`pi --mode rpc`). That gives the isolation pi-web lacks (decision 2) but costs:
- no `navigate_tree` (in-session branch switch) and no `ctx.ui.custom()` panels in RPC mode;
- pi-web's in-process custom tools and policies have to move into an injected extension + a daemon callback channel (T3 pattern; this is the right home for them anyway).

Alternative to evaluate: **our own per-session worker process that hosts the Pi SDK** (`createAgentSessionFromServices` in a child, our protocol on stdio). Same crash isolation, keeps `navigate_tree`, `custom()` and in-process hooks, but we then own the protocol and track SDK changes ourselves. Spec C must compare: RPC child vs SDK worker vs hybrid (RPC by default, SDK worker only where RPC lacks a capability).

### 2.2 Patterns both refs converge on (strong signal)
1. Pi out of process + `agent_settled` + `get_state` idle probe, kill ladder, version floor checked at launch.
2. Injected Pi extension as the policy / permission / platform-tool bridge.
3. Single SQLite (WAL) for platform state; Pi transcripts stay in Pi's JSONL, referenced by file path.
4. One WebSocket carrying typed RPC + streams; every method carries a mandatory permission; capability negotiation instead of version checks; forward-compatible decoding of unknown events.
5. Command idempotency (client command id + receipt) and an append-only journal / outbox.
6. Contracts package as the single source of the wire schema.
7. Real-Pi CI job pinned to a version (Orca `pi-provider-runtime.yml`) + replayed recorded Pi RPC sessions as integration tests (T3 `record-pi-rpc-replay-fixture.ts`).

### 2.3 Anti-patterns (directly relevant to the "sprawl" driver)
- Both are huge (T3 ~930k src LOC, Orca ~2.27M) with god files (T3 `ChatView.tsx` 12k lines, `Orchestrator.ts` 11k; Orca files up to 377 KB). Borrow patterns, never modules.
- Both enforce discipline only after the fact (ratchet baselines). We should start with hard caps: max lines per file, one module per domain, lint rules for boundaries.
- T3's Effect + TS 7 + Vite+ toolchain is powerful but bleeding-edge and demands Effect fluency.
- Both default to full access for agents and depend on a vendor cloud for mobile push. We do the opposite.

### 2.4 Language data point
Both refs are TypeScript on Node 24 with React 19 + Tailwind 4 + SQLite (`node:sqlite`). Pi needs Node at runtime in every install channel (decision 8). A Go daemon would add a second runtime and lose in-process Pi SDK helpers (OAuth, config editing, session reading). Weigh this in the approaches step.
