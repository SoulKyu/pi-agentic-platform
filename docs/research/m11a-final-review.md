## Strengths

- **Caller identity is the daemon's own.** `sessionKind` reads the row and the session policy at every call; `platformVerdict` is pure and the dispatcher runs steps 1–8 without an await (`modules/platform/dispatch.ts:176-243`). An approval is spent only for a type the op allows, for that tool and that tool call, from a browser session (`sessions/approved-calls.ts`, `agent-surface.ts:266-294`). The audit slot is reserved before anything runs (W5-R16). Exit criterion 1 holds by construction and is pinned by `security/platform-ops*.int.test.ts`.
- **Fail closed at every launch.** `agentGate` is the one await before the spawn in `launch` (`service-launch.ts:72-95`), for new, reopened, idle-released and cold-prompted sessions; prechecks are always sandboxed (W5-R31); the probe trusts only root-owned binaries on root-owned paths and needs a canary and a nonce; `ensure()` re-checks the binary before trusting a usable result. Exit criterion 2 holds.
- **The egress proxy is a real cage.** Always `--unshare-net`; one listener per command; the proxy resolves names itself, refuses a name when any answer is blocked, connects to the checked address, and bounds everything on the kernel `Clock`. No report, a cut report or a lost socket taints (`egress-taint.ts`, `egress-link.ts:11`, `index.ts:47`). Hosts an agent chose are hashed in daemon sinks (W5-R54).
- **Secrets.** AES-256-GCM with owner/scope/name in the AAD, a key never re-minted over sealed files, `O_NOFOLLOW` + mode + uid checks on read, receipts hash selectors only, one-use lists authoritative (W5-R37). W5-R60's stream hold-back is in (`pi-host/src/delta-gate.ts`, prefix-aware tail per content block, flushed at `*_end`, message end, error and abort).
- **Taint plumbing across agents** is careful: tainted delegations run isolated with read tools only; reminders carry taint only into the session that set them (W5-R44); reading another agent's home or any runs folder fences and taints (W5-R45); prechecks and payloads never reach a thread; retries and fires of thread targets refuse tokens.
- **Paths.** Homes and scratch folders are opened with `O_NOFOLLOW` and checked by uid and real path; the worker re-checks every spec folder before each spawn; the prompts read uses `/proc/self/fd` to confirm the descriptor (`agents/prompts.ts`).
- **Composition** is small and ordered: agents are bound before the outbox drains (`daemon.ts:352`), links refuse double binds, `compose-m11.ts` is the only M11 entry.

### Important

**I1. A token drives an agent's trusted thread through `sessions.prompt` (and `usage.resumeNow`), against M11R4 / M11R175; ADR 0047 and `agents.md` say a token can do "nothing else about an agent".**
- Where: `apps/daemon/src/modules/sessions/service.ts:295` (`prompt` checks only `owned()`); `sessions:operate` is a token permission (`packages/contracts/src/auth.ts:13-24`); `agents.list` / `agents.get` (`agents:read`) return `threadSessionId` (`packages/contracts/src/agents.ts:208`) and `agents.openThread` is `agents:operate` (`agents-methods.ts:128-129`). `usage.resumeNow` (`usage:operate`) also continues an agent thread for a token (`modules/runs/resume.ts:233-262`, no `sandboxedOnly`). Docs: `docs/adr/0047-platform-calls-and-session-types.md:44`, `docs/agents/agents.md:7`. Probe (scratch int test, real daemon, deleted): a token holding `sessions:read`, `sessions:operate`, `agents:read`, `agents:operate` opened Atlas's thread with `agents.openThread` and `sessions.prompt` on it answered `ok`, while `agents.queueTask` from the same token was refused.
- Why it matters: M11R4's own reason is "a token never makes an agent's trusted thread run, never approves and never sees a secret", and the code refuses tokens on every other way in (`agents/queue.ts:20`, `automation/retry.ts:33-35`, thread-target fires). Through `sessions.prompt` the token's text lands in the thread as an owner message, untainted: the agent runs in its own mode with its vault in its shell, can delegate untainted into other agents' trusted threads, set reminders and rewrite `MEMORY.md`, and the token reads the stream (`sessions:read`), where an encoded vault value is not redacted (ADR 0049's limit). The marginal power over M5 is limited (a `sessions:operate` token can already answer "once" on a plain session's shell card), which is why this is Important and not Critical; but a binding ruling is broken and two documents promise the opposite.
- Fix: refuse a token caller (`forbidden`) for any session row with an `agentId` in `sessions.prompt` and `usage.resumeNow` (and, for consistency, the other run-starting session methods: `compact`, `navigate` with editor text, `autoName`), declare `forbidden` in their `errors`, and pin it in a security int test (a token with every token permission: open thread allowed, prompt `forbidden`, nothing run). If the owner prefers to keep it, correct ADR 0047 and `agents.md` instead and record the ruling.

**I2. A `null` host list means "any host" for the step-up and the permissions sheet, and "no host" for the egress proxy: a standing reach widening saves without the password.**
- Where: the proxy reads null as empty (`apps/daemon/src/modules/sessions/egress-link.ts:30`, `agent-surface.ts:248`; ADR 0047 "no list at all is an empty list"), while `widensReach` reads an owner list of null as "any host: never widens" (`packages/contracts/src/agents.ts:148-153`, W5-R36 as written), the permissions sheet says "Hosts: any host" and counts a networked shell as reaching a host when the list is null (`apps/daemon/src/modules/agents/permissions.ts:96-107`, copy `apps/web/src/i18n/catalog/agent-safety.ts:39`), and `EgressScope.hosts` is documented as "null = any public host" (`apps/daemon/src/modules/egress/allow.ts:10,25`, M11R235's binding code). Two sides of the J3/XS join use opposite readings of the same field.
- Why it matters: the owner's list is null by default (`policy.ts:279`). For a networked agent that uses the owner's list, the proxy reaches nothing; an `agents.update` from `allowHosts: null` to `["attacker.example"]` then opens the proxy to that host with no step-up (`widensReach(..., ownerHosts = null)` is false). That is exactly M11R44's "a stolen browser session widens an agent silently". The sheet, meanwhile, tells the owner the agent reaches any host and raises the exfiltration leg for an agent that reaches none.
- Fix: pick the proxy's fail-closed reading (it is what ADR 0047 says) and make the rest follow it: in `widensReach`, an owner list of null counts as "no host" for an agent whose sandbox has (or gets) network, so null → a non-empty own list widens; the sheet's `hosts` / `reachesAHost` and its copy say "no host for the shell (URL tools: any)"; drop `hosts: null` from `EgressScope` or mark it test-only. Tests: owner null, agent null → `["x"]` with network on → `step_up_required`; the sheet for that agent before the edit says the shell reaches no host.

**I3. An agent thread's Pi file tools read the owner's home (`~/.ssh`, `~/.aws`, `~/.config/gh`) unasked in every mode, while Settings › Agents and the agent form tell the owner the agent never sees it.**
- Where: `packages/pi-host/src/policy/read-target.ts:16-25` (protected reads are pap's own files, Pi's folder, attachments and other agents' homes only) and `stage-approval.ts:59-70` (an agent thread's built-in read goes through the interactive matrix). Probe (scratch test, deleted): with `agent-thread` rules, `read {path: "$HOME/.ssh/id_ed25519"}` ran with no question in `auto-accept-edits`, `supervised` and `read-only`. Copy: `apps/web/src/i18n/catalog/settings-agents.ts:55` ("Neither sees any folder of your home"), `:59-60` ("read, edit, write, grep, find and ls are held back by pap's path rules"), `agent-settings.ts:42` ("never your home folder"); ADR 0048 Context (`docs/adr/0048-the-agent-sandbox.md:9`: "a shell that cannot read the owner's keys") and limit 2 (`:48`) never say that the thread's file tools can.
- Why it matters: the owner turns the sandbox on to keep agents away from their keys; the model reads them with `read` and, with network on, the shell can send them to any host the proxy lets through (they are in the context, not in a file the sandbox hides). The plan's profile table does keep the interactive matrix for thread reads, so the behaviour is planned, but no document or screen says it, and three lines imply the opposite (priority 4: docs that overclaim).
- Fix: at minimum, say it plainly where the owner decides: Settings › Agents' "does not cover" list, the form's sandbox line, ADR 0048 (Context and limit 2) and `agents.md`'s limits ("an agent thread's read, grep, find and ls reach every file you can read, your home included, except pap's files, Pi's folder and other agents' homes; only its edits are kept to its home"). Better, and an owner decision: in the `agent-thread` profile, make built-in reads outside the home and the system folders ask (a protected read), as the isolated-task profile already blocks them.

**I4. Quarantine leaves the agent's outgoing delegations queued and running in other agents' threads.**
- Where: step 2 cancels tasks whose `agent_id` is the quarantined agent (`apps/daemon/src/modules/agents/quarantine.ts:78-84`, `automation/runner-agent.ts:326-328`); a delegation row has `agent_id` = the target and `requested_by` = the requester (`automation/agent-tasks.ts:134-136`). At start, the thread path only checks that the requester exists (`runner-thread.ts:244-252`) and the isolated path the same (`runner-agent.ts:108-113`), so a quarantined requester's untainted requests still enter the target's trusted thread (up to 20 queued per target). Delete is safe (the requester is gone: `not_found`).
- Why it matters: quarantine is the incident response ("nothing the owner granted in the thread before the incident survives it", W5-R52), and Review Focus 6 names "a quarantine while a delegation is queued". An owner who quarantines Atlas because it misbehaved expects Atlas's last requests to stop, not to run in Scout's trusted thread minutes later.
- Fix: in step 2, also cancel the queued (and refuse at start the not-yet-running) tasks whose `requested_by` is the agent, reason `quarantined`; or make both start paths cancel a delegation whose requester is quarantined. Pin with a quarantine int case: Atlas delegates to a busy Scout, Atlas is quarantined, the queued delegation ends `cancelled` and Scout's thread gets no prompt.

### Minor

**M3. **M4. Trusted sources can be fronted to bring third-party content in untainted.** The a1 rule trusts the `CONNECT` name (`pi-host/src/policy/egress-taint.ts:4-10`); TLS SNI and `Host` inside the tunnel are not seen, so a trusted source on a shared CDN can serve another tenant's content as clean. **M5. `secret_request` is registered for agent threads whose sandbox is off, where it always answers `sandbox_unavailable`.** `apps/daemon/src/modules/sessions/agent-surface.ts:161-172` filters by type, handler and switch only; ADR 0047's table says "`agent-thread`, sandbox on only". Fix: drop `secret.request` from `platformOps` when the start-time profile has no sandbox, or say in ADR 0047 that the tool exists and refuses.

## Declined to judge

- The owner's own prompt in a paused agent's thread is not gated: M11R75 ("pause is not cancel; the owner can still talk in the thread").
- An old thread unarchived after a reset starts again as an agent thread: M11R210 anticipates it ("an unarchived old thread gets none back"); only a deleted agent's thread is ruled out (M11R53).
- `agents.prompt` returns agent-written text to a token caller (`agents:read`): ruled by M11R186; a value an agent writes into a file is ADR 0049's "a command the agent runs can print it".
- A hand-off quote from a tainted thread enters another agent's thread fenced but untainted: M11R77 makes it the owner's own act.
- `acceptsDelegation`, the role text and the model change without the step-up: M11R44 enumerates the widening set.
- A sandbox-off agent's Pi `bash` sees the worker's environment, provider keys included: the owner's password-gated choice, and M11R95's copy says "with your files and keys".
- Files a tainted thread wrote into its home stay trusted after a reset or a `clearTaint`: the home persists by design and W5-R46 treats a clear as the owner's statement of trust.
- A token's "once" on a non-platform card (a networked shell) in an agent thread: M5 Q7, and owner m15 limits the token refusal to platform cards. Folded into I1's fix only as an option.
- A Pi CLI session adopted by M4's scan whose folder is an agent home: adoption is unchanged by M11, and reads there taint and edits ask (W5-R45, W5-R46).
- Everything on the brief's known-and-accepted list (M5 redaction limits, the prefix suffix leak, exfiltration through reachable hosts, `AF_VSOCK`, the egress hash, the T12 race, no rail menu, no `memory_review`).
- Domain fronting as an exfiltration path: ADR 0047 already says it.
- `test:int`, `smoke` and the browser checks: not re-run here (the full gate and the owner's preview checks).
