## Strengths

### Important

**I1. A child of an agent thread takes its profile prompt, tools and model from `.pi/agents/*.md` inside the agent's own home when Pi's trust store trusts an ancestor of it, against W5-R27 / W5-R29.**
- Where: `apps/daemon/src/modules/subagents/profile.ts:15-21` and `profiles.ts:31-37` pass the session's folder to the helper whenever `trust.status(cwd) === true`, and `TrustPort.status` answers the decision "for the folder or the nearest folder above it" (`modules/trust/service.ts:47`; the helper's `trustStatus` reports `inherited: true`, `pi-host/src/helper/ops/trust.ts:230`). The helper then reads `<cwd>/.pi/agents` (`agent-profile.ts:103-107`, `agent-profiles.ts:93-97`, `ProjectTrustStore.get` takes the closest saved decision, Pi docs/security.md "a saved decision for the current directory or one of its parents"). For an agent thread the cwd is the agent home. `child-port.ts:243,260` keeps the agent on the child and `open-session.ts:233` appends the file's body to the child's system prompt. Probe (scratch unit test, deleted): with `ProjectTrustStore(agentDir).set(<home>, true)` and `<home>/.pap/agents/atlas-0000/.pi/agents/helper.md`, `trustStatus` answered `{decision: true, inherited: true}`, `listProfiles` listed `helper` as `project`, and `readProfile` returned its prompt `WRITTEN BY A TAINTED RUN`, `tools: [bash, read]`, `model: other/model`.
- Why it matters: the agent home is agent-writable without a question (its sandboxed shell, network off, is judged an edit of the home and runs unasked in auto-accept-edits, tainted or not; M11R30 names no path, so the `.pi` protected segment does not apply to it). W5-R27 refuses project trust inside `$PAP_HOME/agents` precisely because "an agent writes its own home, so trusting it would load agent-written `.pi/APPEND_SYSTEM.md`, `SYSTEM.md`, `.agents/skills` and `.pi/extensions`", and W5-R29 makes the worker answer untrusted for every agent session "whatever Pi's own trust store says (trust recorded by Pi's CLI, a trusted ancestor)" (the comment at `open-session.ts:90` says so). The profile reader is a new reader of the same kind of `.pi/` resource that skips that rule: text a tainted run wrote becomes system-prompt text of a clean child after a reset (the child takes the clean parent's taint, so its answer also comes back unfenced). The precondition is an owner who once trusted their home (or `~/.pap`) in Pi's CLI, which is the case W5-R29 was written for. ADR 0053:17 and `agents.md:58` say project profiles are read "only while Pi trusts the parent's project", and ADR 0053:41 says "a profile cannot widen anything". The marginal power over the accepted "home files stay trusted after a reset" class is limited (the child's tools are still narrowed to the thread's), which is why this is Important and not Critical; but a binding ruling is bypassed by a composition no per-task review could see (29a's reader against M11a's W5-R29).
- Fix: never read project profiles for an agent session: in `profile.ts` and `profiles.ts`, pass no `cwd` to the helper when the session row has an `agentId` (or when its real path is inside `$PAP_HOME/agents`, the W5-R27 test), so only `<Pi agent dir>/agents` is read. Test: an agent thread whose home holds `.pi/agents/x.md` under an ancestor trust gets `not_found` for `profile: "x"` and an empty project list. Correct ADR 0053:17 and `agents.md:58` ("never for an agent's session: its home is not a project, W5-R27").

**I2. A child whose run hits a usage limit is resumed on its own at the reset, after its parent's call has ended: a child outlives its parent's run (M11R139).**
- Where: the child's run ends `limited` → `runs/observer.ts:203` → `resume.ts:143-158` `plan()` enqueues a `run.resume` effect for the child session whenever `autoResume` is on (the default, `contracts/src/automation.ts:292`); the subagents service ends the row `failed usage_limit` and answers the parent `unavailable` (`subagents/service.ts:96,198-202`). Nothing in `plan()` or `refusal()` (`resume.ts:161-171`) knows that the session is a child whose call is over; `stop.ts`'s guard was released at the run end. Probe (scratch int test on the scripted provider, deleted): a plain parent's `subagent` call, the child's script ending with a usage-limit error; the row ended `failed / usage_limit`, the outbox held `run.resume` for the child's session id, and after the clock moved 5 minutes and the outbox drained, the child had a second run `origin: resume` with no parent waiting for it.
- Why it matters: the brief's priority 2 and M11R139 ("a child never outlives its parent's run and keeps spending"; ADR 0053 lists five stop triggers and none covers this). The resumed run is unattended work whose answer goes nowhere, paid as an automatic run (bounded only by M10's owner-wide budget), counted in the agent's day for an agent's child, and it repeats at every reset while the provider keeps limiting it. The parent usually resumes too (same provider) and may call `subagent` again, so the work is done twice. The child also keeps its approvals bubbling to a parent that no longer waits.
- Fix: do not plan or send an automatic resume for a child session: in `plan()` (and, for safety, `refusal()`), skip a session whose type is `child` (a `child` skip reason, `runs.resumeSkipped`), leaving the owner's own "Resume now" on the child's tab. One line in ADR 0053's stop section and `finops.md`. Test: the probe above, expecting no `run.resume` row (or a skipped one) and one child run.
