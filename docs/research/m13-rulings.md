## Plan rulings (M13R1 to M13R57)

**E2E**
- **M13R1** E2E lives in `scripts/e2e/`; journeys are `jNN-name.e2e.ts`; Playwright 1.63.0 exact as a root devDependency. Why: no new workspace package, no boundary-lint element to add, the smoke code is next door and reusable. Cost: `scripts/` grows by about 2 000 lines of test code; every file stays under 400.
- **M13R2** `pnpm test:e2e` = `node scripts/e2e/run.ts`. Mode `local` when `chromium` and `webkit` executables both exist; otherwise mode `container` (podman image `mcr.microsoft.com/playwright:v<installed version>-noble`, `run-server --host 127.0.0.1 --port <free>`, `--network host`, the `playwright-core` folder resolved through `@playwright/test`, mounted read-only at `/pw`, `--ipc=host`: M13R38); `PAP_E2E_MODE=local|container` forces one; with neither it exits 1 with the sentence "no browser and no podman: see docs/agents/e2e.md". The image tag is derived from the installed version, and a test pins it. Why: the host is headless with no sudo (proven by the controller harness); CI installs browsers itself once the repository is public.
- **M13R3** Every spec file (per project) boots its own built daemon, from a worker-scoped fixture (M13R41), on a free port (`startDaemon`, network guard, scripted provider, `PAP_WORKER_SCOPE=off`, `PAP_MIN_FREE_DISK_MB=0`, `PI_OFFLINE=1`), with its own script. Why: one daemon holds one script file and each worker walks it from the start (smoke-lanes). Cost: 3 to 5 s per spec file.
- **M13R4** Locators are `getByRole`/`getByLabel`/`getByText` with text taken from the English catalog through `t(key)` (`scripts/e2e/catalog.ts` builds it from a rewritten temporary copy of `apps/web/src/i18n`, lazy catalogs included: M13R37). No CSS or test-id selectors, no `waitForTimeout`. Why: copy and markup change; the catalog is the contract.
- **M13R5** Passkey: the Chromium project drives WebAuthn with a CDP virtual authenticator (`WebAuthn.enable`, `addVirtualAuthenticator` ctap2 internal, resident keys, user verification). **WebKit has no virtual authenticator: its J01 runs the password path** and the passkey half is `test.skip(browserName === "webkit", "no virtual authenticator in WebKit")`.
- **M13R6** All journeys run on both browsers except the passkey half of J01 and J13 (push enable: Chromium only, stubbed subscription). The skip reason is in the code and in `docs/agents/e2e.md`.
- **M13R7** E2E is a gate step at **J1 and the final review only**, plus the CI job. Not in a task gate, not in a fix-round gate. Runtime budget: 15 minutes in the container for the whole suite; the default test timeout is 60 s, J09 (90 s) and J13 (150 s) declare their own (M13R43).
- **M13R8** The controller runs the journeys in the container after each A task (CE1 to CE5) and hands failures back as fix rounds. An implementer never claims a journey passes; the report says "listed and typechecked, not run".
- **M13R8b** The push journey uses a stubbed `PushManager` and a loopback sink under `PAP_TEST_PUSH_LOOPBACK=1`; nothing reaches a real push service.

**Compatibility, budgets, security**
- **M13R9** Pi-compat = "the newest release of `@earendil-works/pi-coding-agent`, `pi-ai` and `pi-tui` that exists for all three at the same version and is at least `minimumReleaseAge` old", written as an exact version in the catalog before install (no `latest`, no age override). `pnpm pi-compat` runs it locally on demand and restores `pnpm-workspace.yaml` and the lockfile on exit; the nightly workflow does the same once the repository is public. Why: the rule is a supply-chain control; the cost is that a release is tested 3 days late. Today it would test 1.2.0.
- **M13R10** Final budgets are the table above [q4]. The deterministic ones (bundle, SW, payload, RSS) get a 7 to 11 % margin over the measure, except the payload (a ten-exchange snapshot is 9.5 KB; 24 KB leaves room for a real session's preview rows). The two timing budgets keep a large margin because CI hosts are slower: the scanner moves to 2500 ms (2.5 times the measure), the search budget stays at 200 ms until a CI baseline exists (M13R53). `pnpm budgets` asserts all six keys exist and are named, as a whole word, in each of their enforcing files (B1 maps the real ones); `test:budget` joins the CI `budgets` job (about 2.5 minutes). Cost if wrong: a CI flake on a slow host; the fix is one number.
- **M13R11** The ten security rows above are indexed in `docs/agents/policy.md` ("Security tests") as spec item, file, test title; `scripts/security-index.test.ts` fails when a file or a title is missing.
- **M13R12** Crash-isolation additions are integration tests in `apps/daemon/src/modules/sessions/` (`sessions.crash.hard.int.test.ts`), run in the existing int project.
- **M13R13** Spec D §3 for a live worker: while a pap worker is live, a change to its Pi file that appears more than `LIVE_GRACE_MS` (10 000) after the worker's last event and while it is idle counts as written outside pap. It sets `outsideWrite` (the existing snapshot field and banner). **It does not taint**: taint on outside tool results is already decided for released sessions (M7R27) and a live worker never reads the file again. The "last event" is the last `LiveIdle` touch, events and commands (M13R45). Cost if wrong: a banner for two minutes that is not needed; no data effect.
- **M13R14** The egress proxy and push share one strict address predicate: `blockedStrict` (rename of `blockedForPush`, same behaviour) in `kernel/net/address-strict.ts`. `blockedAddress` stays as the base it extends. The feed guard keeps its own `BlockList` in `automation/net-guard.ts`: three predicates with a parity table, not one (M13R46).
- **M13R15** The shrinkwrap is generated **offline** from `pnpm-lock.yaml` by `scripts/npm-shrinkwrap.ts` (production closure of `apps/daemon`, `packages/contracts`, `packages/pi-host`; npm lockfile v3; every entry has `version`, `resolved`, `integrity`; `@pap/*` entries are `inBundle`). `pnpm build:npm` writes it into the package; `pnpm release:check` refuses a package without it or with an entry that differs from the lockfile. The controller verifies once, with the network, the tuple criterion of M13R47 (step CB6). Why: npm resolves floating transitive ranges otherwise (Appendix A defect D3).
